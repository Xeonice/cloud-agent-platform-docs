# 旧入口不停下的首次控制接入协议 PoC

本文定义独立 Control 首次接入的隔离验证，**不是已实现的迁移路径或线上资格**。它补充[独立升级控制系统方案](./2026-10-20-独立升级控制系统.md)，承接[失败审计](../../testing/results/2026-11-06-无感升级失败审计.md)。本协议未通过时，不执行独立 Control 的线上首次接管，不重新使用已终结的迁移、时钟或容量资格；不把 FullControl 接管设为已有兼容业务链 A7 升级的前置。当前执行顺序以第 0 节为准。

## 0. 当前唯一交付与执行顺序（2026-11-09 重排）

**当前唯一交付是：固定 A7 兼容包完成验收，沿现有业务升级链发起一个新的线上请求，取得真实 confirmed 并验证原用户资源连续性。** A7 不含独立 Control 包，仍由原兼容 controller／业务 Coordinator 执行。本文第 1–8 节的首次接管、外层委托、旧动作结算与撤权闭环属于 **FullControl 独立后续里程碑**；原 UNKNOWN、五类正式 not-run 和 `onlineAdoptionImplemented=false` 保留，但不再把完成这些改造作为 A7 兼容升级的启动条件。A7 完成也不能反向宣称 FullControl 完成。

## 1. 要验证的方案与当前结论

保留正在运行的 legacy Foundation、其 Entry 和宿主 TCP bridge。旧 Entry 作为固定外层；旁路启动独立 Entry、Control Agent、Supervisor 和业务候选。用真实受理的 legacy 升级请求及其合法 fence，将外层 API upstream 接到独立 Entry；之后新控制面只管理内层 Entry。已有外层 WebSocket 继续连接原 backend。

现有接口没有直接禁止嵌套代理，但**完整接入尚未成立**。缺少的不是再修改一次磁盘配置，而是以下四项正式能力：

1. 真实旧请求、旧 fence、实际目标包与 gateway upstream 的授权关系。不得把 Entry 进程冒充业务 API 组件，也不得手写 attempt、伪造步骤或无限续期旧租约。
2. 新 Coordinator 对 legacy 控制 RPC 的最小拒绝边界，同时保留独立 Agent 的合法业务调用。
3. 撤权前已通过 fence 的旧 Supervisor 请求全部结算的证明。拒绝后续 RPC 不会取消已在执行的异步函数。
4. 外层 Web 静态资源、digest、受限路由维护委托和鉴权上下文的完整闭环。

该阶段最初新增了[只读 capability 预检](../../../deploy/upgrade/control-adoption-preflight.mjs)及其[本地协议测试](../../../deploy/upgrade/control-adoption-preflight.test.mjs)。预检仅请求运行接口，不产生桥或变更请求；当前恒为 blocked。真实 `/control-epoch` 存在，也不能自动证明 public 签名转发、旧 fence 委托或 Supervisor 撤权。测试中的本地 authority receiver 不是生产业务账本，不能作为本节第一项的通过证据。

## 2. 端口、binary 与证据基线

已有部署记录的入口链是 `Mac 公共 :3000 → 宿主 TCP bridge → Linux loopback :3181 → legacy Entry`，见[端口参考表](../../ops/参考表.md)。已有 Foundation 容器清单使用 host 网络、Ports 为空；不能把它改述为已核实的 Docker `-p 3000` 映射。其他部署若采用 Docker published port，必须另外核验实际映射，不能照搬本实例结论。

本方案不转移 `:3000` 或 `:3181` 的监听权。内层使用独立、已预检的 loopback 端口。宿主 bridge 与旧 Foundation 不随本次业务交接停止。现有 [IP bridge](../../../deploy/host/ip-entry-bridge.mjs) 不支持热改目标；它也不提供既有 TCP 的跨进程移交。

## 3. 嵌套代理的数据面

旧 Entry 每个 HTTP 请求按当前 binding 选择 backend；已经升级的 WebSocket 在建立时固定 backend。旧源码第 62–73 行与[当前实现](../../../deploy/upgrade/stable-entry.mjs)第 94–106 行保留该边界。因此外层切到内层后：

- 新 HTTP 和新 WebSocket 可以进入内层；旧 WebSocket 不被路由更新搬迁。
- 外层保持 `100% → 内层` 后，日常 API 灰度与回退由内层执行，不再为每次 API 更新改外层。
- 长连接不能靠等待一个固定时间就宣称排空。保留旧 API 到自然结束，或经协议通知、detach、重新 attach 同一 terminal/runtime；不能重建 Guest、重发输入或把 TCP 重连称为原连接保留。

旧 `/binding` 会调用旧 Coordinator `assertFence`。PoC 必须证明：请求由原访问保护正常受理，计划指向真实签名目标，controller 合法 claim，gateway endpoint 与真实业务 backend 的身份分别可验证。仅有一个可通过的整数 fence 不够。如果只能修改数据库、构造虚假 attempt 或把 gateway digest 填成业务进程 digest才能继续，本方案在此失败。

### Web 不能只切 API upstream

旧 Entry 的非 API 路径使用 `binding.web`。只改 API upstream 不会切首页。即使 `web.origin` 指向内层，旧源码第 48–54 行仍将 `/_next/*` 和 `/_upg/web/<digest>/*` 从自己的 `web.root`／`retainedWeb` 读取；HTML 代理响应还会覆盖 `x-platform-web-digest`。当前实现对应第 66–81 行。

因此必须先做到：

1. 新 Web 的全部哈希资源位于旧 Foundation **现有可见挂载**中的受限目录，完整字节／树／签名验证通过；内层单独返回首页 200 不足以证明该条件。
2. 保留旧 Web root 和原哈希资源，真实旧页面延迟加载资源仍成功。不得用覆盖同名文件伪造保留。
3. 新 HTML、`/web-process`、公开 digest、全部实际资源引用与激活版本一致。
4. 明确后续如何更新外层 Web binding。全面拒绝旧 fence 校验后，不能假定外层仍能合法更新。

一种待验证的最小方案是保留**受限的外层路由维护委托**：新控制面记录真实 adoption 证据，由持有原 Entry key 的单一兼容控制器执行特定 binding 更新，按原 ID 查询未知 ACK。它不是旧业务租约的永久续期；不能伪造旧 attempt，也不能让旧 Supervisor 重新获得 snapshot、发布或启动权限。目前尚无该正式实现或资格。

## 4. 旧 Supervisor 的最小撤权边界

旧 `coordinator-client.mjs` 第 6、13–16 行每次 RPC 都重新读取 binding，故在合法 writer 接管并发布新 binding 后，旧 Supervisor 后续调用会到新 Coordinator。这为逻辑撤权提供了路径，但不是已经撤权。

| 旧入口／动作 | 旧源码中的执行条件 | 新 Coordinator 必须拒绝的旧链 |
| --- | --- | --- |
| `POST /start` | 路由和 start 函数核对 fence，读取 snapshot，校验固定计划与真实产物后 launch | legacy `/renew` 或 authority-check、snapshot；启动前未知原命令不能略过 |
| `POST /publish` | fence、snapshot，复制／解包前后再次核对 | legacy fence 与 snapshot |
| `POST /activate-installer` | **跳过一般 assertFence**；snapshot 后读取 `controllerHandoff(action=status)`，据历史已交接结果写 authority | legacy snapshot 和 controller-handoff，包括历史 status |
| `POST /retire-reader` | contract fence、contract snapshot；signal 前再次检查 | legacy contract check／snapshot，覆盖已退役回执的查询路径 |
| `POST /current-installer`、`POST /observe` | 路由先检查 fence；本身不授予新生命周期权限 | 不得借旧 fence继续任意调用 |
| `GET /metadata` | 可根据初始 Installer metadata 更新旧 authority 缓存，无 Coordinator 检查 | 不能声称被 Coordinator 撤销；新控制面不得再以该缓存为权威 |
| `GET /retained-readers`、`GET /owner-isolation` | 可刷新注册文件，无 Coordinator 控制授权 | 若保留，限制为历史库存；不得作为新执行授权 |

旧 factory 还返回 `restartCurrentInstaller()` 这个进程内方法；它不经上述 HTTP dispatcher。已匹配的 bootstrap 源码未发现对该方法的调用，但正式闭包核验仍必须覆盖实际调用者／watchdog。不能只审核 HTTP 路由便宣称所有进程内能力已消除。

### independent 模式的旧 RPC 撤权（2026-11-07 增量）

此前 API 只把 ledger 改为只读，旧 snapshot、check-only renew 和 installer status 仍可读取历史；旧 Supervisor 能将历史 adopted 解释为重新写 authority 的依据。本轮在实际 Nest 控制器边界补上 `LEGACY_CONTROL_PROTOCOL_RETIRED`：独立只读 ledger 模式拒绝旧 pending、bootstrap、snapshot、claim、authority-check、lease-renew、progress-checkpoint、commit-receipt、renew、commit、step、controller-handoff（含 status）及旧 contract snapshot/check。原可写 legacy 实例保持原恢复协议。新控制系统的业务参与接口保留原 command envelope；内部鉴权仍先执行。

`deploy/testing/legacy-supervisor-retirement.test.mjs` 运行未改写的历史 `208342ea99` Supervisor 及完整6文件依赖（66,202字节），经实际 HTTP 请求到当前编译的 Nest 控制器与真实只读 SQLite。start、publish、activate-installer、retire-reader 均在副作用前被拒绝；特别验证 activate 跳过 assertFence 后仍被 snapshot 拒绝，原 authority 文件不变，生命周期调用为零。两项本地合同通过；API 另有4项路由／鉴权／参与检查／legacy 恢复兼容合同通过。历史进程记录在测试中仅用于走到真实拒绝边界，未作为物理进程或 Native 接入证明。历史源码位于 `deploy/testing/`，不会复制进正式 installer。

撤权实现应按**方法、真实 scope、command envelope**区分，而非信任调用者自述的 `role`。旧 Entry 与旧 Supervisor 可能持有同一 Coordinator key，不能靠该 key 推断来源。新控制调用可沿现有 [control-plane-client](../../../deploy/upgrade/control-plane-client.mjs) 分流：pending／claim／renew／commit／snapshot／assertFence／contract 权威调用到 Agent；业务 handoff／Owner／migration 调用到 Coordinator 并受 `businessAction` 的原命令约束。新的控制面不需要为了兼容旧 Supervisor 而开放旧 controller-handoff。

若外层维护委托确需保留旧 `renew(checkOnly)`，必须只服务该份真实 delegation，并继续拒绝后续 snapshot、controller-handoff 和 contract 链。该有限响应本身不能被当成 Supervisor 启动授权；还需实测整个旧调用链确实在 dispatch 前失败。

### 已通过 fence 的 in-flight 是独立阻断

旧 start 在最后一次 fence 检查与 `launchAdapter.launch()` 之间仍有文件／日志操作。publish 也存在检查后的写入阶段。新 Coordinator 返回拒绝只能影响未来 RPC，不能取消旧服务器已经运行的 Promise；关闭客户端连接不等于取消服务器动作。

当前旧 binary 没有公开的全局 mutation drain／busy 收敛接口。因此必须证明旧请求入口已经封闭、旧 Installer 已停止接单、全部既有 dispatch 已有原结果且 settled，未知结果只查询原 ID。不能用旧 Coordinator actor=0、一次无 TCP 连接或两次进程快照代替旧 Supervisor 异步工作已结束的证明。若隔离实验不能闭合这个 barrier，本方案仍然 blocked；不能靠撤权后“新请求都403”放行。

### 单管理员正常空闲时的最小结算条件

这里检查的是同一管理员已发起操作的迟到结果与后台恢复，不假设多个用户同时升级。正常停止旧 Installer 也不自动证明已结算：`208342ea99:deploy/upgrade/instance-controller.mjs` 的 `run()` 会捕获每轮错误再退出，`finally` 只等待本地续租与提交队列；远程 RPC 超时后，服务器函数仍可能继续。普通步骤先写 `applying`，远程完成后才写 `applied`，但 Installer handoff 会在远程激活之前先把步骤标为 applied；保留期恢复则使用 `circuitBroken / faultCommit / faultCommitApplied / faultRecordingComplete / recoveryResult`，不能只查 steps。

同一历史主仓 gitlink 的 API 为 `17e2ad52bfacea49ec9834d4f98693e3e66fbd79`。该版本还有独立后台来源：`CoordinatorRecovery.onApplicationBootstrap` 继续处理 releasing 恢复，prepared Coordinator 的 watcher 在满足条件时继续 adopt，`UpgradeContractService` 定时处理已受理 contract 并可调用 Supervisor 的 retire-reader。它们不因 Installer 退出而消失；旧 pending 查询也不包含所有 unknown recovery。上述为历史源码核查，尚未冒充当前实例全部运行闭包实证。

隔离 PoC 应分别验证两档：

- **只有 bootstrap、从未接纳升级意图的实例：** 通过实际业务表、Installer journals 与 Supervisor processes 共同证明没有升级、contract、handoff、recovery 或候选启动意图；正常停止精确 Installer 后复读仍为空，并核对原 Entry／API、Owner、writer 与绑定身份不变。这可作为范围明确的空意图快路，不能外推到有历史失败的现有实例。
- **存在历史意图的实例：** 先暂停新增升级／contract 接纳，再正常停止精确 Installer。逐原 operation 核对步骤、独立恢复、故障提交、contract、handoff、物理角色与绑定终态。任一 applying、releasing、adopting、未知远程结果或未闭合故障都阻断接入，先按原操作查询结果。旧 Supervisor 缺少可核完成结果时，不用固定等待、正常退出码或两次稳定快照代替完成证明。

本轮已新增正式[只读结算采集／校验器](../../../deploy/upgrade/legacy-settlement.mjs)，并接入现有 `control-adoption-preflight`。采集器以 `readonly + query_only` 打开现存 SQLite，对全部原 upgrade、step、event、recovery、handoff、contract、migration 行做有界投影，以及读取原 Installer journal、Supervisor process record、Installer authority 和退役回执。SQL先按SQLite原字节数准入再逐行摘要；step evidence仅保存原摘要，event保留identity／hash／sequence／payload原字节数，只定向读取原journal faultCommit引用的payload，省略范围必须显式声明。inventory为v2，单SQL row 8MiB、单文件32MiB、每轮128MiB，超限拒绝；不能用`.all()`将历史event payload全量搬入Node。原文件摘要与同范围复读保留，旧v1保存文件不能冒充当前完整采集。不调用旧 RPC，不构造 Controller，不修改行、journal 或回执。缺表、缺结果、未闭合后台意图均返回 blocked。前后复读只用于排除混合快照，不当作动作完成证明。

调用者须提供现有只读 Inspector 的新鲜物理观测文件，逐一对应原 Installer 及 Supervisor records 的容器／出生／artifact 身份；缺失立即阻断，不以正常退出码代替。`observeLegacySettlement(config)` 从实际原件产生 observation，`planControlAdoption(entryObservation, { settlementObservation })` 才消费它；普通保存的 JSON 不是本次采集。原 local `applying` 仅能由同一原 DB step 的真实 applied receipt 解释 ACK 丢失，结果仍保留原 journal，不补写成功。Installer handoff 还必须具有实际原 authority 激活结果，contract 必须关联真实 expand／migration 结果，不能只凭各自 completed 标签。

[本地结算合同](../../../deploy/testing/legacy-settlement.test.mjs) 使用[逐字固定的旧 API schema／factory](../../../deploy/testing/legacy-settlement-17e2/README.md)：执行原 28 份迁移和原 `bootstrap / accept / claim / commit / save / handoff`，不直接 INSERT accepted rows；物理观察与部分生命周期结果是明确的隔离测试端口。Node22 下结算 12 项及原预检 7 项通过，覆盖空意图、完整原结果、ACK 丢失、pending 漏掉的 unknown recovery、独立 monitor fault、contract、prepared handoff 和 Installer 激活缺口。

这是已执行的本地结算前置，不是当前旧实例全部运行闭包或 Supervisor drain 实证。结果保留 `requiresActualRuntimeClosureVerification=true`；旧 binary 没有全局 drain 读口，仍须核实实际旧调用者闭包。预检继续返回 blocked，明确 `admissionAuthorized=false`，尚未证明外层委托、撤权竞态或完整接入。尤其已有失败历史的目标实例不能因“当前 pending 为空”直接套用空意图快路。命令行 `node deploy/upgrade/legacy-settlement.mjs <只读配置.json>` 只输出结算摘要；配置指定实例、现存 DB、Installer／publication 根、原 Installer 身份和 Inspector 观测文件，SQLite 驱动来自显式 `sqlitePackageRoot`；无法取证时退出 78，不执行恢复或修复。

## 5. 访问保护与 spoof 拒绝

外层旧 Entry 不会签独立控制 context；嵌套后由内层剥离不可信转发头并签名，Agent 按现有 `control-entry-context.mjs` 校验 peer、method、path、nonce、时效。禁止增加“来自 loopback 即授权”的例外，也禁止把外层透传的浏览器 `X-Forwarded-For` 当真实外部地址。

内层看到的 TCP peer 是外层的 loopback。必须明确受控 peer／未知外部地址的处理，不能凭空补出原客户端 IP。PoC 同时验证原会话 Cookie、Origin、CSRF、权限与会话失效；伪造 `x-platform-*`、`Forwarded`、`X-Forwarded-*` 不能提升权限。只有 `/api/health` 200 不能证明身份、业务可用性或控制请求已到独立 Agent。

## 6. 隔离 PoC 顺序与判定

全部步骤使用隔离目录、loopback 临时端口和测试信任根，不使用线上 DB、私钥、公共端口或真实 Guest。通过正式 factory／迁移生成测试数据；fixture 的端口和合成数据必须标明。以下尚未完成的实验是交付要求，不是已有可运行 executor。

1. **锁定旧 binary 与不可热生效边界。** 对照第 2 节原文、真实运行 metadata 和 import 闭包。运行现有只读预检合同：`node --test deploy/upgrade/control-adoption-preflight.test.mjs`（Node22）。普通 JSON 声明、磁盘新配置和错误凭据不得令预检通过。当前七项本地合同通过仅证明这一预检与当前 factory 的局部行为。
2. **真实受理的旧请求。** 用正式旧访问／请求／claim 路径取得合法 scope。验证目标 manifest、实际业务进程和嵌套 gateway 的对应关系，不直接 INSERT upgrade rows。合法 binding 更新成功；无原 authority、目标不符、过期 fence、未知 ACK 重发均拒绝。任何无法合法表达的步骤记为接口缺口。
3. **嵌套数据面和鉴权。** 启动旧外层、新独立内层、旧／新业务接收端。先建立原 WebSocket，再合法切流。验证新 HTTP／新连接进入内层、旧连接仍原 backend、同请求不被重复执行；随后停业务 backend，独立升级状态仍可经内层访问。逐项执行第 3、5 节 Web、资源、Cookie／CSRF 与 spoof 负例。
4. **整函数旧 Supervisor 撤权。** 运行真实旧 factory，使用真实协议和合法测试记录；新 Coordinator 的拒绝必须来自被测实现，不能 mock 成永远拒绝。逐项测试上表 mutation，特别是历史 adopted installer 的 `/activate-installer` 和 `/retire-reader`。记录全部 launch／signal／authority 写，而不只检查响应码。
5. **必须重现撤权竞态。** 在真实旧 start 最后一次已通过 fence后、真正 dispatch 前暂停受控 IO／launch端口，切新 binding并撤权，再释放旧请求。当前逻辑预计仍可能 dispatch，必须如实记录红例。只有能够给出并实测原命令 settled barrier，才能将该项改为通过；不得缩掉这个实验。
6. **失败和恢复。** 在 binding写入、ACK丢失、writer接管、委托生效各持久阶段中断后，用原 ID 查询并确认实际路由／authority。接管前失败保持旧 Entry、旧业务和 bridge不动；接管后只执行已验证的原恢复路径。不得在新 Coordinator已拒绝旧fence后，假定外层还能回切旧 origin。

每一步都保存原命令、请求 scope、实际响应／身份、观测时间、未知状态和原始错误；不生成“未来成功”回执。通过所有接口实验后，仍需真实大库 writer 交接、资源峰值、公共请求 SLO、同 Shell／任务及逐阶段恢复验收，才能讨论线上执行。

## 8. 11月7日接入实现与真实旧版本兼容路径

目前已实现以下局部执行链，仍未授权完整线上接入：

- API以原业务连接持久化 admission freeze，关闭旧升级调度，追踪原异步工作并等待结算；随后只在原签名目标、writer、固定输入文件和原截止一致时，把控制账本切到只读连接。业务连接、业务事务钩子与原writer不切换。旧SQL statement和异步epoch不能借用新账本；持久冻结后的实际重启仍可提供业务服务。
- [被动维护预留](../../../deploy/upgrade/control-adoption-reservation.mjs)只允许原attach和settlement两条固定命令，不开放普通升级。实际attach回执经新鲜GET核验后才能清除该预留；Control仍为passive。
- [接入编排](../../../deploy/upgrade/control-adoption-attachment.mjs)已串联固定freeze、真实export端口、预留、结算、attach、GET及完成收据。POST前落盘派发记录，未知ACK只查询原结果，不重发、不续截止、不反向修改路由。实际旧调用者及在途命令结算仍是必需的外部观测端口，没有默认成功值。
- [旧入口委托](../../../deploy/upgrade/legacy-entry-delegation.mjs)已实现固定API目标及原命令查询，但尚未接真实独占key custody／旧actor closure生产者。真实历史Entry的负例已证明：只有唯一executing命令不足以约束旧payload-free fence；撤权也不能取消已经通过fence的原Promise。普通旧renew继续关闭。

3. A新增default Owner供新任务使用，同时保留全部旧Owner／Guest和原handle路由。旧`.15` Owner没有新容量接口，不能仅省略owner组件后宣称新任务可用；`reuse-installed`只可用于已实际满足目标协议的Owner。为控制本次桥接范围和构建峰值，A显式保留原签名Web：qualification的`webPolicy=retain-installed`要求原包签名／全树已验证、Web树摘要匹配原签名组件，且构建声明的Web提交等于该原组件提交；原artifactDigest／inputFingerprint／sourceRevision完整保留。新计算的源码指纹单独记录，不把保留产物冒充新构建。正式release不能选此保留策略；后续Web更新单独实际验收。
4. A确认后，其新API才可验证包含真实独立Control包的后续签名目标，读取固定binding目录内的freeze／attach输入，运行期接入独立只读账本。兼容A通过并不等于首迁、外层Web、Control激活或五场景Native通过。

新增 [Foundation/operator 导出端口](../../../deploy/ops/control-adoption-live-export.mjs)。`createLiveControlAdoptionAttachment` 将真实 HTTP／SQLite 导出器接入既有 `exportPassive`，不再要求调用方临时提供成功替身。该特权 worker 位于 `deploy/ops/`，独立 Control 进程不因此获得源业务库或原认证文件的读取权限；本轮没有新增前端操作或 API endpoint。

导出前后核验同一签名目标、原 freeze receipt、实际 confirmed／ready、Coordinator 身份及 writer generation/fence；源库仅 readonly／query_only，复用既有流式白名单导出和逐行幂等 import。仅新私有 Control、导出库和独立认证库可写，Control 始终 passive，不复制业务表、沙箱或探针历史。每个 SQL／流式行及最终持久化之后检查同一个原 deadline；单条同步 SQLite 调用不能被 JS 抢占，但超时不返回成功的 attach 配置。

已完成结果重开时，先核对原 control／export／access 三文件的私有权限和 dev/ino，再允许 importer 逐行复核；缺失、替换、不完整状态或没有原收据的既有目标均拒绝，不截断未知文件、不重导、不刷新 deadline。`settlementObserver` 仍是强制真实端口，UNKNOWN 保持人工复核，不发送 attach，不激活 Control 或修改 Entry，stop-first apply/resume 继续禁用。
