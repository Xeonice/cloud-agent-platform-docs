# 独立升级控制系统

本文是**实现中的方案**，不是当前远端运行架构或上线验收结论。目标是在单台 Linux VM、单实例、单管理员的现有部署模式内，让升级观察、控制、失败恢复不再依赖正在被升级的业务版本；普通业务发布不替换升级控制器，也不改变已有 Guest、任务与终端的归属。

本文补充并调整[原后端实施计划](./2026-10-10-不停机升级与运行环境分离.md)中的控制权、状态持久化和组件更新边界。产品交互以[产品方案](../../product/changes/2026-10-20-独立升级控制与失败恢复.md)为准，恢复状态机以[恢复与回滚方案](../../ops/2026-10-20-升级失败恢复与回滚方案.md)为准，前后端及真实环境验证由[独立测试计划](../../testing/changes/2026-10-20-独立升级控制与恢复测试计划.md)统一定义。

## 1. 当前事实与变更原因

当前已经有 Foundation、稳定入口、独立 Installer 和业务角色，但**独立进程还不等于独立控制系统**：

| 当前实现 | 仍然存在的耦合 | 目标变更 |
| --- | --- | --- |
| Installer 在独立进程运行 | 其版本属于业务发布组件，业务升级中会交接 Installer | 常驻 Upgrade Control Agent 使用独立版本与维护流程，业务包不替换它 |
| 升级请求、attempt、步骤和激活记录经 Coordinator 写入 `platform.db` | 控制权依赖业务库、业务 Store 版本和业务 Coordinator 可用性 | 控制日志及恢复意图迁入独立 `control.db` |
| StableEntry 已持久化路由和 fence | `bootstrap-upgrade-instance.mjs` 为 `verifyFence` 注入 `coordinator.assertFence`，切流仍依赖业务 attempt 租约 | Entry 校验稳定控制 authority 与自己的绑定 CAS |
| 已有观察和连续性门禁 | 完整树校验、完整性扫描、状态采集与控制请求可能竞争同一 VM 资源；独立进程没有消除共同故障域 | 快速控制路径与受限观察 worker 分开，先做资源准入 |
| 业务 Coordinator 有唯一写者租约 | 业务写者安全与部署控制权属于不同职责 | 保留业务事务内 writer guard，另设稳定控制 epoch |

当前远端 `.20` 未完成激活，实际组件组合、历史确认版本与原 Guest 连续性以[现场报告](../../testing/results/2026-10-19-升级证据开销修复与恢复准备.md)为准。本文不修改那些历史事实，也不把尚未确定的 `.20` 超时根因表述为已经定位。

## 2. 名称、拓扑与生命周期

本文将现有角色 `ControlAPI` 称为**业务 API**：它处理项目、任务、凭证等业务 HTTP／WebSocket，并通过 StateCoordinator 访问业务状态。它不是本文的升级控制器。

**Upgrade Control Agent，简称 Control Agent**，是 Foundation 控制底座内的常驻升级控制进程。Foundation 是同一实例的安装与控制边界，不要求所有组件运行在一个 Node 进程。Entry、Control Agent、Supervisor、重型 worker 应有独立事件循环和资源边界；不新增外部控制平台、集群或多管理员审批系统。

| 组件 | 目标职责 | 普通业务升级中的生命周期 |
| --- | --- | --- |
| Foundation | 稳定安装身份、信任配置、控制持久卷及本地受控通信边界 | 保持运行，不随业务包更换 |
| StableEntry | 同源入口、版本化 Web、API 路由、稳定升级路径及绑定 CAS | 保持运行；Control Agent 故障时继续使用最后持久绑定 |
| Control Agent | 用户意图受理、计划冻结、步骤编排、控制 authority、观察汇总、恢复及激活确认 | 保持原版本；不在业务升级中交接自身 |
| Access Authority | 控制底座内最小访问鉴权模块和单一权威状态，沿用现有访问策略 | 保持原会话语义；不是新用户系统或独立网络微服务 |
| CandidateSupervisor | 唯一持有受控 Docker 能力的执行边界，执行固定角色动作并返回物理收据；按独立持久维护记录完成 Control Agent 的更换及失败恢复 | 保持运行；不能接受任意 shell 或下载脚本 |
| 安装／校验／观察 worker | 下载、解包、哈希、只读完整性验证及有预算的证据采集 | 按需运行，受配额和期限约束，不持有控制 authority |
| 业务 API／Web | 业务访问与页面产物 | 按冻结计划准备、验证、切流和排空 |
| StateCoordinator | `platform.db` 唯一业务写者、调度、任务监控及 Owner 路由 | 需要换版时执行专门的 writer 交接 |
| RuntimeOwner | 原 SDK home、Guest、进程、PTY 及任务运行 | 原资源留原 Owner；新版 Owner 只接新的分配 |

原 Installer 的编排职责迁入稳定 Control Agent；下载和安装工作保留为受限 worker。业务 manifest 不再携带“替换 Control Agent／Entry／Supervisor”的可执行步骤。含有此类步骤的业务包必须拒绝，而不是忽略后继续安装。

CD 仍然只构建、签名、发布业务包或控制包。发现版本只读；由管理员决定实例升级时机，不因控制系统独立而重新启用自动部署。

## 3. 控制状态与业务状态分开持久化

### 3.1 独立控制卷与 `control.db`

控制状态放在 Foundation 管理的独立持久卷，不能位于业务数据库目录或某个业务 artifact 下。`control.db` 中的升级业务日志与状态机由当前有效 Control Agent 单写；Entry 仍持久化自己的已应用绑定，业务库仍由 Coordinator 单写。

控制器自身维护有一项受限例外：Supervisor 可在同一控制库事务内核对没有活动升级、恢复、合同或未知命令，再将控制 authority 提升一个 epoch、设为 `passive / maintenance` 并绑定固定维护编号。这个持久屏障不会随租约超时自行解除，防止新旧 Agent 在交接空窗接受业务变更。Supervisor 仅更新维护屏障和维护确认收据，不修改升级历史、业务 writer 行或任务数据；只有实际新 Agent 或兼容回退 Agent 已通过验证后，才按原维护记录解除屏障，保留最高 epoch。该权限不经业务版本授权，也不暴露任意 SQL 接口。

普通运行时，Supervisor只读挂载独立控制账本目录，供引用采集和未启动预留的核验使用；没有自身维护计划时不取得该目录写权限。自身维护时，同一固定目录才提升为上述受限读写挂载。Agent的访问凭证数据库位于另一个私有目录，不在这两类挂载中。

`control.db` 保存：

- 已受理的升级／恢复意图、自动／管理员触发来源、关联授权、requestId、actor、授权时间和固定目标。
- 不可变计划及摘要、attempt、步骤、真实工作量、deadline、结果和失败原因。
- 控制 epoch、有效操作、执行者身份、租约／本地锁及迟到请求拒绝记录。
- desired／实际观测／历史完整确认三类组件清单，路由绑定收据、兼容资格和恢复锚点。
- 候选物理身份、保留引用、资源准入结果、审计事件及证据索引。

完整证据保存为限额、不可变的收据文件；数据库中记录 digest、长度、采集区间、来源和路径引用。心跳只更新常数级时效及引用，不反复写入完整 JSON，也不把未校验的引用当成完整证据。

控制 DB 与收据必须有独立备份、容量上限和损坏处理。空间不足时停止受理或推进新的变更，保留最后绑定和已有业务运行；不能为了腾空间删除仍被回退、Owner 或活动连接引用的产物。

### 3.2 业务库保留最小安全守卫

`platform.db` 保存业务数据、任务状态、调度与资源归属，以及保证单写的最小 `holder / generation / fence` 守卫。业务写入必须在**同一个业务事务**内验证该守卫；交接后的旧写者不能凭内存中的旧租约继续写。

不能将 writer guard 整体移到 `control.db`，再让业务代码“先查控制库、后写业务库”。两个独立数据库之间没有这样的原子性保证。Control Agent 不通过直接 SQL 修改业务 writer 行、任务状态或 ready 字段。

Owner SDK 的自身 journal 与 home 继续由各 Owner 持有，不能当成控制库或业务库迁移的一部分。业务 DB 备份、控制 DB 备份和 Owner home 备份分别标识，不能整卷回写覆盖新数据。

### 3.3 状态来源及交叉核对

Control Agent 的期望不覆盖实际进程和 Entry 绑定。整体完成须核对实际 API／Web／Coordinator／新分配 Owner、Entry 当前绑定、业务 writer guard、迁移兼容证据和原资源连续性，再提交完整激活记录。

控制记录与实际绑定不一致时进入 `reconciling / unknown`，保留各自原始证据。`confirmed release`、当前可服务路径、部分升级组件、当前页面版本分别显示；不能用历史 100%、新包已发布或 API `/version` 冒充整体已完成。

## 4. 两层 authority 与本地交接协议

### 4.1 控制 authority

单实例仅允许一个有效的变更操作；本地锁、单调 control epoch 和条件更新用于阻止旧进程、重发命令及迟到回执。它们不是多管理员并发产品设计。

Entry 和 Supervisor 校验固定实例、当前 control epoch、operationId、commandId／stepId、动作摘要、期望物理身份和绑定 generation。Entry 退流不再调用业务 `renew / snapshot / assertControllerFence`；业务 API／Coordinator 不可用或原升级 attempt 终态，不应单独使控制权和正规恢复能力消失。

控制 authority 过期或未知时禁止新的变更。已持久化路由继续服务，不因失去控制租约清空绑定或停止 Guest。

### 4.2 业务 writer authority

Coordinator 的 quiesce／release／adopt 保留业务事务内的 writer 校验。稳定控制协议为交接提供绑定 operationId、独立 commandId／stepId、动作摘要、epoch、source／target 身份和期望 writer generation 的受限命令；Coordinator 记录每个命令的阶段及结果，并在业务库事务内校验本地单调状态和 writer guard。

control epoch 不等于业务 writer fence，二者不能互相替代。更高控制 epoch 不授权直接抢占仍未证明释放的业务 writer，也不允许从外部补写一行来伪造交接完成。

### 4.3 跨库没有隐含原子事务

交接采用可查询、幂等的本地状态机：Control Agent 先持久化意图；各参与者在同一 operationId 下，按独立 commandId／stepId 和固定动作摘要执行各阶段、记录本地结果；Control Agent 核对真实结果后推进。控制库提交成功、业务结果未知或反之时，精确查询原 operationId 下该 commandId 的结果并对账，不猜测另一个数据库已完成。

恢复中的新 epoch 先确立参与者可验证的控制权，再执行相应 CAS。旧消息若已产生结果必须可按原 commandId 查询；未产生结果的旧消息必须被本地 epoch／generation 守卫拒绝。不以更换 commandId 不断重发 release／adopt 或重复启动进程消除未知状态。

## 5. 稳定、有限的协议

控制协议与业务 API 版本分别编号。第一版只覆盖现有单机需求，不把任意 RPC 暴露为通用管理接口。

| 协议类别 | 有限操作 | 必需约束 |
| --- | --- | --- |
| 身份与能力 | identity、capabilities、status | 实际 artifact、start identity、协议范围、观测时间；不以包声明替代运行身份 |
| 控制请求 | request、lookup、recover | 原访问授权、requestId、固定目标／恢复计划摘要、expected activation／control epoch |
| 角色准备与结果 | prepareRole、operationResult、inspectRole | 固定角色、签名产物、物理身份；结果查询绑定 operationId／commandId，不能偷偷启动或重试 |
| Writer 交接 | prepare、quiesce、release、adopt、handoffResult | 同一 operationId 下各阶段有独立 commandId／stepId 和动作摘要，并绑定 source／target、业务 writer guard、deadline；每个命令可区分已应用／未应用／未知 |
| 入口变更 | admitEpoch、compareAndSetBinding、binding | expected binding digest／generation、新绑定及 epoch；重复同一动作返回原结果 |
| Owner 连续性 | identity、assignments、observeExisting、attachExisting | 原 Owner／home／sandbox／task／shell 身份；无 create／stop／kill 权限 |
| 安全退休 | retirementEligibility、retireRole | 无 current／fallback／连接／业务引用、已释放 authority；不以名称或单个 idle 字段推断安全 |

operationId 关联整个计划，不能单独作为所有阶段的幂等键；prepare、quiesce、release、adopt 等正常下一步使用各自 commandId。每个变更命令分成两部分：

- **不可变副作用 spec**：instanceId、operationId、独立 commandId、stepId、动作类型、原计划摘要、目标物理身份、期望前态／generation、动作参数、原始执行 deadline 及工作预算。副作用摘要只对这部分计算。
- **可更新授权 envelope**：当前 control epoch、执行者／start identity、关联 recoveryId、授权范围及有效期。接管时必须重新验真，但它不进入副作用摘要，也不能修改 spec；授权有效期不延长原执行 deadline。

以 `(instanceId, operationId, commandId)` 唯一标识命令，并绑定其 stepId 和副作用摘要：重复同一命令及摘要返回原结果，同一命令键而 spec 不同则拒绝。动作摘要是冲突校验，不能通过换摘要让同一 commandId 执行第二次。更高 control epoch 及新的执行者可以携新 envelope 查询／接管原 commandId，不因授权变化与原摘要冲突；也不能借此重置原期限、已耗工作预算或已产生的副作用。

超时返回 outcome unknown，不自动当作没有执行；结果查询精确到原 operationId／commandId，并校验原 stepId／副作用摘要。结果仍未知时不换 commandId 再发同一动作。收到明确未应用结果后是否可重试，按冻结计划、原 deadline／剩余预算和当前 authority 再准入；原执行 deadline 已过只能查结果，不能用新 envelope 续做原动作。新恢复计划可为不同的恢复动作建立新命令，但不得复制未知旧动作以绕过原结果。查询与重传不能扩展原命令范围。

协议和载荷有明确大小上限；未知必要字段、未知语义或不满足的能力拒绝推进。业务包声明所需控制协议范围，控制系统声明可支持范围；不兼容时显示“需先维护控制系统”，不能让业务包在升级中先换控制器以绕过兼容检查。

协议可以增加可协商的能力，但不得悄悄改变旧命令语义。内部角色认证、发布签名和管理员访问会话是三条不同信任边界；浏览器拿不到任何 role key。

### 5.1 历史候选的独立维护闭环

`POST /internal/control/retirements`接收真实已受理技术升级的`acceptedUpgradeId`、完整候选物理身份和可选`requestId`，核验原固定计划及组件摘要后，在`control_normal_retirements`写入不可变维护意图。仅Agent既有私有能力可调用；业务管理key、浏览器访问口令和Entry签名不授予该能力。查询使用`GET /internal/control/retirements/:operationId`，运维工具为`deploy/ops/retire-upgrade-candidate.mjs`，不增加用户升级密钥或授权UI。初始安装及旧部署没有对应技术attempt时，记录真实bootstrap／migration来源并保护，不编造attempt取得退休资格。

维护与升级、恢复、合同共享全局互斥。Coordinator先核对真实只读控制意图、当前maintenance epoch／holder、原计划及自身非writer身份；Entry、连接、Owner传输、用户操作和保留引用必须允许，再关闭该旧角色的新工作入口。进程内固定worker清单覆盖构造器、周期任务、排队工作、原Promise与流式订阅。未知provider或未登记worker保持unknown；后台任务返回202、浏览器断开或取消订阅，都不代表原Promise结束。只有明确尚未开始的周期定时器可取消；仍在执行的工作按真实finally结束计数，不停止Owner、Guest或原沙箱任务。

Agent观察实际排空完成后固定退休spec，交由Supervisor按原commandId重新核验全部引用、精确birth与全局fence，再发送一次SIGTERM。正常退出的原收据、双物理inspect和完整实际容器清单确认后，先发布通用Coordinator退出收据，再释放容量及单飞屏障。后续writer稳定性观察消费这份真实退出证明，不能把进程不见了直接当成非writer，也不能把普通退休伪称迁移。

维护原期限为120秒，不因重启、授权续期或新epoch延长。到期未确认的drain／stop进入`expired-unknown`，停止自动推进和续租，保留原命令与物理屏障。持久屏障同时阻止新升级、数据库收缩及控制维护，Agent重启或旧lease到期不解除屏障；所有新grant在同一账本事务中校验。只有尚未发送副作用的prepared意图可以让既有业务操作先行，已释放holder的旧maintenance kind不能使执行循环永久早退。显式`POST /internal/control/retirements/:operationId/reconcile`只在一次5秒授权内查询原结果，不重新POST drain或stop。已证明没有stop派发的维护可以结束为blocked；新的明确维护意图可重新评估，不能复制未知旧动作绕过熔断。

## 6. 低成本控制路径与资源准入

### 6.1 快速路径

authority 检查、续期、有限状态查询、步骤引用、Entry CAS 与原命令结果查询只读取必要行及有界摘要，不同步做完整快照、目录树哈希、数据库完整性或全量连续性扫描。Control Agent 的事件循环不承载这些重任务。

控制 authority 的心跳与业务观察分开调度：一次慢观察不能把合法续期排在后面；步骤执行的 deadline、控制租约期限与观测 freshness 分别记录。沿用或重新制定的门槛必须先写入契约和测试，不用放宽现有 2s／5s 等门槛来掩盖阻塞。

同一次观察只采集一次同 scope 连续性，并让 attach proof 引用该次真实结果。摘要可复用不等于刷新 `observedAt`；每项结果保留真实采集起止、scope 和有效期。

### 6.2 Worker 与共享 VM

哈希、解压、完整性扫描、DB 兼容验证和诊断由 worker 执行，限制 CPU、内存、进程、IO 并发、输出大小与运行期限。超时终止只针对本轮 worker；不能因此向 Owner、Guest 或业务任务发信号。验证使用只读挂载，结果包含输入 artifact／schema／范围及摘要，防止将别次证明用在本次计划。

进程独立仍与业务共享同一 VM 的 CPU、内存和 IO。控制及观察 worker 本身也必须计入资源预算，不能宣称隔离后就没有共同故障域。

启动候选前，按**本次真实组件集合**评估峰值开销：保留源／回退角色、候选、Owner 与 Guest、验证 worker、磁盘展开及控制保留量。资源不足则延期，展示已经证明无引用、符合退休条件的历史对象，以及剩余内存／磁盘等增容缺口；没有合格对象时只提供增容或延期出路，不指引管理员停止用户任务、Guest 或仍被保留的 Owner。不能先启动直到超时，也不能为腾容量停止用户任务。仅在精确身份、authority、连接、原资源与保留引用都允许时，按正规退休协议清理历史角色；资源不足不降低退休证明。

资源模板是安装时明确冻结的每类角色预算，实际预留则绑定每个技术attempt。Supervisor按原意图和原命令幂等建立attempt专属allocation；不能把上一次已成为resident的allocation改回空槽来启动下一个候选。A→B→C连续升级仍须把B及所有保留source、fallback、Owner和Guest完整计费；新的计划不改旧命令的spec、资源或期限。尚未产生运行／业务变更且容量判定明确不足时，持久化deferred并保留原服务；判定或旧动作未知时先查原结果。

退役后的容量释放必须消费同一原命令的真实applied正常退出收据，再以实际完整容器清单核对该CID已退出；首次执行、结果查询与重放都补齐同一出版事务。计划与居民配置半发布后重启，按原intent完成，不丢预算、不凭时间释放。引用状态由受限生产采集器读取真实Entry、连接、writer、命令、恢复、业务worker及Owner传输事实；缺失字段保持unknown，不能把“读取成功”或“表里没找到”转换成全部零引用。

## 7. 稳定同源入口、访问认证与签名

### 7.1 升级入口不经过待升级业务 API

StableEntry 为升级状态、版本发现、升级／恢复命令及其事件提供固定同源路径，直接路由到 Control Agent。实现时冻结具体路由和响应契约并更新 OpenAPI／Web codegen；本方案不把草案操作名视作已存在端点。

这些请求不能先转发给业务 API 再由它代理，否则业务 API 故障仍会切断观察和恢复。业务路径继续沿当前路由工作；控制路径故障不应重写业务绑定。

### 7.2 只有一个访问权威

沿用现有实例访问口令、原 Cookie、有效期、Origin／CSRF 和单管理员语义，不增加升级密钥、身份库或授权页面。Access Authority 是 Foundation 控制底座内的最小模块，不是独立网络微服务或新用户系统。

当前 `PasscodeService` 将口令 hash／默认 session signing secret 放在业务 `system_settings`，并使用进程缓存。目标中这几项访问策略由 Access Authority **一次性迁入并单独成为权威**；保留原有效签名配置以兼容已有 Cookie。原部署配置优先级及受固定配置限制的改口令规则保持。业务的访问设置入口改为调用同一权威，旧业务表不得继续成为另一可写来源；业务和控制共用验证组件与权威版本，不维护两份异步同步的身份 DB。

| 访问事件 | 权威与目标语义 |
| --- | --- |
| 原会话有效／到期 | 按原签名和到期时间验证；业务发布或控制维护不自行重签密钥使会话失效 |
| 普通重新生成口令 | 保持现有行为：新口令改变，不强制使既有会话失效 |
| `invalidateSessions`／明确安全轮换 | 同一权威更新会话失效状态；受固定 session secret 限制时沿用现有拒绝规则，不虚报成功 |
| 退出／撤销 | 沿用已定义的会话失效策略；清浏览器 Cookie 与服务端撤销分别表述。需要服务端撤销的操作必须由同一权威确认，不把客户端清理冒充服务端撤销 |
| 权威不可用、版本不明或迁移同步未确认 | 拒绝管理员新提交的升级／恢复写命令；不能用缓存的“曾经登录”或 Upgrade viewer Cookie 代替授权。原意图已明确授权的自动安全恢复按其持久授权与冻结范围判断 |

Control Agent 受理管理员提交的写命令时核对权威当前访问状态、会话、Origin／CSRF、实例及 requestId，记录授权判定与受理顺序。已确认撤销后的新命令不能因旧缓存继续获准。Entry 传递的内部鉴权上下文必须受保护并绑定请求，清除外来同名头；不能信任客户端自行声称已经登录。

用户会话到期不抹掉已合法受理的持久意图。原操作仍可按冻结计划触发已授权的自动安全恢复，无需再次点击；管理员另行发起的恢复／重试须重新通过当前访问策略。已受理意图不授权扩大范围、改目标或执行 Guest 生命周期动作。

### 7.3 最小权限与发布信任

- Control Agent 无业务 DB RW、SDK home、KVM 或 Docker socket；仅通过受限协议执行必要变更。
- Supervisor 持有强权限，但固定实例／角色／动作／物理身份与签名产物，不接受任意宿主路径、URL、命令或脚本；只读观察凭据不能执行变更。
- Owner home、角色密钥与业务主密钥按现有归属保护。部署权限不获得用户 stop／kill／destroy／cancel 权限。
- 业务包与控制包有独立类型、渠道／命名空间、版本、签名作用域和兼容声明。沿用受信发布根及明确的信任迁移规则，不为新包临时换根。
- 管理员访问、内部角色 RPC 和发布签名分别验真，发布方不持有代替管理员发起实例升级的授权。

## 8. 失败恢复不依赖失败 attempt 的租约

Control Agent 在升级失败后保留原 attempt 的失败终态与全部证据。**自动安全恢复与管理员另行发起的恢复都建立独立 RecoveryIntent、recoveryId、恢复计划和新的 control epoch**，关联原升级及失败位置，不复用原 attempt 的执行权。自动恢复的授权来自原已受理意图中冻结的安全恢复范围，无需管理员再次点击；管理员另行发起的恢复则重新核验当前访问授权。两者均根据当前实际状态核验恢复资格，不能因为自动触发就跳过准入。

正规恢复不重新领取旧失败 attempt、不手改它的三列控制字段、不补写 ready，也不要求旧业务 Store 仍能续期。Entry 退流校验独立恢复的稳定 control authority、当前绑定和回退资格。业务 writer 已交接时，精确查询原交接 commandId 的结果，再按正规业务交接协议处理，不能只将 API 指针回旧版就声称整体回滚。

恢复选择基于当前数据兼容性、真实角色和原资源归属：可退 API／Web、可按协议交接 Coordinator，或保持兼容的混合服务并修复前进。数据库不执行整卷倒灌，原 Owner 和已有 Guest 不迁移。恢复结果分别为已恢复、部分恢复／待确认、恢复受阻；不在 A／B 之间无限循环。详细状态机及不可逆边界见[恢复与回滚方案](../../ops/2026-10-20-升级失败恢复与回滚方案.md)。

## 9. 控制系统自身也需要维护

“稳定”表示业务发布不耦合它的发布节奏和 authority，不表示它永远不用升级。协议、安全或基础依赖修复可能要求低频控制维护。

控制包使用独立签名与版本，管理员明确进入控制维护；没有在途业务升级／恢复，或原操作已安全收敛并持久交接后，才准备 passive 候选。核验控制 DB schema 兼容、旧控制程序可读范围、原路由、权限及资源预算，再以单锁和单调 epoch 交接。

控制维护的执行与恢复由**保持存活的 Supervisor** 负责，不能依赖正在被替换的 Control Agent 为自身回退。停止旧 Agent 前，Supervisor 独立持久化同一个 maintenanceId、固定新旧签名产物身份、控制 DB 兼容范围、交接阶段及允许的失败动作。Agent 崩溃或 Supervisor 自身重启后，先按该记录查询物理身份、原命令结果和控制锁归属，再继续同一次维护；不另建维护操作重复更换。

只有证明旧执行者已停止发令、锁归属清楚且程序兼容当前控制 DB 时，Supervisor 才启动目标或回退到旧 Agent；未知则记录维护受阻，保持 Entry 绑定和 Owner 运行。不能恢复旧控制 DB 快照并让较低 epoch 覆盖仍运行的较高 authority，也不能因 Agent 已死而跳过单写锁或强行启动两个控制器。Supervisor 自身无法工作的恢复属于独立基础维护范围，不由已死 Agent 承担。

Control Agent 的维护默认不更新 Entry、Supervisor、Access Authority、VM 或 Owner。需要变更这些基础组件时单列实际影响和恢复方案：Entry 自身替换可能中断前端连接，VM／Docker／内核维护可能影响任务，不承诺所有基础层维护都绝对无中断。

控制维护期间 Entry 继续使用最后绑定，原 Owner／Guest 保持运行。若无法证明控制 DB 可回退、旧控制进程已失去发令能力或关键操作结果已收敛，停止维护并保留事实，不能让两个控制器同时发令。

## 10. 从 legacy 逐步迁移

迁移必须面对当前混合组件与失败记录，不能把业务最新 tag 当作当前完整状态。每阶段有独立收据与停止点，不依赖先成功执行另一次现有在线升级。

| 阶段 | 执行内容 | 进入下一阶段的条件 |
| --- | --- | --- |
| M0：冻结基线 | 精确记录 Entry、已确认发布、实际组件、业务 writer、所有 Owner／home、原 Guest／任务／终端与历史失败；只暂停新升级受理 | 身份与持久记录一致，原业务保持；不改历史失败或确认版本 |
| M1：只读旁观 | 安装 passive Control Agent 和独立控制卷，导入带来源摘要的 legacy 审计／当前基线；对照观察 | 无控制写能力、无新候选／Guest、投影与原始来源一致 |
| M2：兼容桥 | 实现稳定协议、业务 writer 事务守卫桥、统一访问权威及稳定同源路由；完成隔离验证 | 旧组件兼容范围明确，原 Cookie 和业务行为保持，切换／回退收据完备 |
| M3：控制切换 | 排空旧执行器，证明其停止发令或 authority 已失效；确立新控制 epoch 与参与者授权边界，再启用唯一新执行器 | 新旧不能同时变更 Entry／Supervisor／业务交接；所有未知操作已按原 ID 对账 |
| M4：小范围启用 | 先验证只读、重启恢复和正规恢复，再做普通业务升级演练 | 原 Guest／进程 birth／任务／终端／Owner 归属保持，失败可以通过稳定控制路径安全收敛 |

**现有 Entry 的 `verifyFence` 是启动时注入的闭包，目前没有已实现的在线更换验证器能力。** M2／M3 需要一次性 Foundation／Entry 维护设计，可能使前端 HTTP／WS 连接断开。必须单列维护影响及原会话重新附着验收；不能声称只挂一个旁观进程就能无缝改掉当前授权链，也不能直接重启整套 Foundation／业务角色来代替设计。

这次迁移只改变控制归属和必要的兼容协议，保留原 Owner 进程、SDK home、assignment、Guest、Agent／shell 进程及书签。关闭连接只执行 detach，不注入退出、不重放输入、不重新运行任务。当前源／回退锚点和有引用产物保留，直到新路径证明可服务及可恢复；历史 ledger 留作只读 legacy，不清空重建。

如果 M2 必需的兼容桥无法在现有路径安全部署，应另列一次明确授权的最小维护及影响，不能依赖原失败 attempt 的私有 DB 修补。未知状态先停在 passive／受阻阶段，不能为赶迁移停止原任务。

## 11. 日志与诊断边界

Control Agent、Entry、Supervisor、业务交接和 worker 使用 instanceId／operationId／attemptId／stepId／commandId 关联，恢复另含 recoveryId，控制维护另含 maintenanceId，但各自保存真实来源。控制请求额外记录 `requestKind`，区分写续期、只读 fence 检查、步骤心跳、观察和业务交接，避免只留下相同 URL 无法判断调用者。

每次调用保留：caller role／start identity、control epoch、目标角色／实际 identity、副作用摘要及授权 envelope 的非敏感标识、开始与结束、单调耗时、排队时间、原期限与剩余预算、结果／未知、拒绝原因、载荷字节数及 evidence digest。记录 phase 起止与采样区间，不能用写日志的时刻冒充实际观测时间。

独立诊断采集控制事件循环延迟、worker／候选 CPU、内存、IO 压力及限额、DB 调用／事务总耗时、请求排队与阶段耗时；采集本身受配额。锁等待只记录驱动实际提供的等待证据及其精度；同步 SQLite 调用总耗时不能直接拆算为精确锁等待，无法区分执行、调度和等待时保留 unknown。发生故障保存有界滚动窗口，区分已证触发点与待验证原因。诊断包默认脱敏，无 Cookie、口令、token、role key、完整环境、Guest 内容或业务 DB 全量导出；浏览器只显示阶段、原因、最近确认及可执行恢复动作。

除单条、单角色、单故障包上限外，还须冻结全实例诊断总字节、文件数、保留期、采集／导出队列及CPU／IO期限，为control.db关键写入预留空间。日志轮转只淘汰允许丢弃的诊断材料；仍被执行／恢复资格引用的持久收据不得按普通日志GC。慢盘、磁盘满、导出背压或配额耗尽时采集降采样／截断并标明缺失，不能阻塞业务或无界重试；缺少必要资格证据则停止推进，不伪造确认。具体初始预算及自故障矩阵见独立测试计划。

## 12. 实施顺序与完成门禁

1. 先冻结控制 v1、访问权威、两层 authority、包类型与兼容矩阵，统一相关契约和三份配套文档。
2. 实现独立控制持久化、常数级 fast path、幂等／未知结果查询、稳定同源入口和有界诊断；完成不依赖业务 HTTP 存活的控制验证。
3. 实现 Entry／Supervisor authority 与 Coordinator 兼容桥、独立 RecoveryIntent；验证迟到旧命令、跨库未知和恢复再次失败的收敛。
4. 实现 worker 配额、真实组件峰值资源准入、证据引用及安全退休条件，验证重任务不能阻塞控制路径。
5. 在隔离实例演练 legacy 迁移及控制自身维护，再按单独维护计划迁移现有实例；最后才开放普通业务升级。

独立测试至少覆盖：业务 API／Coordinator 失联时仍可读取真实控制状态并按资格恢复；旧业务＋新控制协议兼容；控制重启／自身维护失败及 Agent 已死后由 Supervisor 按原 maintenanceId 回退；旧 authority 及迟到回执拒绝；同 operation 下多阶段命令、摘要冲突及精确未知结果查询；新授权接管原 commandId 且不重置副作用、原 deadline 或预算；控制／业务记录任一侧成功后的对账；自动／手动独立恢复及各自授权来源；访问到期／改口令／撤销与原 Cookie；资源不足延期及 worker 压力；控制 DB 备份恢复与 epoch 不倒退；Entry 一次性维护后的原资源重连。完成条件以[测试计划](../../testing/changes/2026-10-20-独立升级控制与恢复测试计划.md)和真实收据为准，文档写完、发包成功或单次实验通过均不能替代上线资格。
