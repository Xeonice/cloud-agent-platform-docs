## 0. 命名规则与阅读约定（全文遵守）

### 0.1 路径缩写

| 缩写 | 实际路径 | 说明 |
|---|---|---|
| `A/` | `apps/api/src/` | 部署产物入口 |
| `M/` | `packages/modules/` | 七个限界上下文 |
| `K/` | `packages/shared-kernel/src/` | 共享内核（无业务概念） |
| `C/` | `packages/contracts/src/` | 三层 contract |
| `P/` | `platform/` | registry / config / persistence / outbox / system |

节点写法固定为 **`路径/文件名#类名.方法名()`**；同一文件连续调用只写一次路径。

**两条不可违反的方向规则**（01 §3 已由 eslint-plugin-boundaries 强制，本文所有调用图都符合）：
1. 箭头**只能**从 interface → application → domain，或 infrastructure → domain/contracts；
2. application **绝不**直接 import infrastructure 的具体文件——图中凡是 `APP → INFRA` 的箭头，实际都是**经端口 token 由 DI 注入**，图上标 `«port»`。

### 0.3 事务标记

图中用 `[T1 开` / `T1 关]` 标注事务边界；`«tx»` 表示该调用发生在事务内。事务的所有者永远是 application 层（24 R-1）。

**事务是同步的（审计 P0-2）**：`UnitOfWork.run(fn: (tx) => T): T` 的回调**不是 async**，回调体内不得出现 `await`——`better-sqlite3` 的事务包装器要求同步回调，遇到 `await` 会在让出点提前提交（论证见 23 §4.2）。因此图中所有 `«tx»` 调用都是**同步方法**（`saveSync(tx, …)`），凡是需要 `await` 的（provider / crypto / git / 网络）一律画在事务框**外**。看图时的检查法：**`[T1 开` 与 `T1 关]` 之间不应出现任何箭头指向 `INFRA` 的异步端口**。

### 1.1 逐步骤讲解

| # | 发生了什么 | 为什么在这一层 |
|---|---|---|
| 1 | Controller 只做 DTO 校验与转调 | interface 是**协议壳**；同一份 zod schema 也喂 MCP tool（02 §3），业务不能写在这里 |
| 2 | 门面 `createSandbox()` 转给 handler | 门面是协议无关边界，REST 与 MCP 注入同一个实例（02 §1） |
| 3 | 校验项目与镜像 **经对方门面** | 跨上下文不 import 对方 domain（01 §5）；`assertCanAcceptTask` 这类判断留在对方聚合里 |
| 4 | env 三层合并在**领域服务**里 | 它是零 IO 纯函数（23 §9.5），可穷举单测（25 T-IMG-11..14）。**凭证覆盖不在这一步**——在第 12 步最后写入 |
| 5 | **T1 开**，且整个 T1 在调度互斥区内 | 资源池的"读-判-写"必须串行且原子，否则并发创建超分配（03 §3）；互斥区外没有任何慢 IO |
| 6 | `trySchedule` 是纯函数 | 决策只依赖快照，不碰 DB；便于穷举边界（25 T-SBX-10..12） |
| 7 | 配额登记 + 建 pending 记录 + Outbox **同一事务** | R-3：事件与业务写入必须同事务，否则崩在中间会丢事件 |
| 8 | `save()` 内部双写两张表 | 23 §4.3 例外①；仓储实现负责，application 只调一次 |
| 9 | **T1 关**后立即返回 202 | 用户不该等拉镜像；后续进度靠 WS（24 §1.3）。注意资源池快照在 **T1 之前** `await` 好——同步事务内不能 `await`（§0.3） |
| 10 | 后台 workflow 逐阶段推进 | 多步编排属 application；每次转移**各自独立短事务** |
| 11 | provider 经 registry 取，按 `«port»` 注入 | application 不认识 `aio` 还是 `boxlite`（04 §8） |
| 12 | 凭证在 `starting` 阶段注入（第 ④ 步） | "同名凭证永远赢"靠**顺序**保证而非黑名单（05 §4.1）。**必须在 `provider.start` 之后**——`injectCredential` 收的 `exec` 由 `spawn({tty:false})` 派生，实例没跑起来根本没有 `exec`（此前图里的顺序是错的，已更正） |
| 12.5 | **装 CLI（第 ③ 步）在注入凭证之前** | 先有 CLI 才谈得上给它注凭证；且 `isInstalled` 与 `install` 同样要 `exec`。写库各自短事务、**不进 T1**（23 §4.3 已存档否决理由） |
| 12.8 | **起 agent 会话（第 ⑤ 步）在 provision 里，不在终端网关里** | 「启动时即执行」是产品承诺（P20 §0 / 02 §5.2）；绑在 `openSession` 上会让「关掉浏览器」与「MCP 创建」两条路径必不执行（裁决 D-15 / 03 §4.3） |
| 11.5 | **工作区在 `creating` 之前备好**（审计 P0-1） | 工作区是宿主目录，`provider.create()` 挂载它时源必须已存在（04 §2.4 注释）；顺带让 preparing 失败时的补偿不必销毁实例 |
| 13 | 失败按阶段走三套不同补偿 | 这正是 `preparing-workspace` 独立成状态的理由（03 §4.0）——清理动作不同 = 状态不同 |

## 10. 横切图②：Outbox relay 与 WS 投影

> **投递模型 = 提交后进程内同步派发 + relay 仅补漏**（13 §2.8.1，决策 B / 审计 P2-1）。单机单进程下事务同步提交（23 §4.2），提交即已落库——故**主路径是同步派发**，relay 只兜漏网记录，不是唯一出口。多节点时（11 §4）主派发退化、relay 恢复为纯轮询。

```

└─ 事务内：P/outbox/outbox.repository.impl.ts#appendSync(tx, events)      [13 §2.8.1]
│     → INSERT domain_events (published_at = NULL)   «tx，与业务同事务，R-3»
└─ 提交后（事务外，同步）：#dispatchInProcess(events)
   ├─ 逐条 dispatch(event)：
   │  ├─ K/infrastructure/event-bus.ts#publish(event)     ← 进程内订阅者（跨上下文联动）
   │  │   ├─ M/sandbox/application/event-handlers/credential-revoked.handler.ts     （链路⑥）
   │  │   ├─ M/sandbox/application/event-handlers/project-deleted.handler.ts        （级联销毁）
   │  │   ├─ M/terminal/application/event-handlers/sandbox-state-changed.handler.ts （级联关会话）
   │  │   └─ M/automation/application/event-handlers/sandbox-state-changed.handler.ts（run 终态）
   │  ├─ P/outbox/ws-projector.ts#project(event) → SandboxWsEvent | null   ← **投影映射表** [23 §12]
   │  │   └─ 非 null → P/ws/events.gateway.ts#broadcast(wsEvent)
   │  └─ 成功 → #markPublished(id)
   └─ 主派发抛错不阻断请求（已提交）——留给 relay 兜底

【补漏侧（仅兜底，非主路径）】P/scheduler/timers.ts#every(5s) → P/outbox/outbox.relay.ts#runOnce()
├─ listUnpublished()：扫 published_at IS NULL 且 occurred_at 早于 N 秒的**漏网记录**（同步派发崩溃/多节点）
├─ 对每条走同一 dispatch(event)（与主路径同一函数，不重写）
└─ 归档：P/outbox/outbox.archiver.ts#runOnce() 清理超保留期已投递事件

【消费侧幂等（关键——防主派发与 relay 双投递）】

同步派发已处理、relay 兜底再扫到同一条 → dispatch 二次但 handler 幂等丢弃。
markPublished 与同步派发存在竞态窗口（派发成功、markPublished 前崩溃）→ relay 会重投 → 幂等兜住。

【不经 Outbox 的两条直推（可丢失事件，10 §7.4 纪律）】
ProjectCloneProgressed / waiting-input.detector → ws-projector/gateway#broadcast（不落 domain_events，丢了不影响最终态）
```

| 文件 | 层 | 职责一句话 | 设计元素 |
|---|---|---|---|
| `P/outbox/outbox.repository.impl.ts` | platform | 事务内 append + 未投递扫描 | 13 §2.8.1 |
| `P/outbox/outbox.relay.ts` | platform | **补漏轮询**（扫漏网记录，5s，`runOnce()` 可测）——主投递是提交后同步派发（13 §2.8.1），非 relay | 24 R-3 · 25 §1.4 |

## 14. 怎么用这份文档写第一个功能

1. **看端点**：功能对应哪个端点？→ [02 §5.1](./02-MCP与OpenAPI双协议.md) 或 [10 §6](../shared/10-接口契约与类型共享.md)。
2. **看模型**：动到哪个聚合、有哪些不变量？→ [23](./23-领域模型与聚合设计.md) 对应上下文那一节。
3. **看时序**：事务在哪、失败怎么补偿？→ [24](./24-产品子链路后端设计.md) 对应链路。
4. **看落点**：每一步写在哪个文件？→ **本文对应章节的调用图 + 文件清单表**；新文件的位置从 §13 的索引里找。
5. **看表**：读写哪张表、有哪些约束？→ [13 §2](./13-后端数据库设计.md) 对应上下文那一节。
6. **看用例**：要写哪些测试？→ [25 §3](./25-后端测试体系.md)（按 `I-*` 编号找 `T-*`）。

**六份文档一条编号链**：端点（02/10）→ 不变量 `I-*`（23）→ 链路 `①–⑧`（24）→ 文件与函数（26）→ 表与约束（13）→ 用例 `T-*`（25）。任何一环缺失都说明设计没落完。
