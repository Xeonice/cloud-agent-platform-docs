## 第一部分：后端变更时前端"实时"类型感知

### 1. 三层机制总览

```
[后端仓库]                                  [前端仓库]
  controller/DTO 变更
        │
        ├─(本地 dev)── dev server 暴露 /openapi.json ──► 前端轮询脚本(hash 对比)
        │                                                  │ 变化即重新生成类型
        │                                                  ▼
        │                                          tsc --watch / IDE 秒级报红
        │
        ├─(PR 阶段)── CI 生成 openapi.json diff ──► oasdiff-action PR 评论
        │                                            breaking change 列表（review 期拦截）
        │
        └─(merge 后)── repository_dispatch(PAT) 触发前端 workflow
                          │
                          ├─ 拉取 openapi.json → 重新生成类型
                          ├─ 有 diff → create-pull-request 自动开 PR（附类型 diff）
                          └─ 前端未适配 → tsc/CI 天然打红（最强提醒，无需额外设计）

[运行时兜底]  响应头 X-Schema-Hash ↔ 前端编译期固化 hash 比对
              不一致 → 仅 dev/staging console.warn（生产不做：灰度多版本并存是常态）

[WS 协议]     ws-protocol.ts(zod schema) 为唯一源 → 方案 A 独立 npm 包 / 方案 B hash 比对
```

### 2. 各层细节

#### 2.1 本地 watch 闭环

- **已核实：openapi-typescript CLI 没有 `--watch`**，需自建。它原生支持远程 URL 输入，前端可直接指向本地 NestJS dev server 的 `/openapi.json`。
- 两个独立仓库无共享文件路径，chokidar 无用武之地 → **轮询脚本** `scripts/watch-openapi.mjs`：2–3s `fetch` + sha256 对比，变化才调 openapi-typescript 的 **Node API** 重新生成（比反复 spawn CLI 快）。
- IDE 闭环无需额外设计：tsserver 监听 `.d.ts` 变化自动 reload；建议 `concurrently` 并行拉起「watch-openapi + `tsc --noEmit --watch` + next dev」三进程。

#### 2.2 后端 PR 阶段预警：oasdiff

- **推荐 [oasdiff](https://github.com/oasdiff/oasdiff) 免费版**：当前最活跃的 CI-first OpenAPI diff 工具，支持 3.0/3.1/3.2，可检测 509 种变更，oasdiff-action 免费在 PR 上做 inline annotation。
- 备选对比：OpenAPITools 的 openapi-diff 迭代放缓、社区重心已转 oasdiff；Optic 更重、需云端帐号，适合更大团队。Pro 版的 approve/reject + commit-status 阻断作为升级路径。
- 价值：**后端开发者在合并前就看到 breaking 列表**，把发现时点从联调期提前到 review 期。

#### 2.3 merge 后跨仓联动

- `repository_dispatch` 标准机制；需要 **fine-grained PAT**（contents:write + workflow，org secret）。注意：默认 `GITHUB_TOKEN` 不能跨仓触发、也不能触发 workflow 生成 commit 的下游 workflow——必须显式 PAT，且要防触发死循环。
- 前端侧 workflow：拉 openapi.json → 生成 → 有 diff 用 create-pull-request 自动开 PR（附类型 diff）→ 前端代码未适配则 tsc 打红。业界已有同构实践案例验证可行。

#### 2.4 运行时兜底：X-Schema-Hash 握手（低成本高信号，建议做）

- 后端响应头带 canonical openapi.json 的 sha256；前端类型生成脚本顺手把 hash 固化为常量；API client 初始化时比对。
- **仅 dev/staging console.warn**，不做阻断弹窗、不进生产——灰度发布多版本并存是正常状态，生产告警只会制造噪音。

#### 2.5 WS 协议的同等机制

无 openapi 类机器可读契约，按改动频率二选一：

| 方案 | 做法 | 适用 |
|---|---|---|
| **A（升级路径：改动频繁时采用）** | `ws-protocol.ts`（含 zod schema）拆独立 npm 包，semver 发布 + 前端 Renovate/Dependabot 自动开 PR，tsc 红即 drift | 最贴近"类型系统层面感知"；当前方案是 B（与文档 10 §1 一致） |
| **B（轻量）** | 后端 CI 对协议文件算 hash 写入 release asset；前端 cron workflow 定时比对，不一致任务失败提醒人工同步 | 改动不频繁、不想拆包 |

zod 运行时校验失败上报（文档 16 §3）是**滞后**的最后防线，不能替代以上两者。

> 注：方案 A 与文档 10 "不发 npm 包"的结论不冲突——文档 10 针对的是 REST 类型（有 openapi codegen 这条更优路径）；WS 没有 codegen 路径，独立小包是"类型感知"最强的选项，且仅含协议文件、无运行时代码。起步可先用方案 B，协议趋于频繁变更时升级 A。

### 3. 推荐组合

| 版本 | 内容 | 成本 |
|---|---|---|
| 精简 | 本地 watch + PR 阶段 oasdiff（不做跨仓 dispatch，靠既有漂移检测 CI 兜底） | ~0.5 人日 |
| **标准（本项目推荐）** | 三层全做 + 运行时 hash 握手；WS 先方案 B 起步、改动频繁时升级 A（与文档 10 §3 同口径） | 1–2 人日搭建 + 少量维护 |
| 重度 | oasdiff Pro 阻断 gate + WS 独立包 + changesets | 需专人维护 |

## 第二部分：防止书写时刻意绕过类型

### 4. ESLint 规则清单（前后端共用基线）

```js
// —— 语法层（无需 type info，pre-commit 本地跑）——
'@typescript-eslint/consistent-type-assertions': ['error', {
  assertionStyle: 'as',
  objectLiteralTypeAssertions: 'never',    // 对象字面量断言一律改 satisfies
}],
'@typescript-eslint/ban-ts-comment': ['error', {
  'ts-expect-error': 'allow-with-description',
  'ts-ignore': true,                        // 彻底禁用，强制换 ts-expect-error
  'ts-nocheck': true,
  minimumDescriptionLength: 10,
}],
'@typescript-eslint/no-non-null-assertion': 'error',

// —— 双重断言（as unknown as X）——
// 已核实：typescript-eslint 没有现成规则，用 no-restricted-syntax 拦截
'no-restricted-syntax': ['error', {
  selector: 'TSAsExpression > TSAsExpression',
  message: '禁止双重类型断言（as unknown as X）；确需绕过请 eslint-disable + 理由注释，并收敛到 types/shims',
}],

// —— type-aware 层（parserOptions.projectService，CI 跑）——
'@typescript-eslint/no-explicit-any': 'error',
'@typescript-eslint/no-unsafe-assignment': 'error',
'@typescript-eslint/no-unsafe-call': 'error',
'@typescript-eslint/no-unsafe-member-access': 'error',
'@typescript-eslint/no-unsafe-return': 'error',
'@typescript-eslint/no-unsafe-argument': 'error',
'@typescript-eslint/no-unnecessary-type-assertion': 'error',
'@typescript-eslint/no-unsafe-type-assertion': 'error',  // 8.15+，禁"缩小类型"断言；不在预设里，须手动开
```

- 预设：直接 **`strictTypeChecked` + `stylisticTypeChecked`**（已核实 no-non-null-assertion 在 strict 有、recommended 没有）。
- 性能：`projectService`（8.0+ 稳定）取代旧 `parserOptions.project`；官方 issue 显示个别场景有性能退化，缓解：CI `--cache`、只对 `src/**` 跑 type-aware、**pre-commit 只跑语法层规则，type-aware 留给 PR CI**（与文档 09 的 lint-staged 配置衔接）。
- 配合 `consistent-type-imports` 明确 type-only import，并在 boundaries 规则中对纯类型导入放宽（防误判跨层依赖）。

### 5. tsconfig 严格化清单

| 选项 | 建议 | 坑 |
|---|---|---|
| `noUncheckedIndexedAccess` | **立即开** | 下标访问补 undefined 处理，成本低 |
| `noPropertyAccessFromIndexSignature` | **开** | 对 process.env/动态 config 反而友好 |
| `noImplicitOverride` | 开 | NestJS Guard/Filter 继承场景收益高 |
| `exactOptionalPropertyTypes` | **谨慎：新模块试点，不全量** | NestJS：class-validator `@IsOptional()` 与显式 undefined 赋值冲突、三方 ORM 类型未适配；React：受控组件故意传 undefined 会大面积报错 |
| `verbatimModuleSyntax` | 可选 | ESM 迁移期加分；NestJS 11 CJS 互操作需小心 |

### 6. 类型覆盖率门禁：type-coverage

- 仍是事实标准（低频维护但可用，2026 未见取代者）；`typescript-coverage-report` 可作 HTML 报告互补。
- 用法：`type-coverage --at-least <阈值> --strict --detail`。
- **本项目是绿地仓库：直接设 99%+ 阈值起步**（存量仓库才需要 ratchet 渐进策略）。

### 7. 合法逃逸的治理流程

1. 优先级：`satisfies` / 类型收窄 / 本地 `.d.ts` overrides > 断言 > disable。
2. 确需逃逸：
   - `@ts-ignore` 全禁，只允许 `@ts-expect-error` + ≥10 字符描述；
   - eslint-disable 强制理由：`@eslint-community/eslint-plugin-eslint-comments` 的 `require-description`，约定格式 `-- 第三方库 xxx@1.2 类型缺陷，见 ISSUE-123`（可 grep 审计）；
   - 三方库类型缺陷统一收敛 `src/types/vendor-overrides.d.ts` / `types/shims/`，业务代码只 import 本地强类型封装，**review 只重点盯这一个目录**。
3. 逃逸计数 ratchet（可选加强）：CI 统计 `as unknown as` / `@ts-expect-error` / 裸 any 次数 vs baseline 文件，新增即 fail、改 baseline 必须留痕。注意：机制只是提高绕过成本 + 留痕，**不能替代 code review 文化**。

### 8. 前后端差异化配置

**NestJS：**
- `no-extraneous-class: { allowWithDecorator: true }`（放行纯 `@Module()` 空类，官方标准做法）；
- `no-unused-vars` 对构造函数参数属性（`constructor(private readonly x: Y)`）配例外——DI 核心语法；
- 可选 `eslint-plugin-nestjs-typed`：检查 `@ApiProperty` 与字段类型对齐、Controller 漏 `@ApiResponse`——**直接提升第一部分契约链路的源头质量**，建议引入。

**Next.js/React：**
- `no-unsafe-*` 在三方 UI 回调/`formData.get()` 场景易大面积报警：统一走 zod `parse()` 后再赋给强类型变量，**不逐处 disable**；
- `exactOptionalPropertyTypes` 遗留期不开（受控组件坑大）。

## 10. 类型系统**关不住**的那一类,以及正确的防线在哪一层 ★

> 起因是一次真跑:建沙箱在真后端下**必然失败**,而两仓 CI 全绿、三份 review、
> 33+ 条变异、8 项跨仓门禁,**没有一条碰到它**。值得单开一节,因为这一类缺陷
> 不是"类型没写好",而是**防线补错了层**。

### 10.1 案例:`runtime: 'shell'`

`web/src/containers/SandboxTerminalContainer.tsx` 里有一行 S2 时期的占位:

```ts
// S2:projectId 来自选中的真实项目;runtime 仍占位(S3 接 runtime)。
const S2_DEFAULT_RUNTIME = 'shell';
```

注释自己写了"S3 接 runtime",但 S3 做鉴权时没回头改。后端注册表里只有
`codex` / `claude-code` ⇒ 从这个入口建的沙箱,一律死在 provision 的
`unknown runtime 'shell'`。

**为什么四道防线一道都没拦住:**

| 防线 | 结果 | 为什么 |
|---|---|---|
| 编译期类型 | ❌ 拦不住 | 契约是 `runtime: z.string().min(1)` —— **开放字符串,且不该收窄** |
| openapi codegen | ❌ 拦不住 | 生成出来就是 `runtime: string`,`'shell'` 完全合法 |
| 单测 / Storybook / Playwright | ❌ 拦不住 | **MSW mock 也返回 `runtime: 'shell'`** —— 见 §10.3 |
| docs:check 的 8 项 | ❌ 拦不住 | 它们验的是"两仓与契约一致",而这个值**在契约层面合规** |

### 10.2 根因:开放集**故意**不收窄,所以类型层无能为力

`runtime` 与 `provider` 都是**开放注册表**的键。`ProviderRegistry` 的契约注释
原文:*"Open registry keyed by ProviderId string (**not a closed enum**, 04 §8)"*。
第三方 provider / runtime 在**运行时**注册 —— 收成 enum 会直接砍掉"分离且
**可注册**"这条核心要求(04 §8)。

⇒ **不要试图用类型解决它。** 想收窄的冲动本身就是错的方向。

### 10.3 正确的防线:两层,缺一不可

**① 前端:由注册表驱动 UI,不硬编码任何注册表的值**

这套做法项目里**已经有了**,只是没被普遍应用:

| | 有没有做 |
|---|---|
| `provider` | ✅ `listProviders()` → `providers.map(...)` 渲染,能力位驱动显隐(04 §5) |
| `runtime` | ❌ `GET /api/runtimes` **只在 MSW mock 里出现过**,生产代码从未消费 |

**纪律**:凡是后端以"开放注册表"暴露的集合(今天是 provider / runtime,将来是
image / 其它),前端**一律拉取后渲染**,不得出现字面量默认值。写死一个键 ==
把一个运行时事实钉成编译期常量。

**② 后端:在门口同步校验,不要漏进异步阶段**

`unknown runtime` 是**入参问题**,却漏到了 provision 的**异步**阶段才炸 ——
于是用户先看到"创建中",再收到一次失败的沙箱,而且错误码被归进
`INSTALL_FAILED`(归因也错了)。

它本该和能力位静态校验(`assertCapabilities`,不满足直接 409、**不进调度、
不落库、不调 `provider.create`**,04 §5)在同一个位置:`POST /api/sandboxes`
同步校验 `runtime ∈ registry`,不认就 400。

**纪律**:开放集的合法性校验属于**门口**。异步阶段发现的入参错误,代价是
一次假的资源创建 + 一个错误的归因。

### 10.4 §10.1 表格第三行单独拎出来:**mock 编码了和前端一样的错误假设**

`web/src/mocks/handlers.ts` 里两处返回 `runtime: 'shell'`。于是前端与**它自己的
mock** 完全自洽,真后端从头到尾没进过回路。

这是 S6 集成审查那句总结的又一个实例 —— 只不过这次的"两端"是前端和它自己的
替身:

> 缺口全部落在"**没有任何一侧拥有的那半步**"上。

**纪律见 [12 §3.4](../frontend/12-前端测试体系.md)。** 一句话版本:**mock 的形状
可以手写,mock 的「值」不能凭空**;凡是取自后端开放集的值,替身必须用真实来源
里存在的那些。

### 10.5 判据:什么时候该怀疑"类型关不住"

出现下面任一条,就不要指望类型和 codegen:

1. 契约里是 `string` 而不是 `enum`/`literal` 联合(且**有意为之**)
2. 取值集合由**运行时注册**决定(registry / 插件 / 配置)
3. openapi 里有 `oneOf` / `maxLength` / `maxItems` 之类的**值约束** ——
   `openapi-typescript` 会把它们拍平(S6 已知:`TASK_TIMEOUT_OPTIONS` 的四档
   闭集在生成物里丢成 `number`)

这三类的防线只能是:**注册表驱动 / 门口校验 / 运行时断言**,并且要有测试真的
打到那条路径上。

## 9. 风险与成本

| 风险 | 缓解 |
|---|---|
| PAT 维护（有效期/最小权限/轮换）+ 两仓耦合运维心智 | 明确 owner；fine-grained PAT 最小权限 + 定期轮换 |
| oasdiff 假阳性（如新增必填字段但有默认值） | 规则排除配置 + 人工 override 通道 |
| exactOptionalPropertyTypes 迁移成本数天到数周 | 新代码强制、旧代码 grandfather，绝不存量全开 |
| ratchet 沦为"改个数字就过"的形式主义 | 改 baseline 必须留痕 + review 把关，机制只负责提高成本 |
| type-aware lint 慢数倍拖慢反馈 | cache + job 拆分 + 本地只跑语法层、type-aware 只在 PR CI |
