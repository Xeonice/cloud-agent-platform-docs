## 1. 单机部署形态

平台服务统一运行在 **macOS 宿主 → Colima Linux arm64 VM（Apple VZ、嵌套虚拟化）→ Docker Foundation 与五个独立角色** 中。BoxLite 在 Linux RuntimeOwner 内经 `/dev/kvm` 运行 Guest，安装包目标为 Linux arm64。Darwin SDK／ABI 支持属于本地开发能力，不是平台服务部署方式。

Foundation 常驻 StableEntry 和 CandidateSupervisor，维护本实例的入口、已确认路由及受控角色启动边界。五个业务角色分别是 ControlAPI、Web、StateCoordinator、RuntimeOwner 和 Installer；不能把它们重新合成一个同时持有数据库、凭据和 SDK home 的服务。

2026-10-20的实现将升级控制拆为独立版本的 `control-agent`，入口和Supervisor分别运行于 `control-entry`、`control-supervisor`。下表同时列出迁移期原有部件和新实现的真实挂载闭集；它不是已经完成远端迁移的声明，实例状态仍以[当前部署记录](../ops/统一虚拟化与实例部署.md)为准。

<!-- deployment-roles:start -->
| 部件ID | 运行部件 | 业务库挂载 | Owner SDK home |
| --- | --- | --- | --- |
| `foundation` | Foundation（StableEntry + CandidateSupervisor） | 运维边界 | 运维边界 |
| `api` | ControlAPI | 无 | 无 |
| `web` | Web | 无 | 无 |
| `coordinator` | StateCoordinator | 读写 | 无 |
| `owner` | RuntimeOwner | 无 | 独占 |
| `installer` | Installer | 无 | 无 |
| `control-agent` | 独立升级控制 Agent | 无 | 无 |
| `control-entry` | 独立 StableEntry | 无 | 无 |
| `control-supervisor` | 独立 CandidateSupervisor | 只读 | 无 |
<!-- deployment-roles:end -->

上表的“运维边界”表示 Foundation 是持有 Docker socket 的可信运维部件，能够按已验证配置建立角色挂载、执行受控导入和恢复；它不是另一个业务数据库写者。实际运行权限如下：

独立Agent仅持有私有 `access.db`、控制账本、下载和诊断目录，不持有业务库、SDK、Docker socket、宿主进程或cgroup。独立Supervisor持有受控生命周期权限及业务只读观察；控制维护仅允许对独立控制账本作固定维护屏障CAS，不读Agent的访问策略数据库。其普通启动接口不提供控制角色生命周期权限，维护另用私有凭据与原命令对账。

- **StateCoordinator 是唯一业务库写者**，持有业务根、Vault、状态和调度权。交接遵守 fencing 和唯一写者约束，不能并排启动两个 Coordinator 共同写库。
- **RuntimeOwner 独占自己的 SDK home**，只获得本 Owner 的 home 和所需工作区挂载，不获得业务数据库、整个业务根或整个 Foundation 卷。只有 Owner 使用 `/dev/kvm` 和 privileged；其余角色按适配器收紧 capabilities，并启用 `no-new-privileges`。
- **ControlAPI、Web、Installer 均无业务库、SDK home 和 Docker socket**。ControlAPI 转发请求及流；Web 使用本实例的版本化页面；Installer 只持有所需的已验证产物、只读绑定和信任根，以及自己的下载、journal 等受控写目录。不能为了日志、诊断或升级方便扩大挂载。
- **业务、产物、来源使用独立 Linux 卷**；Foundation 卷保存运维运行根、绑定和各 Owner 的独立 home。初始 Owner home 位于运行根的 `original-owner`，后续 Owner 使用各自独立目录。已存在的 Guest 始终归原 Owner，不能将原 home 同时交给新进程打开。
- 所有角色按适配器获取必要的只读代码和显式 CA 文件；不能把宿主 HOME、SSH 配置、发布私钥或整棵环境文件挂入角色。Docker 查询固定专用配置、socket 和 VM profile，不切换全局 context。

**首次维护导入与后续在线升级是两条流程**。首次导入先确认来源空闲、形成一致冻结导出并停止来源写者，再建立独立 Linux 业务卷、产物和安装记录。这个维护窗口不属于在线无感升级验收，也不能为导入擅自停止用户任务。来源导出保留为只读证据，不能把来源 SDK home 或业务写卷继续当作新实例的运行目录。

后续升级由有实例升级权限的管理员决定时机。CD 只构建、校验、签名和发布不可变版本、安装包、镜像与目录，不部署实例、不切 API／Web、不触发升级。实例发现版本和显示提醒不启动下载或安装；用户明确发起后，实例控制器才固定目标、下载、校验、准备候选并切换。进度来自真实 attempt，失败或 unknown 如实保留。页面刷新由用户在升级完成后自主选择，原 Guest、终端和任务仍通过原 Owner 续接，不重放输入。

签名验证、首次导入成功和一次服务恢复都不等于完整 release 资格或真实跨升级连续性通过。已验证范围以独立验收报告为准；未验的宿主／全栈自动冷恢复、模型 Agent 和完整故障矩阵不能宣称可用。恢复先核对持久配置、绑定、角色身份和日志，不能重复首次安装、手改 ready、整卷回写或执行 prune。

### 1.1 auth helper 的运行形态（05 §2 决策 A 的部署落地）

帐号授权 CLI 在平台管理的 **auth helper 执行环境**内运行，与用户任务 sandbox 解耦。统一部署中，请求经 **ControlAPI → StateCoordinator → RuntimeOwner** 到达 provider，由 Owner 管理 helper 和实际登录进程；ControlAPI 不直接创建 Guest，也不打开 SDK home。本地 CLI 诊断统一按 CONTRIBUTING 执行，不增加实例部署方式。

| 项目 | 部署纪律 |
| --- | --- |
| 固定身份 | 使用 contracts 常量 `AUTH_HELPER_SANDBOX_ID = 'auth-helper'`；不改为随机 id。它是凭据基础设施，**不得写入用户 `sandboxes` 或 `resource_allocations` 表**；调度使用专门的常量预留，不能冒充一个用户任务 |
| 创建入口 | 平台经 provider 创建并启动，使用当前 provider 对应的官方平台预制镜像；不能在运维层手工创建一个同名实例替代 provider 的 token、句柄与归属记录 |
| 执行边界 | 不挂用户工作区、不接受用户代码、不覆盖镜像 entrypoint。helper 与用户 Guest 分离，只执行授权、凭据刷新和必要的 CLI 版本诊断 |
| CLI | 原样安装官方 CLI，保持 helper 与任务镜像的版本契约；版本缺失或不受支持应在诊断中显式报告。官方授权方式的边界见 [05 §2](../backend/05-Runtime鉴权流转.md#2-核心设计决策) |
| 凭据收编 | 登录产生的 `auth.json`／`.credentials.json` 收编到 Vault 后立即清除；不能写入安装包、日志、镜像层或工作区 |

每次 begin／refresh 都用 `mkdtemp` 创建唯一、绝对路径的 `HOME`／`CODEX_HOME`／`CLAUDE_CONFIG_DIR`，通过 `spawn({tty:true})` 的 env／cwd 传入，使用 `try/finally` 清理。不能复用 helper 默认 HOME；交互登录与刷新 scanner 使用互相隔离的临时目录。helper 内的临时根放在其适合 CLI 使用的 HOME 下，不能因宿主或容器的 `/tmp` 约定而漂移。残留临时 HOME 是泄漏信号，应进入诊断；日志和报错不得包含凭据。

helper 的生命周期由运行链路管理：复用前只读 inspect；确认为失效时按 CAS 作废句柄，每次操作至多重建一次。执行遇 provider 错误时走受控失效与重试，不能降级到在用户任务中登录。只读诊断不创建 helper、不 exec、不用可能隐式启动 VM 的 metrics 探活。超时或未知结果不能伪造成凭据拒绝，也不能据此销毁仍可能存活的用户 Guest。helper 不可用导致的刷新失败不计入凭据本身的失败次数，凭据过期仍以 `expires_at` 为准。

离线环境下登录服务不可达应如实诊断；禁止为掩盖网络问题复用其他用户凭据、修改官方 CLI 或绕过鉴权。

### 1.2 `DATA_ROOT`：Linux 业务数据根

`DATA_ROOT` 是 StateCoordinator 看见的业务根。部署使用独立 Linux business 卷，按 bootstrap 配置挂到 `/data`，首次导入实验还使用适配器规定的规范路径 alias。它不是 macOS 仓库目录，也不包含 Owner SDK home。实际宿主来源、容器目标与工作区映射必须来自本实例的固定配置及 `roleMounts`，不能让每个角色自行拼一个宿主路径。

业务根保持以下逻辑布局：

```text
${DATA_ROOT}/
├── baselines/<projectId>/      # 项目基线
├── workspaces/<sandboxId>/     # 任务工作区，Owner 只获得所需工作区挂载
├── logs/runtime.log            # 业务运行日志及 .1… .4 轮转文件
├── logs/agent-tasks/           # 无头任务原始日志
├── .master.key                 # Vault 主密钥
└── platform.db                 # SQLite 及其 -wal、-shm
```

| 存储边界 | 内容与约束 |
| --- | --- |
| Foundation 卷 | `instance` 运维根、持久绑定、受控工具、`original-owner` 及后续独立 Owner home；业务角色只获得必要子目录 |
| business 卷 | 数据库、Vault、项目基线、工作区和业务日志；Coordinator 唯一写库，Owner 仅挂工作区 |
| artifacts 卷 | 按包摘要保存经签名和完整树校验的安装产物；运行代码按角色只读挂载，不原地覆盖 |
| source 卷 | 一致冻结导出；完成导入后保留只读，不再作为运行写卷 |

必须保留以下纪律：

- **路径与身份稳定**：实例 id、业务根、数据库和 Owner home 绑定后不能通过改环境变量随意换库或换 home。工作区挂载的来源与目标必须与记录一致；来源不明或存在相互覆盖时拒绝启动，不能靠复制一份目录“修复”。
- **权限对齐**：业务根和 `${DATA_ROOT}/workspaces` 父目录为 `0700`；工作区按现有执行契约使用 `0777`，由不可 traverse 的父目录收住其他本地用户。`.master.key`、`platform.db` 及 `-wal`、`-shm` 为 `0600`；数据库打开时由 `hardenDatabaseFiles` 收紧权限，主库先于 WAL 建立权限。Owner home、私有配置与密钥父目录为 `0700`，私密文件为 `0600`。
- **复制能力如实报告**：Linux 文件系统支持 reflink 时可使用写时复制，建议适配 btrfs／xfs；不支持时按实际能力复制，不能把全量拷贝宣称为瞬时快照。本地开发的 Darwin 行为由 CONTRIBUTING 管理。
- **容量是实例资源的一部分**：监控业务卷、Owner home、产物和下载／journal 的实际磁盘余量。清理必须基于归属、引用和保留策略；禁止为释放空间删除仍承载 Guest 的 Owner home，禁止 volume／image／system prune。
- **备份与回退保持一致性**：数据库、Vault 主密钥、工作区及归属记录一起评估备份边界。升级回退不得把旧整卷覆盖到已有新写入的业务卷；不兼容数据变更必须按迁移计划和唯一写者交接处理。

#### 1.2.1 `${DATA_ROOT}/logs/`：运行日志必须落盘（v1.1）

业务运行日志仍写入 `${DATA_ROOT}/logs/runtime.log`，产品日志导出经有业务根权限的 StateCoordinator 提供。角色的 stdout、Foundation 和宿主入口日志由受控运维路径采集；不能为了导出日志给 ControlAPI、Web、Installer 增加业务根或 Docker socket。

| 项 | 值 | 理由 |
| --- | --- | --- |
| 路径 | `${DATA_ROOT}/logs/runtime.log` + `.1`…`.4` | 与业务数据一起纳入一致备份和迁移 |
| 轮转 | 按大小，20 MB × 共 5 份，磁盘上限 100 MB | 与产品日志导出上限分别控制 |
| 脱敏 | 写入时脱敏，与凭据纪律同源 | 读出口脱敏不能保护磁盘和备份 |
| 权限 | 文件 `0600`，`logs/` 目录 `0700` | 与业务库、Vault 一致 |

运行日志与产品审计流分开：前者用于故障诊断，后者用于用户可理解的结构化事件。不能把运行栈直接灌进审计面板。落盘与 stdout 并存，跨角色排障按实例、角色、attempt 和时间关联，不输出完整环境、认证头、Cookie 或密钥。

轮转遵循 `end()` 旧流 → 回调内 rename 链 → 重开流；窗口内日志缓冲后重放，SIGTERM 时放干缓冲。日志导出使用可流式的 npm `tar` 或 Node `zlib`，不依赖不同宿主 shell／tar 参数。脱敏规则应由公共能力统一，不能因角色拆分漏掉 CLI 输出、运行日志或升级 journal。

### 1.4 IP 入口与 Linux loopback 边界

宿主 IP 入口只把指定公开端口转到本实例的 Linux loopback StableEntry。Colima／Lima 只转发所需 Entry 端口，不能将内部角色端口、任意 TCP／UDP 或 Docker socket 一并公开。

<!-- deployment-entry:start -->
| IP入口用途 | 宿主公开端口 | Linux loopback Entry端口 |
| --- | --- | --- |
| 正式 | `3000` | `3181` |
| 隔离预演 | `13000` | `4181` |
<!-- deployment-entry:end -->

链路为宿主 IP 入口 → 宿主 loopback 转发 → Linux loopback StableEntry → 本实例已确认的 Web／ControlAPI。入口启动核对预期 instanceId 和健康状态，不能将错误实例的正常 HTTP 响应当成目标就绪。正式与隔离预演使用各自的实例、绑定、信任根和写卷，不共享业务状态。

浏览器 HTTP／WebSocket 使用实例同源入口。Entry 根据已确认绑定切换候选；API、页面和 Owner 生命周期不能仅凭一个端口开着就视作一致。原有 Guest 和终端归原 Owner，连接断开后的重连不等于重建 Guest；平台不能重播输入来伪造连续性。网络恢复与整套服务冷启动恢复分别验收，前者通过不能替代后者。

registry 的地址以 Linux VM／Owner 实际可达的坐标为准：`localhost`／`127.0.0.1`／`[::1]` 指当前网络命名空间。明文 registry 仅允许明确配置的可信地址，不允许先试 HTTPS、失败后静默退回 HTTP。播种失败先核对地址、解析、路由、证书和已发布镜像，不能随意改默认镜像绕过 provider 契约。

## 2. 持久化：SQLite 起步，Postgres 预留

当前使用 `better-sqlite3` 与 Drizzle，SQLite 的业务读写集中在 StateCoordinator。domain 只声明 Repository 接口，持久化细节留在 infrastructure；切换 Postgres 属于单独的数据迁移和适配工作，不能因为已有接口预留就宣称可直接切 driver。

避免将 SQLite 专有行为泄漏到 domain，迁移需验证 schema、数据语义和回退边界。并发 sandbox 超过 50 或 QPS 超过 100 可作为评估 Postgres 的经验信号，实际决策依据事件循环阻塞、事务时延、写入负载和资源观测；它不是自动迁移开关。多节点仍须明确唯一业务写者，不能给各 API 或 Owner 各开一份业务库。

## 3. 无帐号体系下的鉴权预留

当前实例访问口令提供基础访问控制，不引入帐号或多人角色体系。REST／MCP／WS 继续通过统一 Guard／授权边界，后续用户体系接入替换该抽象，不在各业务模块分别实现一套。Vault 的 `owner_ref` 等身份预留不赋予当前部署多租户安全承诺。

默认收紧到 loopback；本轮 IP 访问是显式配置的公开入口，不代表内部角色也应对外绑定。对外提供服务前由运维明确监听范围、网络隔离、TLS 和访问控制，系统状态与日志应如实展示暴露风险。实例持有订阅凭据，不能把“只有内网 IP”当作鉴权。

`HTTP_BIND_GATED_BY` 是“由什么收住外侧访问”的人类可读声明，不是平台已验证网络安全的开关；不能靠检测容器、网卡或某个环境变量自动关闭告警。声明需反映真实宿主入口和访问边界，并保留可审计记录。HTTPS／访问控制设施按部署入口配置，不能绕过实例 Guard 或让浏览器连接到另一个版本的共享页面。

### 3.1 访问口令 Guard（MVP）：用户体系预留位的第一个实现

产品规格见 [P21-8 §3](../product/pages/21-8-部署与初始化.md)。这是“这台实例让不让进”的控制，不是帐号、租户或角色系统。持久设置与会话密钥由 StateCoordinator 管理，不能让 ControlAPI 因鉴权获得业务数据库或 Vault 挂载。

| 项 | 规格与纪律 |
| --- | --- |
| 启用与生成 | 首次启用生成 16 位随机 base58 口令，避开易混字符；明文只回显一次，之后不再由接口返回 |
| 存储 | 只存 `crypto.scrypt` hash。`ACCESS_PASSCODE` 非空时优先，平台修改接口返回 409；部署配置与数据库不能出现“写库成功但并未生效”的假成功 |
| 失败锁定 | 同一客户端连续 5 次错误锁 5 分钟，锁定期返回 429 和 `retryAfterSec`；进程内计数的重启边界如实保留 |
| 审计 | 记录解锁、失败、锁定、锁定期尝试及口令变更。口令、hash、前后缀、长度、Cookie 和签名密钥均不得进入日志或审计详情 |
| 会话 | 签名 Cookie 有效期 7 天，`HttpOnly` + `SameSite=Lax`，HTTPS 下使用 `Secure`。签名密钥与口令解耦并持久保存；重生成口令不应使已通过会话立即掉线，升级不重新生成会话密钥 |
| 覆盖面 | REST／MCP HTTP／WS 一起保护，WS 在握手阶段校验；STDIO MCP 的本地进程边界单独约定 |
| 豁免 | 公开健康／页面身份探针与静态资源按入口门禁提供；业务接口和 `/openapi.json` 不因是文档就豁免。程序化接口的 Bearer 口令与浏览器 Cookie 使用同一实例访问边界 |

安全边界必须在 UI 明示：“访问口令提供基础隐私保护，不是加密安全边界；生产部署请配置 HTTPS + 网络隔离。”首次导入和后续升级保留原口令及已持久化的 Cookie 签名材料；不能以“新容器”为由清空访问设置。

## 4. 多节点调度预留

当前平台实例运行在单个 Linux VM 中。Foundation 与五角色分离是进程、权限和生命周期边界，不等于已经实现多节点调度。

| 现在 | 扩展预留 |
| --- | --- |
| 单实例资源视图与配额 | NodeRegistry 上报 worker 地址和资源快照 |
| 节点内调度 | NodeSelector 选节点，再执行节点内调度 |
| Coordinator 按 Owner 归属路由 | RemoteSandboxProvider 经受控 RPC 使用同一 provider contract |
| 网关经 Owner 附着终端和流 | 跨节点流代理继续保留归属、背压和重连语义 |

扩展时仍保持 Coordinator 的业务写者权、每个 Owner 的独占 home 和 Guest 归属；不能为节点迁移擅自重建任务。跨节点鉴权、资源回收、fencing、持久状态与故障验收需单独设计，不能把挂载共享目录视为已完成集群化。

## 5. 安全基线（单机阶段）

| 项 | 措施 |
| --- | --- |
| 运维权限 | Docker socket 仅在可信 Foundation 运维边界；受控工具固定实例、对象身份和路径，不向业务角色透传 socket |
| Guest 权限 | 仅 RuntimeOwner 获取 KVM／privileged；独占 home，不挂业务库，不在宿主直接运行用户任务 |
| 数据权 | Coordinator 唯一业务库写者；ControlAPI、Web、Installer 不获得数据库、SDK home 或整棵凭据目录 |
| 凭据 | Vault 加密、掩码回显与吊销；私有目录 `0700`、文件 `0600`；helper 临时 HOME 即用即删 |
| 供应链 | 不可变包、签名作用域、产物摘要和完整树校验；发布私钥不进仓库、安装包、远端或 Release |
| 入口 | 只公开已授权 IP 入口或受控 HTTPS 入口；内部端口保持 Linux loopback，访问口令与网络隔离同时生效 |
| 日志 | 写入时脱敏；运行日志、审计和升级 journal 分责，保留真实失败与 unknown 证据 |

## 6. 风险与备选

| 风险 | 缓解与边界 |
| --- | --- |
| Foundation 持有 Docker socket | 将其视为可信运维边界，固定对象归属与最小角色挂载；业务角色不得继承该权限 |
| Owner 的 KVM／privileged 权限 | 仅 Owner 持有，限制挂载为本 Owner home 与必要工作区；不把容器隔离描述成独立于宿主的安全边界 |
| SQLite 并发与单写者瓶颈 | 监控后按 §2 评估迁移，不通过多进程共同写库缓解 |
| VM／宿主重启与角色恢复 | 分层诊断并核验持久绑定；尚未验收的自动冷恢复不能宣称通过，不能靠重复首次安装恢复 |
| 不兼容数据库变更 | 独立迁移计划、兼容窗口、fencing、熔断与数据语义验收；不以旧整卷覆盖新写入回退 |
| 发布或签验成功被当成升级通过 | 区分包资格、首次导入、用户发起升级和真实 Guest／终端连续性；以对应测试报告为准 |
