## 1. 单机部署形态

在仓库根目录执行 `docker compose up --build`：根 `docker-compose.yml` 定义 web 服务，并 include `api/docker-compose.yml`。这两份文件是权威；下面的骨架只用来理解拓扑，`docs:check` 的 C1 核对它与真 compose 的服务集合和 `${VAR:-默认值}` 一致。

```
docker-compose:
  api:                    # NestJS 主服务（单进程；boxlite 是库内嵌，micro-VM 直接由本进程拉起）
    ports:
      - "127.0.0.1:3000:3000"   # ★ 默认只监听回环（审计 P0-3）——改 0.0.0.0 需显式配置且会被告警
    environment:
      DATA_ROOT: ${DATA_ROOT:-/srv/agent-platform/data}   # ★ 与下方挂载【同名】，见 §1.2
      DOCKER_HOST: tcp://docker-proxy:2375                # ★ 没有它 socket-proxy 白挂，见下
      SANDBOX_DEFAULT_IMAGE: ${SANDBOX_DEFAULT_IMAGE:-}   # ★★ 出厂【必须留空】,见下方 ⚠️⚠️
      SANDBOX_DOCKER_NETWORK: platform-sandbox-net        # ★ 没有它一个 Task 都建不出来，见 §1.4
    volumes:
      # ★ 同名挂载：宿主的 $DATA_ROOT 落到容器内**同一个绝对路径**（§1.2 硬约束）
      - ${DATA_ROOT:-/srv/agent-platform/data}:${DATA_ROOT:-/srv/agent-platform/data}
    networks: [default, sandbox]   # ★ 写了 networks 就不再自动接 default，少一个连不上 proxy
    depends_on: [docker-proxy]
  docker-proxy:           # tecnativa/docker-socket-proxy —— 仅 aio 路径需要
    volumes:
      - /var/run/docker.sock:/var/run/docker.sock:ro
    environment:          # 只放行 containers/exec/images 等必需 API 面
      CONTAINERS: 1
      EXEC: 1
      IMAGES: 1
      POST: 1
  web:                    # Next.js 前端（standalone 产物）——★ 用户访问的是它，不是 api

networks:
  sandbox:
    name: platform-sandbox-net   # ★ 显式 name 关掉 compose 的项目名前缀（§1.4）
```

骨架里 api 的 `ports` 来自 `api/docker-compose.yml`，只在单独起 api 时生效。从根目录起整套时，根 compose 清空 api 的端口，只把 web 发布在 `127.0.0.1:3000`；浏览器的 HTTP 与 WebSocket 都经 web 同源转发给容器内的 api。

| 部署纪律 | 说明 |
|---|---|
| **auth helper 不是 compose 服务** | 它由平台经 provider 创建（§1.1）；写进 compose 只会得到一个平台连不进去的容器。镜像在 api 启动后后台拉取，不占首次 `up` 的时间 |
| **`SANDBOX_DEFAULT_IMAGE` 出厂必须留空** | 留空时 `builtinImageRefFor(provider)` 按宿主档位在平台发布的两张镜像里自动选（`ghcr.io/xeonice/agent-platform-sandbox` / `-boxlite`）。填任何值都会让自动选择失效，另一档宿主撞 `IMAGE_PROVIDER_MISMATCH`；`pnpm check:default-image` 与 C1 守着这条 |
| **容器里的 api 必须配 `SANDBOX_DOCKER_NETWORK`** | 否则 agent 地址解析不开，每个 Task 死在 `did not become ready`（§1.4） |
| **web 的 `API_ORIGIN` 是构建参数** | Next 在构建时把 rewrite 目标写进产物，运行期传入无效；根 compose 固定为 compose 内部名 `http://api:3000`，两个 `NEXT_PUBLIC_*_BASE_URL` 留空走同源 |

本项目的 Mac mini 生产不用这套 compose：生产 API 镜像由 `deploy/containers/Dockerfile.api` 构建，并显式设置了 `SANDBOX_DEFAULT_IMAGE`，详见 [运维入口](../ops/README.md)。

- **aio 路径**：DooD 模式（挂宿主 docker.sock）供容器运行时调用；**必须经 socket proxy 限权**而非直接暴露完整 socket（容器逃逸面收敛）。
- **boxlite 路径**：Rust 库进程内嵌，无 daemon、无 socket 暴露面——天然少一整个攻击面；Linux 需 `/dev/kvm`，macOS 用系统虚拟化框架，与本地开发环境同构（04 §2.1）。
- **前端**：可与后端同 compose 部署（Next rewrites 同源转发），也可独立部署。独立部署时（如本项目生产的 Vercel）浏览器直连 API，后端按 `API_ALLOWED_ORIGINS` 精确放行带凭证的跨域请求。

启动日志里有几条属于预期：

| 现象 | 说明 |
|---|---|
| `HTTP is bound to 0.0.0.0 …` | compose 里 api 必须设 `HOST=0.0.0.0`，外侧暴露由 `ports:` 的 `127.0.0.1:` 前缀或"不发布端口"收住。填了 `HTTP_BIND_GATED_BY` 这句声明时降为 INFO（§3），仓里的两份 compose 都已填写 |
| `no usable '<rt>' credential (NO_CREDENTIAL); the agent will start UNAUTHENTICATED` | 全新 `DATA_ROOT` 没有凭证；沙箱、终端、任务发起都能看，agent 真跑要先做一次 runtime 授权（05） |
| 重启后 `reaped ORPHAN ... has no DB record` | 本实例此前建的容器在库里已无记录，启动对账回收（13 §4）；boxlite 是 micro-VM，`docker ps` 看不到 |
| 换过 `DATA_ROOT` / `DATABASE_URL` 后旧容器不被回收 | 实例身份取自"哪个库在裁决孤儿"，换库即换身份，且目前不上报。手动清理：`docker ps -a --filter label=platform.managed=true` |

### 1.1 auth helper 的运行形态（05 §2 决策 A 的部署落地）

帐号授权的 CLI 登录流跑在平台管理的 **auth helper 执行环境**里，与任务 sandbox 彻底解耦。形态由环境变量 `AUTH_HELPER_MODE` 选择（`container` | `host`，默认 `container`）：

| 形态 | 落地 | 取舍 |
|---|---|---|
| **常驻 helper 实例（默认）** | 平台**经 provider 自己创建**一个常驻实例，镜像恒等于当前 provider 的平台预制镜像（`builtinImageRefFor(provider)`，与用户任务同一张，04 §7）；不挂卷、不覆盖 entrypoint，配额 1 核 / 512 MB / 2 GB；后端经 `SandboxProvider.spawn({tty:true})` 在其中起登录命令 | 登录用的 CLI 与任务里是同一版本，不会出现"helper 能登、sandbox 用不了"；后端镜像不必打包两个 CLI；复用既有 provider 抽象。代价是常驻一个实例 |
| 宿主机 CLI（`AUTH_HELPER_MODE=host`） | 后端进程所在环境自带两个 CLI，用 **node-pty 起一个真伪终端**跑登录命令 | 适用于不方便再起一个实例的部署（如后端跑在裸机 systemd 下）；CLI 版本可能与镜像内漂移，需要独立的版本探测 |

形态约束（实测经过见 LIVE-RUN-FINDINGS 附录 D）：

- **helper 只能由平台经 provider 创建**：平台在实例里执行命令走镜像内的 HTTP agent，它的 token 在 provider `create()` 时生成并注入；compose 建的容器没经过这一步。
- **不覆盖 entrypoint**：AIO 镜像的 entrypoint 正是启动 agent 的进程，覆盖它会得到"running 但永远连不上"的实例。helper 与任务沙箱同样启动，区别只在不挂卷、配额更小。
- **宿主机形态必须用真伪终端**：登录 CLI 会检测 TTY，走管道时 `claude setup-token` 不输出任何内容。依赖选 `@lydell/node-pty`：`node-pty` 的 darwin 预编译 `spawn-helper` 以 644 发布（上游 #850），且没有 Linux 预编译产物。
- **隔离 HOME 必须是绝对路径**：它会作为 `HOME` / `CODEX_HOME` / `CLAUDE_CONFIG_DIR` 交给子进程，相对路径随 cwd 漂移。
- **只能原样安装官方 CLI**：承载 Claude Code 并让用户用自己的订阅登录有专门条款（二进制不许改、不许禁用内置的鉴权方式），原文与逐条影响见 [05 §2 决策 A 的合规边界](../backend/05-Runtime鉴权流转.md#2-核心设计决策)。

运行纪律：

- **helper 不挂任何工作区卷、不接受用户代码**——它只跑登录命令，是凭证链路的一部分而不是执行环境；登录产出的 `auth.json` / `.credentials.json` 被 Vault 收编后**即时清除**（05 §4）。
- **每次 begin/refresh 操作用 `mkdtemp` 生成唯一 HOME/`CLAUDE_CONFIG_DIR`/`CODEX_HOME`（照搬 S3 `git-auth.materializer` 的 `mkdtemp` + `try/finally` `rm -rf` 范式，05 §5.1 / §4）**：`finally` 必删、**绝不复用容器默认 HOME**；刷新 scanner 与交互登录用**彼此隔离**的临时根，避免并发操作互串凭证目录（05 §1★ 的 `CLAUDE_CONFIG_DIR` 重定向风险，05 §4.1 黑名单已拦）。**诊断项**：系统状态页/`/diagnose` 检查并报出 **helper 内残留的临时 HOME 目录**（`finally` 漏删的泄漏信号，与 CLI 版本探测同处上报）。
- **容器形态的一次性 HOME 建在容器内 `${HOME:-/tmp}` 下，不是 `/tmp`**：codex 遇到 `/tmp` 会打 `Refusing to create helper binaries under temporary dir "/tmp"`，只警告、照样往下跑，然后在更深的地方坏掉。
- **容器形态靠 `spawn({tty:true})` 的 `env` / `cwd` 兑现这份隔离**：aio 的 ws 通道上行帧放不下这两个字段，由 provider 编进启动命令（做法与代价见 [04 §2.3★](../backend/04-Contract与Registry扩展体系.md)）。丢掉它们的症状是"登录走完了、平台读不到凭证"，用户看到的却是"对方拒绝了这次登录"。
- 启动时**版本探测**并纳入诊断项（P21-5 / P22 §3）：helper 里 CLI 缺失或版本不受支持要在系统状态页显性报出，而不是等用户点登录才失败（05 §6 已列为风险）。
- helper 崩溃/缺失时，下一次登录或凭证刷新会先重建一次（见下方生命周期）；重建仍失败，鉴权端点才返回 `PROVIDER_UNAVAILABLE` + [运行诊断] 引导——**不降级到"在任务 sandbox 里登录"**，那会把决策 A 又退回去。
- 离线环境（P21-8 §1 air-gapped）下 helper 依然启动，但登录必然失败——这是物理约束，诊断项如实报出即可。

#### helper 的生命周期与自愈

- **身份固定**：sandboxId 是 contracts 里的常量 `AUTH_HELPER_SANDBOX_ID = 'auth-helper'`，BoxLite 名为 `<prefix>auth-helper`，同一实例恰好一个。`<prefix>` 为 `platform-boxlite-` 加数据库文件路径（`DATABASE_URL`，缺省 `$DATA_ROOT/platform.db`）的 sha256 前 16 位再加 `-`，哈希的是路径字符串而不是文件内容。**禁止写进 `sandboxes` 或 `resource_allocations`**：发版探针（[api-container.mjs](../../deploy/containers/api-container.mjs) 的 `STOPPED_RESERVATIONS_PROBE`）只豁免这一个规范名、`running`、进程树为 bwrap→bwrap→libkrun VM 且不被任何 `provider_handle` 引用的 helper，`/api/deployment/status` 又把这两张表都算进 blockers。它占的 1 核 / 512 MiB 以常量预留从调度池扣除（03 §1）。
- **创建**：`createOnce` 先按规范名幂等清残留（boxlite 实现 `destroyBySandboxId`），再 create + start；start 失败就销毁刚建的半成品，免得同名重试撞上 BoxLite 的唯一名字。
- **复用前复核**：`require()` 复用就绪句柄前问一次 `provider.inspect`。答出 `instance_running` 为存活；答出其他状态（boxlite 把 failed、configured、stopping 都映射成 `instance_missing`）或抛 `NOT_FOUND` 为失效；其余异常或超时按存活处理。判定失效才按 CAS 作废句柄，每次 `require` 最多重建一次。判定只看 inspect 答出的状态（boxlite 读 `getInfo`）；boxlite 的 inspect 对 running 的 box 会顺带读 metrics，但不会启动已停止的 VM。禁止用 exec 或单独调 metrics 探活：metrics 会隐式启动已停止的 VM。
- **执行失败兜底**：BoxLite 0.9.7 不开 health check 时没有退出监视，VM 被杀后仍记 running，inspect 看不出来，所以 `ContainerAuthHelper` 第一次 exec 遇 provider 错误会作废句柄并重试一次；`dispose` 不再抛错。注意：同一原因，诊断在下一次使用前可能仍报可用；发版探针按真实进程树判定，不受影响。
- **诊断只读**：auth-helper 诊断项读 `observe()`，不建 box、不 exec；有句柄但实例不在运行时报 warn。
- **对账**：对账器认出 auth-helper，不再记 ORPHAN；只清 `stopped` / `failed` 的旧 helper，`running` / `configured` 一律不动。关掉开机对账或调换模块顺序都不再影响 helper。
- **刷新计数**：helper 不可用（`HelperUnavailableError`）导致的刷新失败不计入 `refresh_failures`，只记 warn；凭证是否过期仍以 `expires_at` 为准。
- **不做**：没有后台定时自愈，没人登录、也没有待刷新凭证时，死掉的 helper 留到下一次使用才重建（有 stopped 名额时它会让发布停在 `waiting-idle`，处置见 [发版手册](../ops/发版手册.md)，只读诊断见 [运维手册](../ops/运维手册.md)）；`AUTH_HELPER_MODE=host` 时照旧预热容器 helper。

### 1.2 `DATA_ROOT`：工作区的宿主目录（审计 P0-1 方案 A）

工作区不用 named volume，而是宿主目录 bind mount（理由见 03 §7.1）：

```
${DATA_ROOT}/
├── baselines/<projectId>/      # 项目基线，clone 落点
├── workspaces/<sandboxId>/     # Task 独立副本，bind mount 到实例 /workspace
├── logs/runtime.log            # 平台运行日志（当前份）+ .1….4 已轮转，共 5 份（§1.2.1）
├── logs/agent-tasks/           # 无头任务原始日志（03 §8.6）——与上面平级，两回事
├── .master.key                 # Vault 主密钥（0600，05 §4.2）
└── platform.db                 # SQLite
```

**必须遵守的三条部署纪律**：

| 纪律 | 说明 |
|---|---|
| **宿主路径 = 容器路径** | DooD 下 api 请求挂载 `${DATA_ROOT}/workspaces/<id>` 时，路径由**宿主的**容器运行时解析。compose 必须把宿主的 `$DATA_ROOT` 挂到容器内同名绝对路径（`${DATA_ROOT}:${DATA_ROOT}`），装错会在第一个 Task 创建时挂载失败 |
| **推荐 btrfs / xfs（Linux）** | `cp --reflink=auto` 的写时复制只在这两种文件系统生效，ext4 上静默退化为全量拷贝；启动诊断报出 `DATA_ROOT` 的文件系统类型与 reflink 支持（P22 §3） |
| **权限对齐** | `${DATA_ROOT}/workspaces` 为 `0700`、工作区目录为 `0777`（不是 `chown`，理由见 03 §7.6）；`.master.key`、`platform.db` 及其 `-wal`、`-shm` 为 `0600` |

- reflink 只在 `platform === 'linux'` 时使用。macOS 开发机上直接整份复制，诊断第 ⑦ 项报"不适用"，也不提示换文件系统（P21-5 §9D）。
- `0777` 的工作区靠 `0700` 的父目录不可 traverse 收住：其他本地用户读不到也写不进（防投喂 `AGENTS.md`）；同一平台用户身份的进程仍可达，这是部署形态问题。
- 数据库文件由 `drizzle.connection.ts` 的 `hardenDatabaseFiles` 收紧：建库后先 chmod 主库再开 WAL，因为 SQLite 建边车时照抄主库的权限位；存量部署里 `0644` 的库在下一次打开时补上。

磁盘是本平台的真实瓶颈，已进调度（03 §1）；`DATA_ROOT` 所在分区的余量应纳入运维监控（P21-5 水位）。

#### 1.2.1 `${DATA_ROOT}/logs/`：运行日志必须落盘（v1.1）

平台把运行日志写到 `${DATA_ROOT}/logs/runtime.log`，P21-5 的 `[导出日志]` 按钮读的就是它。不能只靠 `docker logs`：平台不一定跑在容器里（boxlite 档 api 可以裸跑）；即便在容器里，读自己的日志也要挂 docker socket 并知道自己的容器 id。

| 项 | 值 | 理由 |
|---|---|---|
| 路径 | `${DATA_ROOT}/logs/runtime.log` + `.1`…`.4` | 与 DB、工作区同一个数据根，备份/迁移一次带走 |
| 轮转 | 按大小，**20MB × 共 5 份**（当前 1 + 已轮转 4，磁盘上限 100MB） | 与 P21-5 导出上限 50MB 同量级 |
| 脱敏 | **写入时**，与 05 §4 同源 | 读出口脱敏挡不住 DB 文件与备份包两条路 |
| 权限 | 文件 `0600`，`logs/` 目录 `0700` | 同 `.master.key` / `platform.db` |

- **落盘不替代 stdout**：容器化部署仍往 stdout 打（`docker compose logs` 是运维的第一反应），落盘是为了平台自己能导出，两者并存。
- **运行日志 ≠ 审计流**（P21-5 §10.1）：审计流是结构化、给产品用户看的；运行日志是文本、给运维看的。别把运行日志灌进审计面板，也别指望审计流里有栈。
- **轮转顺序**：`end()` 旧流 →（在其回调里）rename 链式移位 → 重开流；`end()` 窗口内到来的日志先缓冲再重放，收到 SIGTERM 时也要放干缓冲。直接 rename 会让旧流跟着 inode 写进改名后的文件，`runtime.log` 这个路径静默消失（预研经过见 LIVE-RUN-FINDINGS 附录 D）。
- **导出打包不要 shell out 到 `tar`**：macOS 是 BSD tar，Linux 镜像是 GNU tar，同一段参数两边行为不同。用可流式的 npm `tar` 包，或 Node 内置 `zlib` + 自拼 tar header。
- **已知债：脱敏器够不着**。05 §4 要求运行日志与审计流同源脱敏，但那套 per-CLI redactor 在 `packages/modules/runtime/src/domain/services/secret-redactor.ts`，没有从包入口导出，`apps/api` 只能复述规则（`log-redactor.ts`）。05 §4.3.2 ③ 对占位常量的论证同样适用于 redactor 本身，正解是把它提到 shared-kernel。

### 1.3 本地起一套来看效果

### 1.4 api 跑在容器里 ≠ 能用：loopback 发布与 DooD 是互斥的

**问题**：默认档把 agent 端口只发布到宿主 loopback，`agentOrigin` 按 `http://127.0.0.1:<端口>` 拼地址。DooD 下 api 自己在容器里，它的 `127.0.0.1` 是容器自己，永远连不上，建 Task 必定 `did not become ready`。这与 §1.2「宿主路径 = 容器路径」是同一类问题：DooD 下 api 说出口的每个坐标都由宿主解析。

**方案**：把 api 与沙箱放进同一个用户自定义网络，用容器名做 `agentOrigin`，agent 端口一个都不发布，暴露面比 loopback 档更小。`network_mode: host` 会丢掉 api 的网络隔离，发布到网桥会扩大暴露面，都不选。形态由显式配置 `SANDBOX_DOCKER_NETWORK` 决定，默认空：

| 值 | 形态 | agent 端口 | `agentOrigin` |
|---|---|---|---|
| 空（默认） | api **裸跑在宿主** | 发布到宿主 loopback | `http://127.0.0.1:<发布端口>` |
| 网络名 | api **在容器里**，与沙箱同在这个用户自定义网络 | **完全不发布** | `http://platform-aio-<sandboxId>:8080` |

- **不探测**（不看 `/.dockerenv`、cgroup，不 ping 网关）：要回答的是"我说出口的地址，对面照着它解析得开吗"，取决于部署者怎么接的网。反例：`network_mode: host` 的容器里 `/.dockerenv` 也在，而 loopback 坐标恰恰是对的。
- **它是一句声明，不是一个开关**：填了网络名 = "沙箱放进这个网络，而我自己也在这个网络里"。前半句由 `agentOrigin` 的 `not attached` 守卫检查，后半句由下面的开机自检检查。
- **compose 的网络必须写 `name:`**：compose 默认给网络加项目名前缀（`<项目>_sandbox`），而 `SANDBOX_DOCKER_NETWORK` 写的是 docker 侧的真名，对不上时都起得来、连不上。
- **必须是用户自定义网络**：默认 `bridge` 没有内嵌 DNS。容器名 `platform-aio-<UUID>` 共 49 字符，在 DNS label 的 63 字符以内；`create` 门口有一道 DNS label 检查，换 id 生成器或 provider 名时报出原因，而不是一次 `did not become ready` 超时。

#### 开机自检：证明"我自己也在这个网络里"

填了 `SANDBOX_DOCKER_NETWORK` 时，平台在启动期取两侧事实的交集：daemon 侧 `GET /containers/json?filters={"network":[…]}` 给出这个网络上的容器与地址，进程侧 `os.networkInterfaces()` 给出本进程持有的地址。同一网络内地址唯一，交集非空就说明"我就是那个容器"。

走容器列表而不是 `/networks/<id>`：生产形态的 `docker-socket-proxy` 只放行 `CONTAINERS/EXEC/IMAGES`，为一次自检开 `NETWORKS`（在 `POST=1` 之下会连带放开建删网络）是拿隔离换便利。返回结果再按网络名自筛一遍，不完全依赖 daemon 侧的过滤。

| 结论 | 处置 |
|---|---|
| 交集非空 | 一条说清证据的 log（我持有哪个地址、它属于哪个容器），照常启动 |
| 交集为空（**名单为空也算**） | **开机失败**，错误里带两侧证据和两条出路：裸跑就删掉这一行；在容器里就把 api 也接上这个网络 |
| 问不到 docker，或本进程没有非回环地址 | 照常启动，但打 **error 级别**的"我没能验证这一条" |

"名单为空"是确凿的否定：本进程若真接在这个网络上，它必然出现在名单里。这正好覆盖"compose 给网络加了项目名前缀"那个经典配错。落点：`sandbox/…/docker/self-network-check.ts`（纯判定与消息）与同目录的 `self-network-check.service.ts`（开机钩子，没配就直接返回，裸跑档一次 docker 都不问）；`SANDBOX_DOCKER_NETWORK` 的唯一读取点是 `shared-kernel/…/domain/sandbox-network.ts`，形态判定与 DNS label 检查在 `sandbox/…/docker/agent-addressing.ts`。

#### 明文 registry 只认 loopback 字面量

`oci-registry.client.ts` 只对 `localhost` / `127.0.0.1` / `[::1]` 走 http，而这三个字面量在容器里指容器自己。⇒ `IMAGE_REGISTRY_INSECURE_HOSTS`（逗号分隔的 `host:port`，与 docker daemon 的 `insecure-registries` 同形状），留空 = 行为不变。不做"先试 https 再退回 http"的自动降级，那等于给任何一次 TLS 故障配一条静默的降级路径。

配它时宿主 daemon 与 api 容器必须用同一个 `host:port` 解析到同一个 registry，具体配方见 `api/images/README.md`。aio 档起容器时不 pull，只查本机镜像库。

#### 播种失败时的"下一步"按形态分岔

| 形态 | 下一步说什么 |
|---|---|
| 裸跑档（没配） | 指向预制镜像，并核对那台 registry 起了吗、镜像 push 上去了吗（注册与播种查的是 registry 的 HTTP API，本机 build 过不算） |
| 容器网络档（配了） | **先别改 `SANDBOX_DEFAULT_IMAGE`**，问的是这个坐标在容器里解析得开吗：loopback 字面量指的是容器自己 / `extra_hosts` / `IMAGE_REGISTRY_INSECURE_HOSTS` / registry 别只发布在宿主 `127.0.0.1` 上 |

落点 `image/…/application/image-seeder.ts` 的 `seedFailureNextStep(ref, network)`，抽成纯函数，两条分支都能在本机测到。

#### 今天可用的形态

| 形态 | 能建 Task 吗 | 说明 |
|---|---|---|
| api 裸跑在宿主（`pnpm start`） | 能 | 默认档 |
| api 在容器里 + `SANDBOX_DOCKER_NETWORK` | 能 | 根目录 compose 的形态 |
| api 在容器里、**不配** `SANDBOX_DOCKER_NETWORK` | 不能 | 每个 Task 死在 `did not become ready`；`.env.example` 与 compose 里都写了这一条 |
| api **裸跑在宿主**、却**配了** `SANDBOX_DOCKER_NETWORK` | **开机就失败** | 开机自检拦下，错误里直接说"删掉这一行" |

## 2. 持久化：SQLite 起步，Postgres 预留

- 起步：`better-sqlite3` 单文件库 + Drizzle ORM（schema-first，drizzle-kit 生成迁移）。
- 隔离：domain 只声明 `Repository` 接口，infrastructure 提供 Sqlite 实现；`PersistenceModule.forRoot({ driver: 'sqlite' | 'postgres' })` 切换。
- 约束：避免 SQLite 专有语法（Drizzle 双方言天然约束）。
- **迁移阈值（经验值）**：并发运行 sandbox > 50 或 QPS > 100 时迁 Postgres——better-sqlite3 是同步 API，高并发下阻塞事件循环。

## 3. 无帐号体系下的鉴权预留

- 全局 `APP_GUARD` 注册 `NoopAuthGuard`（放行）。
- **REST / MCP / WS 三个协议面统一走同一 Guard 抽象**——后续接入用户体系只替换 Guard 实现，不动业务代码。
- `CredentialVault` 记录预留 `owner_ref` 字段（当前恒空，见文档 13 credentials 表），加用户体系时仅数据迁移。
- **默认只监听 `127.0.0.1`（审计 P0-3 ①）**：compose 的 `ports` 默认绑回环；要对外提供服务必须显式改成 `0.0.0.0` 或经反向代理。改了之后：**启动日志打醒目警告**、**系统状态页常驻一条横幅**（"当前实例可被局域网/公网访问"）。理由：这台实例持有用户的 ChatGPT/Claude 订阅凭证（05 §6 已将该风险上调为高），默认对外暴露是不可接受的出厂设置。

  ⚠️ **这里说的「反向代理」与前后端之间那层不是一回事，别混。** 本条讲的是**对外暴露**：
  把实例挂到局域网/公网时，前面通常要有一台 nginx/Caddy 负责 TLS、访问控制、审计。
  前后端之间那层（本地与 compose 形态）**已经由 `next.config.mjs` 的 rewrites 承担了**，
  不需要、也不应该再单起一个进程。两者可以同时存在（外层 nginx → Next → rewrites → 后端），
  但解决的是两个问题。

  ⚠️ **那条告警在 compose 下曾经恒响**（2026-08-30 复验）：compose **必须**设 `HOST=0.0.0.0`
  ——容器内绑 loopback，外面那行 `ports:` 就转不进来——而真正的暴露面由 `ports:` 的
  `127.0.0.1:` 前缀收住。于是每一次 `docker compose up` 都打这条 WARN，而每一次都不代表
  出错。**一条恒真的告警不是多一句话，它训练用户忽略告警**，而这条告警存在的全部理由，
  是有朝一日真的有人把一个持有用户凭证的实例挂到公网上时它能被看见。

  ⛔ **不能靠探测免掉它**：进程内看不见「外侧那行 `ports:` 发布在哪」。看 `/.dockerenv`、
  看 `SANDBOX_DOCKER_NETWORK`，都只能回答「我是不是在容器里」——而在容器里**照样可以**
  被发布到 `0.0.0.0`。靠它关掉告警，就是拿一句猜测去关一个安全提示（与 §1.4 同一条纪律）。

  ⇒ **`HTTP_BIND_GATED_BY`：一句声明，不是一个开关。** 填的是「外侧由什么收住」的人类
  可读答案（compose 里就是那行 `ports:`）。填了 ⇒ WARN 降为 INFO，并把这句声明**原样**
  打进日志：日志里留下的是运维方自己写的那句话，平台没有替他做任何假设，事后审计看得见
  签的是什么字。留空 ⇒ 行为一字不变。⚠️ INFO 那句里**明写**「平台验证不了这句声明」——
  这是它与「加个开关把告警关掉」的唯一区别：平台能保证的是有人为此签过字，不是它为真。
  判定在 `api/apps/api/src/platform/config/env.ts` 的 `describeBindExposure()`（纯函数）。
- **访问口令 Guard 从 v1.1 提前到 MVP（审计 P0-3 ②）**：规格见 §3.1，MVP 即启用；不再依赖"用户自己加反向代理"这个假设。

### 3.1 访问口令 Guard（**MVP**，审计 P0-3 从 v1.1 提前）：`NoopAuthGuard` 预留位的第一个真实实现

产品规格见 [P21-8 §3](../product/pages/21-8-部署与初始化.md)（开关落点在系统状态页 21-5）。它替换的正是本节的 `NoopAuthGuard`，**不引入用户体系**——没有帐号、没有角色，只有「这台实例让不让进」。

> **版本变更（审计 P0-3）**：本节原标 v1.1，现**提前到 MVP**。与 ① 默认回环监听是一对：回环挡住"被别人扫到"，口令挡住"同一台机器/同一内网的其他人随手打开"。两条都做的成本很低（规格本就完整），而只做一条都留着一个明显的口子。**产品文档 P19 §3 与 P21-8 §3 需同步把版本从 v1.1 挪到 MVP**（属产品侧，另行同步）。

| 项 | 规格 | 落点 |
|---|---|---|
| 启用时机 | **MVP 即可用**；首次启动若未启用，系统状态页常驻提示（配合 ① 的监听地址告警） | Guard |
| 口令生成 | 首次启用**自动生成 16 位随机串**（`crypto.randomBytes` → base58 字符集，避免 `0/O/l/1` 混淆）+ [复制] / [重新生成] | 应用层 |
| 存储 | **只存 hash**，`system_settings.access_passcode_hash`；非空即视为启用；**明文只在生成后回显一次**，之后任何接口都不回显。⚠️ **落地用的是 `crypto.scrypt` 而不是本行原写的 Argon2id/bcrypt**：那两个都是**原生插件**，而本仓今天一个原生依赖都没有；scrypt 同属 memory-hard 一类且内置于 Node（参数随 hash 串自描述，见 `passcode-hash.ts`）。这条偏离写在这里、不留给谁去 lockfile 里发现。⚠️ **口令有两个来源，`ACCESS_PASSCODE` env 永远优先**，且它非空时 `PUT /api/system/access-passcode` **整个 409** —— 平台改不动别人的部署配置，让库盖过 env 是悄悄推翻运维签下的一行，让写库「成功」而 env 继续生效则是告诉用户门开了而门还锁着 | 13 §2 |
| 校验失败锁定 | **连续 5 次错误锁 5 分钟**；计数按客户端 IP 存**进程内存**（单机单进程，重启即清空是可接受的宽松失败模式，13 §2 已说明）；锁定期内直接 429 + `retryAfterSec` | Guard |
| 审计 | **五件事全部进平台审计流**（13 §2.8.2 的 `category: 'system'`，本档的第一批生产者）：`system.access.unlocked` / `system.access.unlock_failed`（带连续第几次）/ `system.access.locked`（**`error` 级**，运维筛「仅告警」时必须扫得到）/ `system.access.locked_attempt`（锁定期内再试——这些尝试压根不进 limiter 的计数，不记就彻底没有，而它是「有人在爆破」最硬的信号）/ **`system.access.passcode_changed`**（口令被启用/重生成/关闭；`disable` 那次是 **`error` 级**——那是**平台从此对任何人敞开**的时刻，而 `access_passcode_updated_at` 恰好在同一条语句里被清成 NULL，不记这一行，「谁把门关了」事后没有任何痕迹）。⚠️ **前四条只记 `POST /api/access/unlock` 这一条路径**，Guard 那一侧刻意不记：它的失败分支在任何一个没带 cookie 的受保护请求上都会走到，记进去等于把访问日志灌进产品面板（P21-5 §10.1）。⛔ **口令本身与它的任何投影（明文/前缀/后缀/长度/hash）一律不进 `summary`/`detail`**——长度直接把爆破空间从 58^16 砍到 58^n；纪律建在构造函数签名上（`access-audit.ts` 根本不接受口令参数），写入口脱敏是兜底。⚠️ 单机私有化部署没有用户系统，「谁」没有可记的身份、IP 在 NAT 后面也几乎不携带信息 ⇒ 如实只答「**什么时候**（`at`，毫秒）试了**多少次**（`consecutiveFailures`，由 limiter 唯一交出）」 | 13 §2.8.2 |
| 会话 | 通过后签发**签名 cookie，有效期 7 天**（`HttpOnly` + `SameSite=Lax`；HTTPS 部署下加 `Secure`）；无服务端 session 表；**已通过的会话不受口令重新生成影响**（P21-8 §3「不影响已通过会话」——重新生成只影响新登录）。⚠️ **这一条要求签名密钥与口令解耦**：密钥此前退化到口令本身（`PASSCODE_COOKIE_SECRET ?? passcode`），在口令只能来自 env 的年代没有后果，有了 `regenerate` 之后就等于「换一次口令＝全员当场掉线」。现落 `system_settings.access_passcode_session_secret`（`drizzle/0016`，首次签发时惰性生成），**落库而非每进程现生成**——进程内随机数会把 cookie 承诺的 7 天悄悄砍成「到下次重启为止」 | Guard |
| 覆盖面 | **REST / MCP / WS 三面同时生效**——就是走同一 Guard 抽象的价值所在；WS 在握手阶段校验 cookie，失败直接拒绝升级 | 02 §6 / 06 §2 |
| 豁免 | 仅 `GET /api/health` 与静态资源；`/openapi.json` **不豁免**（它暴露完整接口面） | Guard |
| MCP 面的取舍 | MCP 走 STDIO 传输时天然在本机进程内，无 cookie 概念——STDIO 传输**豁免**口令，HTTP/SSE 传输**必须**带（`Authorization: Bearer <passcode>` 亦可，供程序化消费方免 cookie） | 02 §6 |

**安全边界明示（必须原样出现在 UI 上，P21-8 §3）**："访问口令提供基础隐私保护，不是加密安全边界；生产部署请配置 HTTPS + 网络隔离。"——它挡的是"局域网里被人随手打开"，不是有备而来的攻击者。
