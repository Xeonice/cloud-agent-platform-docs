### 1.1 auth helper 的运行形态（05 §2 决策 A 的部署落地）

帐号授权的 CLI 登录流跑在平台管理的 **auth helper 执行环境**里，与任务 sandbox 彻底解耦。两种形态，**默认取第一种**：

| 形态 | 落地 | 取舍 |
|---|---|---|
| **常驻轻量 helper 容器（默认）** | compose 增加一个 `auth-helper` 服务，**直接复用平台默认 AIO 镜像**（其中已自带 codex / claude code 两个 CLI，04 §7）；`command: sleep infinity` 常驻，后端经同一套 `SandboxProvider.spawn({tty:true})` 在其中起登录命令 | ✅ 与生产环境同构（CLI 版本 = 用户 Task 里跑的版本，不会出现"helper 能登、sandbox 用不了"）；✅ 后端镜像保持精简，不必打包两个 CLI；✅ 复用既有 provider 抽象，零新代码路径。代价：常驻一个容器（idle 时几乎不占资源） |
| 宿主机 CLI（备选） | 后端进程所在环境自带两个 CLI，直接 `child_process` 起登录命令 | 适用于**不方便再拉一个容器**的部署（如后端跑在裸机 systemd 下）；代价：CLI 版本与镜像内版本可能漂移，需要独立的版本探测 |

配置项 `auth.helper.mode = 'container' | 'host'`（默认 `container`）、`auth.helper.image`（默认 = 平台默认 AIO 镜像）。

运行纪律：

- **helper 容器不挂任何工作区卷、不接受用户代码**——它只跑登录命令，是凭证链路的一部分而不是执行环境；登录产出的 `auth.json` / `.credentials.json` 被 Vault 收编后**即时清除**（05 §4）。
- **每次 begin/refresh 操作用 `mkdtemp` 生成唯一 HOME/`CLAUDE_CONFIG_DIR`/`CODEX_HOME`（照搬 S3 `git-auth.materializer` 的 `mkdtemp` + `try/finally` `rm -rf` 范式，05 §5.1 / §4）**：`finally` 必删、**绝不复用容器默认 HOME**；刷新 scanner 与交互登录用**彼此隔离**的临时根，避免并发操作互串凭证目录（05 §1★ 的 `CLAUDE_CONFIG_DIR` 重定向风险，05 §4.1 黑名单已拦）。**诊断项**：系统状态页/`/diagnose` 检查并报出 **helper 内残留的临时 HOME 目录**（`finally` 漏删的泄漏信号，与 CLI 版本探测同处上报）。
- 启动时**版本探测**并纳入诊断项（P21-5 / P22 §3）：helper 里 CLI 缺失或版本不受支持要在系统状态页显性报出，而不是等用户点登录才失败（05 §6 已列为风险）。
- helper 容器崩溃/缺失时，鉴权端点返回 `PROVIDER_UNAVAILABLE` + [运行诊断] 引导——**不降级到"在任务 sandbox 里登录"**，那会把决策 A 又退回去。
- 离线环境（P21-8 §1 air-gapped）下 helper 依然启动，但登录必然失败——这是物理约束，诊断项如实报出即可。

### 1.2 `DATA_ROOT`：工作区的宿主目录（审计 P0-1 方案 A）

工作区不用 named volume，而是宿主目录 bind mount（理由见 03 §7.1）：

```
${DATA_ROOT}/
├── baselines/<projectId>/      # 项目基线，clone 落点
├── workspaces/<sandboxId>/     # Task 独立副本，bind mount 到实例 /workspace
├── logs/runtime.log            # 平台运行日志（当前份）+ .1….4 已轮转，共 5 份（§1.2.1）
├── logs/agent-tasks/           # 无头任务原始日志（03 §8.6）——与上面平级，两回事
│                               # ⚠️ 本行原写 `automation-runs/`，磁盘上实为 `agent-tasks/`（2026-08-27 实况核对）
├── .master.key                 # Vault 主密钥（0600，05 §4.2）
└── platform.db                 # SQLite
```

**必须遵守的三条部署纪律**：

| 纪律 | 说明 |
|---|---|
| **宿主路径 = 容器路径** | DooD 下 api 容器请求运行时挂载 `${DATA_ROOT}/workspaces/<id>` 时，这个路径由**宿主的容器运行时**解析，而不是 api 容器的命名空间。因此 compose 必须把宿主的 `$DATA_ROOT` 挂到容器内**同名绝对路径**（上例的 `${DATA_ROOT}:${DATA_ROOT}` 形态），否则挂载源找不到。这是 bind mount 方案唯一的硬约束，**装错了会在第一个 Task 创建时立刻暴露**（挂载失败），不会静默出错 |
| **推荐 btrfs / xfs** | `cp --reflink=auto` 的写时复制只在这两种文件系统上生效——它让"每 Task 独立副本"的磁盘成本从 N×仓库体积降到接近 1×。ext4 上会静默退化为全量拷贝：**启动诊断必须报出 `DATA_ROOT` 的文件系统类型与 reflink 支持情况**（P22 §3 检查项），否则用户会在 ext4 上疑惑磁盘为什么涨得这么快。⚠️ **这条建议的适用范围是 Linux 部署**：`FsWorkspacePreparer.importBaseline` 只在 `platform === 'linux'` 时走 `cp --reflink=auto`，其余平台（开发机上的 macOS）直接整份复制 ⇒ 诊断第 ⑦ 项在那里报 **ℹ️「不适用」而不是 ⚠️「不支持」**，也**不提示换文件系统**（P21-5 §9D）——在 macOS 上那是一件既做不到也不需要做的事 |
| **权限对齐** | 目录需对沙箱内运行用户（非 root 的 `gem`）可读写；**准备阶段实际做的是父目录 `${DATA_ROOT}/workspaces` `chmod 0700` + 工作区目录 `chmod 0777`，不是 `chown`**（⚠️ 原写 `chown`，已按实现更正；`chown` 在该阶段既缺权限也**拿不到 uid**——实例尚未创建，理由与实测见 03 §7.6）。0777 的子目录靠 0700 父目录**不可 traverse** 收住：其他本地用户读不到、也写不进（防投喂 `AGENTS.md`）；**同一平台用户身份的进程仍可达**，这是部署形态问题。`.master.key` 与 `platform.db` 必须 `0600`。⚠️ **这条纪律 2026-08-30 之前只是一句愿望**：全新 `DATA_ROOT` 实测，`pnpm db:migrate` 建出来的 `platform.db` / `-wal` / `-shm` 都是 **`0644`**（`logs/runtime.log` 倒是 0600，见 §1.2.1）——better-sqlite3 按 umask 建文件，没有 mode 参数可给，也没人给它 `chmod`。**处置是改实现，不是改文档**（`drizzle.connection.ts` 的 `hardenDatabaseFiles`）：这个库与 `.master.key` 放在同一个 `DATA_ROOT` 里，装着任务历史、prompt、仓库地址与**加密后的凭证密文**；把钥匙锁好、把锁着的箱子摊在桌上是一种自欺。⚠️ `-wal`/`-shm` 必须一起收紧（它们装的是**尚未 checkpoint 的同一批数据**），顺序是「建库 → 先 chmod 主库 → 再开 WAL」，因为 SQLite 建边车时照抄主库的权限位；存量部署里那批 0644 的老库在下一次打开时被补上。⚠️ **「必须」写在文档里而实现没做，是最容易被当成已完成的那一类** —— 所以现在有 `apps/api/test/integration/database-file-permissions.spec.ts` 守着（去掉 chmod 三条断言里两条立刻红） |

磁盘是本平台的真实瓶颈，已进调度（03 §1）；`DATA_ROOT` 所在分区的余量应纳入运维监控（P21-5 水位）。

#### 1.2.1 `${DATA_ROOT}/logs/`：运行日志必须落盘（v1.1）

~~⚠️ **现状是没有落盘**：后端只有 Nest `Logger` 打 stdout。~~ ✅ **已落盘（2026-08-30 从零复验）**：全新 `DATA_ROOT` 起完就有 `${DATA_ROOT}/logs/runtime.log`，权限实测 `0600`、`logs/` 目录 `0700`，与本节要求一致。本段保留是为了记住 P21-5 的 `[导出日志]` 按钮**要求平台自己能读到日志**——这个按钮在落盘之前是无物可导的。

**为什么不能靠 `docker logs` 兜住**：
- 平台**不一定跑在容器里**——boxlite 档位下微 VM 由 BoxLite SDK 直接管，api 进程可以裸跑；
- 即便在容器里，要读自己的日志得挂 docker socket **且知道自己的容器 id**，绕且脆（容器被重建就断）。

要求：

| 项 | 值 | 理由 |
|---|---|---|
| 路径 | `${DATA_ROOT}/logs/runtime.log` + `.1`…`.4` | 与 DB、工作区同一个数据根，备份/迁移一次带走。⚠️ 本行原写 `runtime-*.log`，与本节实测块和 P21-5 §10.3 用的 `runtime.log` 对不上，且那个 glob **两者都匹配不上**——已按经典 logrotate 命名统一 |
| 轮转 | 按大小，**20MB × 共 5 份**（当前 1 + 已轮转 4，磁盘上限 100MB） | 与 P21-5 导出上限 50MB 同量级。⚠️ "5 份"原文有歧义（共 5 份 / 还是当前 + 5 份），此处取**共 5 份** |
| 脱敏 | **写入时**，与 05 §4 同源 | 读出口脱敏挡不住 DB 文件与备份包两条路 |
| 权限 | `0600` | 同 `.master.key` / `platform.db` |

⚠️ **落盘不替代 stdout**：容器化部署仍要往 stdout 打（`docker compose logs` 是运维的第一反应），落盘是**为了平台自己能导出**，两者并存。

⚠️ **运行日志 ≠ 审计流**（P21-5 §10.1）：审计流是结构化、给产品用户看的；运行日志是文本、给运维看的。别把运行日志灌进审计面板，也别指望审计流里有栈。

##### 技术预研：轮转自己写，但有一个必踩的坑（2026-08-27 实测）

后端目前**零日志依赖**（无 pino / winston / file-stream-rotator），只有 Nest 内置 `Logger`。按大小轮转不值得为此引入依赖——一个 `LoggerService` + `fs.createWriteStream` 约 40 行就够。但自写轮转有一个静默失败的坑，实测如下：

```
写 BEFORE-1 / BEFORE-2 → renameSync(runtime.log → runtime.log.1) → 写 AFTER-RENAME
结果：runtime.log.1 = "BEFORE-1\nBEFORE-2\nAFTER-RENAME"
      runtime.log   = 不存在
```

⛔ **`rename` 之后旧的 write stream 跟随 inode**，轮转后的所有写继续落进已改名的旧文件，而 `runtime.log` 这个路径**直接消失**——外部 `tail -f` 也一并断掉（`tail -F` 才能恢复）。这个失败是完全静默的：日志照写，只是没人找得到。

⚠️⚠️ **上面这段伪代码照抄成回归测试会得到假绿**（实现时实测确认）。`createWriteStream` 的 fd 是**异步**打开的：写成一整个同步 burst 时，`renameSync` 那一刻**根本还没有 inode 可跟随**，流随后自己新建一份 `runtime.log`——坑不复现，把轮转改成"直接 rename 不 end()"的变异**照样绿**。要让这条断言真的有效，必须**先等到字节真正落盘**（等 `'open'` 事件仍不够，得等实际写入）再 rename。这正是本项目反复踩的「变异无效」形状：断言存在 ≠ 断言有效。

⇒ 正确顺序：**`end()` 旧流 →（在其 callback 里）rename 链式移位 → 重开流**。⚠️ `end()` 是异步的，**这个窗口内到来的日志必须缓冲**，否则 `ws` 为空导致丢行。实测该实现：800 行连续写、阈值触发 4 次轮转，保留窗口内**空洞 0 处**、末行完整。

| 实测项 | 结果 |
|---|---|
| 轮转窗口内丢行 | **0**（缓冲后重放） |
| 保留份数上限 | 生效，超出的 `.N` 被删 |
| 依赖 | **0**（Node 内置 `fs`） |

⚠️ **已知债：脱敏器目前够不着**（实现时发现）。05 §4 要求运行日志与审计流「同源脱敏」，但那套 per-CLI redactor 在 `packages/modules/runtime/src/domain/services/secret-redactor.ts`，**既没从 `src/index.ts` 导出、包 `exports` 又只开了 `"."`** —— `apps/api` 拿不到，只能复述规则。⚠️ 05 §4.3.2 ③ 对占位常量的那套论证（「shared-kernel 是唯一三方都够得着的位置」「绝不允许每处各写一个字面量」）**逐字适用于 redactor 本身**。当前用一条对账测试兜住漂移，正解是把 redactor 提到 shared-kernel。

⚠️ **导出打包不要 shell out 到 `tar`**：开发机是 macOS（BSD tar）、部署是 `node:22-bookworm-slim`（GNU tar），同一段参数两边行为不同，是 e2e 通过、生产失败的经典形状。用可流式的 npm `tar` 包，或 Node 内置 `zlib` + 自拼 tar header。

`.env` 都以 `api/` 为工作目录 —— 请先 `cd api`。
`better-sqlite3` / `ssh2` 是原生模块，install 时就地编译（实测 Linux 上 13s，工具链齐备即可）。

而**全文没有一句说这台 registry 怎么起**。`images/README.md` 只在 compose 的配方里

curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:5001/v2/    # 期望 200

```bash

PORT=3100                                            # 避开被占用的端口

ACCESS_PASSCODE=                                     # 留空 = 口令门禁用(仅本地)

SANDBOX_DEFAULT_IMAGE_TMUX=

# 两档的镜像不可互换（boxlite 那张里没有 :8080 的 agent），平台在建任务门口

```

**这份 `.env` 怎么被读到(以及它曾经根本读不到)**<a id="坑三已修"></a>

`start` 与 `db:migrate` 都带 node 原生 `--env-file-if-exists=.env`(≥20.6)。
三条语义要记住:

| 语义 | 含义 |
|---|---|
| **两个入口都带** | 只给 `start` 带的话,**迁移落到一个库、服务开另一个库**,两边都不报错 |
| `-if-exists` 而非 `--env-file` | 后者缺文件**直接退出**,会打断没有 `.env` 的容器与 CI |
| **shell 变量优先于文件** | compose 的 `environment:` 与 CI 的 env 不会被谁的本地 `.env` 盖掉 |

> 也可以完全不用 `.env`,直接行内给:
> `DATA_ROOT=… SANDBOX_DEFAULT_IMAGE=… PORT=3100 pnpm start` —— 按上表第三条,
> 行内的值总是赢。**CI 与容器就走这条路**,`.env` 只是本地的便利。

**⚠️ 坑一:`DATABASE_URL` 要么给真值,要么整行删掉,不要留空。**

```ts
return process.env.DATABASE_URL ?? resolve(this.dataRoot, 'platform.db');
```

`??` 只对 `null`/`undefined` 回落。`DATABASE_URL=`(**空串**)是有值的 ⇒ 不走默认,
better-sqlite3 拿到空串会开一个**匿名临时库**。表现:领域事件照发、工作区目录照建,
但 `platform.db` **根本不存在**、列表端点永远回 `[]`、创建流程停在「启动实例」。

⚠️ **这颗雷此前是随模板一起发的**:`.env.example` 自带 `DATABASE_URL=` 那一行,
注释还写着 "defaults to `$DATA_ROOT/platform.db` when empty" —— 那句话是假的,
`??` 从不把空串当缺席。该行已改为注释掉。**要么整行不写(推荐),要么给绝对路径**,
不要留一个等号。

**⚠️ 坑二:`SANDBOX_DEFAULT_IMAGE` 必须设成真的 AIO 镜像。**

默认值是 `alpine:3.20`(见 `SandboxApplicationService`)。alpine 里没有沙箱内 API、
没有 tmux、没有 CLI,**而且没有常驻进程会立刻退出** —— 容器一退,
`NetworkSettings.Ports` 就空了,于是报 `agent port 8080 is not published`。
AIO 镜像自带 entrypoint 拉起沙箱内 API,所以平台**故意不设 keep-alive 命令**
(04 §2.1),配 alpine 必然如此。

#### 前端

```bash
# web/.env.local
#
# ⚠️ 这一条**留空**。留空 = 走同源相对路径 `/api/*`，由 next.config.mjs 的 rewrites
#    转给后端。填了绝对地址就是让浏览器**跨源直连后端**，而后端一个 CORS 头都没有
#    ⇒ 请求被浏览器拦下、根本发不出去，表现是一句「网络错误，请稍后重试」。
NEXT_PUBLIC_API_BASE_URL=

# rewrites 的转发目标。**Node 侧读取、不进客户端 bundle**，所以没有 NEXT_PUBLIC_ 前缀
#（也因此改它**不需要**重新 build，与下面那条相反）。
API_ORIGIN=http://127.0.0.1:3100

# ⚠️ 这一条也**留空**。空串 = 同源，socket.io 从 location 推 host 与 ws/wss，
#    由下面那三条 /socket.io rewrite 转给后端。⛔ 不要填绝对地址，理由见下。
NEXT_PUBLIC_WS_BASE_URL=

pnpm build && PORT=3200 pnpm start -H 127.0.0.1        # ⚠️ 必须生产构建，见下
```

**⚠️ 必须用生产构建，不能用 `pnpm dev`。** `providers.tsx` 只判 `IS_DEV` 就无条件
启 MSW —— dev 模式下前端**根本打不到真后端**，你看到的全是替身数据(而替身可能
编码着和生产代码一样的错误假设，见 [12 §3.4](../frontend/12-前端测试体系.md))。

**⚠️ `-H 127.0.0.1` 不能省**（2026-08-30 实测补）。`next start` 默认绑 `0.0.0.0`，
于是前端对整个网段可达 —— 实测从另一台机器直接拿到 200。后端老老实实绑回环，唯独前端
敞着，是**一套里两个标准**；而 §3 那条「默认只监听 `127.0.0.1`」此前只对后端说过，
前端一个字都没有。

⛔ **两种写不对的写法**（都是本节初稿踩过的，各自的失败长得完全不一样）：

| 写法 | 结果 |
|---|---|
| `HOSTNAME=127.0.0.1 pnpm start` | **静默无效** —— 照旧 `*:3200`，局域网照样 200。`next start` 不读这个环境变量（读它的是 standalone 产物的 `server.js`，是另一套东西） |
| `pnpm start -- -H 127.0.0.1` | pnpm 把 `--` 一起透传 ⇒ `next start "--" "-H" "127.0.0.1"` ⇒ **启动即失败**：`Invalid project directory provided, no such directory: …/-H` |

⇒ 只有 `pnpm start -H 127.0.0.1` 是对的。⚠️ 第一种最危险：它**不报任何错**，
你以为绑住了，其实一直敞着 —— 这正是本节反复在讲的那种「看起来做了、实际没有」。

#### ★ 前后端之间那一层：**Next 自己就是它**，REST 与 WS 都是

**后端完全没有 CORS**：带 `Origin` 的响应里一个 `Access-Control-*` 都没有，preflight
`OPTIONS /api/projects` 直接 404；而 `ap_session` 是 HttpOnly cookie，跨源还需要
`credentials: 'include'` + 精确 origin 白名单 —— 两样后端都没有。所以「前端直连后端」
这条路**在真浏览器里从来跑不通**，而单测全绿，因为 MSW 替身让前端与它自己的替身完全
自洽（12 §3.4 共性 2）。

⇒ 解法是 **`next.config.mjs` 的 `rewrites`**：浏览器只跟 Next 同源通信，Next 转给
`API_ORIGIN`。**后端一行不改**，继续 loopback-only（§3）。⛔ 反过来「让后端开 CORS」
是**放宽**攻击面去换开发便利，不做。

```js
skipTrailingSlashRedirect: true,   // ⚠️ 为 socket.io 而开，见下
rewrites: [
  { source: '/api/:path*',       destination: `${API_ORIGIN}/api/:path*` },
  { source: '/socket.io',        destination: `${API_ORIGIN}/socket.io/` },
  { source: '/socket.io/',       destination: `${API_ORIGIN}/socket.io/` },
  { source: '/socket.io/:path+', destination: `${API_ORIGIN}/socket.io/:path+` },
]
```

| 走哪条 | 谁转发 | 配什么 |
|---|---|---|
| `/api/*` REST + SSE | Next rewrites | `NEXT_PUBLIC_API_BASE_URL` **留空** + `API_ORIGIN` |
| `/terminal`、`/tasks`、`/events` WS | **也是 Next rewrites** | `NEXT_PUBLIC_WS_BASE_URL` **留空** |

##### ⚠️ 「WS 不能走 rewrites」是**错的**（2026-08-30 实测推翻）

本节与 `next.config.mjs` 的注释此前都写着「rewrites 只处理 HTTP，不代理 upgrade，
所以 WS 必须用绝对地址直连后端」。**在 Next 15.5.23 上不成立**：加上那三条
`/socket.io` 规则后，polling 与 websocket 两种 transport 都能经 Next 转到后端，
浏览器里真终端的上下行数据流也通 —— 验证是**从局域网 IP 打开**做的，不是
localhost 恰好成立的巧合。

⚠️ **配置上有两个坑，各自的失败长得完全不一样**：

| 坑 | 症状 |
|---|---|
| 没开 `skipTrailingSlashRedirect` | socket.io 的握手路径带尾斜杠（`/socket.io/?EIO=4…`），Next 默认 **308** 到无斜杠版本。308 对 `fetch` 无害，对 WS 握手致命：客户端不会跟着重定向再发一次 upgrade |
| 只写一条 `/socket.io/:path*` | `:path*` 匹配空串时，Next 拼 destination 会把尾斜杠**吃掉** ⇒ 后端收到 `/socket.io?EIO=4…`（少一个 `/`）⇒ 404。空 path 那两条必须把尾斜杠**写死在 destination 里** |

##### 为什么绝对地址在这里是无解的，不只是"不方便"

`NEXT_PUBLIC_*` 是**构建期**烤进 bundle 的，而 WS 基址该填什么取决于**运行时**访问者
用的 host —— 一个构建期常量回答不了这个问题：

```
烤 ws://localhost:3100  ⇒ 你自己开 localhost:3200 ✅
                          同事从局域网开 192.168.1.5:3200
                          ⇒ WS 去连**同事自己机器**的 3100 ❌
```

换一个 host 访问就得重新 build。留空之后连锁消掉三件事：

- **host 一致性**：`ap_session` 是 host-only cookie（`Set-Cookie` 不带 `Domain`），
  **只认 host、不区分端口**。此前要靠人肉纪律保证 WS 的 host 与地址栏逐字一致
  （写错的症状是握手被 `EventsGateway` 拒、前端指数退避**无限重连**，界面一直显示
  「正在重连…」看上去在努力，实际原地空转）。同源之后 host 必然一致。
- **协议配对**：socket.io 从 `location.protocol` 推 ws/wss ⇒ https 部署自动对。
  写死的 `ws://` 在 https 页面下会被浏览器当 mixed content 拦掉。
- **多一个进程**：`next.config.mjs` 的注释里点名过，上一轮撞见时是拿一个临时
  `proxy.mjs` 糊过去的，**「那是脚手架，进程一没就复发」**。⚠️ 2026-08-30 的全新
  部署验证照着本节的旧版**又原样造了一遍同一个 `proxy.mjs`** —— 一份写错的清单不只是
  没帮上忙，它会**主动把人领回已经被解决掉的老问题**。

⚠️ **这条默认值此前没有任何测试保护**：把 `WorkbenchContainer` 的 `WS_BASE_URL` 默认值
从 `''` 改回 `'ws://localhost:3001'`，**1001 条测试一条都不红** —— 那个绝对地址就是这么
被烤进生产 bundle 的（实测在 `chunks/app/page-*.js`，不是 mock 残留）。已补两条断言，
变异验证过：改回绝对地址红、改成 `'/'` 也红。

**⚠️ 前端的 `NEXT_PUBLIC_*` 改了必须重新 `pnpm build`**；`API_ORIGIN` 不是（Node 侧读），
改它只需重启。

#### 起完之后:登记端口,并且**成对**收掉

一套 demo 是**两个进程**(后端 / 前端)，它们只在一起才有意义。

| 端口 | 谁 | 死了会怎样 |
|---|---|---|
| `:3100` | 后端 | 页面还在，但每个 `/api/*` 都 **502**；WS 无限重连 |
| `:3200` | 前端(**唯一该在浏览器里打开的**) | 页面直接打不开 |

⚠️ **半死的一套比全死的一套更难认**。前端还在、页面照常渲染，只是每个请求都 502
—— 界面上呈现为一句 `请求失败(HTTP 502)`(前端 `toApiError` 对非信封响应的兜底，
10 §6.8)，很容易被误读成"这次改动把接口改坏了"。实际发生过一次:后端被后来跑的
全量 e2e 挤掉(端口/运行时锁冲突)，前端活着不知情，几十分钟后才被认出来。
⚠️ 2026-08-30 又撞了一次，这次是**前端**那半死：`nohup` 起的 Next 被 ssh 断开时的
SIGHUP 带走，后端与页面外壳都还在，`/api/*` 照常 200 而首页 502。
远程起进程要 `setsid`(或 `systemd-run --user`)，别只靠 `nohup`。

两条纪律:

1. **起的时候把两个端口连同 PID 一起记下来**(哪怕只是贴在对话里)，
   否则事后 `lsof` 出来的 `node` 认不出是谁的;
2. **收的时候两个一起收**，别只 `Ctrl-C` 一个。留一个半死的比留一个全死的更贵。

#### 会看到、但属于预期的两条

| 现象 | 说明 |
|---|---|
| **compose 下**每次启动都有的 `HTTP is bound to 0.0.0.0 …` | ⚠️ **它曾经是必然出现、又必然不代表出错的一条 WARN**：compose 自己设 `HOST=0.0.0.0`（**必须**如此，容器里绑 loopback 那行 `ports:` 就转不进来），而外侧暴露由 `ports: 127.0.0.1:3000:3000` 收住。一条恒真的告警会训练人忽略告警，恰好废掉这条告警存在的全部理由（审计 P0-3）。✅ 2026-08-30 起用 `HTTP_BIND_GATED_BY` 分岔（详见 §3）：填了那句声明 ⇒ 降为 INFO 并把声明**原样**打进日志；留空 ⇒ 一字不变照旧 WARN。仓里的 `docker-compose.yml` 已经默认填着 |
| `no usable '<rt>' credential (NO_CREDENTIAL); the agent will start UNAUTHENTICATED` | 全新 `DATA_ROOT` 没有凭证。沙箱、终端、任务**发起**都能看,但 agent 真跑需要先走一次 runtime 授权(05) |
| 重启后 `reaped ORPHAN ... has no DB record` | 本实例自己此前建的容器,在库里已经没有记录(清过表、删过行)⇒ 启动对账回收掉(13 §4)。**boxlite 是 micro-VM,`docker ps` 看不到** |
| ⚠️ **换过 `DATA_ROOT`/`DATABASE_URL` 之后,旧容器不会被回收** | 实例身份取自"哪个库在裁决孤儿"(13 §4)——换库 = 换身份 ⇒ 上一轮的容器永远不再被本实例认领。这是"宁可漏收不可误删"的代价,**且今天是无声的**:既不回收,也不上报。要手动清:`docker ps -a --filter label=platform.managed=true`。⏳ 诊断项(P21-5 系统状态页)尚未覆盖它 |

### 1.4 api 跑在容器里 ≠ 能用：loopback 发布与 DooD 是互斥的（2026-08-29 实测 → 已修）

**现象**：`docker compose up` 一切正常（api `Up`、health 200、镜像播种成功），
建 Task 却必定失败：

```
status: failed
failureCode: PROVIDER_UNAVAILABLE
failureMessage: in-sandbox agent at http://127.0.0.1:45171 did not become ready
```

**沙箱容器其实起来了，而且是健康的** —— 同一时刻在宿主上看：

```
platform-aio-<id>  Up 11 seconds (healthy)  127.0.0.1:45995->8080/tcp
```

**根因**是两条各自正确的决定撞在一起：

| 决定 | 落点 | 后果 |
|---|---|---|
| agent 端口**只发布到 loopback**（安全加固，§5 / aio-agent-auth） | `docker-container-runtime.ts:81` `PortBindings: [{ HostIp: '127.0.0.1' }]` | 端口只出现在**宿主**的 netns |
| `agentOrigin` 照着 `HostIp` 拼回调地址 | `docker-container-runtime.ts:154` → `http://127.0.0.1:<port>` | 这个地址**只有宿主上的进程**解得开 |

DooD 下 api 请求的是**宿主的** docker daemon ⇒ 端口发布在宿主 loopback；
而 api 自己在容器里，它的 `127.0.0.1` 是**容器自己的** loopback ⇒ 永远连不上。
实测对照（同一个 `127.0.0.1:18080`）：宿主 `curl` → 401（在），
api 容器内 `fetch` → `fetch failed`（不在）。

⚠️ 这与 §1.2 那条「宿主路径 = 容器路径」是**同一类**问题的两面：DooD 下 api 说出口的
每一个坐标（路径、地址）都由**宿主**解析。路径那一条已经被记下来了，**地址这一条没有**。

#### ✅ 已选方案 ③ 并落地（2026-08-29）

三条候选里选的是 **③ 把 api 与沙箱放进同一个用户自定义网络，用容器名而不是发布端口做
`agentOrigin`**。理由是它**不只修好地址，还把暴露面收得比修之前更小**：

| 候选 | 代价 |
|---|---|
| ① `network_mode: host` | 丢掉 api 容器的网络隔离，为了一个地址问题换掉一整层隔离 |
| ② 端口发布到网桥 | **扩大**暴露面（端口从 loopback 挪到网桥），要重新论证 aio-agent-auth 的前提 |
| **③ 同网络 + 容器名** ✅ | agent 端口**一个都不发布**，宿主上没有任何进程碰得到它 —— 比今天的 loopback 档还小 |

**形态怎么判定：一个显式配置 `SANDBOX_DOCKER_NETWORK`，默认空。**

| 值 | 形态 | agent 端口 | `agentOrigin` |
|---|---|---|---|
| 空（默认） | api **裸跑在宿主**（§1.3 那条，实测全绿） | 发布到宿主 loopback | `http://127.0.0.1:<发布端口>` |
| 网络名 | api **在容器里**，与沙箱同在这个用户自定义网络 | **完全不发布** | `http://platform-aio-<sandboxId>:8080` |

⛔ **不探测**（不看 `/.dockerenv`、不试 ping 网关）。探测回答的是「我像不像在容器里」，
而真正要回答的是「**我说出口的地址，对面照着它解析得开吗**」—— 那取决于部署者怎么接的网。
反例现成：`network_mode: host` 的 api 容器里 `/.dockerenv` 在，而 loopback 那套坐标恰恰是
**对的**。⚠️ 猜错的症状是「健康检查全绿 + 建 Task 必失败」，最难查的那一种；配错的症状是
一条指名道姓的错误（`container … is not attached to the docker network '…'`）。

> ⛔⛔ **上面这句「配错 = 一条指名道姓的错误」曾经是错的（2026-08-30 真机实测推翻，
> 同日已修）。** 它只对「沙箱容器没进这个网络」那一半成立，而那一半平台自己就把容器
> 放进去了，**实际上填不错**。真正会被填错的是另一半 ——「**而我自己也在这个网络里**」
> —— 而那一半当时**一个字都没有检查**。
>
> 实测（api 裸跑在宿主 + `SANDBOX_DOCKER_NETWORK=platform-sandbox-net`）：
>
> ```
> 沙箱容器：running / healthy，已接入 platform-sandbox-net，Ports = {}
> agentOrigin：http://platform-aio-<id>:8080     ← 名字本身是对的
> 而宿主解析不了这个名字（docker 内嵌 DNS 只在网络内部）
> ⇒ sandbox 卡在 starting **超过 6 分钟不动**，无错误、无超时、无一行日志
> ```
>
> `agentOrigin` 的 `not attached` 守卫查的是**沙箱容器**在不在网络上（它在，守卫放行），
> 从来没查过**调用方自己**在不在。于是这个配错产生的正是本节声称已经消灭的那种失败
> ——「看起来在转、实际什么都没发生」，而且比原始 bug **更难查**：原始 bug 至少还给了
> 一句 `did not become ready`，这个连那句都没有。

##### ✅ 补上的那一半：开机自检（2026-08-30）

填了 `SANDBOX_DOCKER_NETWORK` ⇒ 平台在**启动期**证实后半句，验不过**开机就失败**，
而不是等第一个 Task 静静地挂住。

**怎么验才可靠 —— 两侧各自的事实取交集，一个字都不猜：**

| 侧 | 事实 | 来源 |
|---|---|---|
| daemon 侧 | 「这个网络上有这些容器，它们的地址是这些」 | `GET /containers/json?filters={"network":[…]}` |
| 进程侧 | 「我这个 netns 里持有这些地址」 | `os.networkInterfaces()` |

**交集非空 ⇒ 我就是那个容器**：daemon 把这个地址派给了那个网络上的某个容器，而这个地址
此刻在我的 netns 里 —— 同一网络内地址唯一，除非我就是它，否则不可能同时成立。

⛔ **仍然不探测**：不看 `/.dockerenv`、不看 cgroup、不 ping 网关。那些回答的是「我像不像
在容器里」，而这里问的是「我在不在**这一个**网络里」——本节开头否掉探测的那段论证原样适用
（反例：`network_mode: host` 的容器里 `/.dockerenv` 也在）。

⚠️ **为什么走容器列表而不是 `/networks/<id>`**：后者更直白，但生产形态下 api 走的是
`docker-socket-proxy`，白名单只开了 `CONTAINERS/EXEC/IMAGES`；为一次自检去开 `NETWORKS`
（在 `POST=1` 之下会连带放开建/删网络）是拿隔离换便利。容器列表这条路在**今天的白名单里
就能走通** —— 这一条 2026-08-30 在真 Linux（douglas-wsl，Docker Engine 28.3.2 / API v1.51）
上按生产形态实测过，四条证据都摆在这里，因为这个判定的可靠性全压在它们上面：

| # | 实测 | 结果 |
|---|---|---|
| ① | 直连 daemon：`GET /containers/json?filters={"network":["<net>"]}` | 返回该网络上的容器与它在这个网络上的 IP（`172.19.0.2`）—— filter 被真的支持 |
| ② | 在那个容器里 `ip -o -4 addr` | `eth0 172.19.0.2/16` —— **与 daemon 报的一字不差**，交集判定的前提成立 |
| ③ | 宿主自己的地址表里有没有 `172.19.0.2` | **没有** ⇒ api 裸跑在宿主时判定 not-attached，与实情一致（这正是那个真缺陷的形状） |
| ④ | 把网络名写成 `proj_<net>`（模拟 compose 项目名前缀） | 名单返回 `[]` ⇒ 判定 not-attached，与实情一致 |

⚠️ 还按生产形态起了一个白名单相同（`CONTAINERS/EXEC/IMAGES/POST`）的 `docker-socket-proxy`
对照：同一个容器列表请求**穿得过去**，而 `GET /networks/<net>` 回 **403** —— 这就是不走
`/networks` 的实证理由，不是一句推测。⚠️ 返回结果**再按网络名自己筛一遍**，不完全指望 daemon 侧的 filter：万一某个
中间层把 query string 吃掉，全量列表照样能得出正确结论 —— 否则那会是一次**假阴性**，
而假阴性在这里等于开机拒绝启动。

**结论只有三种，没有第四种「大概没事」：**

| 结论 | 处置 |
|---|---|
| 交集非空 | 一条说清证据的 log（我持有哪个地址、它属于哪个容器），照常启动 |
| 交集为空（**名单为空也算**） | **开机失败**，错误里带两侧证据 + **两条**出路（裸跑就删掉这一行 / 在容器里就把 api 也接上这个网络） |
| 问不到 docker / 本进程没有非回环地址 | 照常启动，但打 **error 级别**的「**我没能验证这一条**」——静默放行 = 把一个已知会静静挂住的配置放过去 |

⚠️ **「名单为空」是确凿的否定，不是「没数据」**：本进程若真接在这个网络上，它必然出现在
那份名单里（它自己就是一个跑着的、接在这个网络上的容器）。这正好覆盖了「compose 给网络
加了项目名前缀」那个经典配错 —— 名字对不上 ⇒ 名单为空 ⇒ 判定为不在，与实情一致。

落点：`api/packages/modules/sandbox/src/infrastructure/providers/docker/self-network-check.ts`
（纯判定 + 消息）与同目录 `self-network-check.service.ts`（开机钩子）。
测试 `packages/modules/sandbox/test/unit/self-network-check.spec.ts` ——
判定被抽成纯函数单独测**是有理由的**：「我在不在某个 docker 网络里」在开发机与 CI 上
恒为否，一条直接调真 docker 的断言只会写出「在本机永远为真」的那种测试，它红不了。

⚠️ **它是一句声明，不是一个开关**：填了网络名 = 「沙箱放到这个网络里，**而我自己也在这个
网络里**」。两件事必须同时为真，所以由**同一个**配置表达，而不是两个可以各自填错的配置。
✅ 从 2026-08-30 起，**两件事都真的被检查了**（前一半在 `agentOrigin`，后一半在开机自检）。

**容器名跨形态稳定吗**（这条被专门验过）：名字是 `platform-aio-<sandboxId>`，`sandboxId` 是
UUID ⇒ 49 字符、全小写、只有连字符，稳稳落在 DNS label 的 63 上限内，且在用户自定义网络上
由 docker 内嵌 DNS 解析（**默认 `bridge` 没有内嵌 DNS**，所以必须是用户自定义网络）。
但「今天合法」不是「永远合法」：换 id 生成器或 provider 名就可能不再是 DNS label，而那时
容器**照样起得来**、只是永远连不上。⇒ `create` 门口加了一道 DNS-label 检查，把它变成一条
说得出原因的错误，而不是一次指向沙箱镜像的 `did not become ready` 超时。

落点：

| 文件 | 做什么 |
|---|---|
| `sandbox/…/docker/agent-addressing.ts` | 形态类型 + 从 env 读 + DNS label 判定（**新增**） |
| `sandbox/…/docker/docker-container-runtime.ts` | `create` 按形态二选一（`NetworkMode` / `PortBindings`）；`agentOrigin` 按形态给两套坐标 |
| `api/docker-compose.yml` | 声明 `networks.sandbox`（**带 `name:` 关掉项目名前缀**）、api 接上 `default` + `sandbox`、注入 `SANDBOX_DOCKER_NETWORK` |
| `api/.env.example` | 新增 `SANDBOX_DOCKER_NETWORK`（默认空 = 裸跑） |
| `sandbox/…/docker/self-network-check.ts` | **（2026-08-30 新增）** 开机自检的判定与消息：daemon 的网络成员表 ∩ 本进程的地址表 |
| `sandbox/…/docker/self-network-check.service.ts` | 同上的开机钩子：`fatal` 抛（开机失败）、`unverified` 打 error、`ok` 打 log；**没配就直接返回**，裸跑档一次 docker 都不问 |
| `shared-kernel/…/domain/sandbox-network.ts` | `SANDBOX_DOCKER_NETWORK` 收成**全仓唯一读取点**（`configuredSandboxNetwork()`）—— 因为它有了第二个读者：`ImageSeeder` 的失败提示要按形态分岔（与 `builtinImageRef()` 同源的教训） |

⚠️ **compose 那个 `name:` 不能省**：compose 默认给网络加项目名前缀（`<项目>_sandbox`），
而 `SANDBOX_DOCKER_NETWORK` 写的是 docker 侧的真名，对不上的症状同样是「都起得来、连不上」。

**测试**（`docker-container-runtime.e2e-spec.ts` 新增一组，真 docker）：起一个用户自定义
网络 → 建沙箱容器 → 断言 `Ports['8080/tcp']` **为空**（一个端口都没发布）→ 断言
`agentOrigin` 是容器名 → **从同网络的另一个容器**真的 `wget http://<name>:8080/v1/ping`。
⚠️ 最后一步不能省：那次事故里平台做对了每一件看得见的事，唯一错的是它对自己说的那句地址
—— 只断言「返回的字符串长什么样」的测试，在那个 bug 上照样绿。

#### 顺带修掉同一个病根的另一半：明文 registry 只认 loopback 字面量

`oci-registry.client.ts` 按 host 名硬判 scheme：只有 `localhost` / `127.0.0.1` / `[::1]` 走
http。而那三个字面量在容器里指的是**容器自己** ⇒ compose 形态下配不出可用的本机 registry
（换 `host.docker.internal` 又被强制 https）。这与上面是**同一个**「容器内外坐标不是同一套」。

⇒ `IMAGE_REGISTRY_INSECURE_HOSTS`（逗号分隔的 `host:port`，与 docker daemon 自己的
`insecure-registries` 同形状）。留空 = 行为一字不变。⛔ **不做**「先试 https 再退回 http」的
自动降级——那等于给任何一次 TLS 故障配一条静默的降级路径。

⚠️ 配它时的纪律：**宿主 daemon 与 api 容器必须用同一个 `host:port` 解析到同一个 registry**
（镜像坐标只有一份，却要被两个人解析：api 在注册/播种时问 registry 的 HTTP API，宿主 daemon
在起容器时拉同一个坐标）。具体配方见 `api/images/README.md`。⚠️ 那份配方 2026-08-30 改过
——原来那份照抄跑不通（registry 只发布在 `127.0.0.1` 上够不着 host-gateway、compose 缺
`extra_hosts`、整条路默认要 root），三处的症状都与「registry 根本没起」一模一样。
⚠️ 另外「宿主 daemon 起容器时拉同一个坐标」这句**对 aio 档不成立**：那一步不 pull，
只查本机镜像库（详见 `api/images/README.md` 那张表的 ⚠️）。

#### 播种失败那句「下一步」按形态分岔（2026-08-30）

⚠️ compose 实测抓到的一条**把人指回原地**的提示：播种失败时日志说「把 `SANDBOX_DEFAULT_IMAGE`
指向平台预制镜像」——**可它已经指着了**（`localhost:5001/platform/sandbox:v2`）。真正的根因
是那个坐标**在 api 容器里解析不开**：容器里的 `localhost` 是容器自己，宿主上那台 registry
在这个 netns 里根本不存在。

⇒ 这句话现在按 `SANDBOX_DOCKER_NETWORK`（也就是同一句形态声明）分岔：

| 形态 | 下一步说什么 |
|---|---|
| 裸跑档（没配） | 指向预制镜像 **+ 那台 registry 起了吗、镜像 push 上去了吗**（「本机 build 过」不算数，注册/播种查的是 registry 的 HTTP API） |
| 容器网络档（配了） | **先别急着改 `SANDBOX_DEFAULT_IMAGE`**，问的是这个坐标在容器里解析得开吗：loopback 字面量指的是容器自己 / `extra_hosts` / `IMAGE_REGISTRY_INSECURE_HOSTS` / registry 别只发布在宿主 `127.0.0.1` 上 |

⚠️ **「说错下一步比不说更贵」**（`builtin-image.ts` 记过一次同类账）：它把人送去做一件他刚
做过的事，还让他以为是自己做错了。落点 `image/…/application/image-seeder.ts` 的
`seedFailureNextStep(ref, network)`——**抽成纯函数是有理由的**：形态判断在本机永远走同一支
（本机永远是裸跑档），写在类里的断言红不了。

**今天可用的形态**：

| 形态 | 能建 Task 吗 | 说明 |
|---|---|---|
| api 裸跑在宿主（`pnpm start`） | ✅ | §1.3 那条，实测全绿；本次改动后**行为一字未变**（默认档） |
| api 在容器里 + `SANDBOX_DOCKER_NETWORK` | ✅ | 本次落地；e2e 已从另一个容器真的打通 `:8080` |
| api 在容器里、**不配** `SANDBOX_DOCKER_NETWORK` | ⛔ | 就是上面那个死局；`.env.example` 与 compose 里都写了这一条。症状：每个 Task 死在 `did not become ready` |
| api **裸跑在宿主**、却**配了** `SANDBOX_DOCKER_NETWORK` | ⛔ **开机就失败** | 2026-08-30 之前它是「沙箱静静卡在 starting，无错误无日志」——比上一行还难查；现在被开机自检拦在门口，错误里直接说「删掉这一行」 |

## 2. 持久化：SQLite 起步，Postgres 预留

- 起步：`better-sqlite3` 单文件库 + Drizzle ORM（schema-first，drizzle-kit 生成迁移）。
- 隔离：domain 只声明 `Repository` 接口，infrastructure 提供 Sqlite 实现；`PersistenceModule.forRoot({ driver: 'sqlite' | 'postgres' })` 切换。
- 约束：避免 SQLite 专有语法（Drizzle 双方言天然约束）。
- **迁移阈值（经验值）**：并发运行 sandbox > 50 或 QPS > 100 时迁 Postgres——better-sqlite3 是同步 API，高并发下阻塞事件循环。

## 3. 无帐号体系下的鉴权预留

- 全局 `APP_GUARD` 注册 `NoopAuthGuard`（放行）。
- **REST / MCP / WS 三个协议面统一走同一 Guard 抽象**——后续接入用户体系只替换 Guard 实现，不动业务代码。
- `CredentialVault` 记录预留 `owner_ref` 字段（当前恒空，见文档 13 credentials 表），加用户体系时仅数据迁移。
- **默认只监听 `127.0.0.1`（审计 P0-3 ①）**：compose 的 `ports` 默认绑回环；要对外提供服务必须显式改成 `0.0.0.0` 或经反向代理。改了之后：**启动日志打醒目警告**、**系统状态页常驻一条横幅**（"当前实例可被局域网/公网访问"）。理由：这台实例持有用户的 ChatGPT/Claude 订阅凭证（05 §6 已将该风险上调为高），默认对外暴露是不可接受的出厂设置。

  ⚠️ **这里说的「反向代理」与 §1.3 那层不是一回事，别混。** 本条讲的是**对外暴露**：
  把实例挂到局域网/公网时，前面通常要有一台 nginx/Caddy 负责 TLS、访问控制、审计。
  §1.3 讲的是**前后端之间**那层，而那层**已经由 `next.config.mjs` 的 rewrites 承担了**，
  不需要、也不应该再单起一个进程。两者可以同时存在（外层 nginx → Next → rewrites → 后端），
  但解决的是两个问题。

  ⚠️ **那条告警在 compose 下曾经恒响**（2026-08-30 复验）：compose **必须**设 `HOST=0.0.0.0`
  ——容器内绑 loopback，外面那行 `ports:` 就转不进来——而真正的暴露面由 `ports:` 的
  `127.0.0.1:` 前缀收住。于是每一次 `docker compose up` 都打这条 WARN，而每一次都不代表
  出错。**一条恒真的告警不是多一句话，它训练用户忽略告警**，而这条告警存在的全部理由，
  是有朝一日真的有人把一个持有用户凭证的实例挂到公网上时它能被看见。

  ⛔ **不能靠探测免掉它**：进程内看不见「外侧那行 `ports:` 发布在哪」。看 `/.dockerenv`、
  看 `SANDBOX_DOCKER_NETWORK`，都只能回答「我是不是在容器里」——而在容器里**照样可以**
  被发布到 `0.0.0.0`。靠它关掉告警，就是拿一句猜测去关一个安全提示（与 §1.4 同一条纪律）。

  ⇒ **`HTTP_BIND_GATED_BY`：一句声明，不是一个开关。** 填的是「外侧由什么收住」的人类
  可读答案（compose 里就是那行 `ports:`）。填了 ⇒ WARN 降为 INFO，并把这句声明**原样**
  打进日志：日志里留下的是运维方自己写的那句话，平台没有替他做任何假设，事后审计看得见
  签的是什么字。留空 ⇒ 行为一字不变。⚠️ INFO 那句里**明写**「平台验证不了这句声明」——
  这是它与「加个开关把告警关掉」的唯一区别：平台能保证的是有人为此签过字，不是它为真。
  判定在 `api/apps/api/src/platform/config/env.ts` 的 `describeBindExposure()`（纯函数，
  单测在 `apps/api/test/unit/config/bind-exposure.spec.ts`）。
- **访问口令 Guard 从 v1.1 提前到 MVP（审计 P0-3 ②）**：规格见 §3.1，MVP 即启用；不再依赖"用户自己加反向代理"这个假设。

### 3.1 访问口令 Guard（**MVP**，审计 P0-3 从 v1.1 提前）：`NoopAuthGuard` 预留位的第一个真实实现

产品规格见 [P21-8 §3](../product/pages/21-8-部署与初始化.md)（开关落点在系统状态页 21-5）。它替换的正是本节的 `NoopAuthGuard`，**不引入用户体系**——没有帐号、没有角色，只有「这台实例让不让进」。

> **版本变更（审计 P0-3）**：本节原标 v1.1，现**提前到 MVP**。与 ① 默认回环监听是一对：回环挡住"被别人扫到"，口令挡住"同一台机器/同一内网的其他人随手打开"。两条都做的成本很低（规格本就完整），而只做一条都留着一个明显的口子。**产品文档 P19 §3 与 P21-8 §3 需同步把版本从 v1.1 挪到 MVP**（属产品侧，另行同步）。

| 项 | 规格 | 落点 |
|---|---|---|
| 启用时机 | **MVP 即可用**；首次启动若未启用，系统状态页常驻提示（配合 ① 的监听地址告警） | Guard |
| 口令生成 | 首次启用**自动生成 16 位随机串**（`crypto.randomBytes` → base58 字符集，避免 `0/O/l/1` 混淆）+ [复制] / [重新生成] | 应用层 |
| 存储 | **只存 hash**（Argon2id，退化到 bcrypt 亦可），`system_settings.access_passcode_hash`；非空即视为启用；**明文只在生成后回显一次**，之后任何接口都不回显 | 13 §2 |
| 校验失败锁定 | **连续 5 次错误锁 5 分钟**；计数按客户端 IP 存**进程内存**（单机单进程，重启即清空是可接受的宽松失败模式，13 §2 已说明）；锁定期内直接 429 + `retryAfterSec` | Guard |
| 审计 | **四件事全部进平台审计流**（13 §2.8.2 的 `category: 'system'`，本档的第一批生产者）：`system.access.unlocked` / `system.access.unlock_failed`（带连续第几次）/ `system.access.locked`（**`error` 级**，运维筛「仅告警」时必须扫得到）/ `system.access.locked_attempt`（锁定期内再试——这些尝试压根不进 limiter 的计数，不记就彻底没有，而它是「有人在爆破」最硬的信号）。⚠️ **只记 `POST /api/access/unlock` 这一条路径**，Guard 那一侧刻意不记：它的失败分支在任何一个没带 cookie 的受保护请求上都会走到，记进去等于把访问日志灌进产品面板（P21-5 §10.1）。⛔ **口令本身与它的任何投影（明文/前缀/后缀/长度/hash）一律不进 `summary`/`detail`**——长度直接把爆破空间从 58^16 砍到 58^n；纪律建在构造函数签名上（`access-audit.ts` 根本不接受口令参数），写入口脱敏是兜底。⚠️ 单机私有化部署没有用户系统，「谁」没有可记的身份、IP 在 NAT 后面也几乎不携带信息 ⇒ 如实只答「**什么时候**（`at`，毫秒）试了**多少次**（`consecutiveFailures`，由 limiter 唯一交出）」 | 13 §2.8.2 |
| 会话 | 通过后签发**签名 cookie，有效期 7 天**（`HttpOnly` + `SameSite=Lax`；HTTPS 部署下加 `Secure`）；无服务端 session 表；**已通过的会话不受口令重新生成影响**（P21-8 §3「不影响已通过会话」——重新生成只影响新登录） | Guard |
| 覆盖面 | **REST / MCP / WS 三面同时生效**——就是走同一 Guard 抽象的价值所在；WS 在握手阶段校验 cookie，失败直接拒绝升级 | 02 §6 / 06 §2 |
| 豁免 | 仅 `GET /api/health` 与静态资源；`/openapi.json` **不豁免**（它暴露完整接口面） | Guard |
| MCP 面的取舍 | MCP 走 STDIO 传输时天然在本机进程内，无 cookie 概念——STDIO 传输**豁免**口令，HTTP/SSE 传输**必须**带（`Authorization: Bearer <passcode>` 亦可，供程序化消费方免 cookie） | 02 §6 |

**安全边界明示（必须原样出现在 UI 上，P21-8 §3）**："访问口令提供基础隐私保护，不是加密安全边界；生产部署请配置 HTTPS + 网络隔离。"——它挡的是"局域网里被人随手打开"，不是有备而来的攻击者。

## 4. 多节点调度预留

当前单机实现与未来多节点的边界已在接口层切开：

| 现在 | 预留 |
|---|---|
| `ResourcePool` 读本机 `os.cpus()/totalmem()` | `NodeRegistry`：worker 节点地址 + 资源快照上报 |
| First-Fit 单层调度 | 两级调度：`NodeSelector` 选节点 → 节点内 first-fit（domain 核心逻辑不变） |
| `aio` / `boxlite` 本机执行 | `RemoteSandboxProvider`：gRPC/HTTP 代理调用远端节点上**同一套 SandboxProvider contract** |
| WS 网关直连本机 pty | 网关随 RemoteSandboxProvider 转为流代理 |

## 5. 安全基线（单机阶段）

| 项 | 措施 |
|---|---|
| 容器 API 面（aio） | socket proxy 白名单（§1）；boxlite 无此暴露面 |
| 凭证 | AES-256-GCM 加密 + 掩码回显 + 吊销入口（文档 05） |
| sandbox 隔离 | 资源硬限额；不可信负载可直接选 `boxlite`（micro-VM 级）；更多实现（gVisor/Firecracker 等）按 contract 注册 |
| 日志 | pty 交互日志脱敏 |

## 6. 风险与备选

| 风险 | 缓解 |
|---|---|
| DooD 逃逸面 | socket proxy 限权；长期 microVM Provider |
| SQLite 并发瓶颈 | §2 阈值 + Repository 隔离，迁移成本可控 |
| 单进程网关/调度单点 | 单机阶段可接受；多节点演进路径已预留（§4） |
