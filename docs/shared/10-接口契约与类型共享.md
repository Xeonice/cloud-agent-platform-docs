## 1. 结论先行

| 契约类型 | 方案 | 同步方式 |
|---|---|---|
| REST | `openapi-typescript`（生成纯类型）+ `openapi-fetch`（类型安全 client） | **生成后提交** + CI 漂移检测门禁 |
| WebSocket | 手写 `ws-protocol.ts` 双端同步 + **运行时 zod/valibot 校验兜底** | 手动同步 + CI hash 比对感知变更（文档 14 §2.5 方案 B）；改动频繁时升级为独立协议小包（方案 A） |
| 不采用 | 发布 npm 类型包 | 作为规模扩大后的平滑演进路径预留 |

## 2. REST 契约链路

```
NestJS (@nestjs/swagger)
      │  暴露 /openapi.json
      ▼
前端仓库: pnpm generate:api
      │  openapi-typescript https://backend/openapi.json
      │    -o src/types/generated/openapi.d.ts
      ▼
services/api/client.ts
      │  openapi-fetch 基于该类型创建强类型 client
      ▼
业务代码: client.GET('/api/sandboxes/{id}')  ← 天然类型推导，无需手写 DTO
          （后端设 setGlobalPrefix('api')，openapi paths 含 /api 前缀，见文档 02 §8）
```

选型理由（2026-08 现状）：

- `openapi-typescript`：约 11k star / 50 万周下载，生成**纯类型**（`.d.ts`），零运行时开销；被 TanStack Query 官方文档列为推荐范式之一。
- `openapi-fetch`：与上者配套，无代码生成的运行时薄封装。
- 备选 **Orval**（约 7k star / 35 万周下载）：可直接生成 React Query hooks + MSW mock。需要"开箱即用 hooks + mock"时再评估切换；当前推荐 openapi-fetch 保持数据层显式。

### 2.1 CI 契约漂移检测（关键门禁）

防止"后端契约变化被前端悄悄吃掉"：

```yaml
# static-checks job 内的一步（PR 硬门禁——与文档 09 §1.3、16 §6 的流水线一致）
- run: pnpm generate:api              # 重新从后端 /openapi.json 生成
- run: git diff --exit-code src/types/generated/
  # 有差异 → CI fail → 人工确认并提交更新
```

契约变更因此会出现在 PR diff 中被 review，比 npm 包版本号更新更透明。

### 2.2 为什么不发 npm 类型包

- 双仓库物理隔离，发包意味着版本号对齐、私有 registry、联调时 `npm link`/`file:` hack，对"简易管理入口"级项目工程成本偏重。
- "生成后提交"同样强类型，且改动可 review。
- **演进路径**：若未来多个前端消费同一后端契约，再升级为发布 `@org/api-types`（仅含生成 `.d.ts`，无运行时代码），与现方案不冲突。

## 3. WebSocket 契约

WS 没有 OpenAPI 级别的成熟工具链（AsyncAPI 生态尚不无缝），采用**最低工程成本 + 运行时兜底**：

1. **帧/事件类型的唯一 canonical 定义在 [§7.4](#74-ws-帧类型)**（`TerminalClientFrame`/`TerminalServerFrame` + `SandboxEvent`）——本节此前重复给过一份已删除（交叉评审 P0-1：与 §7.4 冲突过，判别键/字段名/base64/exit/clone phase 都不一致）。后端仓库以 discriminated union 定义、双端各持一份 `ws-protocol.ts`。
2. 双端文件顶部加 `// SYNC WITH shared/10 §7.4 — 修改需双端确认` 注释。
3. **前端对收到的每帧做 zod/valibot `parse`**——类型意外漂移时开发环境立刻抛错，而不是 UI 静默 undefined。
4. **变更感知**：后端 CI 对协议文件算 hash 写入 release asset，前端定时 job 比对，不一致即失败提醒人工同步（文档 14 §2.5 方案 B）；协议改动趋于频繁时升级为独立 npm 协议小包 + Renovate 自动开 PR（方案 A，仅含类型与 zod schema、无运行时代码——与本文档"REST 不发包"的结论不冲突：REST 有 codegen 这条更优路径，WS 没有）。

### 3.1 事件语义表（前端 patch 行为的权威）

| 事件 | 触发时机 | 前端处置 | 后端落点 |
|---|---|---|---|
| `sandbox.created` | 创建请求受理、pending 记录落库后 | 列表插入（或对齐乐观项） | 03 §4 |
| `sandbox.status_changed` | **每一次**状态机转移（含新增的 `preparing-workspace`） | patch 列表项状态 + 驱动阶段进度卡 | 03 §4，事务内双写后经 Outbox 投递（13 §3） |
| `sandbox.removed` | destroyed 终态 | 移除列表项 | 03 §4 |
| **`sandbox.waiting_input`** | `running` 子态**翻转时**（不周期性重发） | 列表项切 🔵 等待输入 图标；**仅展示，不改主状态** | 06 §8 网关内存态；判定与误报纪律见 03 §4.1 |
| **`project.clone_progress`** | 异步 clone 期间节流 **1s** 一帧；`phase:'slow'` 在超 10min 时补发一帧 | 创建弹层进度态；`slow` 出提示、`failed` 就地红字按 `errorCode` 分支引导 | 03 §7.2 |
| `runtime-auth.status_changed` | 凭证过期/吊销/重授权成功 | invalidate `['runtime-auth']` + 横幅 | 05 §5 |
| **`runtime.install_progress`** | sandbox 的 `starting` 段里装 runtime CLI 时，`runtime_installations.status` **每次变更**（`not_installed → installing → installed \| failed`） | 进度卡「启动实例」格子下补一行子文案（「正在安装 claude-code…」）；`failed` 时不单独处置——紧随其后的 `sandbox.status_changed → failed` 才是权威 | 03 §4.3 ③；源事件 `RuntimeInstallationStateChanged`（23 §12），走 Outbox |

两条纪律：

- **`runtime.install_progress` 为什么要单开一条、不复用 `sandbox.status_changed`（S5，[TASK-LAUNCH-DECISIONS](../TASK-LAUNCH-DECISIONS.md) T-3）**：装 CLI 期间 `sandbox.status` 恒为 `starting`，而实测在 AIO 默认镜像上现装 `claude-code` 要 **753 秒（12.5 分钟）**（04 §3 ★1）——没有这条事件，前端只能盯着「启动实例」格子干等 12 分钟。复用 `sandbox.status_changed` 则会推出一串「状态没变的状态变更事件」，破坏本表第 2 行「**每一次**状态机转移」的语义与前端的 patch 行为。它**进 Outbox**（源事件本就是 ✅ Outbox，23 §7.5），因为漏一帧会让进度卡永久停在旧文案。
- **`sandbox.waiting_input` 与 `project.clone_progress` 都是"可丢失"事件**——前者丢了下次翻转会重发（且有 REST 派生字段 `waitingInput` 兜底），后者丢了不影响最终 `clone_status`（REST 可查）。因此**都不进 domain_events Outbox**，直接由网关/编排器推送；进 Outbox 的只有状态类事件（需要可靠投递与回放）。
- 高频事件必须节流：clone 进度 1s、waiting_input 只在翻转推——WS 通道与终端数据流共用连接预算，事件洪水会挤压终端体验。

## 4. 与 sandbox 列表更新的配合

- WS 事件通道推送 `sandbox.*` 事件 → 前端 `queryClient.setQueryData` patch 缓存（推送为主）。
- TanStack Query 保留 30–60s 低频轮询兜底（WS 断线期间防陈旧）。

## 5. 风险与备选

| 风险 | 等级 | 缓解 |
|---|---|---|
| 生成后提交模式下前端未及时重新生成 | 中 | CI 漂移检测作为强制门禁（§2.1），不依赖自觉 |
| WS 手动同步漂移 | 中 | 运行时 schema 校验兜底 + artifact 拉取增强 |
| 后端 OpenAPI 注解不全导致生成类型缺失 | 中 | 后端引入 `eslint-plugin-nestjs-typed` 校验 @ApiProperty 与字段类型对齐（文档 14 §8） |

**SSE 与 codegen 的边界**：`openapi-typescript` 只能生成 `/api/system/diagnose` 的响应 content-type 声明，**流帧的类型必须手写**并与 WS 协议文件同放（同一份 `// SYNC WITH ...` 纪律，§3）——诊断帧结构见 02 §5.3。

### 6.8 统一错误响应 envelope（审计 P1-4）

**所有非 2xx 响应一律是这个形状**，无例外。**codegen 可得性**：`ErrorEnvelope` 必须作为具名 component 进 `openapi.json` 且被所有 error response 引用（`@nestjs/swagger` + nestjs-zod `patchNestJsSwagger()` 才能把 zod 的 enum/discriminatedUnion 如实反射）——否则前端 `components['schemas']['ErrorEnvelope']` 取不到、退化成手写（交叉评审 P1-4）。

```ts
interface ErrorEnvelope {
  code: string;          // 稳定错误码（02 §6.1；未映射的一律 'INTERNAL'，绝不缺省）
  message: string;       // 人类可读，可直接展示；已脱敏（不含明文/URL userinfo）
  retryable: boolean;    // 前端据此决定渲染不渲染 [重试]——不要用 HTTP 状态码猜
  traceId: string;       // 服务端日志关联，用户报障时报这个
  details?: Array<{ path?: string; code?: string; message: string }>;
                         // 逐项错误：env 校验（ENV_NAME_RESERVED 等）、镜像 validate 的 errors[]、DTO 字段校验
}
```

| 规则 | 说明 |
|---|---|
| **`code` 永不缺省** | 兜底也要给 `'INTERNAL'`——裸 500 会让前端连「操作失败（错误码 XXX）」都显示不出来（02 §6.2） |
| **`retryable` 是一等字段** | 它来自 `SandboxProviderError.retryable`（04 §4），不是从状态码推断的 |
| **`details` 只在有逐项信息时出现** | 空数组不如不给；`path` 用点号路径（`env[3].key`） |
| **MCP 侧同构** | tool 错误的文本载荷里带同一个 JSON，字段一致，便于 LLM 调用方解析（02 §6.1） |
| **CI 断言** | 25 每个错误码用例除断言 `code` 外，还断言 envelope 五字段完整性 |

### 7.2 通用值类型

> **可扩展类型原则（needs 6/7：sandbox/runtime/image 经 registry 可扩展）**——这决定一个标识该用**封闭联合**还是**开放 id**：
> - **封闭联合**（`'a' | 'b'`）：取值集合**由平台代码固定**、增删必须改代码（如 `SandboxStatus` 状态机、`CloneStatus`、错误分支）。加一个值 = 平台要处理它 = 本就该改代码。
> - **开放 id**（`type XxxId = string`）：取值集合**由 registry 在运行时决定**、第三方注册即生效、平台代码零改动（`ProviderId` / `runtime` id / `image` id）。**provider/runtime/image 必须是开放 id**——把它们写成 `'aio' | 'boxlite'` 这种封闭联合，等于每注册一个新 provider 都要改一次 wire 契约，直接违背"registry 可扩展"（04 §8：第三方注册的 runtime 自动出现、前端零改动）。
>
> ```ts
> type ProviderId = string;   // 已注册的 sandbox provider id；内建 'aio'（默认）/'boxlite'，但取值不封闭——registry 解析
> // runtime、image 同理已是 string；前端下拉的可选值来自 GET /api/providers / GET /api/runtimes / GET /api/images
> //   （运行时数据），不是编译期字面量
> // 内建集合仅作文档记载与默认值，不进类型约束——校验"是否已注册"在后端 registry，不在 TS 联合类型
> // 默认档同理不是前端常量：GET /api/providers 每项自带 isDefault，前端取那一项（§6.1）
> ```
>
> **反例存档（2026-08 已修复）**：前端曾写死 `SANDBOX_PROVIDERS = ['aio','boxlite'] as const` + `DEFAULT_SANDBOX_PROVIDER`，后端 registry 注册的第三方 provider 因此**在 UI 里根本看不见**——这正是本原则要防的那类漂移。现已删除，选项与默认档全部来自 `GET /api/providers`。

### 7.4 WS 帧类型

> **本节是 WS 协议的唯一 canonical 定义**（§3 已删除，其语义表并入本节下方）。两个通道各有一套判别字段：**/terminal 帧用 `type`、/events 事件用 `event`**——这是刻意的（终端是字节流帧协议、事件是业务投影，两套无关的 union，判别字段名不同以防误 parse 到对方）。前后端各持一份 `ws-protocol.ts`，`SYNC WITH` 注释指向本节，改动经 X-Schema-Hash CI 比对（§1、14 §2.5）。

```ts
// —— /terminal 通道 ——（URL query 带 socketSessionKey，服务端生成，06 §6；判别键 type）
type TerminalClientFrame =
  | { type: 'input'; data: string }              // 用户键入（plain string，非 base64）
  | { type: 'resize'; cols: number; rows: number }
  | { type: 'ping' };
type TerminalServerFrame =
  | { type: 'data'; data: string }               // pty 输出（plain string；xterm 直接 write，无需解码；16ms 批量转发 + 前端 rAF 批处理）
  | { type: 'exit'; code: number }               // agent CLI 进程退出（137=OOM 等）——前端据此显示 exit code + 人话解释（08 §8）
  | { type: 'pong' }
  | { type: 'session'; socketSessionKey: string }; // 开会话首帧下发重连凭据

// —— /events 通道 —— 判别键 event
type SandboxEvent =
  | { event: 'sandbox.created'; sandboxId: string; projectId: string }
  | { event: 'sandbox.status_changed'; sandboxId: string; status: SandboxStatus; phase?: string }
  | { event: 'sandbox.removed'; sandboxId: string }
  | { event: 'sandbox.waiting_input'; sandboxId: string; waiting: boolean; sessionId?: string }  // 翻转时推；可丢失；不进 Outbox（06 §8）
  | { event: 'project.clone_progress'; projectId: string; phase: 'cloning' | 'slow' | 'done' | 'failed'; receivedBytes?: number; totalBytes?: number; percent?: number; errorCode?: string }  // git 内部 counting/receiving/resolving 统一投影为 'cloning'，字节进度单独带（03 §7.2）
  | { event: 'runtime-auth.status_changed'; runtime: string }
  | { event: 'runtime.install_progress'; sandboxId: string; runtime: string; status: RuntimeInstallStatus; versionDetected?: string; errorCode?: string };  // 装 CLI 进度（03 §4.3 ③）；进 Outbox；status 复用 §7.1 的 RuntimeInstallStatus
```

**决策记录（2026-08，交叉评审 P0-1）**：`data` 用 **plain string 非 base64**（xterm 直接 write，省一次编解码）；**保留 `exit` 帧**（04 的 `ProcessStream.onExit` 需要一条上报通道，删了前端无法得知进程退出）；终端帧判别键统一 `type`。此前 §3 与本节冲突（§3 用 `payload`/base64/无 exit/`SandboxSummary` 嵌套/clone 6 值）已删 §3、以本节为准。

### 7.5 错误 envelope

见 §6.8（`ErrorEnvelope`：`code / message / retryable / traceId / details?[]`）——所有非 2xx 一律此形状，REST 与 MCP 同构。

### 7.6 类型总量与派生链

| 类别 | 数量 | 单源 |
|---|---|---|
| 枚举 | 19（含 AuthStatus） | 后端 zod `z.enum` / 字面量联合 |
| 通用值类型 | 10（含 `SandboxProviderCapabilities` / `RequiredCapabilities`） | zod schema |
| DTO（请求+响应） | ~40（含 `ProviderDto`） | `createZodDto()`（02 §3） |
| WS 帧/事件 | 2 通道 union（**7** 事件 + 3+3 帧） | 手工同步 `ws-protocol.ts`（14 §2.5，带 X-Schema-Hash 握手） |
| 错误 envelope | 1 | §6.8 |

**一份类型的五处消费**（02 §3）：`zod schema` → ① `createZodDto()` REST DTO → ② `@nestjs/swagger` 反射 → `openapi.json` → ③ 前端 `openapi-typescript` → `openapi.d.ts`；zod schema 又直接作 ④ `@Tool({parameters})` MCP inputSchema、⑤ 运行时 `.parse()` 入参校验。**改一处 zod，五处同步**——CI 漂移检测（§2.1）+ X-Schema-Hash（14 §2.4）双保险。后端实现形态见 [28 类型与领域类型详细设计](../backend/28-类型与领域类型详细设计.md)，前端消费形态见 [前端 07/28]。

> **provider / capabilities 三个类型走的正是这条链，前端一个字都不手写**：`ProviderDto` / `SandboxProviderCapabilities` / `RequiredCapabilities` 在前端分别是生成物 `components['schemas']['ProviderResponseDto']`、该 DTO 的 `['capabilities']`、`components['schemas']['CreateSandboxDto']['require']` 的别名（前端 28 §1）。因此**后端加一位能力位 → `generate:api` → 前端编译期报红**，而不是运行时静默少一位。同理 ④：MCP tool `create_sandbox` 的 `require` 参数与 REST 共用同一份 schema，**无需单独实现即自动获得**（27 §11.1）。
