## 1. 结论先行

| 契约类型 | 方案 | 同步方式 |
|---|---|---|
| REST | `openapi-typescript`（生成纯类型）+ `openapi-fetch`（类型安全 client） | **生成后提交** + CI 漂移检测门禁 |
| WebSocket | 手写 `ws-protocol.ts` 双端同步 + **运行时 zod/valibot 校验兜底** | 手动同步 + CI hash 比对感知变更（文档 14 §2.5 方案 B）；改动频繁时升级为独立协议小包（方案 A） |
| 不采用 | 发布 npm 类型包 | 作为规模扩大后的平滑演进路径预留 |

## 2. REST 契约链路

```
NestJS (@nestjs/swagger)
      │  暴露 /openapi.json
      ▼
前端仓库: pnpm generate:api
      │  openapi-typescript https://backend/openapi.json
      │    -o src/types/generated/openapi.d.ts
      ▼
services/api/client.ts
      │  openapi-fetch 基于该类型创建强类型 client
      ▼
业务代码: client.GET('/api/sandboxes/{id}')  ← 天然类型推导，无需手写 DTO
          （后端设 setGlobalPrefix('api')，openapi paths 含 /api 前缀，见文档 02 §8）
```

选型理由（2026-08 现状）：

- `openapi-typescript`：约 11k star / 50 万周下载，生成**纯类型**（`.d.ts`），零运行时开销；被 TanStack Query 官方文档列为推荐范式之一。
- `openapi-fetch`：与上者配套，无代码生成的运行时薄封装。
- 备选 **Orval**（约 7k star / 35 万周下载）：可直接生成 React Query hooks + MSW mock。需要"开箱即用 hooks + mock"时再评估切换；当前推荐 openapi-fetch 保持数据层显式。

### 2.1 CI 契约漂移检测（关键门禁）

防止"后端契约变化被前端悄悄吃掉"：

```yaml
# static-checks job 内的一步（PR 硬门禁——与文档 09 §1.3、16 §6 的流水线一致）
- run: pnpm generate:api              # 重新从后端 /openapi.json 生成
- run: git diff --exit-code src/types/generated/
  # 有差异 → CI fail → 人工确认并提交更新
```

契约变更因此会出现在 PR diff 中被 review，比 npm 包版本号更新更透明。

### 2.2 为什么不发 npm 类型包

- 双仓库物理隔离，发包意味着版本号对齐、私有 registry、联调时 `npm link`/`file:` hack，对"简易管理入口"级项目工程成本偏重。
- "生成后提交"同样强类型，且改动可 review。
- **演进路径**：若未来多个前端消费同一后端契约，再升级为发布 `@org/api-types`（仅含生成 `.d.ts`，无运行时代码），与现方案不冲突。

## 3. WebSocket 契约

WS 没有 OpenAPI 级别的成熟工具链（AsyncAPI 生态尚不无缝），采用**最低工程成本 + 运行时兜底**：

1. **帧/事件类型的唯一 canonical 定义在 [§7.4](#74-ws-帧类型)**（`TerminalClientFrame`/`TerminalServerFrame` + `SandboxEvent`）——本节此前重复给过一份已删除（交叉评审 P0-1：与 §7.4 冲突过，判别键/字段名/base64/exit/clone phase 都不一致）。后端仓库以 discriminated union 定义、双端各持一份 `ws-protocol.ts`。
2. 双端文件顶部加 `// SYNC WITH shared/10 §7.4 — 修改需双端确认` 注释。
3. **前端对收到的每帧做 zod/valibot `parse`**——类型意外漂移时开发环境立刻抛错，而不是 UI 静默 undefined。
4. **变更感知**：后端 CI 对协议文件算 hash 写入 release asset，前端定时 job 比对，不一致即失败提醒人工同步（文档 14 §2.5 方案 B）；协议改动趋于频繁时升级为独立 npm 协议小包 + Renovate 自动开 PR（方案 A，仅含类型与 zod schema、无运行时代码——与本文档"REST 不发包"的结论不冲突：REST 有 codegen 这条更优路径，WS 没有）。

### 3.1 事件语义表（前端 patch 行为的权威）

| 事件 | 触发时机 | 前端处置 | 后端落点 |
|---|---|---|---|
| `sandbox.created` | 创建请求受理、pending 记录落库后 | 列表插入（或对齐乐观项） | 03 §4 |
| `sandbox.status_changed` | **每一次**状态机转移（含新增的 `preparing-workspace`） | patch 列表项状态 + 驱动阶段进度卡；**`status:'failed'` 时读 `errorCode` 出 P22 §1 人话**，无码才退化成兜底文案 | 03 §4，事务内双写后经 Outbox 投递（13 §3） |
| `sandbox.removed` | destroyed 终态 | 移除列表项 | 03 §4 |
| **`sandbox.waiting_input`** | `running` 子态**翻转时**（不周期性重发） | 列表项切 🔵 等待输入 图标；**仅展示，不改主状态** | 06 §8 网关内存态；判定与误报纪律见 03 §4.1 |
| **`project.clone_progress`** | 异步 clone 期间节流 **1s** 一帧；`phase:'slow'` 在超 10min 时补发一帧。带 `stage`/对象数/速率（03 §7.2★） | 创建弹层进度态；`slow` 出提示、`failed` 就地红字按 `errorCode` 分支引导 | 03 §7.2 |
| `runtime-auth.status_changed` | 凭证过期/吊销/重授权成功 | invalidate `['runtime-auth']` + 横幅 | 05 §5 |
| **`runtime.install_progress`** | sandbox 的 `starting` 段里装 runtime CLI 时，`runtime_installations.status` **每次变更**（`not_installed → installing → installed \| failed`） | 进度卡「启动实例」格子下补一行子文案（「正在安装 claude-code…」）；`failed` 时不单独处置——紧随其后的 `sandbox.status_changed → failed` 才是权威 | 03 §4.3 ③；源事件 `RuntimeInstallationStateChanged`（23 §12），走 Outbox |

两条纪律：

- **`runtime.install_progress` 为什么要单开一条、不复用 `sandbox.status_changed`（S5，[TASK-LAUNCH-DECISIONS](../TASK-LAUNCH-DECISIONS.md) T-3）**：装 CLI 期间 `sandbox.status` 恒为 `starting`，而实测在 AIO 默认镜像上现装 `claude-code` 要 **753 秒（12.5 分钟）**（04 §3 ★1）——没有这条事件，前端只能盯着「启动实例」格子干等 12 分钟。复用 `sandbox.status_changed` 则会推出一串「状态没变的状态变更事件」，破坏本表第 2 行「**每一次**状态机转移」的语义与前端的 patch 行为。它**进 Outbox**（源事件本就是 ✅ Outbox，23 §7.5），因为漏一帧会让进度卡永久停在旧文案。
- **异步失败的错误码有且只有两条出口，两条都必须留（S5 前端反馈）**：provision 在 202 之后才可能失败，**没有同步响应可承载错误码**（04 §4）。① **即时**：`sandbox.status_changed` 在 `status:'failed'` 时带 `errorCode`；② **刷新后可恢复**：`SandboxDto.failureCode` / `failureMessage`（§7.3，源 `sandboxes.failure_code`，13 §2.1.1）。**缺 ① 前端要等下一次轮询才知道原因，缺 ② 用户刷新一次原因就永久消失**。⚠️ 不要以为 `runtime.install_progress` 能兜底——它只覆盖装 CLI 那一段，**`IMAGE_CONTRACT_VIOLATION`（镜像缺 tmux）根本不经过它**，没有 ①② 就只剩兜底人话。`errorCode` 是**码不是句子**：人话由前端按 P22 §1 查表出。
- **`sandbox.waiting_input` 与 `project.clone_progress` 都是"可丢失"事件**——前者丢了下次翻转会重发（且有 REST 派生字段 `waitingInput` 兜底），后者丢了不影响最终 `clone_status`（REST 可查）。因此**都不进 domain_events Outbox**，直接由网关/编排器推送；进 Outbox 的只有状态类事件（需要可靠投递与回放）。
- 高频事件必须节流：clone 进度 1s、waiting_input 只在翻转推——WS 通道与终端数据流共用连接预算，事件洪水会挤压终端体验。

## 4. 与 sandbox 列表更新的配合

- WS 事件通道推送 `sandbox.*` 事件 → 前端 `queryClient.setQueryData` patch 缓存（推送为主）。
- TanStack Query 保留 30–60s 低频轮询兜底（WS 断线期间防陈旧）。

**任务镜像选择器的查询契约（2026-10 迁移）**：`runtimeId` 单独出现仍取可选集；未传时取历史版本。传 `provider` 时优先返回完整历史（含禁用与 `invalid` 版本），每行附 `providerCompatibility?: Record<string, boolean>` 与 `isProviderDefault?: boolean`，供前端解释不可选原因并识别该 provider 配置的默认镜像。两个字段都是可选；未取 provider 投影时缺席。兼容性不代表该版本已启用或验证通过，创建入口仍做准入校验。

> ★ **为什么「启用」不能走 PATCH，而「禁用」可以（2026-08）**
>
> 判据是**要不要换指针**，不是对称性：
>
> - **禁用**是单行操作——把这一行标成不可选，不影响任何别的行。PATCH 天然合适。
> - **启用**在 `unique(image_id, version) WHERE is_active` 之下**必然要停掉同 tag 的现任**。
>   那是一个两行的事务，语义是「换」不是「加」。用 PATCH 表达它，读起来像在改一个字段，
>   实际会让另一行悄悄下线——**副作用大于字面**。
>
> 所以 `PATCH {isActive:true}` 直接 400，`message` 指向 `POST /api/images/:id/activate`。
> ⚠️ 一个动作只有一个入口：`activate` 同时是「更新到新版本」和「回滚到旧版本」，
> 两者在实现上本来就是同一件事（换当前指针），只是方向不同。分成两个端点会让
> 「回滚」看起来是个特殊操作，而它不是。

>

#### 6.6.1 `/api/system/audit` 的双向游标（前端设计驱动，F21-5 §3A）

13 §2.8.2 原写「与 `SandboxJobs` 的游标同语义」，但那套是 **read forward** 的单向 tail（契约 `readJobOutput`：「Read forward from `cursor`，省略则从头读」）——它只覆盖「拉更新的」。**审计面板要两个方向**：增量刷新拉更新的，向下滚动拉更老的。一个 `cursor` 参数表达不了，故拆开：

| 参数 | 方向 | 语义 | 谁用 |
|---|---|---|---|
| `since=<seq>` | 向新 | 返回 `seq > since` | 增量刷新（与 `SandboxJobs` 的 forward 同源） |
| `before=<seq>` | 向老 | 返回 `seq < before` | 历史滚动（本平台此前**没有**这个方向） |
| 都不传 | — | 从最新开始 | 首屏 |

- **互斥**：同时传两个 → 400 `VALIDATION_FAILED`。
- **`from` / `to`（ISO 时间）与游标正交**：游标管**翻页位置**，时间范围管**过滤条件**，两者可同时传。⚠️ 别用 `to` 代替 `before` 翻页——13 §2.8.2 已定「不用时间戳翻页，同毫秒多条会漏」；也别把时间范围折算成 seq，`at` 与 `seq` 只是**近似**同序（并发插入下可微小乱序），折算会在边界上悄悄吞掉记录。走 `idx(at)`，实测 20 万条下各类筛选均 < 0.5ms。
- **响应恒按 `seq` 降序**（最新在前），与方向无关——UI 渲染顺序因此统一，`since` 的结果 prepend、`before` 的结果 append，两边都不需要再排。
- `limit` 默认 **200**（= P21-5 §10.2 的「最近 200 条」），上限 500。
- **`severity` 是逗号分隔的多值**（`info` / `warn` / `error` 的任意子集），服务端按 `WHERE severity IN (...)` 过滤：`severity=error` 单值照旧、`severity=warn,error` 即产品要的「**仅告警**」；重复值去重；含非法值 → 400 `VALIDATION_FAILED`（与互斥那条同一套信封，带 `sideEffectFree: true`）。⚠️ 因此它在 `openapi.json` 里**不是 enum，而是一个带说明的 string**——query enum 描述不了「子集」，声明成 enum 会让 codegen 出的签名拒掉唯一能表达「仅告警」的取值。

⚠️ **「仅告警」必须在服务端过滤，客户端裁剪是一条死路。** 等值过滤时前端只能不带 `severity` 拉回一页（最多 500 条）再自己裁，而那一页是**最近的** N 条：平台平稳跑一周、最近 200 条全是 info，昨天那次 provision 失败落在更老的位置 ⇒ 用户勾「仅告警」得到空列表 + `hasMore:false`，读出来的结论是**「平台从没告警过」**，而告警就在第 201 条。服务端 `IN (...)` 之后 `ORDER BY seq DESC LIMIT n+1` 扫的是**匹配行**的最新一页，「空 + `hasMore:false`」才真的等于「全表没有这一档」；客户端裁剪那套（以及它带出的「裁完为空但还有更老的」翻页入口缺失）也随之消失。


⚠️ **`since` 不是「顺序读取」游标，它是「最新 n 条 + 下界过滤」。** 因为响应恒按 `seq` 降序再 `LIMIT`，`since=X` 返回的是**比 X 新的那些里最新的 n 条**，而不是紧接着 X 往上数的 n 条。这一条决定了两件事，它们其实是同一件事的两面：

1. 拉满 `limit` 就说明中间漏了（下面这段）；
2. **填补断层不能用 `since`**——`since: gap.afterSeq` 取回的正是顶上已有的那一批，洞一条都不会少。填洞要用 `before: gap.beforeSeq`（向老翻一页，逐步收窄）。⚠️ 这个错误的代价是「按钮点了、请求发了、列表看着刷新了，洞还在」——F21-5 §5 此前正是这么写的，已订正。

⚠️ **`since` 拉满 `limit` 意味着有断层，这一点必须显性传达。** 异常风暴时 30s 内产生 >200 条事件——那恰恰是最需要看清的时刻——一次拉不完。若前端只 prepend 一页就停，列表中间会出现**看不见的空洞**：UI 上是连续的，实际漏了。故响应带 `hasMore`，且**前端不得假装连续**（消费纪律见 F21-5 §3A）。

⚠️ **`seq` 是公开列，不是 opaque token**：前端要按它排序、比较、判断断层，所以直接用数字。这与 `JobCursor` 的「stored, never parsed」是**刻意的不一致**——那边游标是 stdout/stderr 双偏移的内部结构，这边就是一列主键。

### 6.8 统一错误响应 envelope（审计 P1-4）

**所有非 2xx 响应一律是这个形状**，无例外。**codegen 可得性**：`ErrorEnvelope` 必须作为具名 component 进 `openapi.json` 且被所有 error response 引用（`@nestjs/swagger` + nestjs-zod `patchNestJsSwagger()` 才能把 zod 的 enum/discriminatedUnion 如实反射）——否则前端 `components['schemas']['ErrorEnvelope']` 取不到、退化成手写（交叉评审 P1-4）。

```ts
interface ErrorEnvelope {
  code: string;          // 稳定错误码（02 §6.1；未映射的一律 'INTERNAL'，绝不缺省）
  message: string;       // 人类可读，可直接展示；已脱敏（不含明文/URL userinfo）
  retryable: boolean;    // 前端据此决定渲染不渲染 [重试]——不要用 HTTP 状态码猜
  sideEffectFree?: boolean;
                         // true = 这次请求在产生任何副作用之前就被拒（不进调度、不落库、
                         // 不调 provider.create，04 §5）。缺席 = 未表态 ⇒ 按「可能有副作用」读
  traceId?: string;      // 服务端日志关联，用户报障时报这个。**REST 上一定有**（ErrorEnvelopeFilter 统一注入，10A §3）；
                         // 类型仍是 optional 因为本形状与 MCP 共用，而 MCP tool 不经那个 filter——标 required 会对 MCP 撒谎
  details?: Array<{ path?: string; code?: string; message: string }>;
                         // 逐项错误：env 校验（ENV_NAME_RESERVED 等）、镜像 validate 的 errors[]、DTO 字段校验
                         // ⚠️ 只放「路径 + 规则 + 期望」，绝不放用户提交的值（见下 §「DTO 校验」）
}
```

| 规则 | 说明 |
|---|---|
| **`code` 永不缺省** | 兜底也要给 `'INTERNAL'`——裸 500 会让前端连「操作失败（错误码 XXX）」都显示不出来（02 §6.2） |
| **`retryable` 是一等字段** | 它来自 `SandboxProviderError.retryable`（04 §4），不是从状态码推断的 |
| **`sideEffectFree` 同样是一等字段** | **「被拒」与「失败」不是同一件事**：零副作用的拒绝没有 id、列表里不留记录、没有任何东西可供 [重试] 作用，正确呈现是**就地改请求**；而「已受理、中途失败」才该出失败卡 + [重试]。前端曾用 `httpStatus === 409` 当代理来区分，**而四条门口拒绝里它只覆盖到一条**（见下表）——状态码是传输事实，「平台有没有改过状态」是平台事实，只有平台能表态 |
| **`sideEffectFree` 缺席 = 保守读法** | `undefined` 不是 `false`，是**未表态**，消费方一律按「可能有副作用」处理（= 本字段存在之前的行为）。**它是 optional 正因如此**：改成必填会逼几十条异常路径去表态一件它们不知道的事，猜错的那条会告诉用户「什么都没发生」——而漏标只是退化回现状。**少报是降级，多报是撒谎** |
| **`details` 只在有逐项信息时出现** | 空数组不如不给；`path` 用点号路径（`env[3].key`） |
| **`details` 不回显用户提交的值** | 只放**路径 + 规则 + 期望**。zod 的 issue 原样透出会带 `received`（枚举/字面量/联合），而校验失败的字段最可能是 prompt 正文或明文凭证；信封会进渲染、进日志、进用户截图。例外只有类型名（`expected`/`received` 是 `string`/`number` 这类**类型**，不是值）——详见 [backend/04 §4.2](../backend/04-Contract与Registry扩展体系.md) |
| **DTO 校验失败也是信封** | `VALIDATION_FAILED` / 400 / `retryable:false` / `sideEffectFree:true`（04 §4.2）。此前它出线的是 `nestjs-zod` 默认的 `{statusCode, message:'Validation failed', errors}`——不是信封，于是**每个端点的每一次字段校验失败**都被前端压成「请求失败（HTTP 400）」 |
| **MCP 侧同构** | tool 错误的文本载荷里带同一个 JSON，字段一致，便于 LLM 调用方解析（02 §6.1） |
| **CI 断言** | 25 每个错误码用例除断言 `code` 外，还断言 envelope **必填**字段完整性；`sideEffectFree` 是可选字段，只在门口拒绝上断言（见下表与守卫用例） |
| **★ 由 filter 结构性保证，不靠逐处自觉** | 「所有非 2xx 一律此形状」此前**不成立**：实测同时存在四种形状，其中**裸 Nest 异常 26 处**是最多的一类，前端 `isErrorEnvelope` 认不出就整条替换成「请求失败（HTTP 404）」——后端那句指名道姓的话就此丢掉。现由全局 `ErrorEnvelopeFilter` 在出线前统一归一（与 `sideEffectFree` 由**位置**挣得、`atDoor` 出口盖章是同一手法，只是用在传输层）。**逐个改 26 处 throw 是 26 次可以漏的机会，而且下一个人写 `throw new NotFoundException` 时不会想起这条约定** |
| **★ filter 不给 `sideEffectFree` 兜底** | 传输层**不知道**平台有没有改过状态，只有位置知道。猜 `true` 会让本该给 [重试] 的失败变成「就地改配置」，半成品沙箱就没人回收——与上面「缺席 = 保守读法」是同一条纪律的两半 |
| **★ 已是完整信封的原样放行** | 门口拒绝与 zod 管道自己就知道 `sideEffectFree`/`details`，filter 不插手 |

#### 错误的四类（按**用户该做什么**分，不按 HTTP 状态分）

`retryable` / `sideEffectFree` 两个字段真正要表达的就是这四类：

| 类 | 含义 | `retryable` | `sideEffectFree` | 前端呈现 |
|---|---|---|---|---|
| **A 门口拒绝** | 请求本身不被接受，平台没动过任何状态 | `false` | `true` | 就地提示改配置，不出失败卡、不给 [重试] |
| **B 已受理后失败** | 平台改过状态，中途失败 | 视情况 | 不带 | 失败卡 + [重试]（仅可重试时） |
| **C 前置条件不满足** | 状态机不允许（如非 `ready` 态 sync） | `false` | `true` | 就地提示 **+ 指出什么时候可以** |
| **D 基础设施故障** | 网络/磁盘/超时 | 多为 `true` | 视位置 | 人话 + [重试]/[诊断] |

**A 与 C 的区别值得写明**：A 是「请求内容不对」（分支不存在、runtime 未注册），
C 是「请求没错但此刻不行」（项目还在克隆）。两者都零副作用，但 **C 要多说一句「什么时候可以」**。
C 类此前全是裸异常（`sync` 非 ready、`convert-to-empty` 非 failed、`retry-clone` 非 failed），
现由 filter 归成 `INVALID_STATE`（409），且 **message 原样透传**——那句话往往是唯一说清「到底哪儿不对」的东西。

⚠️ **`ALREADY_INITIALIZED` / `OFFLINE_NOT_ACKNOWLEDGED` 必须是两个码，⛔ 不许合并回 `INVALID_STATE`（2026-08 真机验证补）。**
它们**曾经共用 `INVALID_STATE`**：同一个端点、同一个 409、同一个码，而调用方要做的事**恰好相反** ——
一个「放行进工作台」，一个「留在向导里把那句话说给用户看」。
用一个码表达两件需要不同处理的事，等于逼**每个**调用方在拿到 409 之后再打一次 `GET /api/system/init-status`
去二次探测自己拿到的是哪一种；而不做那次探测、照着「409 = 已初始化 ⇒ 放行」写的那一版（F21-8 §8 约束 3 的原文），
会把一台**根本没初始化**的机器放进工作台 —— 用户看到工作台、下次刷新又被弹回向导，**中间一句错误都没有**。
加码的代价（本表一行 + A5 对账）是**一次性**的，二次探测的代价是**每个调用方每一次**。
这与上面四个 `PRESET_IMAGE_*` 不许合成一条「镜像不可用」是同一条纪律：**闭集的价值在于分得开，不在于短**。

⚠️ **`BINARY_NOT_FOUND` / `PARSE_ERROR` 今天在源码里「声明了、但一处都没抛」。**
它们是 `AdapterAuthErrorCode`（`runtime/src/domain/errors/adapter-auth.error.ts`）这个**六成员闭集**的一部分，
所以本表收录它们——A5 对账的是**源码里声明的码集合**，一个闭集成员即使还没有 throw 处也已经是契约的一部分。
但要如实记两笔：① 全仓没有 `throw new AdapterAuthError('BINARY_NOT_FOUND', …)`；
② `runtime-application.service.ts` 的 `mapAdapterError` 只给六个成员里的**四个**写了 case，
这两个落在 `default: return e` ⇒ 真抛出来会逃过 HTTP 映射，被 `ErrorEnvelopeFilter` 兜成 `INTERNAL`，
**用户拿不到这两个码本来要说的那句话**。补 throw 处时必须同时补 `mapAdapterError` 的 case。

⚠️ **本表 2026-08 因 A5 扫描器修复新增四行**（`SCHEMA_MISMATCH` / `SANDBOX_REQUIRED` / `BINARY_NOT_FOUND` / `PARSE_ERROR`）；2026-09 随终端多标签新增一行（`TERMINAL_TARGET_INVALID`，06 §5）。
它们**一直**在源码里，是门禁没看见：`ERROR_CODE_SOURCES` 曾是一份手写路径清单（漏了 `runtime/src/domain`），
而联合类型的上下文判据曾要求类型名里含 `Code`（`WsHandshakeRejection` 不含）。
⚠️ 这次的失效方式是**静默**的——门禁照常报「集合相等」，而 `AdapterAuthErrorCode` 那个六成员闭集**被扫了三分之二**。
病因与 `GIT_TRACE` 那份四字面量清单同源：**枚举本身就是病因**（03 §7.3 G）。现已改为全 `src` 目录扫描 + 形状判据。

⚠️ **`—` 表示「不带该字段」，不是 `false`**。`sideEffectFree` 缺席 = 未表态，按「可能有副作用」读（见上表）。

⚠️ **B 类多数不是 REST 响应**：它们走沙箱状态机与 WS `sandbox.status_changed.errorCode`（04 §4 闭集）。
放进同一张表是因为**前端的文案表按码查，不分传输**——同一个码在两条路上出现，用户看到的该是同一句话。

⚠️ **四个 `PRESET_IMAGE_*` 走的是第三条传输：`POST /api/system/diagnose` 的 SSE `check` 帧**
（`DiagnoseCheckFrame.errorCode`，帧契约在两仓的 `sse-protocol.ts`，B5 对账）。它们进本表的理由与上一段完全相同——
**码表按码查、不分传输**；而它们**必须是四个码而不是一个**，是 P21-5 §9A 的硬性要求：
五步的下一步动作完全不同（改配置 / 推镜像 / 换成自建那张 / 重启平台 / 只是等一会），
合成一条「镜像不可用」等于把诊断退化成一个红灯。

⚠️ **诊断的其余七项刻意不发码**，所以本表里没有它们的行。那七项的结论天然带着这一次实测出来的具体数字
（哪个端口、被谁占、还剩多少 GB），按码查一句固定文案反而更差；为它们凭空造一批只在这一个端点出现、
前端也不会分支的码，只会让本表变长而没有消费方——那正是下面那一节存在的理由。
⚠️ 02 §5.3 的示例帧里写着 `"errorCode":"NETWORK"`，**那是示意而不是契约**：`NETWORK` 从来不在本表里，
本轮实现也不产出它（已在 02 §5.3 就地标注）。

⚠️ **第 5 步（未 staged）没有码，因为它不是失败**：它是 `status:'info'`「首个任务需要数分钟准备镜像」
（实测 13GB 镜像冷启动 190 秒）。给它一个错误码就等于承认它是错误，而渲染成 ⚠️/❌ 会让用户去修一个不需要修的东西。

> **为什么单开一节，而不是往上表补行**：上表是 **A5 门禁的对账基准** ——
> 它与 api 源码扫出来的错误码集合**逐条全等比较**。往里加一行没有产出方的码，A5 当场红，

> **这条规则做过变异验证，不是读代码读出来的**（原文的两句实测存档，数字是当时的）：
> ① 把 `REF_NOT_FOUND` 塞进当时的主表 ⇒ A5 立刻红（「表 46 行 / 源码 45 个码，差集 1 条：
> 文档表有、源码无」）；② 它留在本节 ⇒ A5 仍是「45 行，集合相等」。
> **「它红过吗」是这个仓对任何绿灯的最低要求**（[LIVE-RUN-FINDINGS](../LIVE-RUN-FINDINGS.md) 共性 2）。
> 本轮的反向验证同样跑过：九个码的产出方一写出来，A5 立刻报「源码 60 个码，表 49 行，
> 差集 11 条：源码有、文档表无」——**门禁不是在挑刺，它是在说这张表该更新了**。
>
> **但「不进主表」不等于「不用管」。** 这正是 `BRANCH_NOT_FOUND` 那次事故的另一半形状：
> 一个码在某一侧被当成已定案，另一侧压根不知道它存在，两边各自完整、合起来漏一条。
> 所以它们记在这里，带齐落地时要填进主表的四个字段，**不留在别人脑子里**。

**落地纪律（三条，缺一条这张表就会变成新的谎话）**：

1. **码一旦有了产出方，必须从本表移进上面的主表**，并补齐「何时出现」一列。本表只登记「设计已定、代码未有」的码，**不是第二张常驻码表**。
2. **同时把前端文案表补齐**（`sandboxErrorCopy.ts` 的 `COPY_TABLE`）。后端产出 / 本表 / 前端文案，三处齐了才算落地——这是 A5 存在的全部理由。
3. ⚠️ **扫描范围必须能看见新模块**。原文这里要求「落地时同步改 `scripts/docs-check.mjs` 的 `ERROR_CODE_SOURCES`」，因为那曾是一份**硬编码路径清单**、里面没有 image 模块——不加就扫不到产出方，于是**A5 会一直是绿的，而绿的原因是它根本没在看**。
   **这条已经不需要做了，但不是因为它不重要**：`ERROR_CODE_SOURCES` 本身在 2026-08 被删掉，换成 `errorCodeSourceRoots()` 遍历 `apps/api/src` + 每个 `packages/*/src` 与 `packages/modules/*/src`——**枚举本身就是病因**（同 `GIT_TRACE` 那份四字面量清单，03 §7.3 G）。本轮 `packages/modules/image/**` 一建出来就被扫到了，无需任何门禁改动，A5 当场从「集合相等」变成「差集 11 条」。
   这正是 [LIVE-RUN-FINDINGS](../LIVE-RUN-FINDINGS.md) 共性 2（「证据本身可能是假的，绿灯不等于覆盖」）在门禁自己身上的版本：**门禁的扫描范围写窄了，它就会指着一张不完整的表说它是对的**（第一版 A5 把范围只写到 `errors.ts`，结果 10 个码全部误报，是同一个坑的另一面）。

#### 「门口拒绝」（零副作用）全量清单 — `POST /api/sandboxes` 创建门（04 §5）

|---|---|---|---|---|
| provider 不在注册表 | `UNKNOWN_PROVIDER` | 400 | ❌ | ✅ |
| runtime 不在注册表 | `UNKNOWN_RUNTIME` | 400 | ❌ | ✅ |
| 镜像引用含控制字符 | `INVALID_IMAGE_REFERENCE` | 400 | ❌ | ✅ |

| 项目尚不能接任务（I-PRJ） | `PROJECT_NOT_READY` | 409 | ❌ | ✅ |
| 请求的分支不在基线里 | `BRANCH_NOT_FOUND` | 400 | ❌ | ✅ |

> **门口拒绝一律 `retryable: false`，这是门的性质而非逐条判断**：门给的答复是「这个请求本身不被接受」，原样再发一次必然同样被拒——要变的是请求或它的前置条件，不是重试次数。同 `UnknownRuntimeError.retryable = false` 的理由（04 §4）：每按必败的 [重试] 比没有按钮更糟。
>
> **⚠️ 上表里三条此前根本不产出 envelope（2026-08 修复）**：`UNKNOWN_PROVIDER` / `INVALID_IMAGE_REFERENCE` / `UNKNOWN_RUNTIME` 是裸 `BadRequestException(string)` 抛的，出线的是 Nest 默认 `{statusCode, message, error}`——**没有 `code`、没有 `retryable`**。前端 `toApiError` 判定「不是信封」后整体替换成 `{code:'UNKNOWN', message:'请求失败（HTTP 400）'}`，于是后端那句指名道姓的话（`unknown runtime 'shell'`）**从来没到过能据此行动的人眼前**。**给一个没人读的 body 加字段等于没加**——所以这三条先被改成真信封，字段才有意义。这也顺带证明了「缺席 = 保守读法」的设计是对的：漏改一处，前端读到 `undefined`，落回今天的行为（错，但不是谎）；若字段必填或默认 `true`，同一处遗漏就变成对着没人检查过的请求说「什么都没创建」。
>
> **DTO 校验失败走的是另一条路，但落到同一个信封（2026-08）**：上表七条是**创建门**里的拒绝；而 `POST /api/sandboxes` 的 `initialPrompt` 超过 8000 字符这类**字段级**违规，在 controller 之前就被全局 zod 管道拒了，根本到不了 `admit`。它现在同样产出信封——`VALIDATION_FAILED` / 400 / `retryable:false` / **`sideEffectFree:true`**，后者在这里是**构造上**成立的（管道跑在 controller 之前，没进 application service、没落库、没进调度），与 `atDoor` 同一套「位置换取标记」的道理。`message` 指名字段与规则（「请求参数 initialPrompt 长度超过上限 8000 字符」），`details[]` 给逐项 `{path, code, message}`。权威说明见 [backend/04 §4.2](../backend/04-Contract与Registry扩展体系.md)。
>
> **落地形态：位置换取，而不是逐点标注**。创建门收敛成 `SandboxApplicationService.admit` 一个方法——它不持 `uow`、不写库、不调度、不碰 `provider.create`，所以「零副作用」对**这里抛出的每一条**都是构造上成立的；`atDoor` 在出口处把这个结构事实翻成 `sideEffectFree`。创建门的标记由这一出口统一提供；zod 校验管道和初始化等领域也会在确认无写入的拒绝路径给出标记，不能据此声称全库只有两处。于是**将来新增的门口校验只要写在这个方法里就自动标对**，作者根本不需要知道有这个字段——而逐点标注正是三条漏标的成因。新版验收见 `api/acceptance/sbx/protocol/task-lifecycle.spec.ts` 与 `api/acceptance/prj/protocol/project-creation-recovery.spec.ts`：通过真实 HTTP 检查不存在项目、未知 runtime 和未就绪项目的拒绝信封，并验证 provider 未执行、失败项目没有新增任务。结构事实另由生产 admit 实现复核，不将这些有限场景称为任意未知拒绝实跑。

## 7. 通用（wire）类型索引与消费

wire 唯一来源是后端 `packages/contracts/src/schemas/` 的 zod 定义与对应 REST DTO。本文给类型索引和语义边界；不维护另一份手写 DTO。REST 经 OpenAPI 生成前端类型，WS/SSE 使用当前 canonical 协议。端点见 §6，具体生成类型消费见 [前端28](../frontend/28-前端类型详细设计.md)。

### 7.1 枚举（字面量联合）

枚举定义位于 `schemas/enums.ts` 及所属领域 schema；前端从生成 DTO 字段派生。例如 SandboxStatus 取 SandboxResponseDto.status，CloneStatus 取 ProjectResponseDto.cloneStatus，CredentialStatus 取 RuntimeResponseDto.credentialStatus。

沙箱生命周期仍是 pending/scheduling/preparing-workspace/creating/starting/running/idle/stopping/stopped/destroying/destroyed/failed。waitingInput 是观察字段，不属于第十三种生命周期态。无头任务、自动化运行、诊断、凭证摘要有各自状态，不能拿沙箱状态 union 代替。

runtime、provider 和镜像 registry 标识是开放字符串；状态机、method、调度种类和错误语义由平台定义。前端不枚举可注册对象，也不因某个能力位存在就自行出现尚无业务端点的按钮。

### 7.2 通用值类型

ProviderResponseDto 下发 name、isDefault 及完整 capabilities。当前七位为 spawnTty、volumeMount、updateResources、pauseResume、snapshot、watchEvents、headlessTask。CreateSandboxDto.require 只接受前五位的可选要求，不包括内部 watchEvents 或无头运行能力开关；未声明的键不作为公开旋钮。

镜像解析内部 ImageRef 是 name 与可选 tag/digest；wire 请求的 ref/image 是坐标字符串。manifest 响应单独返回固定 digest、版本与资源默认值，不能把旧 `{registry, repository, tag, digest}` 示例当作所有层通用 DTO。

MaskedGitCredentialResponseDto 的 knownHosts 是实际 KnownHost 条目数组（host/keyType/fingerprint/firstSeenAt），不是一段字符串；lastUsedAt 可缺席或 null。掩码与公开 host 指纹不是 secret；API Key、Token、私钥及 Secret 原文都不回读。

AuthChallengeResponseDto 有 challengeRef、method、kind、instructions 和可选验证 URL/设备码/到期时间。method 与生效 mode 是不同事实；缺少 expiresAt 时不编造倒计时。分页仅用于真实分页端点，不能给裸数组列表加不存在的信封。

### 7.3 各上下文 DTO（请求体 + 响应体）

以下均为当前 OpenAPI 的真实 schema 名；前端通过 `components['schemas'][…]` 取别名。DTO 映射在 `packages/modules/<domain>/src/interface/http/dto/`，平台系统 DTO 在 `apps/api/src/platform/`。

| 领域 | 请求 schema | 响应 schema |
|---|---|---|
| 沙箱 | CreateSandboxDto、DestroySandboxDto、ExecInSandboxDto | SandboxResponseDto、ProviderResponseDto、ExecResultResponseDto |
| 无头任务 | RunAgentTaskDto | AgentTaskResponseDto |
| 项目与成果 | CreateProjectDto、DeleteProjectDto | ProjectResponseDto、ProjectDeletionPreviewResponseDto、RetainedVolumeResponseDto |
| Agent 登录与凭证 | BeginAuthDto、CompleteAuthDto、SubmitSecretDto、SetAuthModeDto | RuntimeResponseDto、AuthChallengeResponseDto、AuthStatusResultResponseDto、MaskedCredentialResultResponseDto、RuntimeSettingsResponseDto、RuntimeCredentialDeletionPreviewResponseDto |
| Git 凭证 | CreateGitCredentialDto、InlineGitTestDto、StoredGitTestDto | MaskedGitCredentialResponseDto、StoreGitCredentialResponseDto、GitTestResultResponseDto |
| 镜像 | RegisterImageDto、PatchImageDto | ImageManifestResponseDto、RegisterImageResponseDto、ValidationOutcomeResponseDto、RevalidateOutcomeResponseDto、CheckImageUpdateResponseDto、ImageDeletionPreviewResponseDto |
| 自动化 | CreateAutomationDto、UpdateAutomationDto、WebhookTestRequestDto | AutomationResponseDto、AutomationRunResponseDto、PaginatedAutomationRunsDto、AutomationAttentionItemResponseDto、AutomationDeletionPreviewResponseDto、WebhookTestResultDto |
| 初始化与系统 | InitRequestDto、UpdateSystemSettingsDto | InitStatusResponseDto、SystemSettingsResponseDto、SystemResourcesResponseDto、SystemProvidersResponseDto、ProviderLogsResponseDto、SystemVersionResponseDto、AuditListResponseDto |
| 访问控制 | UnlockRequestDto、AccessPasscodeRequestDto | AccessPasscodeResponseDto |

```ts
import type { components } from '@/types/generated/openapi';
type SandboxDto = components['schemas']['SandboxResponseDto'];
type CreateSandboxRequest = components['schemas']['CreateSandboxDto'];
type AuditEventDto = components['schemas']['AuditListResponseDto']['items'][number];
type ImageConfig = NonNullable<components['schemas']['PatchImageDto']['imageConfig']>;
```

当前字段语义：

- CreateSandboxDto 的 availableRuntimes 不存在；SandboxResponseDto 的该字段是默认 runtime 与实际注入成功项的并集，默认 runtime 出现在其中不表示已经登录。image 可选，传坐标而非 manifest id；provider 缺省取配置的默认 registry 档。
- SandboxResponseDto 使用已有 name、status、waitingInput、availableRuntimes、超时/版本/失败来源/自动化来源、hasRun 和可选 createdAt/updatedAt。没有 lastActiveAt；响应不回显 initialPrompt。image/imageId/imageDigest/imageIsBuiltin 是锁定快照，缺席不推断。
- AgentTaskResponseDto 的 artifact.modifiedAt 可选；成果响应包含 sandboxName 与实际自动化来源，任务弱引用不阻止查看已保留成果。
- SubmitSecretDto 支持 api-key 与 access-token-paste，method 保留真实值；Git 测试按 source 判别 inline/stored，不能只传 repoUrl 或用假仓库尝试 secret。GitTestResultResponseDto.message 可选。
- ValidationOutcomeResponseDto 的 errors/warnings 是 ValidationIssue 数组，条目为 `{path?, code, message}`，不是字符串数组；该 DTO 没有 findings 或 supportedRuntimes 字段，支持的 runtime 由 manifest 返回。
- PatchImageDto 的 env 每项 value 必填、secret 可选；已存 Secret 的空 value 表示保持密文，输入新值才覆盖。cmdOverride 是 string[]。每版配置独立，更新继承不覆盖目标用户编辑。
- SystemResourcesResponseDto 的 RAM/disk 使用 totalBytes/usedBytes/availableBytes，单位为 bytes；镜像 resourceDefaults 的配额单位另行定义，不能混用。真实调度容量与使用率分开；SystemProvidersResponseDto 下发失败率阈值与窗口。unknown/no-sample 不折成零或正常。日志不可读带实际原因，诊断清单来自首帧。

### 7.4 WS 帧类型

完整 canonical 位于 `api/packages/contracts/src/ws-protocol.ts`、`sse-protocol.ts`；前端同形文件为 `web/src/types/ws-protocol.ts`、`sse-protocol.ts`，B4/B5 门禁对账。此处不复制一套容易过期的 union。

`/terminal` 使用 type 判别，输入/输出为字符串字节；session 凭据由服务端生成，刷新断连只 detach，主动关闭独立 shell 才销毁该会话。exit 的 code 是 number，原生空退出码在 gateway 转为 -1，不写成成功；该帧没有独立 signal 字段。shells 的 null 是无法查询，不等于空列表。

`/events` 使用 event 判别。status_changed、waiting_input、clone_progress、runtime-auth、runtime.install_progress、instance_progress 各有独立载荷；创建受理响应也可能比后续运行事件晚到，不能反过来覆盖已存在的较新投影。重连重取以及 REST/事件的竞态以实际验收为准。

`/tasks` 输出使用 taskId 与单调 seq；fromSeq 是排他的已有游标，caught_up 表明实际回放边界；退出、取消和输出断线分别处理。REST 上的最后游标不是尚未持有输出的可跳过位置。

诊断与预制镜像 SSE 分开。诊断 start 给本轮 checks/timeoutMs，结果按 id 归位，done 才是完整结束；缺项或断流不能伪装全部通过。超时预算取 PARAM.DIAG_ITEM_TIMEOUT_MS。预制镜像阶段保留真实来源、进度/未知百分比与失败位置，不能编 ETA。

### 7.5 错误 envelope

ErrorEnvelope 形状为 code、message、retryable 和可选 traceId/details/sideEffectFree。HTTP、MCP 与 WebSocket 的错误出口按各自传输协议表达同一业务含义，不把裸 Nest 文本当统一信封。

code 用于业务分类与可执行文案；details[].path/code 定位字段。环境变量 ENV_* 原因已有实际产出方，顶层仍是 VALIDATION_FAILED。创建门与字段校验的 sideEffectFree 只在结构上无写入/调度时给出；未带标记不可推断零副作用。开放或未知错误由前端保守兜底，不从 message 反解析码。

### 7.6 类型总量与派生链

不维护手写的「19 枚举、42 DTO、8 事件」总量；新增端点、嵌套 schema 与协议分支可能改变统计而不改变现有行为。实际集合由 OpenAPI components、领域 schema、canonical 协议和 typecheck 给出。

派生链为 zod → createZodDto/OpenAPI → openapi-typescript → 领域别名 → service/hook → view model。生成 DTO 不表示已验证运行时值，也不表示执行过完整 AC。真实服务/SQLite/协议、新组件交互与全稿浏览器分别记录证据，旧测试数量不作为新验收结果。
