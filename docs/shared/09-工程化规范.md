### 1.1 工具链

| 环节 | 工具 | 关键配置 |
|---|---|---|
| Lint | ESLint（flat config）+ eslint-plugin-boundaries | 分层规则 error 级，规则详见文档 07 §4 |

| 提交规范 | commitlint（可选） | commit-msg hook |
| CI | GitHub Actions | 全量门禁 |

### 1.2 precommit

```json
// .lintstagedrc.json
{
  "*.{ts,tsx}": ["eslint --fix --max-warnings=0", "prettier --write"],
  "*.{json,md,css}": ["prettier --write"]
}
```

```bash
# .husky/pre-commit
npx lint-staged

# .husky/commit-msg（可选）
npx --no -- commitlint --edit $1
```

注意：pre-commit 阶段的 eslint 只跑**语法层规则**（type-aware 的 `no-unsafe-*` 等留给 PR CI，规则拆分见文档 14 §4）——保证提交速度不被 type-aware lint 拖慢。

### 1.3 CI（GitHub Actions）

```yaml
name: CI
on: [pull_request, push]
jobs:
  lint-typecheck-test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 22, cache: 'pnpm' }   # Node 22 LTS，前后端统一
      - run: pnpm install --frozen-lockfile
      - run: pnpm lint --max-warnings=0   # boundaries 违规直接 fail，无法以 warning 绕过
      - run: pnpm typecheck               # tsc --noEmit
      - run: pnpm prettier --check .
      - run: pnpm run check:story-coverage  # 每个 view 必须有 story（文档 12 §2.5）
      - run: pnpm generate:api && git diff --exit-code src/types/generated/
        # 契约漂移门禁（文档 10 §2.1），属 static-checks 第一道门（与文档 16 §6 一致）
      # 测试分四道门并行/串行执行，完整 workflow 见文档 12 §5 / 16 §6：
      # static-checks → (bun unit-tests ∥ storybook-tests) → playwright e2e → build
```

关键原则：

- **`--max-warnings=0`**：架构违规（boundaries）必须是 error 且无法以 warning 形式混过合并。
- **build 进 CI**：xterm 等 client-only 依赖的 SSR 边界问题只有 `next build` 能暴露。
- 测试执行顺序（bun 单测 → Storybook 逐层验证 → Playwright 集成）待文档 12 落定后补充到此 workflow。

### 1.4 分层制度的"强制"闭环

```
编辑器（eslint 插件实时提示）
  → pre-commit（lint-staged 增量拦截）
    → CI（全量 lint + typecheck + build 门禁）
      → 分支保护（required check，不过不给合并）
```

**四级拦截**保证"视图/逻辑分离"不是口头约定而是机器强制。（术语区分：这里的"四级拦截"是拦截时机维度；文档 12 §5 的"CI 四道门"是 CI 内部阶段划分，两者是不同维度的四。）

### 2.2 DDD 分层 lint 约束（boundaries 配置思路）

```js
settings: {
  'boundaries/elements': [
    { type: 'domain',         pattern: 'packages/modules/*/domain/**' },
    { type: 'application',    pattern: 'packages/modules/*/application/**' },
    { type: 'infrastructure', pattern: 'packages/modules/*/infrastructure/**' },
    { type: 'interface',      pattern: 'packages/modules/*/interface/**' },
    { type: 'shared-kernel',  pattern: 'packages/shared-kernel/**' },
    { type: 'contracts',      pattern: 'packages/contracts/**' },
  ],
},
rules: {
  'boundaries/element-types': ['error', {
    default: 'disallow',
    rules: [
      { from: 'domain',         allow: ['domain', 'shared-kernel'] },
      { from: 'application',    allow: ['domain', 'contracts', 'application', 'shared-kernel'] },
      { from: 'infrastructure', allow: ['domain', 'contracts', 'infrastructure', 'shared-kernel'] },
      { from: 'interface',      allow: ['application', 'interface', 'contracts'] },
      { from: 'contracts',      allow: ['contracts'] },       // contract 禁止反向依赖任何实现
    ],
  }],
}
```

补充禁令（`no-restricted-imports`）：

- `domain/**` 禁止 import 任何三方 IO 库（provider SDK / drizzle-orm / socket.io …）——白名单方式列出允许的纯工具库。
- `application/**` 禁止 import `**/infrastructure/**` 具体实现（DI 运行时注入接口 token）。

### 2.4 文档一致性门禁 `docs:check`（审计 P1-16）

文档是本项目的主要交付物，但此前**没有任何机器校验**——README 过期了一整轮、计数漂移（17/16 张表、11/12 个状态）都是人工才发现的。加一道轻量 CI。

**落地状态**：已实现，落在**文档主仓**（`cloud-agent-platform-docs`，`docs/` 与 `api`/`web` 两个 submodule 同仓）。

| | |
|---|---|
| 脚本 | [`scripts/docs-check.mjs`](../../scripts/docs-check.mjs)（Node ESM，**零依赖**，只用内置模块） |
| 跑法 | `pnpm docs:check` · 或干净环境直接 `node scripts/docs-check.mjs`（**不需要 `pnpm install`**） |
| 排查 | `node scripts/docs-check.mjs --verbose` 额外打印从 `10 §6` / `27 §2–§9` 解析出的端点集合，以及 B2 从 api 源码与 `02 §5.2` 解析出的 MCP tool 集合 |

#### B 类的 skip 语义（**大声 skip，不失败**）

`api` submodule 拿不到时（CI 没 checkout、本地没 `git submodule update --init`），B 类**每一项各自 skip**——B1 的判据是 `api/openapi.json` 存在，B2 的判据是 `api/apps` 或 `api/packages` 存在，B3/B4/B5 的判据是两仓对应的那两个文件都存在——各自打印**醒目的 skip 提示 + 修复命令**并让整轮以 `0` 退出，A 类照常把关。理由：文档主仓的 A 类检查不该因为子仓没拉下来而全线瘫痪；但 skip 会在结尾汇总里点名（`✔ … 4 项检查全绿，2 项 skip（B1、B2）`），不会被静默吞掉。

#### B6 的边界：**只查一个方向**

B6 查的是「没标 ⏳ ⇒ 必须已实现」。反过来「标了 ⏳ 但其实已经实现」它**不管**（变异验证过：
给一个已落地端点标上 ⏳，门禁照样绿）。

这是**有意的**，理由与 A2 降级同源 —— 严的那一侧要能被一条命令救回来（`pnpm openapi:emit`
之后摘掉 ⏳ 即可），松的那一侧只会让一条已实现的端点看起来还没做，**不会让人把不存在的
东西当成已有**。而后者正是这条门禁存在的全部理由。

⚠️ 代价要说清：一个忘了摘的 ⏳ 会永久留在表里，读起来像「这块还没做」。⇒ **实现一个
端点时，顺手摘掉它的 ⏳**，与「加端点时顺手补 ⏳」是同一条纪律的两半。

#### ⚠️ 跨仓改动：文档先行时 A5 **必然**先红一轮（2026-08-30 撞出）

A5 拿文档表跟 **submodule 指针指向的那个 api commit** 对账。而跨仓改动天然分几个 PR，
指针又**不该**在子仓 PR 合并前就指向一个未合并的 commit ⇒ 中间必然存在一个窗口：

```
docs PR：10 §6.8 表已有 ALREADY_INITIALIZED / OFFLINE_NOT_ACKNOWLEDGED
指针指向的 api commit：还没有这两个码
⇒ A5 源码 67 / 表 69，差集 2 条 ⇒ 门禁红
```

**这不是门禁的缺陷，正是它该做的事** —— 它拦住的是「文档写了一个当前 main 还不存在
的码」，而这句话在那一刻**字面为真**。合并顺序是唯一解：

1. 先合 **api PR**（新码进 main）
2. 在 docs 分支上把 submodule 指针更到 main
3. docs PR 转绿 → 合

⚠️ **本地会是绿的**，因为本地 `api/` 工作区往往正停在那个功能分支上 —— 于是「本地全绿、
CI 红」，而两边跑的是同一个脚本、同一份文档。**差别只在 submodule 指到哪。**
排查时先 `git -C api log --oneline -1` 看指针，别去翻脚本。

> 这条与「B 类的 skip 语义」是**两种不同的缺席**：submodule **拿不到**是 skip（不失败），
> submodule **拿得到但落后**是 fail（该失败）。后者正是本条描述的窗口。

#### 章节引用（A2）的降级口径

**不做全深度硬校验**。本仓大量 `§x.y` 指的是章节**正文里的编号条目**而非标题——`P20 §9.4`、`P22 §4.11`、`17 §5.1` 都是表格行/列表项。全深度校验会产生 **48/2163** 的误报，全是噪音，门禁会立刻被无视。实际口径是**逐级下探**：从最高一级开始，某一级在目标文档里**存在同级标题兄弟**时才要求命中；该级根本没有标题细分（说明引用的是节内条目）就停止下探。实测误报 0，并抓到了真悬空引用（后端 `28 §3` 里两处把 `23 §5.6` 误写成了 `§256`）。**代价**：节内条目编号写错抓不到。要更严就得先把这类条目都提成标题，成本远大于收益。

#### MCP 传输层排除清单（B1 专用）

`openapi.json` 里有三条 path 是 **MCP 协议面的传输管道**，由 `McpModule.forRoot({ transport: [SSE, STREAMABLE_HTTP, STDIO] })` 自动挂载（02 §6 Bootstrap），**不是**"前端消费的 REST 业务端点"，因此**刻意不进 `10 §6`**——10 §6 的定位是前端写 service、后端建 controller、Playwright 建 mock 的对表清单，前端源码对它们零引用（只出现在生成物 `openapi.d.ts` 里）；它们的权威清单是 02 §5.2 的 tool 列表。

| path | 是什么 |
|---|---|
| `POST /api/mcp` · `GET /api/mcp` · `DELETE /api/mcp` | Streamable HTTP 传输 |
| `GET /api/sse` | HTTP+SSE 传输（旧传输）的事件流 |
| `POST /api/messages` | HTTP+SSE 传输（旧传输）的回帖通道 |

清单**显式写在 `scripts/docs-check.mjs` 的 `TRANSPORT_ONLY_PATHS` 里，每条带理由**，不是静默忽略；排除项若已不在 `openapi.json` 中，B1 会提示摘掉。**维护纪律**：往里加一条 = 声明"这个 path 永远不该进 10 §6"，必须写清理由；业务端点一律走"补进 `10 §6` + 补进 `27 §2–§9`"，**不许用排除清单绕过**。

**不做的事**：不校验正文措辞、不做拼写检查、**不再新增全局编号文档**（编号已到 28，再加会让引用体系更脆；新内容并入既有文档的子章节）。

## 3. 双仓库共同约定

- Node 版本、pnpm 版本用 `.nvmrc` / `packageManager` 字段钉死，CI 与本地一致。
- 分支保护：`main` 必须过全部 required checks。
- commit 规范（若启用 commitlint）双仓库共用同一套 preset。
