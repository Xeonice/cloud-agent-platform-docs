## 读法

每个领域文件的结构相同（格式沿用 format-pilot/docs/product/system-status.md，01 §4.5）：

1. **元数据头**：领域、流程、`last_verified`（三仓 SHA + 日期）、`covers`（代码范围）、`supersedes`（取代了哪些旧文档的哪些部分）、`merged_from`（来自哪几个片段）。
2. **一屏摘要**：这一域回答什么、3–5 条「必须 / 不得」、现状、待定问题。只看这一屏也能知道这一域的口径。
3. **需求索引**：编号、标题、状态、版本、验收条数、稿件、待定问题（链到 open-questions.md）。
4. **与旧文档的对照**：旧文档（代号见下表）的哪几处被改写、哪几处作废，由各条「改写了哪条旧文」汇总。
5. **需求块**：`### REQ-<域>-NNN · 标题` → 状态行（状态 · 版本 · 来源 · 关联 · 待定问题 · 稿件）→ 陈述（**必须** / **不得**）→ 折叠的「为什么」→「改写了哪条旧文」→ 合并说明（如有）→ AC 表。
6. **AC 表**：`AC | 层级 | Given | When | Then | 现状`。层级 = 最低验证层：单元 / 组件 / 集成 / API / e2e；另有 `文档`（文档一致性检查）、`视觉`（截图比对）、`真机`（只在试点底稿里出现一次）。「现状」以状态词开头，后面是证据。
7. **附录**：A 改写对照（片段原表）· B 片段里的默认决定与待确认（原文，本地编号见 open-questions §7）· C 参数（待登记 params.yaml）· D 边界、覆盖对照、待核实 · E 合并时改动的地方。

几条约定：

- **编号**：REQ-<域>-NNN / AC-<域>-NNN.n（01 §4.4）。每个流程有自己的编号段（plan.json `flows[].req_range`），段内留空的号是预留，不补。SYS / DIA / AUD 在试点编号上续编（新增从 REQ-SYS-070、REQ-DIA-040、REQ-AUD-020 起），整块改写的旧条在索引里标「（改）」；被删掉的旧 AC 只在改写对照里留墓碑，编号不复用。PRJ、CRD、IMG、ACC、WB 是暂定域码（沿用 02 测试域码），P1 合并 id-scheme 时确认。
- **「现状」列的出处**暂时写到文件:行（api a453bb7 / web 93f03c5），便于核对与转 issue；入库时按 01 §4.2 换成证据 ID。
- **合并说明**：合并时统一口径或更正的地方，都以「**合并说明**：」开头写在该需求的 AC 表之前，并在另一处留交叉引用；附录 E 有清单。
- **待定问题**：统一编号的 Q-<域>-NN 都在 open-questions.md；不回复时按那里的默认走，稿件与原型已经按默认画。Q-DS-15…28 是设计轨已有的决定，不在本清单。
- **数值**：正文只写 `PARAM.X`（现值写在括号里），定义待登记 docs/reference/params.yaml（各文件附录 C）。
