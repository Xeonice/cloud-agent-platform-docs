# 升级体验与启动可观测性优化

本文根据[本次双实例升级验收](../../testing/results/2026-10-17-CLI镜像与双实例更新验收.md)整理优化方案，2026-10-18用户已要求实施。现已先将规则合入既有UPG／LCH／SBX产品需求、原前后端计划、现有HTML设计稿及独立测试文档；前后端代码及本地验证已完成，见[本轮实现验证](../../testing/results/2026-10-18-升级体验与启动观察实现验证.md)；已完成实例限定发包、两台`.14`更新和`.15`新界面单击实验，实际结果与未覆盖范围见[本轮发版验收](../../testing/results/2026-10-18-升级优化发版与双实例更新验收.md)。保持UPG的9条需求／52条AC编号并扩充原条件，不把文档或原型通过写成实现／线上验收通过。执行方法的教训单独写入Claude项目记忆。

## 1. 先区分问题性质

| 类别 | 本次已知事实 | 产品上应怎样处理 |
| --- | --- | --- |
| 已修复的实现缺陷 | 旧部署工具缺失Web目录／来源不可见、切Web后观察scope不完整、连续升级路由及代数判断、全库检查挤占短事务／主线程 | 保留回归与真实通路门禁；不要让用户理解或手动修补内部角色、数据库、目录和兼容版本。已修复不能当作当前线上仍失败 |
| 主路径仍不够完整 | 本次实际分桥接版、最终版分别更新，失败后出现过“历史确认版本不变、部分角色已替换”的真实组合 | 用户只选择最终目标并发起一次；系统完成固定兼容链。失败后显示真实服务可用性、上次完整确认版本和本次未完成步骤 |
| 可观测性不足 | 旧页面短控制超时导致拿不到状态；后续迁移总量未知时总体percent为空；新Guest长时间只有starting | 状态查询及时返回；已有的下载／阶段进展仍可展示；未知如实标记，等待要有阶段、时长、最后进展及下一步 |
| 慢操作原因未明 | 远端新Guest从创建到版本实测及清理约10分33秒；provider.start超过120秒后仍inflight，同一Guest最终自然成功 | 先补准确阶段和耗时观测，再决定预热、缓存或下载优化；不能把总耗时全部写成镜像下载或停机 |
| 执行流程过重 | 多轮修复后反复发包、下载，临时工具与审阅过多，外层SSH测量边界不清 | 改执行规范；不把这些人工手续转成管理员审批、密钥或新增产品步骤 |

现有核心决策保持：一个通过已有访问保护进入平台的操作人决定本实例何时升级；CD只发布；不增加升级密钥、再次输入口令、多人协同或审批。已有沙箱保持原环境，平台更新不替它们更换CLI。

## 2. 推荐的主路径

**发现最终可安装版本 → 点击一次“立即升级” → 系统完成固定兼容准备、更新与验证 → 显示实际结果 → 页面确有变化时由用户刷新。**

用户在主界面只需要知道三件事：现在还能否继续工作、更新到了哪一步、是否需要自己做什么。角色摘要、锁、fence、SQL和原始错误码留在主动展开的诊断详情。

| 用户所处位置 | 应看到什么 | 系统负责什么 |
| --- | --- | --- |
| 尚无新版 | 顶栏没有升级入口；系统页可查看当前版本 | 只读检查目录，不建立attempt、不执行包下载或迁移 |
| 发现新版 | 沿用右上角图标和常驻小浮卡；显示当前服务与最终目标、简短变更和“立即升级” | 根据已签元数据核验架构及允许版本链；有桥接时简述“将自动完成兼容准备”，不要求用户找中间包 |
| 点击后尚未确认受理 | “正在确认升级请求”；保留当前工作台，不重复点击 | 持久化处理请求标识；结果不明只查询原请求，不换ID重投、不提前伪称已有升级进度 |
| 请求已受理 | “准备升级”以及真实阶段进展；用户可继续切到原任务 | 固定最终目标、签名版本链与策略；下载、验证和长检查异步执行，后续CD发布不改变本次目标 |
| 升级进行中 | 紧凑浮卡显示主阶段；系统页展示展开的进展、已用时间和最后更新 | 内部桥接及最终阶段由实例编排，桥接完成后继续同一用户计划，无需再次点击 |
| 已整体确认 | 显示最终服务版本；同一Web则收起更新入口，不强行刷新 | 只有最终目标确认才算本次升级完成；原Guest保持；本次确有受管默认镜像变化时，再说明选择该默认镜像的新任务适用新版 |
| 有新页面可刷新 | “服务已更新，刷新可使用新版页面”；用户自主刷新 | 保留登录与任务选择，attach原终端；不新建替代Guest或重放输入 |
| 升级未完成 | 系统页保留准确原因、当前可用性、已完成和未完成部分 | 先停止推进并保护实际健康组合；只在存在合格修复方案时提供明确的下一步 |

右上浮卡沿用“今天不再提醒”、次日重新核验以及仅有有效更新状态时显示的规则。失败详情留在系统页和本次记录，不为失败新增全宽警告或强制弹窗；原任务确有连接问题时仍在原任务位置提示。

## 3. 优先补齐的产品能力

### 3.1 P0：操作快速受理，查询不等待长检查

鉴权、目标身份、幂等和代际检查保留；整库扫描、包下载、目录树验证、镜像准备和观察窗口不占用升级命令或页面状态查询的同步等待。受理与长操作执行分别建模，先把已受理的事实、阶段及原请求引用及时呈现。

UI可读取最后已确认的状态及时间；证据过期时标“状态待确认”。实际切换、成功确认等决策仍核验实时控制权和新鲜证据，不能用界面缓存刷新时间冒充新证明。240秒控制等待预算不能作为正常页面响应慢的解决方案。

**验收建议 P-01：** 在受控环境、约1GB数据库及重检查执行中，升级命令的受理确认与轻量状态查询目标均为2秒内；长工作在后台继续。客户端响应丢失、刷新或重复点击，只能找回同一请求和执行，不重复副作用。未知状态及时返回，不为了满足响应时间伪造通过结果。

### 3.2 P0：一次选择最终目标，兼容桥内部完成

这补齐[前端计划](../../frontend/changes/2026-10-10-升级提示与原终端续接.md)已有的固定兼容链要求，不另造多层审批或通用任务DAG。用户选择的版本是最终目标；点击时固定允许的桥接节点、digest、顺序及回退范围，内部可保留独立技术attempt。

面向用户的一次升级，在最终确认前始终是进行中。中间桥接完成写“兼容准备完成”，不能先宣告整体100%再回到0%。底层桥接attempt的真实100%和历史确认记录仍原样保留，不能为了界面连续而改写历史。链中断后不自动循环重试、不跟随CD追加新目标。

**验收建议 P-02：** 从需要桥接的旧版只点击一次，得到固定最终目标；两阶段不中断用户操作、不要求再次触发。中途刷新找回同一计划；最终阶段失败时保留中间已确认版本及实际组件状态，不声称最终版安装成功。

### 3.3 P0：服务可用性与升级结果分开

系统版本卡分开表达：上次完整确认的服务版本、当前服务可用性、本次最终目标与结果、实际加载的页面版本。成功历史不因后续故障被改写；健康接口200也不能替代目标版本确认。

失败后不能一律写“旧版本未变、已完全回退”。存在部分角色替换时，显示“升级未完成，部分组件已更新”，按独立证据说明服务是否可用；实际组合放在详情。可以继续使用时给“继续使用”；检查只读。只有服务端根据实际组合和当前数据确认存在安全修复计划时，才显示有明确目标的修复动作，并由用户发起。

没有合格修复方案时提供“检查状态／复制诊断信息”，不能给无条件“回滚旧版”“重启全部服务”或恢复旧数据库的按钮；没有证据也不能宣称任务仍在运行。

**验收建议 P-03：** 覆盖未接流失败、部分切换失败、迁移已提交后失败及成功后ready撤销。每种状态都能回答“服务现在怎样、目标是否完成、已做了什么、下一步是什么”，查询或健康恢复不暗中开始新升级。

### 3.4 P0：请求超时与后台执行终结分开

本次实际正确保留了原启动操作；产品文案和后续实现必须保持这一行为。HTTP／RPC等待超时仅说明这次没有及时拿到结果。后台仍运行或结果未知时，不标任务failed、不说“平台先停下了”、不释放仍占用的名额，也不引导“重新发起”另建Guest。

沿用同一任务的准备卡，显示“启动请求仍在执行，正在确认结果”，给“检查状态／继续等待”；不让继续等待重置真实启动时间、阶段进入时间或最后进展时间。只有服务器证实原操作已经终结，才能按对应业务失败展示后续动作。用户明确取消仍走原取消流程，资源未确认结束前不当作已经回收。

**验收建议 P-04：** 模拟provider.start超过120秒、延迟到达成功或结果暂不可查。只执行一次start，保留同一Guest和占用；刷新和手动检查不重复启动；真实结果到达后转入对应状态。

### 3.5 P1：把已知进展展示出来，未知部分不造百分比

主阶段统一用用户能理解的“下载与校验 → 兼容与数据准备 → 验证并切换服务 → 完成”。下载有真实总字节时，显示已下载量／总量及阶段百分比；迁移工作量未知时显示“正在确认数据准备进度”，仍保留已完成阶段和当前可确认事实。不能因后续迁移总量未知而隐藏已经知道的下载进展，也不编总体预计完成时间。

展开详情显示当前阶段已等待时长、最后确认时间及真实步骤结果。健康观察期间说明“正在验证新服务”，只有依据真实窗口才能显示剩余观察时间；状态陈旧时停止冒充实时倒计时。子阶段百分比必须标明所属阶段，不能冒充本次整体进度；没有整体工作量时可只展示步骤，不人为分配固定权重。

**验收建议 P-05：** 覆盖下载已知／未知长度、后续迁移总量未知、桥接完成继续最终版、Web复用和不同Web、新观测窗口、状态响应过期。阶段进展准确，最终100%仅来自最终目标整体确认。

### 3.6 P1：新沙箱启动阶段可追踪，再决定性能优化

复用现有任务准备卡，增加来自实际操作的镜像准备、运行环境创建／启动、环境初始化、Agent工具准备等子阶段。事实缺失时写“正在确认准备情况”，不能从starting推断正在下载、网络慢或进程卡死。

每次操作应记录阶段进入时间、最后实质进展、最近查询／心跳时间及原操作是否仍在执行。心跳证明可联系，不能等同下载或启动已有进展；有真实字节／阶段事件才前进。超过合理等待阈值时说明当前已知事实并提供检查，不能仅凭时间承诺“不是卡死”。

先用这些记录拆分本次10分33秒的真实耗时，再选择镜像预取、缓存、下载路径或运行环境启动优化。预取若需要新增执行动作，应放在用户已授权的固定升级准备或独立镜像准备流程；目录检查不暗中拉执行包、创建验证Guest。不能每次平台升级都额外创建测试沙箱，或把所有镜像预热变成新的升级门槛。

**验收建议 P-06：** 覆盖首次镜像、已有镜像、慢provider、心跳正常但无进展、观测暂不可用及真正失败。每个状态都保留原操作，可解释等待；重新打开页面不丢计时，继续等待不重置历史，无证据不归因网络。

### 3.7 P1：完成后说明新版CLI适用于谁

本次确实更新了受管默认镜像时，完成文案说明“平台已更新；之后选择该默认镜像的新任务使用新版，已有沙箱继续原环境”。用户自定义默认、显式选择的其他镜像沿用原配置；只有API／页面更新时不显示镜像换版承诺。镜像选择器和管理页沿用[镜像版本声明](../requirements/IMG.md#REQ-IMG-062)，任务内实际执行过的版本单独展示；不能把镜像声明写成已有任务已更新，也不为了更新CLI重启存量任务。

**验收建议 P-07：** 有受管默认镜像更新时，新任务选择该默认镜像并能查看对应CLI声明；自定义默认、显式选择旧镜像及仅API／页面更新不被改写为CLI已更新。旧任务仍显示原环境事实；旧新任务、同一镜像不同digest和未知声明不串值，原任务续接不运行安装或更新命令。

## 5. 实施与验证顺序

1. **先做P0。** 把一次最终目标、快速受理／查询、失败真实状态和超时非终态整理进权威PRD、现有设计稿及独立测试计划，再实现相应前后端契约。优先复用已有request、attempt和状态，不先扩建通用编排平台。
2. **再做P1可观测性。** 后端给实际阶段、时间、进展及原操作状态；前端按事实呈现并保留刷新恢复。需要诊断时复制脱敏信息，不要求管理员SSH上机才能知道在等什么。
3. **根据实测再优化性能。** 区分下载、校验、数据准备、观察、创建／启动、初始化和清理耗时；变更哪一项，验证对应指标。约1GB真实隔离升级、原终端、链式升级及超时后原操作最终成功都应成为固定联合场景。
4. **分别记录完成标准。** 发布成功、目标服务激活、页面加载、新建沙箱就绪、CLI声明／实测、原任务续接各有证据，不用其中一个替代全部。后台观察时长、频率和保护阈值不因追求更快而直接放宽。

P-01至P-07已落实到原REQ／AC、前后端计划及独立测试文档，作为本轮实施验收要求；对应代码与本地功能回归已完成；约1GB独立响应实验、Native整链、真实模型及线上验收分别记录，未执行项不标通过。文档先行不新增业务审批或升级授权步骤。
