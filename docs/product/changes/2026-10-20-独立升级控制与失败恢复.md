# 独立升级控制与失败恢复

本次修订回答三个问题：升级的观察与控制如何独立于业务版本；失败后如何恢复；下一次故障怎样得到足够证据。沿用 [UPG 的 9 条需求、52 条 AC](../requirements/UPG.md)，保持单实例、单个已进入平台的管理员主动升级，不增加多人协作、集群调度或升级专用密钥。

**状态：实现与专项验证进行中，尚未更新远端。** 最近实验包 `.20` 在候选 Coordinator 准备期间失败，未确认激活；最近记录的组合为 API `.18`、Coordinator `.19`、未来任务 Owner／Installer `.20`，已确认版本仍为 `.18`，入口候选权重已恢复为 0。详见[实际验收与诊断边界](../../testing/results/2026-10-19-升级证据开销修复与恢复准备.md)。已知存在旧业务服务承载控制快验、故障恢复权限受旧 attempt 约束等问题；本次超时究竟消耗在何处仍缺分段证据，不能据此断言 OOM 或数据库锁就是根因。

## 1. 产品决策

| 问题 | 本次决定 | 用户看到的结果 |
| --- | --- | --- |
| 观察、控制随业务包一起被替换，修复要等旧版完成交接 | 将升级控制、升级账本、入口切换控制与基础观察放进独立版本的常驻控制系统；业务包只声明协议兼容范围 | 业务候选启动慢、失败或业务 API 不可用时，仍能查到升级状态与恢复结果 |
| 失败后依赖失败 attempt 的过期租约才能退流 | 恢复作为关联原操作的独立过程，由稳定控制系统取得新的恢复权威，按固定范围核验、执行并确认 | 一次已同意升级内的安全恢复自动执行；不要求用户手改数据、补授权密钥或反复点击 |
| “回滚”混用了退流、组件退版和数据恢复 | 默认选择能恢复服务的最小动作；涉及 writer 的退版另做安全交接，不能在线恢复旧数据卷 | 保留原任务和升级后新产生的数据；回不去时明确说明并修复前进 |
| 只看到笼统 RPC 超时，无法判断阶段和等待位置 | 同时补结构化日志、分段调用链、低成本资源指标、持久动作收据及同构故障验收 | 系统详情给出简明原因、真实恢复阶段和脱敏诊断，不把猜测当结论 |

“独立”指独立产物、版本、进程、状态存储和维护生命周期。它不是另一台机器，也不表示同一 VM 的内存耗尽、磁盘或内核故障被消除了。控制系统职责与协议保持小而稳定；必要安全修复及协议演进仍通过独立维护流程进行，业务发版不得顺带替换它。

## 2. 一次普通升级怎样运行

1. CD 发布经过门禁的不可变业务包及版本目录。实例只读发现可安装新版，管理员选择时间。
2. 管理员点击一次“立即升级”。稳定同源入口沿用已有访问保护，控制系统持久接纳原 `requestId`，固定最终目标、兼容链、资源预算和安全恢复范围。访问失效走原解锁流程，无额外升级口令。
3. 控制系统先检查现有服务、原 Owner／Guest、数据兼容与资源余量。预算必须涵盖现有业务、候选、验证工作和恢复保留量；不够就延期，旧服务继续运行，不以停止任务释放资源。
4. 限额工作进程校验产物、准备候选和语义证据。业务 API 继续承接请求；控制租约和 fence 快验不读取完整 manifest、历史证据或整库快照。候选容器存活、管理接口响应、prepared-ready 是三个不同状态。
5. 通过门禁后按计划完成唯一 writer 交接、未来任务分配与入口灰度；旧 Owner 继续持有原任务。外部观察贯穿准备、切换、确认及必要恢复，不能只观察最后几档流量。
6. 最终目标的实际组合与连续性确认后才记 100%。不同且实际 ready 的页面由用户自主刷新；接回原沙箱与原终端。
7. 发生异常先停止推进，再执行已核验的最小恢复。原升级结果与恢复进展分别记录，恢复成功不等于目标版本升级成功。

详细职责、协议、控制维护及首次迁移见[独立升级控制系统](../../backend/changes/2026-10-20-独立升级控制系统.md)。独立控制账本不获得业务数据库写权限；业务唯一 writer 的守卫仍与业务写入在同一事务校验，不能把升级 epoch 当作直接接管业务 writer 的许可。

## 3. 失败恢复的产品路径

| 当时的真实状态 | 默认恢复路径 | 不满足资格时 |
| --- | --- | --- |
| 候选未接流、未取得业务权威 | 保留来源服务，隔离失败候选；核实后清理本次无引用候选 | 结果未知先查询原动作，保留现场，不重复启动 |
| API／Web 已部分切换，当前 writer 健康 | 验证当前数据、已加载新页面及全部 Owner 后，只退必要流量／页面入口 | 保留有证据的健康组合，不先清零唯一安全入口 |
| writer 已交接，新 writer 故障 | 选择能理解当前数据的合格 writer，以新代际、原子守卫和实际交接恢复 | 旧 writer 是否已释放不明则禁止抢权；不能证明退版则走兼容桥或修复前进 |
| 已完整确认后才发生新故障 | 保留原成功及当时 100%，追加故障、当前 ready 撤销及独立恢复记录 | 当前状态按实际组合和新鲜证据展示，不能继续冒称目标 ready |
| 恢复自身失败、共享数据库／Owner 故障 | 停在明确受阻状态，保持已证健康部分与原任务，提供具体原因和诊断 | 不自动 A↔B 循环，不新建升级尝试，不把整包退版当作共享故障修复 |

恢复过程以独立 `recoveryId` 与控制 epoch 进行，原 attempt 失败或租约过期不阻断取得恢复权威。控制器崩溃重启后对账并继续**同一个恢复过程**，不能由此复活失败升级或重新接纳用户命令。迟到 ACK、超时及进程身份变化先查原动作；新升级、新目标、扩大恢复范围或破坏性 contract 仍需用户明确发起。

入口退流、组件退版、业务数据灾难恢复各有资格和确认标准。已有新写入、取消意图、幂等键、任务游标与原执行身份必须保持。旧版不能理解当前数据时禁止降级；备份恢复属于[独立灾备流程](../../ops/灾备与重建.md)，不属于普通升级自动恢复动作。阶段矩阵、状态机与清理规则见[升级失败恢复与回滚方案](../../ops/2026-10-20-升级失败恢复与回滚方案.md)。

## 4. 前端和诊断展示

沿用现有右上角按钮、紧凑浮卡与系统版本卡，不新增全宽警报、强制刷新或阻断弹层。可安装新版、进行中、不同 ready 页面待刷新才显示更新入口；没有独立有效更新状态的失败／受阻过程从系统页主动查看。

系统版本卡分别呈现：上次完整确认版本、实际服务组合与可用性、本次目标及升级结果、恢复当前阶段及结果、实际加载页面、各自确认时间。失败后部分组件更新时继续使用“升级未完成，部分组件已更新”。只有恢复确认才说“服务已恢复”；未知时显示最后已知值与时间。原升级的最后真实百分比保留，恢复使用自己的阶段，不借原 100% 或凭时间补进度。

控制系统版本与协议版本只放在主动展开的系统详情；它们不推进业务已确认版本，也不新增一个普通用户升级按钮。详情提供简明阶段、错误类别、受阻条件及脱敏诊断标识；PID、fence、SQL、原始堆栈只在维护诊断中，不进入工作台默认文案。诊断导出仅包含脱敏元数据，不采集凭据、环境、终端内容或模型正文。

“补日志”需同时补四种证据：

| 证据 | 回答的问题 | 约束 |
| --- | --- | --- |
| 结构化日志 | 哪个操作、阶段、角色报了什么错误 | 明确区分 lease-renew 与 fence-check，不只打印同一个 `/renew` 超时 |
| 分段 span | 请求在哪段等待或执行，预算在哪里消耗 | 本地单调计时；区分排队、数据库调用、Owner RPC、校验和序列化，无法细分的耗时保持未知 |
| 低频指标与限额故障现场 | 当时 CPU、事件环、GC、内存、I/O、数据库和 cgroup 是否异常 | 进程外采集，有采样／内存／磁盘上限；采集失败不反过来拖垮业务 |
| 持久动作收据 | 到底切过什么、谁执行、恢复后是否真实生效 | 在阶段与权威边界落账；心跳引用已有证据，日志不能代替成功确认 |

字段、初始预算及验证标准见[专项测试计划](../../testing/changes/2026-10-20-独立升级控制与恢复测试计划.md)。没有这些证据时，结论限定为已知超时及未知分段，不能再靠连续发包碰运气定位。

## 5. 实施顺序及交付门禁

以下任务均为 planned，本文未改代码或运行实例。

| 顺序 | 交付 | 完成条件 |
| --- | --- | --- |
| T1 | 稳定控制协议、状态机、两类 fence 与诊断契约 | 精确职责及未知结果语义冻结，前后端共享状态契约；不增加第二业务写者 |
| T2 | 独立 Control Agent、control.db、稳定入口鉴权与 Supervisor 固定动作 | 业务 API 卡顿时仍可读控制状态／进行合格恢复；原会话及既有改口令／退出／撤销语义、旧命令拒绝验证完成 |
| T3 | 恢复执行、对账、容量准入和候选退役 | 原 attempt 终态／lease 过期仍可安全恢复；恢复重启续同一身份，资源与失败次数有界，不使用外部 SQL 修权限 |
| T4 | 角色兼容适配与业务交接 | 数据语义由版本适配器校验；writer 守卫同事务、原 Owner／Guest 不迁移；业务包移除控制器更新动作 |
| T5 | 前端消费独立状态与脱敏诊断 | 现有提示位置和低打扰规则保持；升级／恢复／当前可用性分开，无伪进度和额外授权步骤 |
| T6 | 独立前后端与 ARM64／KVM 同构故障验证 | 固定旧二进制、真实混合来源、历史数据分布、完整候选准备、低资源延期及恢复矩阵通过，证据绑定精确输入 |
| T7 | 一次性迁移方案与正常升级验证 | 先在隔离实例演练；单一控制权交接被确认，再由管理员安排实例迁移；后续普通业务升级不替换控制系统 |

首次安装独立控制系统与修正现有 Entry 验证绑定是单独迁移。当前实现没有已验证的在线更换全部控制基础能力，可能需要连接中断和恢复窗口，必须事前说明实际影响并验证重连；已有 Owner／Guest 继续运行。不能用这次基础迁移的结果冒充今后普通业务升级已无中断。

正式交付需同时满足现有 52 条 AC 与本次专项测试；原局部通过记录不被改写，未执行项继续 not-run。实验发布也需先有对应隔离复现与恢复证明，不能把活跃线上实例作为唯一故障发现环境。
