# 不停机升级与沙箱续接 · 产品需求

本文定义本轮新功能的目标行为，共 **9 条 REQ、52 条 AC**。实施顺序及现状见[需求变更说明](../changes/2026-10-10-不停机升级与沙箱续接.md)，配套[交互设计稿](../../design/upgrade-sandbox-reconnect.html#task-login)；默认待升级示例为 `?scene=upgrade-available`，用户明确发起后的过程为 `?scene=upgrade-progress`，已安装待刷新为 `?scene=upgrade-ready`。操作和新一轮校验状态见变更说明。验收条件需要后续实现和真实实例升级门禁证明。

2026-10-20补充[独立升级控制与失败恢复](../changes/2026-10-20-独立升级控制与失败恢复.md)：升级控制和基础观察独立于业务版本维护，恢复不依赖失败attempt租约，并补齐分段诊断与同构故障门禁。本次仍为planned设计修订，沿用既有REQ／AC编号，不代表已实现或上线。

## 一屏摘要

本轮按一个通过已有访问保护进入平台的操作人管理当前实例设计，不新增多用户升级产品流程、用户管理或多人协同界面。发现新版、决定升级时机、查看进度和刷新续接都由该操作人完成；防止重复执行只处理重复点击、页面重开和回执丢失。

操作流程为：**发现最终可安装版本 → 主动点击一次“立即升级” → 实例完成固定兼容链并显示真实阶段 → 最终目标确认后按需刷新并接回原任务**。兼容桥由系统编排，不要求用户找到中间包或再次点击。后台锁、执行记录和失败回退用于保证这一次升级可靠完成，不增加审批、多人确认或跨实例协调步骤。

- CD 只发布经过验证的版本和安装包，不远程自动升级或迁移任何实例。实例升级时机由已进入平台的用户主动决定；打开页面、检查更新、关闭提醒、目录变化和 CI 重试均不启动升级。
- 已通过原有访问口令解锁进入实例后，用户可直接点击“立即升级”，无需再次输入口令、申请授权或管理升级密钥。访问保护未启用时沿用实例现有访问策略；升级命令仍由服务端验证访问会话、Origin／CSRF、实例绑定、精确目标、requestId 与 CAS。
- 用户明确点击“立即升级”、服务端接纳幂等命令后，才建立本实例 attempt 并下载、验证、迁移和切换。常规实例升级不安排服务停机，不停止、销毁、重启已有沙箱或取消任务，也不暂停自动化。
- 已有任务保留运行环境和执行身份。刷新页面、更新前端或重连终端，只接回原任务，不新建替代沙箱、不重放原指令。
- 本实例核验有可安装新版、用户发起的升级实际进行中，或已安装且有不同页面可刷新时，显示顶栏右上 32px CircleArrowUp 和未暂停的紧凑常驻浮卡。待升级显示“发现新版本”和已进入平台用户的“立即升级”，没有 attempt 或百分比；进行中显示真实阶段／进度；已安装后仅不同页面实际 ready 时显示“刷新页面”。
- 百分比只来自本实例已接纳升级 attempt 的真实工作量，CD 构建／发布进度不能冒充它。100% 要求实例激活、所需生产产物可用、兼容与整体确认；页面是否刷新、原终端是否接回分别说明，API 单独更新或 Web 产物复用不要求刷新。
- 关闭浮卡表示“今天不再提醒”：按用户与实例的本地自然日暂停，待升级、进行中、待刷新及同日新版本、跨页／刷新／多标签均保持，次日只重新核验提示。暂停与恢复提醒都不发起升级，有效入口和手动查看保留。
- 无可安装新版、纯候选／未核验目录、失败／延期／未知且无独立有效更新状态时隐藏顶栏；系统页始终可查实例服务、可安装版本、实际页面、原因与手动检查。页面已是目标构建不能掩盖实例服务尚待升级。
- 连接状态与任务状态分开。确认原运行环境持续运行后才能说“任务仍在运行”；无法确认时保留现场并如实说明。
- 发布异常先熔断推进、扩流／新增分配步骤和后续迁移批次；尚未接流的候选可隔离，已接流的唯一安全入口在没有合格替代前继续服务，保留健康业务与原任务。数据库不兼容变更必须先分阶段兼容化；只有剩余步骤无法证明连续性时才延期、限制对应功能或另列必要维护，不把维护作为默认路径。运行环境与宿主重启仍走独立维护流程。

## 范围与术语

**常规升级**覆盖 Web、控制 API 及主仓文档／设计／测试／发布工具更新，也覆盖经过兼容桥与分阶段转换、满足连续性门禁的数据库变更。原始 schema 不兼容不能直接作为安排停机的理由；未能兼容化的残余步骤单独评估，必要短维护必须说明无法在线完成的证据与影响范围，原任务继续留在原 owner。已有沙箱的镜像、Agent CLI、执行进程和代码副本不随平台版本自动替换。RuntimeOwner 自身更新同样不能搬迁或停止已有任务：新任务可使用经过验证的新 owner，存量继续归原 owner，自然排空后退役。

**版本发布、实例升级、页面刷新是三个动作。** `published release` 只表示目录中的版本及安装包已发布；本实例受信激活记录与 `activation-confirmed` 才证明实例整体激活确认，浏览器不可变 Web 构建身份才证明页面已刷新。目录更新、首次／次日检查只能核验真实性、适配架构、允许的版本链和兼容性，产生 `available`／待用户升级；不能建立 attempt、拉取执行安装包、迁移或切生产。用户发起时服务端重新核验并固定精确 target release、manifest／digest／信任来源及版本链，其他新版本不擅自替换该目标。每实例的 Web 产物入口固定到其已确认版本；CD 不 promote 共享生产 alias 来替未选择升级的实例换页面。

**本轮复用当前实例已有访问保护，不增加独立升级授权步骤。** 用户通过现有访问口令解锁后即可直接发起升级，不另设升级口令、密钥、授权按钮或对话框，也不新增用户管理或 RBAC。服务端仍验证当前访问会话、Origin／CSRF 和实例绑定；真实访问会话失效时走原解锁流程，不新增升级专用认证。发布签名、固定信任根与内部角色 RPC 密钥由系统保留，用户无需取得、输入或管理。服务端按 instance 的 CAS 保证最多一个活动 attempt，重复点击、页面重开或网络断开按 requestId 查询同一命令结果，不能重复创建执行；操作人一次明确发起允许该范围内经过门禁的安全自动熔断／回退，熔断后再次尝试、新 target 或破坏性 contract 须重新由操作人发起，CD 不能代替操作人重试。

工作台 URL 的 `/?taskId=<id>` 沿用现有实现，`id` 指向工作台任务的 **Sandbox ID**。无头执行的 AgentTask ID、执行轮次和日志序号是另一组标识，不混用。浏览器连接、网关 attachment 和短期认证票据可以重建；原 `sandboxId`、Provider 实例、tmux 会话、任务执行轮次必须保持。页面显示任务名与终端名，运行标识只用于内部验证。

首次从历史单 API 容器架构迁移时，存量任务继续由原实例服务，不能把迁移理解为已支持热搬微 VM。后端分离与安全切换的前置条件见[后端计划](../../backend/changes/2026-10-10-不停机升级与运行环境分离.md)。

**独立控制系统为planned目标。** 升级命令、权威、账本、恢复和基础观察常驻于稳定控制底座，使用独立产物、版本与维护生命周期；普通业务包不替换它。业务ControlAPI与升级Control Agent职责分开，查询／恢复不先经过待升级业务API或依赖其完整历史快照。控制底座仍可独立修复，不承诺永不变化；首次迁移、底座或VM维护另列实际影响与重连验证，不计为常规业务无中断通过。独立进程仍共享宿主资源，必须有容量准入和采集限额；不得为释放升级资源停止原任务。

下文恢复的“新generation”指独立恢复控制代际；控制epoch、业务writer代际与实例整体activation分别记录。只退API流量不要求改写writer或伪增整体激活，真正交接writer才推进其事务守卫代际。

### REQ-UPG-001 · 存量沙箱、任务与自动化持续运行 {#REQ-UPG-001}

CD 发布和用户发起的常规实例升级均不得调用已有沙箱或执行任务的 stop、destroy、kill、cancel，也不得通过容器退出、资源清理、重建 owner 等间接方式终止它们。用户尚未升级或升级等待期间既有任务继续运行，等待输入的任务仍可交互；自动化保持原启用状态，按其既有规则执行。不能要求用户停止任务来“解锁更新”。用户独立、明确执行的停止／销毁和任务自身真实退出保持原语义。

| AC | 层级 | Given | When | Then |
| --- | --- | --- | --- | --- |
| AC-UPG-001.1 | 真实运行环境 | 一个有持续输出的交互任务运行中 | 升级 Web 和控制 API | 原沙箱／Provider 实例／tmux 会话／进程启动标识保持，输出继续；无停止、销毁、取消调用 |
| AC-UPG-001.2 | 真实运行环境 | 无头任务正在执行且持续写结果 | 升级并刷新浏览器 | 原 AgentTask、执行轮次和 job 持续，初始指令只执行一次，产物不倒退 |
| AC-UPG-001.3 | 真实运行环境 | 自动化已启用且将在升级期间触发 | 正常发布及失败回退 | 启用状态保持；到期运行不因发布漏发或重复发起 |
| AC-UPG-001.4 | 集成 | 活跃任务阻止尚不具备连续性的部署方式 | 发布等待或达到超时 | 保留旧版并记录等待原因；不停止任务、不暂停自动化、不清资源占用 |
| AC-UPG-001.5 | 真实运行环境 | 旧 RuntimeOwner 仍持有运行任务 | 部署新 owner 版本 | 旧 owner 和原实例继续运行；独立的新 owner 不抢旧 home 或隐式拉起已停止实例 |
| AC-UPG-001.6 | 集成 | 用户自行停止任务或任务真实结束 | 同时存在发布活动 | 按真实业务原因结束；审计可区分用户操作／自然退出与发布，不能伪造连续运行 |

### REQ-UPG-002 · 常规发布连续可用与访问会话保持 {#REQ-UPG-002}

CD 只产出目录版本，不在发布时替换实例。用户发起的常规实例升级中，候选在不影响现网业务的条件下完成准备和 readiness，稳定入口保持可用后才切换。兼容、有效的业务请求不能因实例升级得到计划性 503、连接拒绝或空白初始化页。每实例生产入口与认证签名密钥保持，普通升级不令已解锁浏览器重新输入访问口令；“立即升级”复用原访问会话，不要求额外升级授权或再次输入口令。任务运行环境与常驻连接入口的生命周期不能绑定到控制 API 容器替换。

本机、网络、凭据和用户操作正常的隔离验收环境中，连续探测 **10 次／秒**，兼容的读请求及幂等写请求必须成功，单次响应不超过 **2 秒**。探针覆盖短时控制查询和合法操作的接收确认，不将 VM 启动、仓库克隆或 Agent 执行的全过程误计为 HTTP 响应时间；长操作按其原异步契约跟踪原执行和结果。这是交付门禁目标，异常外部网络或用户主动停机分别记录。终端连接可以在页面刷新或需要连接切换时短暂恢复，任务执行不得随之中断。

升级命令完成必要的访问／目标／代际快验后，持久接纳原请求并及时返回可查询标识；重完整性扫描、包／目录树校验、镜像准备及健康观察异步执行。上述受控环境中，接纳确认与轻量状态查询同样以2秒为目标，不同步等待长工作。尚未证实受理时显示“正在确认升级请求”，不能伪造attempt或百分比。UI可返回最近已确认快照及其真实时间，过期时标待确认；切换与成功确认继续实时校验控制权、新鲜证据和原门禁，不能以界面缓存替代。

| AC | 层级 | Given | When | Then |
| --- | --- | --- | --- | --- |
| AC-UPG-002.1 | 真实升级 | 持续访问平台详情／健康接口并提交带幂等键的合法操作 | 候选就绪、路由切换、旧 API 退役 | 10 次／秒探测无发布导致的拒绝／5xx，响应在 2 秒目标内；操作只产生一次副作用 |
| AC-UPG-002.2 | 真实升级 | 候选版本启动慢、readiness失败或现有业务／候选／验证／恢复保留量超出容量预算 | 从候选准备前开始部署尝试 | 请求和既有连接继续由来源服务承接，独立控制状态可查；预算不足先延期，不先关旧服务、停止任务腾空间或暴露半初始化候选；校验与采集自身受资源限额 |
| AC-UPG-002.3 | 跨仓浏览器 | 浏览器已解锁并打开原任务 | 升级、刷新页面 | 访问会话仍有效，回原任务；没有因版本更新进入首次初始化向导或再次要求口令 |
| AC-UPG-002.4 | 真实升级 | 用户终端连接及运行进程都活跃 | 控制 API 替换 | 运行 owner 保持；稳定连接入口保持服务，必要的重新 attach 只改变传输连接 |
| AC-UPG-002.5 | 真实升级 | 主仓只改文档／设计／测试，API 运行内容未变 | CD 发布，并在用户另行发起时应用该版本 | CD 不更新实例；应用时复用相同 API 产物，不重建／重启 API 或 RuntimeOwner；目录及实例记录均能追溯三仓完整 SHA与实际复用产物 |

### REQ-UPG-003 · 刷新后续接原任务与原终端 {#REQ-UPG-003}

从 URL 或已存选中记录定位原项目和 Sandbox；无头任务再定位原 AgentTask。重新认证后读取原终端清单，恢复 Agent／用户终端标签及上次选中标签，再 attach 已存在会话。可持久化的选择书签必须是无授权能力的公开标识；口令、token、cookie、socketSessionKey 和可用作接入凭据的 shellId 不写入本机选择存储。

同页短断连保留 xterm 画布；浏览器整页刷新后，终端从原 tmux 会话恢复当前屏幕，任务日志按持久化序号续播。无限历史滚屏、未提交的终端输入和客户端内存画布不属于恢复承诺。无法确认原终端时保留任务上下文，不暗中新开替代终端、不重复运行 Agent。

| AC | 层级 | Given | When | Then |
| --- | --- | --- | --- | --- |
| AC-UPG-003.1 | 跨仓浏览器 | 原项目／任务已选中且仍存在 | 升级后手动刷新或直接刷新 `?taskId=` 页面 | 读取同一 Sandbox，返回原项目与任务；不调用 create、start 或 provision |
| AC-UPG-003.2 | 跨仓浏览器 | Agent、两个用户终端已存在，当前选中第二个用户终端 | 刷新并完成认证清单校验 | 恢复原标签及当前标签，attach 同一 tmux 会话，不新建替代 shell |
| AC-UPG-003.3 | 协议／跨仓 | 无头任务正在输出 | 刷新、断线后恢复 `taskId + fromSeq` 订阅 | 原执行轮次保持，已确认日志顺序连续、去重；初始指令不重发 |
| AC-UPG-003.4 | 跨仓浏览器 | 原任务详情或终端清单暂时超时／服务恢复中 | 尝试恢复 | 保留 URL、选择与已有标签；不按不存在清除，不悄悄回新任务页面 |
| AC-UPG-003.5 | 协议／跨仓 | 断线前存在未确认的输入或命令提交 | 重连或刷新 | 不自动重放终端输入／initialPrompt；合法幂等操作按原请求标识查询结果 |
| AC-UPG-003.6 | 跨仓浏览器 | 服务端确证原任务销毁，或原用户终端真实退出 | 恢复选择 | 说明准确原因并提供原有合理出路；不把普通连接失败当销毁，不替换原会话 |

### REQ-UPG-004 · 连接状态和运行状态如实区分 {#REQ-UPG-004}

升级／重连是连接层状态，不写成任务的 stopping、stopped、failed。断连时保留工作台、任务树、标签、输出和已有表单；不抢焦点、不盖住画布，不发送尚未连通的终端输入。只有服务端确认原运行身份和状态后才显示“任务仍在运行”。状态未确认时写“连接暂时不可用，正在确认任务状态”。

正常升级或刷新后，恢复到原终端可交互的目标时间为 **5 秒内**；超过 **15 秒**提供轻量的手动重连／状态检查入口。超过时间不是任务终态，也不触发重新启动。事件列表的旧状态标为最后已知值，恢复后重新同步。

### REQ-UPG-005 · 新版提示低打扰，由用户主动升级及刷新 {#REQ-UPG-005}

CD 发布版本后，目录经真实性、架构、版本链和兼容核验，确有适用于本实例的 installable newerRelease 时，显示 `available`／待操作人升级。顶栏右上 32px 中性 CircleArrowUp 和未暂停的紧凑常驻浮卡写“发现新版本”，分别列当前实例服务与可安装版本；已通过本实例已有访问保护的操作人可直接点击“立即升级”，不出现独立授权入口。此阶段无 attempt、无百分比，不把新版已发布写成本实例已升级，也不因页面恰好已是目标构建而隐藏仍待升级的实例状态。

用户明确点击且服务端通过权限、精确目标与instance CAS校验后，持久接纳带requestId的用户级升级操作；阶段资格成立后才创建对应真实技术attempt，按固定计划下载／验证、迁移、候选与切换。尚无技术attempt时标“准备升级”，不能把operationId当attemptId。右上同一浮卡显示实例vA→最终目标vB与真实阶段／进度；重复点击、重开和结果未知只查询原请求，不重建用户操作、不暗换目标或停止任务。目录检查、首次／次日开页、关闭／稍后和CI重试均不发送升级命令。

同一操作人串行升级后，浏览器恢复的原请求A可能已不在最新实例状态B中。查询证实A成功、失败或延期等明确终态后，只解除A自己的本地等待和同requestId持久标识，不以A的历史结果覆盖B的版本、阶段或页面刷新资格。迟到结果须仍匹配当前实例、访问scope、存储key和待确认requestId；存储已记录下一请求时不得删除。A尚未终结、暂查不到、响应无效或网络失败均保留原ID继续只读查询，不重复提交。

需要兼容桥时，一次用户命令固定最终目标、完整已签节点／digest／顺序及允许的恢复范围。该用户级操作可以顺序关联多个技术attempt，但同时至多一个活动技术attempt；桥接确认仅显示“兼容准备完成”，继续原固定链，不要求第二次点击。用户级整体进度在最终目标确认前保持0–99%或未知；底层桥接attempt已确认的100%和真实历史不改写。链中断停止推进，已确认中间版本与实际组合保留；再试由用户明确发起，不跟随目录更新自动扩链。

实例激活和整体确认后才到 100%。只有目标 Web 在本实例实际入口 ready、兼容且与 loadedWeb 不同时，浮卡提供“刷新页面”，刷新接回原任务；仅 API 更新、相同 Web artifact 或已实际加载相同页面时不要求刷新。按钮显示条件为独立核验的 available、有效实例升级进行中或已安装待刷新；available 和实际待刷新可有静态小点，进行中无点。无可安装更新／纯候选、失败／延期／未知且无其他有效更新状态时隐藏，系统卡仍可查版本、历史进度和原因，不自动跳页。

关闭 available／进行中／待刷新浮卡，或在这些有效状态的完整 popover 选择“稍后”，都将**当前操作人＋本实例＋浏览器本地自然日**记为暂停自动浮卡；稍后同时关闭 popover。当天跨页、整页刷新、新标签和多标签同步保持暂停，available→操作人发起→进行中→待刷新、百分比／阶段变化及同日新版本不能绕过。下一本地日期只重新核验真实 available／进行中／待刷新状态并恢复提醒，不升级、不按滚动 24 小时或永久 revision／attempt 去重。偏好仅存非凭据作用域和日期，保留现有身份与实例错配拒绝，不增加用户切换流程；有效顶栏入口与已进入平台操作人手动发起、合法刷新仍保留。

浮卡不占正文布局、不推动画布或任务树、不移焦、不动画、不定时消失、无全宽横幅；完整 popover 仅主动打开。系统卡和 popover 可手动只读检查、查看详情、稍后，以及按状态分别立即升级或刷新页面；Esc／外部关闭只收 popover，不记当天暂停。刷新前沿原离开规则保护未提交表单和中文组合输入，刷新只重载并续接，不部署、不新建／停止／迁移沙箱或重跑任务；“立即升级”才是独立的服务端受权命令，不能与刷新混为一个动作。

### REQ-UPG-006 · 旧新版本兼容与安全迁移 {#REQ-UPG-006}

稳定控制协议与业务版本分别声明兼容范围，不匹配时延期业务升级并说明需独立底座维护，不能让业务包暗中交接控制器。控制操作epoch／租约只授权编排；业务writer守卫仍与业务写入在同一数据库事务内校验。Control Agent不直接写业务库、不持有SDK home或Guest停止权限；不得以控制权有效替代旧writer已释放的证明。

版本兼容按明确的协议能力／支持范围判断，不凭源码 SHA 或 schema hash 不同就强制刷新。兼容窗口覆盖 Web A／API A、Web A／API B、Web B／API B 和 Web B／API A，以及原 RuntimeOwner；新增可选字段等兼容变化维持原会话。页面自主刷新不能解决旧代码无法理解当前数据库或新写入语义的问题。

**数据库在线转换为 planned 交付。** 对原始不兼容变更，必须优先按以下顺序拆分：上线能理解旧新表示的兼容桥版本 → 增加影子字段／表 → 唯一 StateCoordinator 在同一事务内维护两种表示 → 按版本／游标分批回填并对账新增、更新和删除 → 灰度读取新表示 → 切读新表示并保留旧表示及回退窗口 → 旧代码、页面、运行 owner、在途操作的依赖退出且回退窗口关闭后，独立执行 contract。兼容桥不是第二个业务写者；迁移执行者持唯一迁移锁编排批次，数据更新仍经过 StateCoordinator 的唯一写入控制，重复／恢复批次不能覆盖更晚的更新或复活已删除数据。

这条版本链仅在用户明确发起、实例接纳并固定相应计划后执行，目录兼容预检只读，CD 发布不启动实例迁移。独立 contract 的破坏性步骤另须用户主动发起并通过门禁，不能在窗口到期或 CD 重试时自动删除旧结构。

独立清理入口放在系统页版本卡的“旧数据格式清理”区域。展示所属服务版本、回退窗口截止、旧版本读者及已受理请求的阶段／行数；只有服务端确认当前权限、精确计划和实例状态可执行时，提供“清理旧数据格式”。确认对话框说明历史回退资格将关闭，取消不发起请求。受理结果不明时只查询原 requestId，不重复提交。清理失败或结果待确认保留升级历史的100%记录，并独立展示当前清理状态。

本轮项目名称转换的实施实例是 `projects.name` 到影子表示中的 `display_name`：回退窗口内维持双表示；独立清理后新表示成为名称权威，旧字段仅保留平台内部占位值。这里收缩的是旧名称表示，未执行全局删除列／全表重建，不能把数据表示 epoch 当作新增全局数据库迁移。未经连续性验证的全局不兼容 DDL 继续延期，原任务保持运行；实现与实际验收状态见[实施记录](../../testing/results/2026-10-12-升级实现验证记录.md)。

回退窗口内，旧版不能理解的新语义必须禁用或隔离，不能静默丢弃、截断或近似转换成旧表示。若无法无损保留旧表示，必须在接纳这类新语义之前明确标记不能向该旧版回退、只允许修复前进，并通过相应故障恢复门禁；不能等故障后才发现旧版已不可用。

可隔离的影子转换错误不应使原本合法的旧业务普遍失败。旧表示仍是完整权威、没有不可旧表示的新语义时，可由已演练的兼容桥撤掉新读，保留旧业务与持久变更记录同事务提交，暂停迁移并标影子不可切换；修复后只补投影并重新对账，不重放业务。共享库损坏、原事务／变更记录提交失败或旧权威不完整时不得这样降级，也不得提前返回成功。

SQLite 的 WAL 不构成无锁 DDL 或全表重建保证。优先影子结构、限额回填和短 epoch 切换，在任务持续写入负载下验证 REQ-UPG-002 的连续可用预算；超预算则暂停／延期该变更或限制对应新功能。必要短维护是穷尽在线方案后经证明的残余步骤，单列影响与安排，不计作常规无停机验收通过，不停止原 owner 或已有任务。不能在任务持续产生结果时停库拷贝或恢复发布前整个数据卷，也不能把两个持有同一 BoxLite home 的 API 直接并排启动。

### REQ-UPG-007 · 升级失败保留原服务，安全回退 {#REQ-UPG-007}

恢复权威由独立控制账本以新recoveryId／epoch取得，不要求原失败attempt复活、重新claim或继续持有未过期租约。退流、组件退版和灾难数据恢复分别核验：优先最小退流，必要writer退版重新交接且保留当前数据；数据卷恢复不属于普通在线恢复。超时／ACK丢失先对账原动作，重启后可续同一恢复过程，不能盲重放。恢复失败有界停止并报告受阻条件，不自动A↔B循环或新建升级。候选清理只退役确证无入口、写权、Owner／Guest、在途引用及回退依赖的本次资源；未知保留，资源准入须防止连续失败无限叠加候选。方案见[失败恢复与回滚](../../ops/2026-10-20-升级失败恢复与回滚方案.md)。

**熔断和恢复为 planned 交付。** 用户主动发起的实例升级计划中事前固定每阶段健康／兼容门禁、统计劣化阈值、观察窗口、观测有效期及安全回退资格；一次明确发起允许该计划范围内安全自动熔断与回退，不允许 CD 建立升级 attempt。任何一次误 stop、重复执行、双写者、数据损坏或任务身份错配均立即熔断；错误／延迟、积压等统计劣化或观测缺失达到预设策略即熔断。熔断先停止升级推进、扩流／新增分配步骤和后续迁移批次。候选尚未接流时可隔离、不接生产请求；已经切流时，没有合格 fallback 不能先将唯一安全的 B 路由清零或关闭，只在回退资格成立后转移流量。已接纳操作按原幂等标识确认结果，进行中的事务在安全边界处理；不能将熔断理解为停止健康服务、原任务或自动化。

候选失败不影响健康原服务。切流后只有回退目标健康、能兼容当前数据库与新版已接纳数据、已加载 Web B、全部运行 owner，并且发布控制权有效时，才允许自动退 API 路由／Web 指针。退 Web 指针只影响之后加载的页面，已有 Web B 不会自动变成 A。回退保留当前最新业务数据、产物、游标、取消意图、幂等记录和原执行身份，不恢复旧整卷、不重放业务。共享数据库或 owner 故障不能假定由 API 回退解决；资格缺证据时冻结危险步骤，保留确证仍健康的服务组合，按原因修复前进或专门处置，不盲目退版。

回退使用关联原 attempt 的独立 recoveryAttempt、新 generation 和预先固定的恢复工作计划，在该次用户发起所允许的安全恢复范围内自动执行。实例整体激活确认前失败的原 attempt 记录 failed／reverted；已 activation-confirmed 后发生新故障不得改写原成功结果或当时的 100%，须追加故障、当前 ready 撤销及独立恢复事件。CD 的 published 历史与这些实例结果分开保存，两者都不改写。原进度不沿用作恢复或新升级的完成进度，恢复旧组合不等于升级目标已安装。熔断后同 attempt 不循环重试；诊断及用户检查只读，修复后须已进入平台的用户再次明确发起，才创建新 attempt 重过全部门禁，CD 不能自动重发，新 target 也不能擅自替换原目标。

用户页面继续聚焦任务。失败、延期或未知且无另外核验的有效 available／进行中／待刷新状态时，隐藏顶栏更新按钮和浮卡，不自动跳页；用户主动进入系统版本卡可查看真实阶段、简明原因及只读检查，具备权限且门禁成立时自主重新发起升级。候选失败、旧 owner 等待排空等完整运维证据放在维护者状态与实例升级记录中，不要求用户停止任务或重新发起来配合升级。

系统卡分开说明“服务当前可用性”“上次完整确认版本”“本次最终目标与结果”“实际页面版本”。失败后部分角色已切换时显示“升级未完成，部分组件已更新”，不能套用“旧版完全未变／已全部回退”。有真实可用性证明才能说可继续使用；无证据标待确认。仅当后端针对当前实际组合、数据与固定目标给出合格修复计划时提供有明确目标的修复动作；没有方案只给只读检查与脱敏诊断，不提供无条件回滚／重启／恢复旧数据按钮。

### REQ-UPG-009 · 当前版本与升级目标常驻可查、状态如实展示 {#REQ-UPG-009}

系统主动详情单列控制系统版本／协议、恢复当前阶段与确认时间，不将其冒充业务已确认版本或新增普通更新按钮。业务API不可用时仍可从稳定同源控制入口取得最近确认状态及真实新鲜度。简明故障原因和脱敏诊断关联标识可复制，凭据／终端／模型正文不得进入诊断；基础观察失效如实标待确认。恢复结果与原升级结果各有状态，不能用“已发送回退命令”替代“服务已恢复”。

版本信息属于正常平台界面。系统页始终分别显示**本实例已确认服务版本、可安装版本、当前实际页面版本、已接纳 attempt 的固定目标与状态／进度、确认时间**。CD 目录的 published release、available 和实例 activation-confirmed 是不同事实；发布新版不推进实例服务版本，检查版本也不执行升级。页面已是目标构建不能掩盖服务尚待升级，只有 API／元数据更新或 Web artifact 复用时不要求再次刷新。

**可安装版本来源为 planned 契约。** 受信发布目录须验证精确 release manifest、安装包 digest、签名或等价受控信任与 provenance、三仓及实际组件身份、目标架构／平台、允许版本链、schema 与 API／Web／owner 兼容。目录标签更大、GitHub latest、单独 staged／candidate 或另一实例版本都不足以标 installable。用户发起时实例重新核验精确目标和安装计划，禁止目录新版本或迟到响应改写已接纳 attempt 的 target；每实例 Web 入口固定其已确认产物，CD 不切共享生产 alias 来替未升级实例更新页面。

本实例当前服务取受信激活 ledger，实际 loadedWeb 取不可变公开 Web build manifest；available release 与二者独立。复用旧 API artifact 或旧 RuntimeOwner 时仍记录真实 SHA／digest／归属，新整体实例版本只有应用并确认后才推进，CD 仅发布时不能冒充已应用。无法确认版本时标待确认／上次值与时间，无确认可安装目标写暂无可用更新，只有成功核查更新源后才说已是最新，不以 package.json 兜底。

available 没有 attempt 或百分比。实例升级沿用已有访问保护，由服务端校验会话、Origin／CSRF 与实例绑定；已进入平台用户的“立即升级”发送精确 target 与 requestId 的幂等命令，instance CAS 只允许一个活动 attempt。重复点击／页面重开／断网后按 requestId 查询同一结果；直到接纳才开始下载、校验、迁移、候选和切换。未通过已有访问保护时不能读取受保护状态或提交命令；普通检查／详情／首次与次日开页／关闭／目录变化／CI retry 不建立 attempt、拉取执行包、迁移或换入口。新升级、新 target、熔断后再试与独立破坏性 contract 均须用户重新发起，不由 CD 自动生成。

**实例百分比来源为 planned 契约。** controller 绑定 instanceId、attemptId、generation、单调 sequence 和已接纳的固定 target／计划，按真实完成工作量和阶段证据提供 0–99%。CD 构建／打包／发布进度不是实例升级进度；前端不按 timer、请求、时长或任务输出推算。available 不伪造0%；已接纳 attempt 缺观测时标进度待确认，有历史可附最后阶段／百分比／时间，过期或跨实例／attempt 响应不能覆盖新事实。
