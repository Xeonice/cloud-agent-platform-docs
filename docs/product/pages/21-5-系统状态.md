## 9A. 诊断第 ⑧ 项「预制镜像就绪」（v1.1 新增）

### 为什么补这一项：七项全绿，一个 Task 都建不出来

2026-08-28 实测的真实形态：容器运行时在、`/dev/kvm` 可用、磁盘 200G+、端口没被占、外网通、WS 回环正常、`DATA_ROOT` 文件系统正确——**七项全绿**，而用户点「发起任务」得到的是：

> 无法用当前配置创建：平台还没有可用的预制镜像。当前 `SANDBOX_DEFAULT_IMAGE` 指向 `ghcr.io/agent-infra/sandbox:latest`，而它没有注册进来。

⚠️ **前七项问的是「这台机器能不能跑东西」，没有一项问「平台自己备齐了没有」。** 而后者才是「能不能建出第一个 Task」的决定条件。

⚠️ **更糟的是报错出现的时机**：它出现在**新建任务弹窗里**——用户已经建好项目、选完运行时、填好指令、点了按钮，才被告知平台根本没准备好。这是整条链路上最晚、也最挫败的时机。

### 检查链（五步，任一失败即止，每步的修复动作都不同）

| # | 检查 | 失败时说什么 |
|---|---|---|
| 1 | `SANDBOX_DEFAULT_IMAGE` 配了没有 | 没配 ⇒ 回落到内置默认（`alpine:3.20`），那里面没有沙箱 API、没有 tmux、没有常驻进程，容器一退端口就空——**必炸**。给出配置位置 |
| 2 | 它指向的镜像在 registry 里存不存在 | ⛔ **先问「字节够不够得着」，够得着就自己搬**（P21-8 §2 ⇒ 新判据）：本机 docker 库已有 / 发布资产清单里有 / 上游 registry 可达 ⇒ 给 **[准备镜像]**，平台自己 push 或装载；只有 Dockerfile、非 build 不可时，才给 registry 地址与 `docker push` 的完整命令 |
| 3 | **它是不是平台自建的那一张** | ⚠️ 这一步最容易被误解：上游镜像（`agent-infra/sandbox`）只是平台镜像的 `FROM`，注册时会被**血统检查**拒。报错必须说清「注册也会被拒」，否则用户会以为只是少做了一步注册，照着去注册再撞一次墙。给出构建脚本路径 |
| 4 | 有没有注册进平台且 `validationStatus = valid` | 给出「平台开机会自动播种」的说明与重启提示 |
| 5 | 本机是否已 staged（rootfs 铺好没有） | ⚠️ 这一步**不是失败**，是 ℹ️ 提示：未 staged ⇒ 告知「第一个 Task 需要数分钟准备镜像」（实测 13GB 镜像冷启动 190 秒） |

⛔ **五步的失败不许合成一条「镜像不可用」**——它们的下一步动作完全不同（改配置 / 推镜像 / 换成自建的那张 / 重启平台 / 只是等一会）。合成一条等于把诊断退化成一个红灯。

### 与向导的关系

同一条检查链在 P21-8 §2 的初始化向导里**提前跑一次**——那才是它该出现的时机：**在用户建第一个项目之前**，而不是在他点下「发起任务」之后。

⛔ **第 2 步与第 5 步都要能「自己动手」，不能只报事实**（2026-09-05 订正）。第 2 步见上表；
第 5 步（未 staged）今天只说「第一个 Task 需要数分钟准备镜像」，那句话是对的，但同样
**只描述、不提供**——用户看到它之后除了等没有别的选择。⇒ 两处共用同一个准备动作
（`POST /api/system/preset-image/provision`，10 §6），区别只在触发时机与紧迫度：
第 2 步是「不做就用不了」，第 5 步是「现在做能省下第一个 Task 的等待」。

⚠️ **搬运之前必须先过第 3 步的血统检查。** 上游 `agent-infra/sandbox` 只是平台镜像的
`FROM`，搬来了照样过不了注册——**那等于白搬一遍字节**。血统靠
`resolve()` 读 manifest + config blob 判定，**零字节层下载**（04 §7 ★），
所以这个前置检查很便宜，没有理由不做。

## 9B. 诊断第 ④ 项「端口占用」要报**被谁占了**（v1.1 修订）

⚠️ 「端口 3000 被占用 ❌」这句话没有任何可执行性——用户下一步要做的是**找出占它的东西**，而这恰恰是诊断能直接答、用户手动查却很费劲的部分。

2026-08-28 的实证：本机 3000 被占，`lsof -nP -iTCP:3000 -sTCP:LISTEN` 报出 `com.docke`（Docker Desktop 的端口转发），**看到进程名的那一刻才判断出**是 Docker 里另一个应用占着，而不是平台自己起了两份。只报「被占用」的话，这一步要用户自己去查。

⇒ 这一项必须带上：**端口号 · 占用它的进程名与 pid · 平台原本要用它做什么**。

⚠️ 检查的是**平台配置的端口**（`PORT` 等实际取值），不是硬编码的 3000——用户改过配置的话，检查一个他没在用的端口只会制造假警报。

## 9D. 两条实测订正（2026-08-28 落地后复验）

后端落地后在本机复验，抓到两条**「把好的东西报成坏的」**——它们比漏报更贵，因为都会把
用户支去做一件不需要做的事。两条都已修。

### ⑤ 外网连通：带端口的本地 registry 被判成不可达

实测：`SANDBOX_DEFAULT_IMAGE=localhost:5001/platform/sandbox:v2`，同一时刻
`curl http://localhost:5001/v2/_catalog` 返回 **200**，而诊断报「`localhost:5001` 不可达」，
建议还是「内网环境通常要配代理」。三重叠加：

| # | 根因 | 为什么它单独也足以致命 |
|---|---|---|
| 1 | 坐标的权威部分 `localhost:5001` 被**整个当主机名** | `tls.connect({host:'localhost:5001'})` 必然 `ENOTFOUND` |
| 2 | 探测端口**硬编码 443** | 内网 registry 常年跑在 5000/5001 |
| 3 | 本地 registry 是**明文 HTTP**，TLS 握手必失败 | —— |

⇒ 修法：坐标拆成 `host` + `port`；**只有 loopback 降级成明文**并改探 registry 自己的
`/v2/`（**200 与 401 都算通**——「要认证」与「没起来」是两件事）。
⛔ **外部 registry 不因为带了显式端口就降级 TLS**（`registry.corp:5000` 依然要 TLS）——
为了让某一台机器变绿而放掉校验，会让这项检查在一个中间人面前照样报绿。

⚠️ 顺带修掉同一处的两个静默缺陷：**loopback 一律不走代理**（代理修不了本机的东西），
以及 **`noProxy` 此前是「存了但完全没人读」**——设置页收下了排除清单，探测却照样把内网
地址送进代理，于是「配了 NO_PROXY 还是报不通」查无可查。

⛔ 这一项失败时若目标是 loopback，**建议里一个字都不许提代理**：那是本次事故的第二半
伤害——诊断不但把一个好的 registry 报成坏的，还把用户支去配一个根本不需要的代理。

### ⑦ DATA_ROOT 文件系统：APFS 被报成「未知 magic 0x1a · 不支持 reflink」

实测（macOS/APFS）：报「未知（magic 0x1a），不支持 reflink —— 每个 Task 工作区会实占
一份完整副本」+「建议换 Btrfs/XFS」。两处都错：

- `0x1a` 是拿 **Linux 的 statfs 魔数表**去查 macOS 的 `f_type`（那是 **vfs 类型序号**，
  不是魔数）⇒ 现在按平台取名字（Linux 读 `/proc/self/mountinfo`、darwin 读 `mount`），
  **魔数表只在 Linux 上查**；
- `COPYFILE_FICLONE_FORCE` 在 darwin 上恒 **`ENOSYS`** —— libuv 的 FICLONE 分支**只有
  Linux 有**，那句 ENOSYS 说的是「这个平台的 `copyFile` 不实现 reflink」，**不是**「这个
  文件系统不支持克隆」（APFS 本身支持 `clonefile`）。

⇒ 结论改成**三态**：`支持` ✅ / `不支持` ⚠️（附换文件系统的建议）/ **`无法判定` ℹ️**。
非 Linux 走第三态，并说清**为什么谈不上 CoW**：`FsWorkspacePreparer` 只在
`platform === 'linux'` 时用 `cp --reflink=auto`，其余平台直接整份复制 ——
**这是开发机形态的既定行为，不是可修的故障**，所以那一条**不给任何建议**。

⚠️ 探测本身也改成探**平台真正会用的那条路径**：Linux 上用 `cp --reflink=always`
（`always` 而不是 `auto` ——`auto` 在不支持时静默退化成整份复制并返回成功，正好把
「不支持」测成「支持」）。

⚠️ **别让第三态退化成一个恒 ⚠️ 的噪音项**：它在 macOS 上是**稳定**结论，所以必须是安静的
ℹ️。一个恒 ⚠️ 的检查项等于没有检查项——看久了没人看，还会把另外七项的可信度一起拉低。

## 9E. 内存水位取数错误（2026-08-28 第三条实测订正）

⛔ **这一条比前两条严重：它不只是误导，是直接挡住功能。**

实测：后端报 `ram: {usedPercent: 96.3, level: "critical"}`，而同一时刻这台机器真实占用
约 **59%**。后果是前端 `overallResourceLevel`（取 CPU/RAM/磁盘三档的**最大值**）把整页
判成 **「🔴 资源耗尽，无法创建新 Task」** —— 平台在一台只用了一半内存的机器上拒绝干活。

### 根因：`os.freemem()` 返回的不是「可用内存」

它只算**当前完全空闲**的页：

| 平台 | `freemem()` 漏掉了什么 |
|---|---|
| macOS | `inactive`（实测 12 GB）/ `speculative` / 文件缓存 —— 全都可回收，却被算成已用 |
| Linux | buff/cache —— 同理 |

### 修法：两个平台各取权威口径

- **Linux**：`/proc/meminfo` 的 **`MemAvailable`**，内核自己算好的答案。
  ⛔ **不用 `free + buffers + cached` 那个老公式** —— 它在有 cgroup / 透明大页的机器上会
  算偏，而 `MemAvailable` 正是为取代它才进的内核。取不到（内核 < 3.14）⇒ 如实降级。
- **darwin**：`vm_stat` 的 `free + inactive + speculative`。
  ⚠️ **`Pages purgeable` 刻意不加**：实证 `free+active+inactive+speculative+throttled+wired+compressor`
  已经等于 `hw.memsize`，purgeable 是 active/inactive 的**子集**，再加一次就是重复计数。
  ⚠️ 页大小从 `vm_stat` 表头取，**不写死 4096** —— Apple Silicon 是 16384，写死差 4 倍。

### 测不准时：`level` 钉在 `ok`

⛔ **绝不让一个测不准的读数把机器判成「耗尽」。** `usedPercent` 仍给出 `freemem()` 口径的
数字（那是唯一还剩的），但**不拿它判档**，并打一条 warn 日志。与第 ⑦ 项 reflink 的三态
同一条纪律：「不知道」既不是「好」也不是「坏」，但它**绝不该**变成「坏」。

### 顺带确认的两条（都**没有**改）

- ✅ **磁盘那条是对的**：后端 93.4% 与 `df` 的 94% 吻合。（Finder 显示更宽裕是因为它把
  purgeable 算进可用，那是 Finder 与 `df` 的口径差异，不是平台的 bug。）
- ⏳ **CPU 那条口径要记一笔**：`usedPercent = loadAvg1m / cores` 是**饱和度**，不是 CPU
  时间占用率。本机实测 loadavg 2.17 / 10 核 = 21.7%，而同一时刻 `top` 报真实占用 16%
  （11.2% user + 4.8% sys）。两者相关但不相等 —— loadavg 数的是**可运行线程数**，
  Linux 上还含 D 态（不可中断 IO）线程。⚠️ 本平台恰恰重 IO（clone 大仓、拉 13GB 镜像），
  所以存在「CPU 空闲却因 IO 把 loadavg 顶到 ≥95% 而报 critical」的假阳性路径。
  **本轮未改**（前端刚照现有契约落地，改字段语义要跨仓同步），单独记为待办。

## 9F. 三条「把用户推向 docker」的误判（2026-09-05 实测订正）

⛔ **这三条单独看都只是文案，合起来是一条错误的产品结论。** 一个 macOS 用户走完初始化
向导会连着读到：

> ① 「微 VM 档位（boxlite）在此平台**不适用**」 ② 「容器运行时**可达**」
> ③ 「去 `docker run` 一个 registry」

**每一条都在把他推向 docker，而他机器上 boxlite 本来就跑得好好的**——`hostPreferredProvider()`
是 `darwin ? 'boxlite' : 'aio'`，boxlite 在 macOS 上走 Hypervisor.framework，官方原话
"no root, no background service"。实测佐证最强的一条：本机第一次实例化 `JsBoxlite` 失败的
原因是 **`Failed to acquire runtime lock at ~/.boxlite`**——锁正被**运行中的后端服务**持有，
也就是说 boxlite 此刻就在这台 mac 上跑着，而诊断在说它「不适用」。

### 判据总纲：一项检查报多重，取决于「**谁需要它**」

⚠️ **无条件要求某个依赖在，与恒 ⚠️ 的噪音项是同一种失败**（P21-5 §9D 末尾那条纪律的另一面）。
默认档由 `hostPreferredProvider()` 按宿主定，权威读数是 provider registry 的
`defaultProvider`（第三方 provider 仍可把它移走）：

| 这一项 | 默认档需要它 | 默认档不需要它 | 默认档是第三方 provider |
|---|---|---|---|
| 依赖在 | ✅ | ✅ | ✅ |
| 依赖不在 | ❌ 它挡住了开箱即用那条路 | ℹ️ 如实说「当前默认档不需要它」 | ⚠️ 「不知道它要不要」——**不猜** |

### ② `/dev/kvm`：在 boxlite 唯一默认启用的平台上报「不适用」

`/dev/kvm` 是 **Linux 专有**的 KVM 设备节点，macOS 上永远不会有——这句话对，但由它推出
「微 VM 档位在此平台不适用」是**反的**：那只是 boxlite 在 Linux 上的形式，macOS 上的形式
是 Hypervisor.framework。**这条检查把「Linux 上的实现细节」当成了「boxlite 的通用前置」。**

⇒ 按平台问对的问题：

| 平台 | 问什么 | 满足时 |
|---|---|---|
| **darwin** | Apple Silicon（Intel 官方标注 coming soon）· macOS 12+ · Hypervisor.framework 在 · `kern.hv_support` | **✅**（此前恒 ℹ️「不适用」） |
| **linux** | `/dev/kvm` 可读写 | ✅ |
| 其余 | —— | ℹ️ 如实说 boxlite 不支持，**不提 `/dev/kvm`**（那与结论无关） |

⚠️ **版本判据是 Darwin 主版本（macOS 12 = Darwin 21），不做「Darwin − 9 = macOS」那个映射**：
那个偏移在 macOS 26（Darwin 25）上已经断了，写一张映射表只会在下一个大版本再错一次。

⚠️ **`kern.hv_support` 问不出来（`null`）不许判坏**——与 reflink 三态、内存 `unmeasurable`
同一条纪律：一个测不准的读数绝不该把一台好机器判成坏的。

⚠️ **展示名跟着改**：`/dev/kvm 可用（boxlite 微 VM）` → **`微 VM 档位（boxlite）可用`**。
在一台报 ✅ 的 mac 上，标题写「/dev/kvm 可用」而正文写「Hypervisor.framework 就绪」自相
矛盾，而用户先读到的是标题。⛔ **检查项 id（`dev-kvm`）不动**——它是跨仓契约的闭集成员
（两仓 `DIAGNOSE_CHECK_IDS` + canonical 串 + 前端替身，改动要四处同步并过 B5），而 label
只是逐帧下发的展示文案，改它不碰任何契约。

### ① 容器运行时：一个假 ✅，以及一个不该有的 ❌

**假 ✅ 那一半**：「socket 文件在」≠「daemon 活着」（Docker Desktop 停掉后文件还留着），
而「connect 成功」「HTTP 200」也都还差一步——那个地址上可能坐着别的服务。
⇒ ✅ 必须有**证据**：docker 的 `/_ping` 会带 `Api-Version` 响应头并回一行 `OK`，认这个才算通，
否则如实说「有服务在应答，但它不像一个容器运行时」（与第 ⑤ 项 `/v2/` 那条「不像一个镜像
仓库」同一口径）。⚠️ **一个假 ✅ 比报错更危险：它让人完全不去查 docker。**

**不该有的 ❌ 那一半**：判据挂到「谁需要它」上（见上表）。一台默认跑 boxlite 的 mac 上
docker **一个字节都不需要**，此时报 ❌ 是在一个完全健康的部署上亮红灯，还把用户支去装一个
他不需要的东西。⇒ 改报 ℹ️「当前默认档 'boxlite' 是微 VM，不需要它，这不挡任何默认路径」。

### ⑤ 本机 registry 的建议：躲过了代理，掉进了 docker

**这一项本身是对的**——微 VM 档确实要这个本地 HTTP 镜像站（BoxLite 自己的镜像库没有断点
续传，十几 GB 的预制镜像靠它中转）。错的是建议只给了 `docker run`：在「mac + boxlite +
没装 docker」下**执行不了**，还会让人以为平台依赖 docker。

⛔ **讽刺的是这段代码上方就写着同型纪律**（§9D 末尾：「诊断不但把一个好的 registry 报成
坏的，还把用户支去配一个根本不需要的代理」）。它躲过了「支去配代理」，掉进了「支去装 docker」。

⇒ 文案要回答三件事：**谁**要它、**为什么**要、以及一条**不依赖 docker** 的路——
① 起任意一个 OCI registry（zot 是单个二进制）；② 有 docker 的一条命令；
③ 把 `SANDBOX_DEFAULT_IMAGE` 指向一个已经可达的仓库（公网也行）。

### 顺带记下、本轮**没有**改的两条

- ⏳ **第 ② 项在 Linux 上是个恒 ⚠️ 的噪音项**：严格按上面那张表，一台默认跑 aio 的 Linux
  机器上没有 `/dev/kvm` 应当是 ℹ️ 而不是 ⚠️（这一项因此在绝大多数 Linux 部署上常年顶着
  一个黄灯）。判据总纲已经写在这里，但改它会动到 Linux 侧的既有口径，单独排期。
- ⏳ **第 ⑧ 项与向导第 1 步问的不是同一个问题，界面上却没说**：`preset-image` 报 ✅
  （镜像**已注册、已 staged**）而向导第 1 步报 `localhost:5001` ❌（registry **此刻不可达**）
  ——两个结论可以同时为真（镜像早就铺开在本机了，registry 只是现在没起）。**结论不冲突，
  但界面没告诉用户它们问的是两件事**，用户只会读成「诊断和向导互相矛盾」。

## 10. 审计日志与运行日志（v1.1 新增）

### 9C. 落地口径修正（2026-08-28）

⚠️ **保留卷统计并入 `GET /api/system/resources`，不再有 `GET /api/system/volumes`。**
本页 §7 此前并列了两个端点，而它们回答的是同一屏上同一张卡里的同一件事，且分母
（`DATA_ROOT` 总容量）只有 `/resources` 那一侧有 —— 拆成两个端点意味着前端要自己把两个
响应拼起来算百分比，也就是把「保留卷占了磁盘多少」这条产品规则抄到第三个地方。

⚠️ **「保留卷」有确切定义**：`cleanup({keep:true})` 之后状态文件写成 `kept` 的那些工作区。
还在跑的 Task 的工作区是 `ready`，把它们算进「30 天内会被清理的成果」既让数字虚高，
也会让用户以为清理动作会波及正在跑的任务。

⚠️ **体积按实占块数算（`blocks × 512`）而不是文件逻辑大小**：这一项要回答的是「删了能腾出
多少」，而 CoW 加速开着时两者能差一个量级。目录太多时统计会停并如实标 `truncated` ——
截断了却说「45GB」，用户清完发现没腾出预期的空间，此后不会再信这个数字。

### 10.1 为什么是两样东西，不是一样

| | 审计流（`audit_events`） | 运行日志（stdout / 落盘文件） |
|---|---|---|
| 回答 | **发生了什么**（谁、对谁、结果、耗时） | **为什么**（栈、第三方库输出、原始报文） |
| 形态 | 结构化、可筛、可分页 | 非结构化文本行 |
| 读者 | **产品用户 / 管理员**，在页面上看 | 运维 / 开发，出问题时翻 |
| 留存 | 30 天 + 总量双闸（13 §2.8.2） | 按大小轮转 |

⚠️ **不要把运行日志灌进审计面板**——那会让页面变成一屏刷不完的噪音，用户第一次点开就再也不点第二次。反过来也不行：审计流刻意**不含**栈和原始报文，深度排障仍要看运行日志。

### 10.2 审计面板（本页新增区块）

- **筛选**：类别（沙箱 / 项目 / 凭证 / 镜像 / 系统）· 严重度（仅告警）· 时间范围；默认「最近 200 条」

  ✅ **五个类别现在都有产出了**（2026-08-28 后端补齐镜像 / 系统 / 项目改动型 / auth-mode 四组写入点；逐类 `type` 清单见 13 §2.8.2「各 `category` 的生产者清单」）：

  | 类别 | 后端是否在写 | 说明 |
  |---|:--:|---|
  | 沙箱 `sandbox` | ✅ | 创建 / 状态流转 / 无头任务 / provision 阶段 / 探测 / 工作区 / 会话 / 凭证缺席 / 运行时安装 |
  | 项目 `project` | ✅ | 创建 · **重试克隆 / 转空项目 / 取消克隆 / 同步基线 / 删除** |
  | 凭证 `credential` | ✅ | 存 / 吊销 / 注入 · **切换生效凭证方式（`PUT /auth-mode`）** |
  | 镜像 `image` | ✅ | **注册 / 校验 / 启用 / 停用 / 改运行参数 / 删除** |
  | 系统 `system` | ✅ | **访问口令：解锁成功 / 失败 / 达阈值锁定 / 锁定期内再试** |

  ⚠️ **这不等于「尚未记录」那句文案可以删。** 判定逻辑与那句话都保留：类别是**开放增长**的（automation 是 v1.1，13 §2.7；`sandbox.health` 也还空着，03 §7.8），下一个新类别落地前照样会有一段「契约允许但后端不写」的窗口。把机制拆掉，那段窗口里用户又会对着「当前筛选无匹配记录」徒劳地调筛选。

  ⚠️ 两句必须分开的理由不变：**用户的下一步动作不同**——「尚未记录」该等平台补上，「筛选无匹配」该去调筛选条件。⚠️ **类别的判定压过其它筛选**：某个未产出的类别 + 仅告警而空时仍然说「尚未记录」。

  ⚠️ **这份「哪些类别已产出」的知识在前端是一份手抄**（真实来源在后端仓，openapi 表达不了「契约允许 ≠ 今天在写」）。所以它被两道锁夹着：编译期的穷尽性检查（契约增删改名一个类别就红），加上与 msw 替身的**双向**对账（标已产出的替身里必须有、标未产出的一条都不许有）——**单改一边过不去**。⇒ 本轮后端补上镜像/系统写入点，前端那道守卫**会红，这正是设计意图**：替身补上镜像与系统事件、`AUDIT_CATEGORY_EMIT_STATUS` 两项改成 `emitted`，两边同时动才过得去。
- **增量刷新**：按 `seq` 游标拉取，不整页重刷——⚠️ 不用时间戳翻页，同毫秒多条会漏
- **每条**：时间 · 严重度图标 · 一行 `summary`；展开看 `detail`（已脱敏）
- **[查看该沙箱完整时间线]**：跳到工作台沙箱详情的时间线视图（按 `subject_id` 筛），回答「这个沙箱经历了什么」
- **空态**：「暂无记录」而不是空白——空白让人以为坏了

### 10.3 [导出日志] 的准确定义

⚠️ **本页此前写着「导出最近 24h 或 50MB」，而平台当时根本没有日志留存**：后端只有 `Logger` 打 stdout，没有任何落盘设施——那个按钮无物可导。本节把它定死：

导出物是一个 **tar.gz 包**，含三份：

1. `audit.jsonl` —— 审计流（时间范围内，脱敏后）
2. `runtime.log` —— 运行日志（同范围，脱敏后；见 §10.4）
3. `diagnose.json` —— 导出时刻的一次诊断快照（§6）+ 版本 / 资源水位
4. **`export-range.json`** —— 实际截取范围说明（实现时补）

取「最近 24h」与「50MB」中**先到的那个**，包内注明实际截取范围——⚠️ 截断了却不说，会让人以为日志本来就只有这些。

⚠️ **为什么范围说明要单独成第 4 份**：前三份各有固定格式（jsonl / 纯文本 / 诊断快照），把范围塞进任何一份都要么破坏格式、要么藏在读者不会看的地方。它记录：实际时间窗、是否 `truncated`、以及**每一份缺失时的 `omittedReason`**——`runtime.log` 有三种缺法（日志设施未启用 / 范围内无内容 / 读取失败），三者对排障的含义完全不同，混成"文件不在"等于没说。

### 10.4 运行日志要落盘（技术缺口）

⚠️ **现状：没有落盘。** 单机私有化部署里，平台自己必须能读到日志才能提供导出——依赖 `docker logs` 不行：平台不一定跑在容器里（boxlite 档位下可裸跑），而且要挂 docker socket + 知道自己的容器 id，绕且脆。

要求：写 `${DATA_ROOT}/logs/`，按大小轮转（初值 20MB × 5 份），与审计流**同一套脱敏**（05 §4）。技术侧落点见 11 §部署配置。

### 10.5 边界

- 审计写入**永不阻断业务**：它是观察设施，不是账本（13 §2.8.2）。极小概率会「操作成功但没记上」，产品文案不得声称审计流"完整无遗漏"。
- 审计与运行日志**都不含凭证明文**，脱敏发生在**写入口**而非导出时——否则 DB 文件与备份包两条路仍会漏。
