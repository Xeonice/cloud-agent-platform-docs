## 1. 链路定义

```
契约层              编解码层            状态层                映射层           渲染层          运行时
openapi.d.ts   →   services/      →   hooks/          →   containers/  →   views/    →   浏览器实际行为
ws-protocol.ts     (fetch 封装/       (Query/Mutation/      (props 组装)     (DOM/xterm)
                    WS 帧编解码/        状态机/store 读写)
                    zod 运行时校验)
       │                │                  │                  │               │
       ▼                ▼                  ▼                  ▼               ▼
  生成+漂移检测    services/*.test.ts  hooks/*.test.ts   *.stories.tsx   *.stories.tsx
  (CI)             (bun test)          (bun test)        (Storybook)     (Storybook)
                                                                │
                                                                ▼
                                              Playwright（整链，含真实浏览器 WS/DOM）
```

核心问题：**每段都有输入/输出类型契约，验证的就是类型与运行时行为能否在每段无损传递，断链后有没有机制发现**。

## 2. 类型链路：从 openapi.d.ts 流动到 view props

**不断链的正常路径**（关键在"自动推导 + 边界显式标注"）：

1. `openapi.d.ts` 定义响应 schema 类型；
2. `openapi-fetch` 的 `client.GET('/sandboxes')` **自动推导**返回类型——service 层无需手写返回标注（这正是选 openapi-fetch 的核心价值：此段由编译器保证而非人工同步）；
3. `useQuery` 的 `data` 类型由 queryFn **自动推导**（v5 完全类型推导，不写泛型）;
4. container 把 data 映射为 view props 时，**view 必须有显式 props interface**——TS 在此检查"hook 给的字段"满足"view 要的字段"；
5. view 的 props 类型来自自身显式声明。

**tsc --noEmit 抓得住的断链**：

- 后端删/改字段 → 重新生成 openapi.d.ts → container 对该字段的引用立刻报错；
- hook 的 `data: T | undefined`（loading 态）未判空传给非空 view props → 报错。注意：**view props 不要过度用 `?` 兜底**——过度宽松的可选类型会削弱 tsc 把关能力。

**tsc 抓不住、需其他机制兜底的断链**：

| 断链场景 | 为什么 tsc 抓不到 | 兜底机制 |
|---|---|---|
| service 层 `as any` / 强制断言中转 | 断言让 TS 闭眼相信，类型追踪就此失效 | ESLint 断言禁令（详见文档 14）+ review |
| WS 手写类型与后端实际 payload 不一致 | TS 是编译期静态断言，`JSON.parse(x) as WsMessage` 本质是"信任声明"，对运行时数据零校验 | **zod 运行时校验**（§3，WS 唯一防线） |
| 后端**行为**变了但 OpenAPI spec 没更新（字段实际返回 null 但 spec 标必填；枚举加值没写进 spec） | 类型源头本身就错，下游"合规地错"，全程编译通过 | **契约测试 + staging 冒烟**（§5） |
| 复杂 `.map()` 回调推导退化为 any | 推导不精确而非断言 | `noImplicitAny` + 跨层边界函数强制显式返回类型 |

## 3. 运行时链路：zod 校验的必要边界

| 边界 | 必要性 | 策略 |
|---|---|---|
| **WS 消息入口**（ptySocket 收到 message 第一步） | **必须**——本项目唯一没有编译期工具链保障的契约 | 每种帧类型对应 zod schema，`safeParse`；开发环境 throw + 详细 diff，生产环境上报但**不阻断渲染**（协议小问题不能导致终端白屏） |
| 鉴权接口响应的防御性校验 | 必须（纵深防御） | 校验响应不含疑似完整 token 明文，触发则拒绝渲染该字段并告警 |
| REST 响应逐个校验 | **默认不做**——openapi-fetch 编译期已强保障，全量 zod 等于手写第二遍 schema，与类型生成初衷冲突 | 仅关键高风险接口（如鉴权状态）选择性加轻量校验 |

**开发环境 fail-fast**：统一 `assertContract()` 工具——校验失败 `console.error` 详细 diff + 页面顶部**不可关闭的横幅**（如"⚠️ 契约校验失败：WS data 帧 payload 类型不符，请检查后端协议变更"），强制联调阶段第一时间暴露契约漂移；生产降级为上报 + 静默容错。

## 4. 每层验证手段矩阵

| 链路段 | tsc | boundaries | zod | bun test | story | play fn | Playwright |
|---|:---:|:---:|:---:|:---:|:---:|:---:|:---:|
| 契约同步（openapi.d.ts / ws-protocol.ts） | ✅ 生成+漂移检测 | — | ✅ WS 唯一防线 | — | — | — | — |
| service（编解码/请求封装） | ✅ 返回推导 | ✅ | ✅ 消息解析处 | ✅ **主战场** | — | — | — |
| hook（状态机/Query） | ✅ | ✅ 禁依赖 views | — | ✅ **主战场**（renderHook） | — | — | — |
| store（Zustand） | ✅ | ✅ 仅 hooks/containers 可访问 | — | ✅ action 纯逻辑 | — | — | — |
| container（映射组合） | ✅ props 匹配 | ✅ 唯一粘合层 | — | 不适用 | ✅ decorator mock | ✅ 状态切换 | 间接 |
| view（纯渲染） | ✅ 显式 props | ✅ 禁副作用 | — | 不适用 | ✅ **主战场**，每 variant | ✅ 纯 UI 交互 | 间接 |
| 整链（真实浏览器） | — | — | ✅ 真实 payload | — | — | — | ✅ **主战场**，唯一验证真实 WS 行为 |

没有任何单一手段是全链路万能的——矩阵即"契约层 zod+生成检测、逻辑层类型+bun、渲染层 story、整链 Playwright"分工的具象化。

## 5. 验证缺口分析（矩阵之外的故障模式）

| 故障模式 | 为何漏检 | 补法 |
|---|---|---|
| 后端行为与 spec 漂移 | spec 文本错则全链"合规地错" | **staging 契约检查**：CI/定时任务对 **staging 真实响应**跑 zod 校验（复用 §3 的 schema）——"用运行时校验反向验证契约文档真实性"；mock-based E2E 验证的是模拟环境，必须补真实后端这层 |
| WS 时序问题（乱序/丢失/重复/多连接串扰） | routeWebSocket 是脚本化模拟，无法穷举真实网络时序 | ① Playwright 显式设计乱序/延迟/丢包对抗性用例（逐步补充）；② staging 冒烟：真实创建 sandbox、真实输入输出、真实断网重连 |
| 长时间运行的内存泄漏（LRU dispose 未正确触发） | 现有测试都是短时场景 | **长稳测试**：自动化脚本长时间频繁切 sandbox + 内存快照采样；不进常规 CI（成本高），作发布前专项或每周低频任务 |
| 视觉体感偏差（像素 diff 过但动画卡顿等） | 自动化只捕捉像素差异 | 发布前人工走查清单兜底，不追求自动化 |

**结论**：矩阵覆盖"确定性、可脚本化"的回归；漏掉的都是依赖真实环境的不确定性问题，通用解法是 **staging 定期/发布前探针式验证**，与本地自动化互补而非替代。

## 6. CI 执行编排（与文档 12 四道门统一）

```
static-checks
  ├─ eslint（boundaries 全套）            ← 矩阵 boundaries 列
  ├─ tsc --noEmit                        ← 矩阵 tsc 列
  ├─ prettier --check
  ├─ openapi 契约漂移检测（重新生成 diff）
  └─ check:story-coverage
        ↓
  ┌──────────────────┬─────────────────────┐
  │ unit-tests       │ storybook-tests     │   ← 并行
  │ (bun: services/  │ (Vitest addon:      │
  │  hooks/store，   │  view/container     │
  │  含 zod schema   │  variant + play)    │
  │  单测)           │                     │
  └──────────────────┴─────────────────────┘
        ↓
  e2e-tests（Playwright：整链 + 真实 WS）
        ↓
  build
        ↓（独立于 PR 流水线：nightly / 发布前触发）
  staging-contract-check（真实 staging 后端 zod 校验）
  staging-smoke（关键路径冒烟）
```

要点：PR 级 CI 只跑可脚本化的确定性验证（快的先跑）；**staging 检查独立于 PR 门禁**——依赖真实环境、成本高、验证的是"环境真实性"而非"代码正确性"，混入 PR 会拖慢迭代。

## 7. 核心用户旅程脚本（整链验证的唯一主脚本）

这是"契约 → UI"矩阵在**一条真实用户路径**上的合闸检查：单独看每段都通、拼起来断链的问题只有它抓得住。脚本与文档 12 §4.2 用例组 G 是**同一份实现**（`e2e/journey.spec.ts`），此处定义每一步"验什么契约"。

链路总览（对齐 P20 §1）：

```
① 初始化/冷启动 → ② 建项目 → ③ 分组任务树 → ④ 向导 Step1（含拦截面板）
   → ⑤ 确认步（项目/镜像/指令）→ ⑥ 进度卡 5 阶段 → ⑦ 终端回显
```

| # | 步骤 | 验证的契约段 | 关键断言 |
|---|---|---|---|
| ① | 冷启动 | REST `GET /api/projects` + WS `/events` 建连 | `initialized=true` 时进工作台；`projects` 为空 → 建项目引导（不是空表格）；WS 建连后角标「△ 数据可能非最新」消失 |
| ② | 建项目 | `POST /api/projects` + WS `project.clone_progress` | 克隆进度事件能 patch 到 `['projects','list']` 并驱动弹层进度文案；**终态走 invalidate**（文档 15 §2.3）；成功后自动选中新项目 |
| ③ | 分组树 | `GET /api/sandboxes` × `GET /api/projects` 的**派生**（文档 15 §5） | 组头任务数与组内行数一致（两个 Query 的一致性，最容易断链处）；折叠 persist；跨项目点击自动切上下文并展开 |
| ④ | Step 1 + 拦截面板 | `GET /api/runtimes` 聚合 + `POST/GET/POST /api/runtimes/:rt/auth/*` 或 `/credentials/secret` | 卡片凭证徽标与聚合端点返回一致；三分支**均在面板内完成**；**请求 URL 中不出现 sandbox 维度**；成功后 2s 自动进确认步 |
| ⑤ | 确认步 | `GET /api/images`（过滤规则）+ 本地 `wizardData` 往返 | 镜像下拉过滤三条件生效；「＋ 新建项目…」往返后**任务指令不丢**；`POST /api/sandboxes` body 的 `projectId` = 确认步所选 |
| ⑥ | 进度卡 | WS `sandbox.status_changed` → 阶段派生 | **5 个阶段、无登录步**；阶段名与后端状态机的映射不漏态；失败阶段就地变红且已 ✅ 阶段锁定 |
| ⑦ | 终端回显 | WS `/terminal` 帧协议（zod 校验的唯一防线，§3） | `initialPrompt` 非空时终端回显该指令并开始执行；输入字符 → 收到 `input` 帧；断线 → 重连 → tmux 重绘 |

三条脚本纪律：

1. **一次跑完，不拆成互不相关的小用例**——旅程的价值就在于"上一步的输出是下一步的输入"，拆开就退化成组件测试。
2. **每一步都断言"数据从哪来"而不只是"页面长什么样"**——例如 ⑤ 不只断言下拉里有几项，还要断言那几项确实来自 `GET /api/images` 且经过了过滤规则；否则前端写死默认值也能让用例通过。
3. **旅程脚本同时作为 staging 冒烟的脚本源**（§5）：mock 版跑在 PR 流水线，真实后端版跑在发布前——同一份步骤定义，只换 mock 层，避免"两套脚本各自漂移"。

**旅程覆盖不到、仍需专项的**：横幅优先级与"当天不再弹"（跨天时间依赖，用组件测试 + 假时钟）、LRU 内存长稳（§5）、镜像 env 的 secret 不回显（组件层断言 DOM，比整链更可靠）。
