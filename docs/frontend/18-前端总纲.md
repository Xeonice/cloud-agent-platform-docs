## 1. 仓库定位与文档地图

前端是**用户发起并观察 Task 的主工作区**：左侧按项目分组的任务树、右侧 xterm 终端、发起任务向导（modal，含一次性鉴权拦截面板）、以及独立路由的设置页三子页（凭证/镜像/系统状态）。架构上以"视图/逻辑分离 + 机器强制"为第一原则，六层单向依赖。

**面向用户的第一概念是 Task 不是 sandbox**：代码里的 `sandbox` 命名（query key、service、WS 事件）沿用后端契约不改，但**一切用户可见文案只出现"任务/Task"**，不出现 sandbox/容器（P21 §3）。

## 2. 六层架构与数据流总图

```
                    app/（路由，只做装配）
                        │
                  containers/（唯一粘合层）
                   │                │
          ┌────────┘                └────────┐
          ▼                                  ▼
       views/（纯渲染，props 驱动）        hooks/（全部逻辑）
                                          │        │
                                          ▼        ▼
                                     services/   stores/（Zustand 单 store+slices）
                                      │     │         │
                              ┌───────┘     └──────┐  │
                              ▼                    ▼  ▼
                        api/（openapi-fetch）  ws/（ptySocket, WS 构造注入）
                              │                    │
   ═══════ 契约边界 ═══════════╪════════════════════╪═══════════════
                              ▼                    ▼
                    openapi.d.ts（生成）      ws-protocol.ts（手动同步 + zod）
                              │                    │
                          后端 REST            后端 WS 网关
```

**数据流四条主干**：

1. **服务端资源流**：REST → services/api → hooks（useQuery）→ containers → views；WS 事件通道 → `setQueriesData 全族（见 15 §2.3）` patch 缓存（推送为主、轮询兜底），含 `sandbox.waiting_input`（🔵 等待输入子态）与 `project.clone_progress`（15 §2.3）。
2. **分组树派生流**：`['projects','list']` × `['sandboxes','list']` × `taskListFolds` → `selectProjectTaskTree()`（lib 纯函数）→ ProjectTaskTreeContainer → 树 views。**树是派生视图不是新状态**（15 §5）。
3. **终端流**：ptySocket（帧协议）→ useSandboxTerminalSocket / useTerminalInstance → terminal registry（Zustand）→ TerminalContainer → TerminalPane.view。
4. **鉴权流**：useRuntimeAuthFlow（三分支状态机）→ AuthGateContainer → AuthGatePanel + Device/SetupToken/ApiKey views；**同一套组件被向导拦截面板与凭证管理页复用**。

## 4. 质量保障体系统合（四套机制一张网）

四套机制各管一段，合起来覆盖"写代码 → 提交 → CI → 运行时"全程：

| 机制 | 管什么 | 何时生效 | 文档 |
|---|---|---|---|
| **分层强制**（boundaries + no-restricted-syntax） | 依赖方向、view 禁副作用、store 访问面 | 编辑器实时 + precommit + CI | 07§4, 09§1 |
| **类型链路**（codegen + strictTypeChecked + 防绕过） | 契约到 props 的类型流动不断链、不被 as 逃逸 | tsc/lint（语法层 precommit，type-aware 在 CI） | 10, 14, 16§2 |
| **测试金字塔**（bun / Storybook / Playwright） | 逻辑分支、组件渲染交互、整链真实行为 | CI 四道门 | 12 |
| **运行时校验**（zod at WS 边界 + assertContract） | 编译期覆盖不到的契约漂移 | dev fail-fast 横幅 / staging 契约检查 / 生产上报 | 16§3/§5 |

一个模块要合入，需同时穿过：story 覆盖检查（每个 view 必有 story）→ 语法层 lint → tsc → bun 单测 → Storybook 交互测试 → Playwright 关键路径 → build。

**产品定稿带来的三条新增质量红线**（各自都有对应的机器检查，不靠人工记忆）：

| 红线 | 检查手段 |
|---|---|
| 任务指令 / 授权 code / API key **绝不进 persist** | stores 单测断言 `partialize` 白名单快照（12§3.2）+ e2e 断言 `localStorage` 无明文（12§4.2 用例组 B/C） |
| 镜像 env 的 **secret 原值不写入 DOM** | EnvVarEditor story 的 play 函数断言（12§2.2.1）+ e2e 用例组 D |
| 创建流程**没有「等待登录」阶段**、鉴权端点**无 sandbox 维度** | CreationProgress story 的 variant 约束 + e2e 用例组 B 的请求 URL 断言（12§4.2） |

## 8. 与后端的对端关系速查

| 前端侧 | 后端对端 | 契约载体 |
|---|---|---|
| services/api（openapi-fetch） | REST Controller（02） | openapi.d.ts（生成后提交 + 漂移检测 + oasdiff + dispatch，10/14） |
| project.service（`GET/POST/DELETE /api/projects`） | projects 端点族（P20 §9.4，13§2 projects 表） | openapi.d.ts |
| sandbox.service（`POST /api/sandboxes`、`DELETE /api/sandboxes/:id { keepVolume? }`） | SandboxApplicationService（03） | openapi.d.ts |
| runtime.service（`GET /api/runtimes`、`/auth/{begin,status,complete}`、`/credentials/secret`、`PUT /auth-mode`） | RuntimeApplicationService + CredentialVault（05） | REST（AuthChallenge 结构，04§3）；**端点无 sandbox 维度**（auth helper，05§2 决策 A） |
| image.service（`GET /api/images`、validate/create/patch/delete） | 镜像注册与 manifest 校验（04§7） | openapi.d.ts |
| services/ws/ptySocket | Terminal WS Gateway（06） | ws-protocol.ts（手动同步 + zod + hash 比对，10§3/14§2.5） |
| services/ws/sandboxEvents | Outbox → WS 事件通道（13§2） | 同上（`SandboxWsEvent`，含 `sandbox.waiting_input`、`project.clone_progress`） |
| useRuntimeAuthFlow | RuntimeApplicationService.beginAuth/complete（05） | REST（AuthChallenge 结构，04§3） |

**契约命名纪律（审计 P1-5）**：**对外一律 camelCase**——query（`?projectId=`）、body（`{ isActive, imageConfig }`）、响应字段（`credentialStatus` / `maskedIdentifier` / `validationStatus` / `waitingInput`）全部 camelCase；DB 的 snake_case 映射由后端 repository 层完成，**前端永远只见 camelCase，不做任何字段名转换**。这条同时是 review 的检查点：前端代码里出现 snake_case 字段名 = 要么抄了 DB 文档、要么后端漏映射，两种都得改而不是在前端兼容。

**错误消费纪律（审计 P1-4）**：所有非 2xx 遵循统一 envelope `{ code, message, retryable, traceId, details?: [{path, code, message}] }`（shared/10 §6.8）。前端三条固定用法——① `code` 走 P22 §1 人话映射表；② **`retryable` 决定是否渲染 [重试] 按钮**（不再靠前端猜哪些错该重试）；③ `details[].path` 用于表单类错误的**逐行定位**（镜像 env 编辑是主用例，见 [F21-4](./pages/21-4-镜像管理.md)）。`traceId` 在错误详情里可复制，便于对日志。

**依赖后端补齐的缺口**（产品侧已登记，前端按上表编码但需后端落地）：`GET /api/runtimes` 聚合端点（P22 §4.11）、projects 端点族与异步 clone 进度事件（P22 §4.13）、`waiting-input` 子状态的 pty 静默检测与推送（P20 §9.8）、销毁请求的 `keepVolume` 语义（P22 §4.2）。
