### 3.1 boundaries 允许的边（写之前先对一遍）

`web/eslint.config.js` 用 `eslint-plugin-boundaries` 把依赖方向做成了硬门禁（`pnpm lint --max-warnings=0`），
本页组件树必须落在这套规则里：

| from | allow |
|---|---|
| `app` | `container` · `view` · `type` · `component` |
| `container` | `view` · `hook` · `type` · `store` · `component` |
| **`view`** | **`view` · `type` · `component`** —— 不含 `hook`，**也不含 `lib` 和 `service`** |
| `hook` | `service` · `store` · `type` · `hook` · `lib` |
| `service` | `service` · `type` · `lib` |
| `lib` | `lib` · `type` |

对本页最要命的是 **view 连 `lib/` 都不能 import**（比"view 不能 import hook"还紧一格），
直接决定三处设计：

1. **`EnvVarEditor.view` 不能自己调 `lib/image/validateEnvVar.ts`**。校验必须在 `useImages`（hook 层）跑完，
   view 只接收 `errors` prop 然后渲染——这正是 07 §8.3.1 纪律 ② 写的那条，只是那里是纪律，这里是 lint 会拦。
2. **「解析于 3 天前」这句相对时间不能在 view 里算**。它要么由 hook 调 `lib/image/` 的纯函数算好传下来，
   要么整个卡片走「view model」形态——凭证页就是后者：`lib/credential/runtimeCredential.ts` 产出
   `RuntimeCredentialCardModel`（类型在 `src/types/runtimeCredential.ts`），`RuntimeCredentialCard.view`
   只收一个 `model` prop。本页 `ImageCard.view` 照同一形态收 `ImageCardModel`。
   顺带一提，view 层还被 `no-restricted-syntax` 禁掉了 `useEffect`/`useLayoutEffect`，
   **想在 view 里挂个定时器让"3 小时前"自己走字也不行**。
3. **story 天然安全**：`*.stories.tsx` 放在 `src/views/**` 下，被 boundaries 判为 `view` 元素，
   于是 story 也不能 import service/store——这与 12 §2.5 的约束同源，不需要额外配置。

**env 错误码映射（前后端同名，02 §5.1）**——前端 `validateEnvVar` 的分类直接用这四个码；后端 400 按**统一错误 envelope**（shared/10 §6.8）返回：

```jsonc
{ "code": "VALIDATION_FAILED", "message": "…", "retryable": false, "sideEffectFree": true,
  "traceId": "…", "details": [{ "path": "env[2].key", "code": "ENV_DUPLICATE_KEY", "message": "…" }] }
```

⚠️ **顶层 `code` 是 `VALIDATION_FAILED`，不是 `ENV_VALIDATION_ERROR`**（上一版写的那个码不存在，本轮已按
`10 §6.8` 的定案更正）。这四个 `ENV_*` 码住在 **`details[].code`** 里，**不会**出现在顶层。
对前端的实际影响有两条，都不是文字游戏：
① 顶层错误文案表（`sandboxErrorCopy.ts` 那类按 `envelope.code` 查表的地方）要认的是 `VALIDATION_FAILED`，
**给四个 `ENV_*` 各配一句顶层文案是白配的**——它们永远查不到；
② 行内红字走的是 `details[].code`，与顶层查表是**两条不同的路**，别合并成一条。

前端按 `details[].path` 归位到具体变量行、`details[].code` 命中同一套文案，**不做二次翻译**：

| 错误码 | 触发 | 行内文案 |
|---|---|---|
| `ENV_NAME_INVALID` | 不匹配 `^[A-Za-z_][A-Za-z0-9_]*$` | 「变量名只能包含字母、数字、下划线，且不能以数字开头」 |
| `ENV_NAME_RESERVED` | 命中黑名单 / `GIT_`·`CODEX_` 前缀 | 「该变量名为系统保留，请使用凭证管理配置」 |
| `ENV_LIMIT_EXCEEDED` | KEY >64 / **VALUE >4096 字节** / 条数 >50 | 就地计数转红；条数到顶时 [+ 添加变量] 置灰 |
| `ENV_DUPLICATE_KEY` | 同一镜像内 KEY 重复（**大小写敏感**） | 两行同时红边「变量名重复」 |

⚠️ **VALUE 的上限是 4096 _字节_，不是 4096 _字符_**（`10 §6.8` 本轮写明）。前端计数器若写成
`value.length`，一个全中文的值在 1366 字左右就会被后端拒掉，而计数器上还显示"1366 / 4096"——
这正是本页反复要避免的"前端说 OK、后端换个说法拒绝"。**用 `new TextEncoder().encode(value).length`**，
计数单位在 UI 上也要写成"字节"。KEY 不受影响：正则限死了 ASCII，字节数恒等于字符数。

⚠️ **重复判定大小写敏感**：`LOG_LEVEL` 与 `log_level` 是**两个不同的变量**，不算重复。
这与「小写不报错、只是惯例」是同一条口径的两面——既然小写合法，那它就得是个**独立的**合法变量名。

这样做的好处：前端提示与后端拒绝**永远是同一句话**——用户不会遇到"前端说没问题、后端换个说法拒绝"的割裂感；也让 §7.1 的单测可以直接断言错误码而非文案。

### 5.1 tag 漂移：digest 怎么呈现、两颗按钮怎么分工

> **产品裁决已落定**（`P21-4 §5 ★`「注册即钉住 digest，tag 只是标签」）：注册时 `resolve` 出的 digest
> 写进库，此后**每个 Task 都按这个 digest 拉**；tag 只承担两件事——卡片上的显示名，以及 [检查更新] 的解析入口。
> 本节写的是**前端这一侧怎么落地**。⚠️ 上一版本节假定"只有一颗 [重新验证]、它顺带重解 digest"，
> **与裁决不符，已整节改写**——裁决把它拆成了**两颗语义不同的按钮**，合并就等于把"换镜像"藏进了"重跑校验"。

#### 呈现：ref / digest / 解析时间，三样同一行，全是派生值

`ImageCard.view` 收一个 `ImageCardModel`（`src/types/image.ts`），由 `lib/image/imageCardModel.ts` 从 `ImageDto` 算出来，
**view 自己不算**（§3.1 规则 2：view 连 `lib/` 都不能 import，也不许 `useEffect`）：

| 呈现 | 取自 | 形态 | 为什么这么定 |
|---|---|---|---|
| **ref**（主标题下） | `ref.registry/repository/tag` | `docker.io/myrepo/ml-agent:v1.0` | 用户认得的就是这个，永远第一位 |
| **钉定 digest** | `ref.digest` | `钉定 digest: sha256:4b17…a02`（**前 12 位** + 尾 3 位，点击展开全串 + 一键复制） | 全串 71 字符会把卡片撑爆；截断是 OCI 生态惯例，够定位、够对账。**不做"点了才显示"**——它是"你跑的到底是哪个镜像"的唯一答案，藏起来等于没有 |
| **解析时间** | `lastValidatedAt` | 「**解析于** 3 天前」 | ⚠️ **措辞是裁决的一部分**（P21-4 §3）：原稿的「最后验证」暗示结论会随时间烂掉；钉定 digest 之后结论描述的是一个**不可变对象、不会烂**，会变的只是"这个 tag 现在还指向它吗"。**前端不许改回"最后验证"，也不许再给它加"已过期"的黄字**——那会把一个已经被解决的问题重新说成没解决 |
| **上游有新版本** | 最近一次 [检查更新] 的结果 | 🔄 蓝色角标「上游该 tag 已指向新镜像 [查看变更]」 | 蓝色而非黄色：这**不是告警**，当前镜像仍然完全可用；它只是一条"有新东西可以看"的信息（P21-4 §5） |
| **以 digest 注册** | `ref` 形如 `repo@sha256:…` | 标「以 digest 注册（无 tag）」；[检查更新] 置灰 + tooltip | 没有 tag 就没有漂移，按钮**置灰并说明理由**而不是隐藏——隐藏会让人以为"这张卡少了个功能" |

⚠️ **digest 是哨兵值时不要静默留白**：契约说它非空（`10 §7.3`，不变量 I-IMG-6），产品裁决说它必须钉定，
**而今天唯一写 digest 的代码是硬编码**——`api/packages/modules/sandbox/src/application/workflows/provision-sandbox.workflow.ts`
里 `return { ref: sandbox.imageRef, digest: 'sha256:unresolved' }`（P21-4 §0 也把这条列进了实现状态表）。
所以前端要把 `digest` 当**可能为空或为哨兵值**处理：命中空串 / `sha256:unresolved` 时显示「⚠️ 未解析」，
并**同时置灰 [检查更新]**（没有基准 digest，"比对"无从谈起）。
**理由**：留白读作"这个镜像没有 digest"，显示假哈希读作"已经钉死了"——两句都是假话，
只有「未解析」为真。这条落成 §7.1 与 §7.3 的断言（见 §8.4）。

#### 触发：两颗按钮，两件事，**别做成一个**

`P21-4 §3` 把话说死了：「前两个的区别见 §6，**别做成一个按钮**」。前端这一侧的落法：

| 按钮 | 问的问题 | 端点 | 会改什么 | 何时置灰 |
|---|---|---|---|---|
| **[重新验证]** | 「**这个 digest** 还合格吗？」 | ✅ 契约已有：`POST /api/images/:id/validate` | `validationStatus` / `supportedRuntimes`。**不动 digest、不动 `isActive`** | 重验中 |
| **[检查更新]** | 「这个 **tag** 现在还指向它吗？」 | ⛔ **契约里没有这个端点**（§8.1） | 不直接改；比对结果交给用户决定（[更新到新版本] 才写 digest + 重跑 validate） | digest 形态的 ref · digest 未解析 · 解析中 |

**为什么必须分开**（把裁决的理由落到前端）：合成一颗按钮意味着"重跑校验"这个动作会**顺手换掉镜像**——
用户点的是"再检查一下"，得到的却是"内容变了"。而 [重新验证] 存在的真实场景是**平台侧规则升级后重判存量**
（2026-08 tmux 从 SHOULD 升 MUST 就是活例子，`04 §7`），那种时候用户**恰恰不想**让镜像跟着变。

**MVP 两颗都只手动触发**（P21-4 §6：无轮询、无周期自动重验证）。⚠️ 因此**不要**给列表加"进页面自动全量检查更新"——
那是 N 次镜像仓库往返，且用户没要求；`refetchInterval` 同理不加。

#### 乐观更新：这两条边**都不做**

| 操作 | 乐观更新 | 理由 |
|---|---|---|
| `toggleImage`（`isActive`） | ✅ 做 | 布尔翻转，失败回滚代价为零（15 §2.4） |
| `saveRunParams`（`imageConfig`） | ❌ 不做 | 校验可能失败，乐观改要回滚一整张表（§8.2） |
| **`revalidateImage`** | ❌ **不做** | **前端根本不知道结果**。乐观地把卡片先刷成"✅ 刚验证"，而后端可能返回 ❌——那一瞬间用户看到的是一个平台自己编出来的结论 |
| **`checkUpdate`** | ❌ **不做**（更严） | 它的结果是"上游 digest 是什么"，前端**连猜的依据都没有**；而且它**本来就不该直接改卡片**——比对结果要等用户在对比弹层里点了才写 |

落地形态：点 [重新验证] → 该卡进 `revalidating`（按钮 loading + 三态区 spinner，
**卡片其余部分保持可读，不整卡骨架屏**——用户要对照的正是"验证前是什么样"）→
成功则 `invalidateQueries(imageKeys.list())` 整卡刷新 + toast；失败按 `retryable` 决定给不给 [重试]（§8.2），
**卡片保持原结论一个字不变**。[检查更新] 同形，只是终点是 toast「已是最新（sha256:…）」或对比弹层。

## 6. 状态矩阵落地

| 产品状态（P21-4 §5） | 渲染分支 |
|---|---|
| 加载中 / 空 | `isPending` → 卡片骨架；`data.length===0` → `ImagesEmptyState` + CTA |
| ✅ 有效 | `validationStatus==='valid'` → 绿勾 + 适用 runtime 列表 |
| ⚠️ 警告 | `warnings.length>0` → 黄色 + **后果说明**（如"该镜像未预装 claude-code，创建时需现装，实测约 12.5 分钟"），仍可用。⚠️ **原例子「终端断线恢复将降级」已失效**：缺 tmux 自 2026-08 起是 ❌ 无效镜像而非 ⚠️ 警告（技术 04 §7） |
| ❌ 无效 | `validationStatus==='invalid'` → 红 + errors 列表 + [查看镜像要求]；卡片标记"不可用于创建" |
| 验证中 | `validatePreflight.isPending` → 弹窗 [验证] loading、[保存] 不渲染；`revalidate.isPending` → 卡片内 [重新验证] loading、三态区显 spinner |
| 已禁用 | `isActive===false` → 卡片置灰 + [启用]；**同时从 `ImageSelect` 选项中消失**（同一缓存派生） |

1. **不能假设 `digest` 一定是真哈希**。`lib/image/imageCardModel.ts` 把空串与 `'sha256:unresolved'`

2. **哨兵串不进 DOM**。`'sha256:unresolved'` 是平台内部占位值，原样显示等于用一个长得像哈希的字符串

3. **前端不承担"解析 digest"这个动作**。它属于后端的 `resolve`；前端只提供入口（[检查更新]）与呈现，

⚠️ **一条容易被"顺手优化"掉的纪律**：既然产品说了"按 digest 拉、tag 只是显示名"，
