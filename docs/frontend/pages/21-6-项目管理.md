## 1. 页面职责

Project = 工作区（git repo 或空目录）+ Task 集合的容器。管理形态**轻量化、无独立页面**：浏览/切换由左侧任务树承担，创建走树底与向导确认步两个入口，管理走组头「⋯」侧弹层。**本文只描述"项目"这一横切能力的前端落点**——它的宿主是工作台（[F21-1](./21-1-工作台.md)）与向导（[F21-2](./21-2-发起任务向导.md)）。

## 2. 路由与骨架落点

| 项 | 落点 |
|---|---|
| 路由 | **无独立路由**（07 §7.3）；项目上下文体现在 `uiSlice.selectedProjectId` 与深链 `/?taskId=` 的反向定位 |
| 宿主 | 工作台 `app/page.tsx`（树、指示器、树底入口、组头菜单）+ 向导 modal（确认步项目行、「＋ 新建项目…」） |
| 弹层 | `CreateProjectModal`（`currentModal='createProject'`）、`ProjectMenuPanel`（`currentModal='projectMenu'`）；两者不同时存在（modal 不堆叠） |
| 两条回程 | **`wizardReturn`**：向导 →创建项目 → 回确认步；**`pendingProjectCreate`**：创建弹层 → Git 凭证页 → 回创建弹层**重试克隆**（携 `projectId`，回程调 retry-clone 而非重新创建）。二者**语义分离、状态位不复用**（15 §3.1.1 纪律 3） |
| 创建语义 | `POST /api/projects` **先落库再异步 clone**（24 §3）——**项目在 clone 开始前就已经存在于列表**，clone 失败时它以 `cloneStatus='failed'` 持久化，而不是"什么都没发生"。这决定了所有重试都走 `retry-clone`（§5），**任何路径都不得重新 POST create**，否则产生重复项目 |

>

> 骨架（`ConfirmDialog.view`）"）。那个组件自带 `fixed inset-0 z-50` —— 叠在 `ModalShell`
> 之上就是**两层弹层**，而 P20 §8.4 / 本页 §2 明写 modal 不堆叠（Esc 会变成"退哪一层"的
> 猜谜）。实现保留了它的**形状**（标题 + 后果说明 + [取消]/[确认] 一行），就地渲染在

> 同一处理。另外那个组件的 `message` 是单串，而这里有三段各答一个问题的文案，本来也塞不进去。

> ② **`CurrentProjectIndicator` 是「文本 + 定位按钮」两个元素**，不是"整个名字就是一个按钮"。
> 做成后者的话，`getByRole('button', { name: /项目名/ })` 会同时命中它与左侧树的组头按钮，
> **全仓（含 e2e）按项目名点项目的地方一起变成 strict-mode 二义匹配**。组头「⋯」出于同一
> 理由把无障碍名定为 `项目菜单`（项目名放 `title`）。行为不变：点击只做树内定位展开（§5）。
>
> ③ ⚠️ **failed 项目在实现里仍然可以选为当前项目** —— 与 §5/§6/§9.1 #12e 那条
> 「failed 不可选、点组头仅展开」**不一致，而且是刻意的**。理由：§10.2 A 的裁决明写
> 「恢复面板留在原地不动」，而 `ProjectRecoveryContainer` 正是靠"选中失败项目 → 主区渲染
> 恢复面板"才触达得到的（P0-1：刷新/切走再回来也能恢复）。挡掉选中，那条通路当场断掉，

> 组头的点击处置 —— 那会做出一个"点失败项目什么都不发生"的死界面。§7.2 里
> `ProjectGroupHeader` 那条否定性 play（"failed 态点组头 → `onSelectProject` 未被调用"）
> **本轮未实现**，同因。

## 4. 状态与数据接入

| 类别 | 具体 | 来源 |
|---|---|---|
| Query | `projectKeys.list()` → `GET /api/projects`（含各项目 Task 数聚合） | 15 §2.1 |
| Mutation | `createProject` → `POST /api/projects` —— **先落库再异步 clone**（后端 24 §3）：立刻返回 **202 + `{ id, cloneStatus:'cloning' }`**，项目此刻**已经在列表里**；进度经 WS | 24 §3 |
| Mutation | **`retryClone`** → **`POST /api/projects/:id/retry-clone`** —— 对**已存在的 `cloneStatus='failed'` 项目**重试克隆（27 §10.4） | 02 §5.1 |
| Mutation | **`convertToEmpty`** → **`POST /api/projects/:id/convert-to-empty`** —— 对 failed 项目：`source→empty`、工作区清空、`cloneStatus→ready`，**保留项目 id / 名称 / 已有 Task**；非 failed 态调用返 **409** | 02 §5.1 |
| Mutation | `deleteProject` → `DELETE /api/projects/:id`（级联） | P21-6 §7 |
| Zustand（persist） | `selectedProjectId`、`taskListFolds` | 15 §3.1.1 |
| Zustand（不 persist） | `selectedProjectForMenu`、`currentModal`、`wizardReturn`、`pendingProjectCreate` | 15 §3.1.1 |
| 派生 | `selectProjectTaskTree(projects, tasks, folds)`（分组树） | 15 §5 |
| WS | **`project.clone_progress`** → patch `projectKeys.list()` 驱动进度；**终态走 invalidate** | 15 §2.3 |

**`cloneStatus` 只有三个合法值**（后端 13 §2.2 的 CHECK 约束）：

| 值 | 含义 | 前端表现 |
|---|---|---|
| `cloning` | 克隆进行中 | 弹层进度态；项目已在树中 |
| **`ready`** | **工作区就绪可用**——克隆成功、`convert-to-empty` 成功、以及**空项目自建起就恒为此值** | 组头 `variant="normal"`，可选为当前项目 |
| `failed` | 克隆失败 | 组头 `variant="cloneFailed"`。⚠️ **仍可选为当前项目** —— 恢复面板正是靠「选中失败项目」才渲染得出来（§3 ③） |

⚠️ **没有 `success` 这个值**——正常态一律写 `ready`。类型从 contract 生成的 union 取，不手写字面量；`lib/projectGroupState.ts` 的入参类型即这三值的 union，写错第四个值会在 tsc 阶段就红（§7.1）。

## 5. 交互实现要点（产品交互表逐行映射）

| 产品交互（P21-6 §6/§9） | container + handler | 调用 |
|---|---|---|
| 切换项目（树内点击组头/任务） | `ProjectTaskTreeContainer.handleSelectTask/handleSelectGroup` | `uiSlice.expandProject(projectId)`（同时切上下文 + 展开）→ 右侧终端切到所点任务；`selectedProjectId` persist |
| 顶部指示器点击 | `handleLocate()` | 只做树内定位展开，**不打开下拉、不承载创建/管理入口** |
| 树底 [＋ 新建项目] | `handleOpenCreateProject()` | `currentModal='createProject'`，`wizardReturn=false` |
| 确认步「＋ 新建项目…」 | 由 [F21-2](./21-2-发起任务向导.md) 触发 | `wizardReturn=true` + `wizardData` 全量暂存 → 同一个 `CreateProjectModal` |
| 创建（空项目） | `handleCreate({name, source:'empty'})` | `project.service.create()` → 即时成功 → invalidate + 自动选中 + toast |
| 创建（git clone） | `handleCreate({name, source:'git', url})` | `POST /api/projects` → 弹层转进度态，进度由 `project.clone_progress` 驱动；>10min 提示「仓库较大或网络缓慢 [继续等待]/[取消]」；**30min 硬超时**转失败 |
| 创建成功回程 | `onCreated(id)` | `wizardReturn` 真 → 回向导确认步并选中新项目；否 → 关弹层 + `expandProject(id)` |
| clone 失败·网络/URL | `CloneErrorPanel variant="network"` | 就地红字「仓库不可访问：检查 URL 或网络」+ [重试] / [改为空项目]。**[重试] 调 `project.service.retryClone(projectId)` → `POST /api/projects/:id/retry-clone`**，**不是**重新 `POST /api/projects` |
| clone 失败·权限 401/403 | `CloneErrorPanel variant="permission"` | 就地 [配置 Git 凭证] → 置 `pendingProjectCreate={ **projectId**, name, source, url }` → 路由跳 `/settings/credentials` → 配置完成回本弹层 → **[重试克隆] 同样调 `retryClone(projectId)`** |
| **[改为空项目]**（创建弹层内 + 组头菜单两处） | `handleFallbackToEmpty(projectId)` | `project.service.convertToEmpty(id)` → **`POST /api/projects/:id/convert-to-empty`**。**与 retry-clone 是两回事**：这条是**放弃克隆**、把该项目就地转为可用的空项目（保留 id/名称/已有 Task），既不重试也不新建。成功后 `cloneStatus→ready` → 组头红标消失、转 `variant="normal"`；用 `setQueryData(projectKeys.list())` patch 该项即时更新，再 `invalidateQueries` 兜底（15 §2.3 的 patch 优先、复杂则降级 invalidate 原则） |
| 组头「⋯」（failed 项目） | `handleOpenGroupMenu(projectId)` | 打开 `ProjectGroupMenu`，**三出口**：[重试克隆] → `retryClone` · [改为空项目] → `convertToEmpty` · [删除] → 走删除确认。三者共用同一个 `projectId`，**不经创建弹层**。⚠️ 前两项经**同一个** `useProjectRecovery`（§10.2 A 裁决），⛔ 菜单不持有第二份 `retry-clone` |
| 组头「⋯」（cloning 项目） | 同上 | 多一项 **[取消克隆（保留项目）]** → `POST /api/projects/:id/cancel-clone`（2026-09-01 落地）。⚠️ 与 [删除项目…] **是两件事**：删除对 cloning 项目会先取消克隆**再把项目一起删掉**，两项文案不能像（§10.6 第 2 条） |
| 点击 failed 项目的组头/任务 | 无前置判定（与 normal 同路） | ⚠️ **本条已作废**（2026-09-01，§3 ③）：原写「failed 不可选、点组头仅展开」，但那会切断 `ProjectRecoveryContainer` 的唯一触达路径（它靠选中失败项目 → 主区渲染恢复面板，P0-1）。⇒ failed 项目**照常可选**，选中后主区给的是恢复面板而不是终端。⛔ 要恢复这条否定性行为，得先把恢复面板搬进菜单 |
| 组头「⋯」→ 侧弹层 | `handleOpenProjectMenu(projectId)` | 置 `selectedProjectForMenu`（**不改 `selectedProjectId`**）+ `currentModal='projectMenu'` |
| 删除项目 | `ProjectMenuContainer` + `useDeleteProject` | 二次确认，文案含"将删除该项目下 N 个 Task 及其数据卷（保留的成果卷除外），不可逆"；**存在运行中 Task 时追加「含 N 个运行中任务将被强制停止」**（数字来自 `countRunningTasks`，0 时也照说"当前没有运行中的任务"）→ `DELETE /api/projects/:id` → invalidate projects + sandboxes；**删的正是当前选中项目时同时清 `selectedProjectId` / `selectedSandboxId`**（§10.6 第 1 条）。后端拒绝（409 等）⇒ 弹层**留在原地**显示原因，⛔ 不静默关闭 |
| 欢迎态 [开空项目] | `handleQuickCreateEmpty()` | **跳过弹层**，自动命名「未命名项目 N」（`lib/nextUntitledName.ts`）→ 创建 → 自动选中 → 引导发起第一个任务 |
| 归档项目（v1.1） | `handleArchive(id)` | 归档后组在树底淡显；选中后工作台只读（发起入口置灰） |

## 6. 状态矩阵落地

| 产品状态（P21-6 §4） | 渲染分支 |
|---|---|
| 无任何项目（冷启动） | `projects.data.length===0` → 工作台 `WorkspaceEmptyState variant="no-project"`（[📦 用我的代码库] / [📄 开一个空项目]）；指示器显"未选择项目" |
| 正常 | 指示器显当前项目名；树渲染全部项目组 |
| 克隆中 | `cloneStatus==='cloning'` → 弹层进度态（字节进度）；**此时项目已在树中**（先落库语义，§2） |
| 克隆失败·网络/URL | `cloneStatus==='failed'` 且错误码为网络/URL 类 → `CloneErrorPanel variant="network"`（[重试] → retry-clone） |
| 克隆失败·权限 | `cloneStatus==='failed'` 且 401/403 → `CloneErrorPanel variant="permission"` + [配置 Git 凭证] |
| **克隆失败·树内形态**（产品 P21-6 §9 已定） | 项目以 `cloneStatus='failed'` **持久留在树中**（先落库的直接后果）→ 组头渲染 `variant="cloneFailed"`：**`🔴 📁 ProjectName ⚠️ 克隆失败 ⋯`**；「⋯」菜单三出口 [重试克隆]/[改为空项目]/[删除]；**计入项目上限 50**；**无法选为当前项目**（点组头仅展开、点任务无效） |
| 转空项目成功 | `convertToEmpty` 成功 → `cloneStatus='ready'` + `source='empty'` → 组头回到 `variant="normal"`、红标消失；**项目 id / 名称 / 已有 Task 均不变** |
| **项目菜单不展示「来源」** | 产品已定：`ProjectMetaSection` **不渲染「来源」行**——无论 git 克隆、空项目还是 failed 转空，一律不显示。因此"转空后来源显示什么"这个问题在 UI 上不存在；`source` 字段仍在数据里（后端语义需要），只是**前端不呈现** |
| 归档项目（v1.1） | `status==='archived'` → 组在树底淡显；选中后发起入口置灰 |

## 9. ★ 项目只读条与基线同步（本轮新增）

### 9.1 为什么补这一块

此前平台上**看不到任何 git 远端情况**：项目在界面上只是树里一行（名字 + 任务数 +
克隆徽标）。而 `projects` 表里 `repo_url` / `repo_branch` / `baseline_size_bytes` /
`updated_at` **一直都在**，只是没进 DTO —— 不是没做，是数据卡在持久化层。

10 §7 里此前那条 *"「来源」字段不对外展示（产品定案）——repoUrl 不入 DTO"* 由本轮
推翻：那条定案的场景是"用户不需要知道代码从哪来"，而完整克隆（03 §7.2★）之后，
**基线体积**与**最后同步时间**都成了用户必须看得见的信息。

### 9.2 只读条（不是详情页）

选中项目时，工作台主区**顶部**一条只读信息 —— 不新开页面：工作台主区在"没选任务"
时本来就是空的，为四个字段开一个页面不成比例。

| 字段 | 来源 | 空项目 |
|---|---|---|
| 远端地址 | `ProjectDto.repoUrl` | 不显示（整条降级为"空项目"） |
| 分支 | `ProjectDto.repoBranch` | — |
| 基线体积 | `ProjectDto.baselineSizeBytes` | — |
| 最后同步 | `ProjectDto.updatedAt` | 显示创建时间 |

**只读**：改远端、切默认分支、重新 clone 都**不在这条上**。它回答的是"我在拿什么
代码干活"，不是项目管理。

### 9.3 [重新同步]

唯一的动作：`POST /api/projects/:id/sync`（仅 `ready` 态）。

⚠️ **一个刻意不做呈现的语义**：同步只更新基线，**已有 Task 的工作区一律不动**
（它们是当时的写时复制副本）。于是同一项目下的两个 Task 可能跑在不同代码上，而界面
上看不出来。做这个呈现属于"完整"那一档；本轮只用「最后同步」这一格让"我的基线是
什么时候的"可见 —— 有意识地留下的缺口，不是遗漏。

### 9.4 新建项目：改成真弹窗，并补分支输入

⚠️ **今天它不是弹窗。** `currentModal==='createProject'` 这个名字是假的——
`WorkbenchContainer` 把它 **return 成 `mainContent`**，是主区换页。改成走仓内既有 overlay
（`ConfirmDialog.view` 的 `fixed inset-0 z-50 … bg-black/60`），与「新建任务」弹窗**形态对称**
——两个新建动作长一个样，这正是本轮要解决的"两个描述都不清晰"（详见 [F21-2](./21-2-发起任务向导.md) §N.0）。

字段：名称 / 来源（Git 仓库 · 空项目）/ 仓库地址 / **分支**。
`CreateProjectRequest.repoBranch` **契约里一直有**，表单从来没接——本轮补上（留空 = 远端默认分支）。

改形态时**顺手把 `currentModal` 的名字兑现**，并清掉 `'registerImage'` / `'wizard'` 两个死值
（全仓无人 set、无人读）。

## 8. 依赖与缺口

- 依赖后端：`GET/POST/DELETE /api/projects`、**`POST /api/projects/:id/retry-clone`**、异步 clone 与 `project.clone_progress` 事件、错误码**必须区分权限类与网络类**（P22 §2 依赖）。
- ✅ **创建语义已定案（24 §3）：先落库再异步 clone**。`POST /api/projects` 返回 202 + `{id, cloneStatus:'cloning'}`，项目立刻进列表；clone 失败则以 `cloneStatus='failed'` 持久化。**由此所有重试路径一律走 `POST /api/projects/:id/retry-clone`（27 §10.4），前端任何分支都不得重新 POST create**——否则每次重试都多出一个同名项目。`project.service.ts` 的 `create` 与 `retryClone` 是两个不可互换的方法（§7.1 有结构性断言）。
- ✅ **[改为空项目] 端点已锁定**：**`POST /api/projects/:id/convert-to-empty`**——对 failed 项目 `source→empty`、工作区清空、`cloneStatus→ready`，**保留项目 id / 名称 / 已有 Task**；非 failed 态调用返 **409**。语义上它与 retry-clone 平级（都作用于已存在的 failed 项目），与 create 无关。两个入口（创建弹层内、组头「⋯」菜单）走**同一条链路**。
- ✅ **失败项目的树内形态已定**（产品 P21-6 §9）：组头 `🔴 📁 ProjectName ⚠️ 克隆失败 ⋯`；「⋯」三出口 [重试克隆]/[改为空项目]/[删除]；**计入项目上限 50**；**无法选为当前项目**（点组头仅展开、点任务无效）。三条行为由 `lib/projectGroupState.ts` 纯函数固化（§7.1）。
- 重命名/归档/已保留卷/自动化为 v1.1，MVP 在 `ProjectMenuPanel` 中渲染为禁用态 + 版本角标。
- ✅ **保留卷端点统一在一个资源前缀下**（审计 P2-5）：`GET /api/retained-volumes?projectId=` · `DELETE /api/retained-volumes/:id`——原先"一个嵌套（`/projects/:id/volumes`）一个平铺（`/volumes/:id`）"的双形态已废弃。`RetainedVolumesEntry` 与 [F21-5](./21-5-系统状态.md) 的磁盘治理横幅 [去清理] 消费同一端点，前者按项目过滤、后者看全局总量。

#### VS-1 · 私有仓库 clone 失败到成功的完整回程（跨三页）

| 步 | 操作 | 期望 | 判定通过 |
|---|---|---|---|
| 1 | 树底 [＋ 新建项目] → 填名 + 私有 git URL → [创建] | 后端 **202 返回 `{id, cloneStatus:'cloning'}`**；弹层转克隆进度态；**树中已出现该项目** | 先落库语义（24 §3），不是"成功了才出现" |
| 2 | mock clone 阶段返 403 | 就地显示「克隆失败：无权访问该仓库」+ **[配置 Git 凭证]**；该项目在树中转 `failed` 态 | 权限类与网络类**分支不同**（`classifyCloneError`） |

| 6 | [重试克隆] → mock 成功 | 发出 **`POST /api/projects/:id/retry-clone`**；项目就绪 + 自动选中 + toast | 回程闭环 |
| 7 | 检查项目列表 | **该项目仍只有一条**（名称/URL 相同的重复项目数 = 0） | **本脚本的防回归核心**：重试若走 re-create 就会出现两条 |
| 8 | 检查网络记录 | 全程 `POST /api/projects` **只发生过 1 次**（步骤 1） | 同上，从请求侧再确认一次 |

### 10.6 三条容易做错的地方

1. **删除后选中态往哪去。** 删的可能正是当前选中项目。⛔ 不许留一个指向已删项目的
   `selectedProjectId`（21-4 那条「该沙箱已被销毁（404）→ 清掉持久化选中并回到新建入口」
   是同一类问题，照它的处置）。判据：删除当前项目 → 选中态清空 + 主区回到引导态，**不是白屏**。
2. **`cloning` 态删除是两步。** 后端会先取消克隆再删（10 §6），确认文案要说清；
   ⚠️ 「只取消克隆、保留项目」是另一个端点 `cancel-clone`，**菜单里这两项要分开、文案不能像**。
   ✅ 落地形态：cloning 项目的组头「⋯」里多一项 **[取消克隆（保留项目）]**（→ `cancel-clone`），
   与 **[删除项目…]** 并列；删除确认里另有一段
   「该项目正在克隆：删除会先取消克隆，再连同项目一起删掉。若你只想停下这次克隆、把项目留着，
   请改用菜单里的 [取消克隆（保留项目）]」——**明写另一条路的名字**，而不是只说"两步"。
3. **运行中任务警示读的是真数据。** 级联后果里那句「有 N 个任务正在运行」必须来自
   实际的沙箱状态，⛔ 不许写死成「可能有正在运行的任务」这种永远正确因而永远没用的话。
