## 1. 页面职责

私有化部署的**启动卡点**：首次冷启动时以阻塞式向导完成出网检测 → 代理配置 → 资源确认，写入 `initialized=true` 后才放行工作台。另外定义两个渲染在系统状态页（[F21-5](./21-5-系统状态.md)）内的区块规格：访问保护（**MVP**，审计 P0-3 提前）与升级备份（v1.5）。

**与 F21-5 的分工**：本页是一次性卡点，F21-5 是常态运维面；两者共用后端检测能力（P21-8 §2）。

## 2. 路由与骨架落点

| 项 | 落点 |
|---|---|
| 路由 | **无独立路由**——在工作台首屏之上以阻塞层渲染（未初始化时不允许进入任何业务路由） |
| 判定位置 | `app/layout.tsx` 之下的 `AppBootGate`（container）：读 `GET /api/system/init-status` 的 `initialized` → false 时**只渲染向导**，不挂载工作台/设置页 |
| 路由拦截 | 未初始化时直接访问 `/settings/*` 或 `/new` 一律被 `AppBootGate` 拦下（不做 redirect，避免与深链恢复打架） |
| 阻塞语义 | 向导内**没有 [取消]、没有 Esc 逃逸**（与 P20 §8.4 的全局 Esc 分层规则的唯一例外，需在实现处显式注释） |
| 一次性 | 完成后此后配置修改**全部走 F21-5**，向导不再出现（P21-8 §7） |

## 4. 状态与数据接入

| 类别 | 具体 | 来源 |
|---|---|---|
| Query | `systemKeys.init()` → **`GET /api/system/init-status`**（`initialized` + **上次出网检测结果** + 已存代理配置）——首载判定用它，**不重跑检测** | 02 §5.1 |
| Query | `systemKeys.settings()` → `GET /api/system/settings`（代理等配置 + 版本信息，供 F21-5 与本页表单回填） | 02 §5.1 |
| Mutation | `saveProxyConfig` → **`PUT /api/system/settings`**（保存代理等配置，**不写 `initialized`**） | 02 §5.1 |
| Mutation | `finishInit` → **`POST /api/system/init`**（初始化向导的终结动作，**非幂等·一次性操作**：已初始化重复调用返 **409**）→ 写 `initialized=true` | 02 §5.1 |
| Mutation | 出网检测 → **复用 `POST /api/system/diagnose` 的 SSE**（与 F21-5 同一实现，02 §5.3） | 02 §5.3 |
| Mutation（MVP） | `setAccessPasscode` → **`PUT /api/system/access-passcode { action: 'enable' \| 'regenerate' \| 'disable' }`**；**enable/regenerate 的响应体一次性返回 16 位明文**，此后永不回显 | 02 §5.1 |
| Mutation（v1.5） | `POST /api/system/backup`、导出全量数据、检查更新 | 见 §8 |
| Zustand | **本页不写任何全局 UI 状态**——向导步骤是 `InitWizardContainer` 的局部 state（一次性流程，无跨组件共享需求，15 §1 判定准则③） |
| 派生 | 离线模式判定（两个模型 API 均不可达）→ 供工作台 🔴 阻断类横幅与"发起入口置灰"使用 | 07 §8.4 |

**离线模式的跨页影响**：`initialized=true` 且模型 API 不可达时，`useGlobalBanner` 产出 🔴「离线模式：Agent 不可用 [重新检测]」，同时 [+ 新任务] 入口置灰——这是本页唯一持续影响其他页面的输出。

## 5. 交互实现要点（产品交互表逐行映射）

| 产品交互（P21-8 §2/§3/§4） | container + handler | 调用 |
|---|---|---|
| 首载判定 | `AppBootGate` 首次渲染 | `GET /api/system/init-status`；**pending 期间渲染骨架而非工作台**（防闪现） |
| Step1 检测结果 | `handleAutoCheck()`（挂载即跑） | **优先读 `init-status` 里的上次检测结果直接渲染**（进向导不等一轮检测）；无历史结果或用户点 [重新检测] 时才跑 `POST /api/system/diagnose` 的 SSE，逐项到达逐项渲染；单项超时由后端下发超时结果帧，**不阻塞整轮**（02 §5.3） |
| [重新检测] | `handleRecheck()` | **3s 内不可重复点击**（节流，`lib/throttle` 或 button disabled 计时） |
| Step2 展开条件 | 由检测结果驱动 | 有失败项 → 自动展开代理表单；全通过 → 可跳过 |
| 保存代理 → 重检 | `handleSaveProxyAndRecheck()` | `PUT /api/system/settings`（**只存配置，不放行**）→ 再重跑 Step1 |
| 模型 API 全失败 | `OfflineNotice.view` | 明示"Agent 将不可用"，仍提供 [继续] → 进 Step3 |
| Step3 镜像检查（v1.1） | `handleImageCheck()` | 复用 `POST /api/system/diagnose` 的第 ⑧ 项（P21-5 §9A），**不新增端点**。五步链失败在哪一步就渲染哪一步的修复命令 |
| Step3 未就绪仍可继续（v1.1） | `handleSkipImage()` | ⚠️ **不阻塞**，但必须明示"在此之前无法发起任何任务"——这是唯一一处「放行了但功能不可用」，说漏了用户会在建 Task 时才发现 |
| Step3 修复命令 [复制]（v1.1） | `handleCopyFix(cmd)` | 与 F21-5 诊断项的 [复制] 同一套 |
| Step3 [确认，开始使用] | `handleFinish()` | **`POST /api/system/init`** → 成功后 `setQueryData(systemKeys.init(), {initialized:true})` → `AppBootGate` 放行 → 直接进入**建项目引导**（P20 §2.1） |
| 保存失败 | `InitErrorPanel` | 就地人话原因 + [重试]，**不放行**（阻塞语义） |
| 访问口令启用/重新生成（MVP） | `handleSetPasscode(action)` | `PUT /api/system/access-passcode { action:'enable'\|'regenerate' }` → **口令由后端生成**（16 位），响应体**一次性返回明文** → 前端即时展示 + [复制] + **明示"仅此一次，关闭后无法再查看"**；面板关闭即从内存丢弃，**不写 store、不写 persist、不进日志** |
| 访问口令关闭（MVP） | `handleSetPasscode('disable')` | `PUT /api/system/access-passcode { action:'disable' }` → 二次确认（关闭后任何人可访问） |
| 口令校验（MVP） | `PasscodeGate` | 连续 5 次错误 → 前端锁定 5 分钟（倒计时），成功后 session 7 天 |
| [检查更新]（v1.5） | `handleCheckUpdate()` | **失败一律静默**：只显示"无法连接更新源"，**绝不阻塞任何功能、不弹层、不进横幅栈** |
| [立即备份] / [导出全量数据]（v1.5） | 对应 handler | 触发下载；UI 明示"凭证密文默认不入包" |

## 6. 状态矩阵落地

| 产品状态（P21-8 §5） | 渲染分支 |
|---|---|
| 未初始化 | `initialized!==true` → `AppBootGate` 只渲染 `InitWizardContainer`（工作台不挂载） |
| 检测中 | 三项各自 spinner，已返回项立即定格 |
| 部分失败 | 展开 Step2 代理表单 + 失败项 ⚠️ 说明 |
| 模型 API 全失败 | `OfflineNotice` + [继续]（不阻断初始化完成） |
| 初始化完成·出网正常 | 放行 → 正常冷启动流程（无项目 → 建项目引导） |
| 初始化完成·离线模式 | 工作台可用 + 🔴 横幅「离线模式：Agent 不可用 [重新检测]」+ 发起入口置灰并附说明 |
| 代理失效（运行期） | 由 F21-5 诊断引导回代理配置（本页不重复实现，跳 `/settings/system`） |

| `hooks/useVersionCheck.ts`（v1.5） | 检查失败时**不抛出、不进横幅栈**，仅返回 `unavailable` 态（静默失败的结构性回归） |

## 7A. Step3「预制镜像」的设计要点（v1.1 新增）

> 产品依据 P21-5 §9A（五步链）与 P21-8 §2。**这一步是 2026-08-28 实测补的**：前七项诊断全绿、向导三步走完，用户建第一个 Task 时仍然撞墙——`SANDBOX_DEFAULT_IMAGE` 指向的是上游镜像，注册会被血统检查拒。

**① 五步链的每一步都要有自己的文案与修复命令**，不能合成一个红灯：

| 失败步 | 用户要做的事 |
|---|---|
| 未配置 | 改配置项（给出文件位置与正确取值形态） |
| registry 里没有 | `docker push`（给完整命令） |
| **不是平台自建的那张** | ⚠️ 文案必须说清「注册也会被拒」——否则用户以为只是少做一步注册，照着去注册再撞一次墙。给构建脚本路径 |
| 未注册 / 未通过验证 | 重启平台（开机自动播种） |
| 未 staged | ℹ️ **不是失败**：告知「首个任务需要数分钟准备镜像」 |

**② 未 staged 那一支不许渲染成 ❌ 或 ⚠️。** 它是完全正常的状态（镜像备齐了，只是还没铺开），渲染成警告会让用户去"修"一个不需要修的东西。⇒ 用 ℹ️，且文案是**预期管理**而不是问题报告。

**③ 这一步不阻塞，但「放行了但不可用」必须说出来。** 向导里其余步骤放行后功能都是可用的，只有这一步例外——[稍后配置] 之后平台能进、项目能建、**任务建不出来**。这句话不说，用户会在最挫败的时机（填完指令点按钮）才发现。

## 8. 依赖与缺口

- ✅ **系统设置与初始化端点已定案**（02 §5.1）：
  | 用途 | 端点 |
  |---|---|
  | **放行判定**（`initialized` + **上次出网检测结果** + 已存代理配置） | **`GET /api/system/init-status`** |
  | 读取系统设置（代理配置、版本信息） | `GET /api/system/settings` |
  | 保存配置（代理等，**不放行**） | `PUT /api/system/settings` |
  | 初始化终结动作（写 `initialized=true`，**非幂等：已初始化重复调用返 409**） | **`POST /api/system/init`** |
  | 出网检测 | 复用 `POST /api/system/diagnose` 的 SSE（02 §5.3） |
  | 访问口令（MVP，审计 P0-3） | `PUT /api/system/access-passcode { action: 'enable' \| 'regenerate' \| 'disable' }` |
  - **三条前端关键约束**：
    1. **首载判定读 `init-status` 而不是 `settings`**——前者带上次检测结果，进向导可直接渲染历史，**不重跑一轮检测**（用户不必每次冷启动都干等 5s×3）。
    2. **`PUT settings` 不放行，只有 `POST init` 放行**——`PUT settings` 可以调任意多次（每次改代理都存）；混用会导致"填了代理还没确认资源就进了工作台"。
    3. **409 = 已初始化，优雅跳过向导进入应用**——`POST init` 是**一次性操作、非幂等**，重复提交/多标签页并发时后端返 409。这不是"把 409 当成功"，而是**对"已完成"状态的正确处理**：目标状态（`initialized=true`）已经达成，用户该做的事已经做完了，再把他卡在向导里显示错误既没道理也没出路。前端拿到 409 就置 `initialized=true` 并放行，不弹错误。
    三条都已写成 §7.1/§7.3 的断言。
  - **口令明文一次性**：enable/regenerate 的响应体是明文**唯一一次**出现的地方。前端纪律——即时展示 + [复制] + 明示"仅此一次"，面板关闭即从内存丢弃；**不进 store、不进 persist、不进任何日志/上报**。这条与"任务指令/授权 code/API key 不落存储"属同一类红线，§7.1/§7.3/§7.4 三处都有对应断言。
- ✅ 检测能力复用：初始化 Step1 的出网检测与 F21-5 的诊断**共用 `/diagnose` 的 SSE 实现**（02 §5.3），`system.service.ts` 用两个方法名区分用途；单项超时由后端下发结果帧，前端不自行计时。
- 🕐 **v1.5 维持标注**：`POST /api/system/backup`、导出全量数据、版本检查源——本页只保留占位设计与"检查失败一律静默"的红线。
- ✅ `systemKeys.init()` / `systemKeys.settings()` **已合入 15 §2.1**：`init()` staleTime/gcTime 均为 `Infinity`（一次性放行判定，完成后由 mutation `setQueryData` 置 true）；`settings()` 60s/10min，`PUT` 后显式 invalidate（见 15 §2.2）。
