### 4.1 运行档位（provider）的服务端驱动契约

> 历史：S1 曾在前端写死 `SANDBOX_PROVIDERS = ['aio','boxlite'] as const` + `DEFAULT_SANDBOX_PROVIDER`，导致**后端 registry 注册的第三方 provider 在 UI 里根本看不见**（10 §7.2 反例存档）。现已删除，`SandboxProvider` 是开放 `string`，以下规则取代那份闭集。

| 规则 | 行为 |
|---|---|
| **选项来源** | `GET /api/providers` 响应各项的 `name`。**前端不枚举、不过滤、不补齐**——第三方 provider 注册后自动出现，前端零改动 |
| **默认档** | 响应里 `isDefault === true` 的那一项（**默认档挂在每项上，无顶层字段**）。用户未手选时跟随它，registry 换默认档即刻生效 |
| **默认档兜底** | registry 非空却无任何 `isDefault` 属**契约异常**（后端不该发生）→ 取首项，**不留空**：留空会让创建按钮一直禁着、看起来像 bug，取首项能保住核心链路且用户仍可改选 |
| **加载中** | 出骨架（`aria-busy`）并禁用创建按钮——**不静默展示空列表**（空列表会被误读成"后端没 provider"） |
| **加载失败** | `role="alert"` 错误文案 + [重试加载运行档位] 按钮；**不静默降级为空列表** |
| **空 registry** | `role="alert"`「后端未注册任何 provider，暂无法创建沙箱」+ 禁用创建——与"加载中"必须可区分 |
| **能力驱动（今天只有一条真分支）** | 所选 provider `capabilities.spawnTty === false` → **禁用「新建沙箱并打开终端」** + `role="alert"` 说明原因 + 该列表项标注「— 不支持终端」。这与后端的无条件拒绝同源（04 §2.5 / 03 §3.1），前端只是把 409 提前成不可点 |
| **其余五位能力位** | 全量透出到 view 备用，但**不为它们凭空造按钮**（没有"暂停"功能就不画"暂停"按钮）。后端加位 → codegen → 前端编译期可见（10 §7.6） |

**`require` 本期不发送**：`CreateSandboxDto.require` 的类型别名已在 `types/sandbox.ts` 标出口子，但没有对应 UI 入口，因此请求体里不带该字段。将来若加「必须支持快照/暂停」之类勾选，直接填进 `createSandbox` 的 body 即可，后端不满足会以 **409 `UNSUPPORTED_CAPABILITY`** 拒绝（10 §6.1 / 27 §2）。

## 6. 状态矩阵落地

| 产品状态 | 渲染分支 |
|---|---|
| 弹窗首开 | `lastUsedRuntime` 高亮；`runtimes.isPending` → 卡片骨架；分支选择器按 `useProjectBranches` 加载 |
| → 闸门就地展开 | 所选 runtime **`credentialStatus ∈ {'none','expired'}`** → `authGateSlot` 内渲染 `AuthGatePanel`（**无步骤编号，不换屏**） |
| → 可创建 | **`credentialStatus ∈ {'active','expiring'}`** → 显示"将以 a***@gm 身份运行"；`expiring`（<7 天）**不拦截**，只给 ⚠️ 预警 |
| 面板·轮询中 | `authFlow.state==='polling'` → 倒计时 + "等待授权中…" |
| 面板·过期 | `state==='expired'` 或倒计时归零 → 红色 + [重新获取]（对齐 `AUTH_CHALLENGE_EXPIRED`） |
| 面板·成功 | `state==='success'` → "✅ 配置完成"，2s 后**面板就地收起**（不跳步） |
| 面板·API key 拒绝 | `AUTH_REJECTED` → `ApiKeyAuth.view` 的 `error` prop 渲染就地红字 + 原因列表（**不弹层**） |
| 创建中 | `mutation.isPending` → `SandboxStartupProgress.view`，阶段由 WS 事件映射 |
| 门口拒绝 | 后端标 `sideEffectFree` → **就地提示改配置**（`rejectionMessage`），不出失败卡、不留残骸 |
| 拉镜像卡住 | 当前阶段 300s 无进展 → "⚠️ 可能卡住"；`>10min` → [强制停止] |
| 失败 | `mutation.isError` → 对应阶段变红 + P22 §1 人话映射 + [重试] |
| 成功 | WS `status==='running'` → 关弹窗 + 选中新 Task + 开终端 |

**阶段映射表**（后端状态 → 进度卡 **4 个展示格**，多对一；**没有第 5 个"等待登录"格**）：

> ⚠️ 上一版在此列了 **5 格**并多出一格「连接终端」，**与代码不符**：
> `lib/sandboxLifecycle.ts` 的 `STARTUP_PHASES` 只有 4 格，且 **`running` 根本不点格**——
> `classifyStatus('running')` 返回 `'running'`，进度卡就此退出、切去开终端。本轮改正。

| 后端状态（技术状态机顺序） | 进度卡格（`STATUS_TO_PHASE_KEY`） |
|---|---|
| `pending` / `scheduling` | 初始化 |
| **`preparing-workspace`** | **准备工作区**（展示第 3 格） |
| `creating` | 拉取镜像（展示第 2 格） |
| `starting` | 启动实例 |
| `running` / `idle` | **不映射任何格**——退出进度卡，开终端 |

⚠️ **展示顺序 ≠ 状态机顺序，这是刻意的**：技术上工作区必须先备好
（`scheduling → preparing-workspace → creating → starting`，这样 `provider.create()` 时卷已存在）；
但用户心智里"拉镜像"在"准备工作区"之前（先有环境再有代码）。
**实现时不要"顺手把展示顺序改成和状态机一致"**——`STATUS_TO_PHASE_KEY` 只管状态→格，
格的顺序由 `STARTUP_PHASES` 静态数组决定，两者解耦；百分比另走 `STATUS_TECH_RANK`
保证单调递增（否则会出现"进度倒退"）。

「启动实例」格内发生**装 runtime CLI、注入凭证、起 agent 会话**三件事（`INSTANCE_PHASE_KEY`），
`runtime.install_progress` 的子文案挂它下面——实测未预装 CLI 时该格可达 **753 秒**，没有子文案会像卡死。

### ★ 9.0 一条本轮定案：两个弹窗**不嵌套**

上一版让「新建任务」弹窗里放一个项目下拉行，底部挂「＋ 新建项目…」，创建完再经
`wizardReturn` 回程保值。本轮取消——**两个弹窗，两个交互**：

- 新建项目：从左侧树进，独立弹窗；
- 新建任务：继承树上**已选中**的项目（"上下文先行"本来就是 P20 §3 的原则），弹窗内**没有**项目下拉。

理由：嵌套会让它变成"一个交互带分支"而不是两个交互，也正是 `20 §8.4`「modal 不堆叠」
要给创建项目开例外的原因——不嵌套，例外和 `wizardReturn`（本就是死值）一起消失。

⚠️ **代价说清楚**：想给非当前项目建任务，得先在树上切过去。多一次点击，换掉一层嵌套弹层
与一条往返保值链路——本轮认为划算。**若你要保留下拉行，这条推翻即可，其余不受影响。**

## ★ 本轮改造：两个弹窗，两个交互

### N.0 病根：这两个都不是弹窗

| | 新建项目 | 新建任务 |
|---|---|---|
| 今天的形态 | `currentModal==='createProject'` → 但它 **return 成 `mainContent`**，是主区换页 | `sandboxId===null` 时的**兜底分支** |
| 入口 | `WorkbenchContainer.tsx:143` 一处 | **没有入口** |

`currentModal` 这个名字是假的——它的值直接进主区，不是弹层。而"新建任务"**根本不是一个动作**：
没有"创建"这个行为，只有"没有沙箱时你会落在这儿"。这是它读起来看不懂的根源。

目标：**两个真弹层，形态对称**，都用 `ConfirmDialog.view` 那套 overlay。

### N.1 新建任务弹窗（单弹窗一屏）

```
┌─ 新建任务 ──────────────┐
│ Runtime   [codex      ▾]│
│ Provider  [官方        ▾]│
│ 分支      [main       ▾]│  ← 本轮新增
│ 指令      ┌───────────┐ │
│           └───────────┘ │
│      [取消]  [创建]     │
└─────────────────────────┘
```

**丢掉两步壳、保留鉴权闸门**：闸门（`AuthGateContainer`）是真建成、真复用的，凭证缺失时
在弹窗内**就地展开**，而不是插在两步之间。丢掉的只是那个从未存在的 `WizardShell`。

⚠️ **入口必须新建**——今天一个都没有。它不能再依赖"沙箱为空"这个条件，否则"新建任务"
永远只是个兜底态而不是一个动作。

**分支选择器**（本轮补的那一层）：

- 数据来自 `GET /api/projects/:id/branches`，**不碰网络、不需要凭证**：完整克隆
  （03 §7.2★）之后读的是**本地**引用（`git branch -r`）。这是选完整克隆而非"按需 fetch"
  的直接红利——这条路上一条网络失败路径都没有；
- **缺省 = 基线当前分支**：不选也能发起。与"平台没有默认 runtime"那条**不同**——分支有
  天然缺省，runtime 没有（04 §8）；
- **空项目不出这个选择器**：没有 git，谈不上分支；
- 分支不存在时在**门口**被拒（零副作用，04 §5），走「就地提示改配置」，不是失败卡。

### N.2 新建项目弹窗

同一套 overlay，字段：名称 / 来源（Git 仓库 · 空项目）/ 仓库地址 / **分支**。
`CreateProjectRequest.repoBranch` **契约里一直有**，表单从来没接——本轮补上（留空 = 远端默认分支）。

改形态时**顺手把 `currentModal` 的名字兑现**：它要么真的是弹层，要么就别叫 modal。
`'registerImage'` / `'wizard'` 两个死值一并清掉（全仓无人 set、无人读）。

### N.3 无头面板：只挂无头沙箱，且建完之后是详情

★ **先解决"它该不该在那儿"。** 此前无头面板对**每个**沙箱无条件渲染（只判断 runtime
已知），于是**交互式**沙箱底下也挂着一条「无头任务」。那条永远停在空态说"这个沙箱还没有
任务"——因为交互式沙箱的 AgentTask 列表恒为空。

而界面上**另一处也叫"任务"**：左侧树的 `项目 · N` 数的是 **Sandbox**（Task 的产品叫法，
名字就是用户填的指令）。于是同一屏上出现「· 1」与「还没有任务」直接打架——两句话各自都对，
说的却是两个东西。

| 界面位置 | 它说的"任务" | 数据来源 |
|---|---|---|
| 左侧树 `项目 · N` | **Task = 一个沙箱** | `SandboxDto` |
| 无头面板 | **AgentTask = 沙箱内部的一次无头运行** | `GET /api/sandboxes/:id/tasks` |

模式在创建时**二选一**（P20 §3.2「◉ 交互式终端 / ○ 无头任务」，`SandboxDto.headless`）——
交互式沙箱的全部界面就是终端本身，底下不该再挂任何东西。**门控加在
`SandboxTerminalContainer` 的 `headlessSlot` 上：`headless === true` 才渲染。**

面板内的按钮同步改名 `[新任务]` → `[发起无头运行]`：侧栏的 `[＋ 新任务]` 建的是**新沙箱**，
面板里建的是**同沙箱内的下一次运行**，两者同名正是混淆源。



`HeadlessTaskContainer` 只要沙箱 `running` 就渲染 `HeadlessTaskLauncher`（带指令 textarea
与发起按钮），**与这个沙箱有没有正在跑/跑完的任务无关**。于是建完任务之后，界面主体仍然是
"再发起一个"的入口。

| 状态 | 呈现 |
|---|---|
| 无任务 | 引导去开「新建任务」弹窗 |
| 有任务 | **只读详情**：状态、耗时、产物、退出码 + [新任务] 入口 |

⚠️ **「指令」拿不到，别留空格子。** `AgentTaskResponseDto` 没有 prompt 字段——后端**刻意不回显**任务指令（10 §7.3 / 15 §3.5，指令属敏感上下文）。详情里明写「不回显」，要真显示得后端加字段，那会直接抵触这条安全红线。

⚠️ **[新任务] 入口不能省。** `GET /api/sandboxes/:id/tasks` 是列表、`selectedTaskId` 记的是
"用户上次盯着哪一个"——数据模型本来就是**一个沙箱多个任务**。"建完就没有发起入口"会把多任务
能力从界面上抹掉；正确形态是「详情 + 显式新建」，不是「详情替代发起」。
