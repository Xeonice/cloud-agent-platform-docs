## 1. 页面职责

管理两族凭证：**Runtime 凭证**（帐号授权 / API Key，模式二选一全局生效）与 **Git 凭证**（私有仓库访问）。掩码查看、页内即时重授权/添加、模式切换、吊销。**页内完成一切**——不跳向导、不依赖任何 sandbox 宿主。

## 4. 状态与数据接入

| 类别 | 具体 | 来源 |
|---|---|---|
| Query | `runtimeKeys.list()` → `GET /api/runtimes`（**主数据源**）：`{ id, displayName, vendor, authMethods, credentialStatus: 'none'\|'active'\|'expiring'\|'expired', maskedIdentifier?, expiresAt?, activeAuthMethod? }`——字段全 camelCase（02 §5.1，审计 P1-5） | 15 §2.1 |
| Query | `runtimeAuthKeys.status(provider)` → `GET /api/runtimes/:rt/credentials/status`（重授权后的**局部刷新**） | 15 §2.1 |
| Query | `sandboxKeys.list()` → 本地按 runtime 过滤，算"受影响的运行中 Task"（吊销确认用） | 15 §2.1 |
| Query | `gitCredentialKeys.list()` → **`GET /api/credentials?kind=git`**（`kind` 必填，MVP 只接受 `git`）；返回掩码列表 `{id, kind:'git', type:'ssh-key'\|'https-token', maskedIdentifier, platform?, knownHosts?, lastUsedAt, createdAt}` | 02 §5.1 |
| Mutation | `beginAuth` / `pollAuthStatus` / `completeAuth` / `saveSecret` / `setAuthMode` / `revokeCredential` | 07 §6.3 |
| Mutation | Git：**`POST /api/credentials/git`**（保存 SSH/Token，body 因形态而异）· **`POST /api/credentials/git/test`**（测试连接，后端 `git ls-remote` 15s，**只回 `ok` / `errorCode`，不回 ref 名**）· **`DELETE /api/credentials/git/:id`**（吊销，**无联动清除**——Git 凭证不注入 sandbox） | 02 §5.1 |
| Zustand | 仅 `currentModal`（吊销确认）；**本页不写任何凭证值到 store** | 15 §3.1.1 |
| container 局部 state | 粘贴的 code / API key / SSH 私钥 / Token —— 提交即清空 | 07 §6.4 |
| WS | `runtime-auth.status_changed` → patch `runtimeAuthKeys.status` + invalidate `runtimeKeys.list()` | 15 §2.3 |

## 5. 交互实现要点（产品交互表逐行映射）

| 产品交互（P21-3 §6/§10.2） | container + handler | 调用 |
|---|---|---|
| ◉/○ 模式单选切换（目标**已配置**） | `handleSwitchMode(rt, method)` | 确认弹层 → `runtime.service.setAuthMode(rt, method)` → `PUT /api/runtimes/:rt/auth-mode` → invalidate → [生效中] 徽标移动 + toast |
| ◉/○ 切到**未配置**模式 | 同上，分支判断 | **不直接报错**（后端 409 也不透传）→ 就地展开该模式的 `AuthGateContainer`，**配置完成即自动切换** |
| [重新授权]（帐号授权类） | `handleReauth(rt)` | 卡片内展开 `AuthGateContainer`（device-code/setup-token 按 runtime）→ `beginAuth`/`pollAuthStatus`/`completeAuth`；成功后旧凭证按吊销语义处理，**无需额外确认** |
| [添加 API Key] / [更换] | `handleAddKey(rt)` | 卡片内展开 `ApiKeyAuth.view` → `saveSecret`；提交即清空 |
| [帐号授权]（未配置态） | `handleAuth(rt)` | 同 [重新授权]，**无任何前置**（不需要 sandbox 宿主） |
| [吊销] | `handleRevoke(rt, credentialId)` | `RevokeConfirmDialog`（列受影响运行中 Task，**最多 10 条 +「等共 N 个」**）→ `DELETE /api/runtimes/:rt/credentials/:credentialId` |
| 吊销**生效中**模式 | 同上，确认文案分支 | 额外提示"该模式将不可用"；吊销后另一模式已配置 → 询问是否切过去，否则转「未配置」 |
| 搜索 | `handleSearch(q)` | 纯客户端过滤 runtime 名 / 掩码帐号 |
| Git [配置 SSH 密钥] | `handleConfigSsh()` | 弹层粘贴私钥（遮罩）→ 本地校验"带 passphrase 不支持" → [测试连接] → 保存；展示仅指纹 |
| Git [配置 HTTPS Token] | `handleConfigToken()` | 选来源 + scope 提示 → 粘贴 → [测试连接] → 保存；展示仅尾号 |
| Git [测试连接] | `handleTestConnection()` | `POST /api/credentials/git/test`（后端 `git ls-remote`），前端 15s 超时兜底 + loading；响应只有 `ok`/`errorCode` → 按 P22 §1 映射人话，**不展示任何 ref 名** |
| Git [吊销] | `handleRevokeGit(id)` | 二次确认 → `DELETE /api/credentials/git/:id` → invalidate `gitCredentialKeys.list()`；**确认文案不提"清除已注入文件/环境变量"**（那是 Runtime 凭证的语义，Git 凭证不注入 sandbox，P21-3 §10.3） |
| Git clone 权限失败回程 | 由 [F21-6](./21-6-项目管理.md) 触发 | 携 `pendingProjectCreate` 进本页 → 配置完成 → 回创建弹层 [重试克隆]（**与 `wizardReturn` 语义分离**，15 §3.1.1 纪律 3） |

## 6. 状态矩阵落地

| 产品状态（P21-3 §5） | 渲染分支 |
|---|---|
| 加载中 | `runtimes.isPending` → `CredentialCard` 骨架屏 |
| 无凭证 | 该 runtime 两类均未配置 → 简化态卡片 + [帐号授权] / [添加 API Key] CTA |
| 有效 | `expiresAt - now >= 7d` → 正常卡片 + 绿勾 |
| 即将过期 | `< 7d` → ⚠️ 黄 + "建议在 X 前重新授权"（与全局横幅同源，同一 `runtimeKeys.list()` 数据） |
| 已过期 | `expiresAt < now` → ❌ 红 + [重新授权] |
| 重授权中 | 卡片 `expandedPanel === rt` → 内嵌 `AuthGatePanel`（**不是 modal**） |
| 重授权成功 | mutation 成功 → `invalidateQueries(['runtime-auth'])` + `runtimeKeys.list()` + toast |
| 吊销确认中 | `currentModal==='revokeConfirm'` → 受影响 Task 列表（>10 折叠） |
| 吊销成功 | 卡片转未授权态 + toast；工作台相关 Task 行标 ⚠️（由 invalidate 联动） |
| Git 未配置 / 已配置 / 测试中 / 测试失败 | `GitCredentialCard` 四态 |

**API Key 特例**：一般无过期时间 → 不渲染倒计时，仅在校验失败时标 ⚠️（P21-3 §9）。

## 8. 依赖与缺口

- 依赖后端：`GET /api/runtimes` 聚合、`DELETE /api/runtimes/:rt/credentials/:credentialId`、`PUT /api/runtimes/:rt/auth-mode`、auth helper。
- ✅ **Git 凭证端点已定案**（02/05/10 三处一致落盘）：

  | 用途 | 端点 |
  |---|---|
  | 读（掩码列表） | **`GET /api/credentials?kind=git`**——`kind` 必填，MVP 只接受 `git`（其他值 400） |
  | 写（保存 SSH/Token） | `POST /api/credentials/git` |
  | 测试连接 | `POST /api/credentials/git/test`（后端 `git ls-remote`，15s；只回 `ok`/`errorCode`） |
  | 吊销 | `DELETE /api/credentials/git/:id`（**无联动清除**——Git 凭证不注入 sandbox） |

  - **读写分形态是后端的有意设计**：读端用 `?kind=` 是为未来的其他 kind 留位；写端走 `/credentials/git` 是因为 body 结构因 kind 而异，塞进泛集合会得到一个联合类型的请求体。前端照此实现即可，**不试图把两者统一成同一形态**。
  - 前端纪律：`kind='git'` 在 `git-credential.service.ts` 内**写死为字面量**，不作为方法参数暴露——MVP 只有一种 kind，提前开放参数只会让调用方有机会传出 400。将来后端真的加了 kind，改 service 一处即可。
  - 掩码契约：列表回 `maskedIdentifier`（SSH = 指纹、Token = 尾号）+ `type`/`platform?`/`knownHosts?`/`lastUsedAt`/`createdAt`；**SSH 私钥与 Token 明文永不回显**（P21-3 §10.3），前端不提供任何"查看"入口。`knownHosts` 用于凭证详情里核对首次连接自动记录的指纹（P21-3 §10.2）。

### 9.3 覆盖缺口汇总（本页 8 项）

| 缺口 | 影响 | 建议补法 |
|---|---|---|
| **#13/#14 两条否定性验收**（重授权不弹二次确认、Task 侧无 per-task 覆盖） | 否定性要求最容易在迭代中被"顺手加个确认框/加个下拉"破坏 | 各加一条 story play 否定断言 |
