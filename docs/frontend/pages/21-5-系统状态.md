## 1. 页面职责

运维视角看板：资源池水位、provider 可用性、连接状态、一键诊断与日志导出，**以及平台级审计流**（v1.1）。**唯一允许出现资源/配额概念的页面**——任务列表与发起链路一律不暴露（P22 §4.6）。

⚠️ 本页同时承载**两种日志**，它们在产品上是两样东西（P21-5 §10.1）：审计流是结构化事件、给产品用户看、可筛可分页；运行日志是文本行、给运维看、只在 provider 卡片里露出最近 20 行。**别合并**——见 §3。

### 3A. 审计流的双向游标消费（v1.1 新增）

> 这是本项目**第一个游标无限列表**（此前 `automationKeys.runs` 用的是 offset 页码），且它撞出了三个必错点。契约侧见 [10 §6.6.1](../../shared/10-接口契约与类型共享.md)，缓存策略见 [15 §2.1/§2.2](../15-前端状态管理.md)。

**① offset 分页在 append-only 流上是错的。** `automationKeys.runs(ruleId, page)` 那套照抄过来会错位：审计流一直在头部追加，用户翻到第 2 页时若新到了 7 条，第 2 页会重复显示第 1 页尾部的 7 条——而且**看起来完全正常**。必须用 `seq` 游标。

**② 两个方向必须分开，且只有一个能自动轮询。**

| 方向 | 触发 | 机制 | 为什么 |
|---|---|---|---|
| 历史（`before`，向下滚） | 用户滚到底 | `useInfiniteQuery.fetchNextPage`，`staleTime: Infinity` | append-only ⇒ 已加载的历史页**永不改变**，重拉是纯浪费 |
| 增量（`since`，新事件） | `refetchInterval: 30_000` | 独立轻量 query + `setQueryData` **prepend 进第一页** | 与本页其它卡片同频 |

⛔ **不要给 `useInfiniteQuery` 加 `refetchInterval`**——它会重拉**已加载的全部页**。用户向下滚了 10 页，每 30 秒就重打 10 个请求，返回内容还与缓存逐字节相同。这个错误不会有任何报错，只会让人纳闷网络面板为什么这么吵。

**③ 增量拉满 `limit` = 有断层，必须显性说。** 异常风暴时 30s 内可能产生 >200 条事件——**那恰恰是最需要看清的时刻**。此时 `since` 一次拉不完，`hasMore: true`。

- ✅ 产出 `gap: { afterSeq, beforeSeq }`，渲染 `AuditGapNotice`：「此处有未加载的事件 [加载中间部分]」
- ⛔ **不许**只 prepend 一页就当无事发生——列表在 UI 上是连续的，实际中间漏了，用户据此判断"这段时间没事发生"
- ⛔ **不许**自动循环追平到底——异常风暴下这是无界请求，且把用户正在看的位置冲走

**④ 筛选切换靠 query key 重置**——但只有**游标**是天然重置的，hook 自己的 state 不是。 `systemKeys.audit(filters)` 把 filters 放进 key：换筛选 = 换 key = 新缓存 = **游标**天然重置，这一段不需要手动 reset。⚠️ 若 filters 不进 key，`before=5000` 这个游标在「全部」和「仅告警」下指向完全不同的位置，会拉回一段与当前筛选无关的数据——**同样是静默错乱**。

⛔ **但这句只对 `useInfiniteQuery` 的游标成立，别推广到 hook 里的普通 `useState`。** 本节此前写的是「不需要**任何**手动 reset 代码」，实现完整继承了这个过度概括，于是 `gap` 跨筛选活了下来：全部类别下拉满产出 `gap {afterSeq:900, beforeSeq:1100}`，切到「类别=凭证」后 `historyKey` 变了、缓存换了，**`gap` 原样保留**，于是在凭证列表中间渲染出一个**属于另一条流、在这里根本不存在的洞**；点 [加载中间部分] 还会把一整页凭证历史 prepend 进去，再生成一个同样虚构的洞。

⇒ **凡是「跟着当前筛选才有意义」的 state（`gap` 是唯一一个），都要绑定到 `historyKey` 上显式清空。** 这条在测试里也要有断言——原来那条「filters 变化 ⇒ 游标天然重置」的用例只断言了新请求不带旧 `before`，**没断言 `gap` 是否为 null**，所以这个 bug 从头到尾没被任何用例碰到。

**⑤ 三个筛选一律走服务端，一律进 query key，一个都不许在客户端裁。** 类别是等值过滤；**严重度是多值**（`?severity=warn,error`，后端 `inArray`，见 10 §6.6.1）；时间范围走 `from`/`to` 过滤而**非游标**——它和 `before` 是两套坐标，混用会出错：`at` 与 `seq` 只是近似同序（并发插入下可微小乱序），把时间折算成 seq 会在边界上悄悄吞记录。

⛔ **「仅告警」曾经是一条死路，因为它被放在了客户端。** 契约最初把 `?severity=` 定成等值三选一，表达不了 `warn ∪ error`，于是前端拿 200 条回来自己裁——裁完为空时用户看到「当前筛选无匹配记录」，**而告警可能就在第 201 条**。真实形状：平台平稳跑一周，最近 200 条全是 info，昨天那次 provision 失败落在更老的位置，用户勾「仅告警」得到的结论是「平台从没告警过」。

⇒ 改由服务端 `WHERE severity IN (...) ORDER BY seq DESC LIMIT n+1` 之后，扫的是全表、取的是匹配项里最新的 n 条，于是**「返回空 + `hasMore:false`」就真的等于「全表没有匹配」**。⚠️ 顺带一提：这也意味着**「空列表 + 还有更早一页」在真实后端构造不出来**（`hasMore = rows.length > limit`，空页恒 false）——所以别为这个组合写容器级用例，它只能靠编造一个后端产不出的响应才跑得起来；翻页 footer 与 `rows.length` 的解耦测在 view 层（props 驱动）。

⚠️ **替身也要实现这个筛选**。msw 此前根本没实现 `severity`，「仅告警」在 dev / Storybook / e2e 里等于没筛——替身漏实现一个筛选条件，比实现错更难发现。

**⑥ 空态与失败态不许压成一个形状。** `useAuditStream` 刻意不窄化掉 `isError`。「暂无记录」盖住一次 500 是本页最坏的谎：用户会以为平台什么都没发生，而真相是审计接口挂了。P21-5 §10.2 要求空态显示「暂无记录」而非空白，那是**空态**的要求，不是失败态的。

⚠️ **而「空」本身还要再分三种**——⑥ 说的「空 vs 失败」只是第一刀：

| 空的种类 | 文案 | 用户的下一步 |
|---|---|---|
| 真的没有记录 | 「暂无记录」 | 什么也不用做 |
| 筛选没筛出来 | 「当前筛选无匹配记录 [清除筛选]」 | **去调筛选** |
| 该类事件尚未产出 | 「该类事件平台尚未记录」 | **等平台补上**（调筛选是徒劳的） |

⚠️ 第三种今天**没有类别命中**（2026-08-28 起五个类别都有产出，13 §2.8.2「各 `category` 的生产者清单」），但它照旧要实现并被测到：判据是`AUDIT_CATEGORY_EMIT_STATUS`，而那张表随后端增长——把分支删掉，下一个新类别落地前的那段窗口里，用户又会对着「筛选无匹配」徒劳地调条件。

⇒ 判据是**用户的下一步动作**，不是「后端返回了什么」——三种情况的 wire 响应完全相同（`items: []`），区别全在前端能不能说清。⚠️ 因此 `hasActiveFilters: boolean` 这种两态标志装不下三个事实，留着只会渲染出互相矛盾的组合；要用一个三值的 `emptyKind`。⚠️ 测试里每一个空态用例都要带**对另外两句的否定断言**——否则两句话同时渲染也会绿。

**⑦ 增量通道自己的失败也要可见——它是 ⑥ 的第二个时间点。** 历史方向的 `isError` 接出来了不等于完事：增量轮询是**另一条独立通道**，它挂掉时列表还在、首屏还在，用户看到的只是「新事件不再出现」。⑥ 禁止「失败伪装成空」，这里是**「静默停止更新伪装成没有新事件」——同一个谎，换了个时间点**。而异常风暴时审计接口最可能挂，那恰恰是用户最需要知道「我看到的不是全部」的时刻。

⇒ 透出 `isLiveUpdateError` / `retryLiveUpdate`，在卡片顶部渲染**一行**（`role="status"`）「实时更新已中断，列表可能不是最新的 [重试]」。⚠️ **是一行不是一块**——不许用整块错误态盖住已经拿到的列表；历史方向本身在报错时也不叠这一行。

| [加载中间部分]（v1.1） | `handleFillGap(gap)` | 以 **`before: gap.beforeSeq`** 向老翻一页，逐步收窄；**一次只填一段**（不自动循环，§3A ③）。⚠️ 本行原写 `since: gap.afterSeq`，**是错的**：`since` 返回的是「比它新的里面**最新**的 n 条」（10 §6.6.1），取回来正是顶上已有的那批，**洞一条都不会少**——按钮点了、请求发了、列表看着刷新了，洞还在。实现时按文档写会红 3 条用例 |

### 5A. 帧类型在哪（✅ 后端已落地，2026-08-28）

**`src/types/sse-protocol.ts`** —— 与 `ws-protocol.ts` 同放、同一套 `SYNC WITH` 纪律，
对面是 `api/packages/contracts/src/sse-protocol.ts`，两边的 `SSE_PROTOCOL_CANONICAL`
**逐字节相同**，由主仓 `docs:check` 的 **B5** 对账（shared/09 §2.4）。
⚠️ **openapi 生成不出流帧类型**（10 §6：它只能生成 `/diagnose` 的 content-type 声明），
所以这份是手写的 —— 改帧形状必须两仓同时改，否则 B5 当场红。

消费这条流时有五条不那么显然的规矩：

| # | 规矩 | 不这么做会怎样 |
|---|---|---|
| 1 | **按首帧 `event: start` 渲染八项占位**，不要用本地那份 `DIAGNOSE_CHECK_IDS` 当清单 | 八项并行，最快的可能是第 ⑥ 项；「收到一项画一项」会先画出一行孤零零的「WS 回环 ✅」，看起来像诊断只有一项 |
| 2 | **`check` 帧按 `id` 归位，不按到达顺序追加** | 并行执行下到达顺序 ≠ 展示顺序（P21-5 §6：异步并行但顺序固定） |
| 3 | **`status: 'info'` 渲染成 ℹ️，不是 ⚠️** | 第 ⑧ 项第 5 步（镜像未 staged）常态就是它。渲染成 ⚠️ 会让用户去修一个不需要修的东西，而他能想到的「修法」是删了重推 |
| 4 | **第 ⑧ 项的五步不许合成一条**：按 `step` + `errorCode` 分开渲染各自的 `hint` | 五步的下一步动作完全不同（改配置 / 推镜像 / 换成自建那张 / 重启平台 / 只是等一会），合成一条等于把诊断退化成一个红灯（P21-5 §9A） |
| 5 | **`errorCode` 当开放集合读**（`PRESET_IMAGE_CODES.includes()` 判分支，不认识的照常渲染 `summary`） | 收窄成 zod enum 会让后端新增一个码时**整帧校验失败** —— 「后端多说了一句」放大成「前端一个字都收不到」 |

其余七项**不发 `errorCode`**（它们的 `summary` 天然带着这一次实测出来的具体数字：哪个端口、
被谁占、还剩多少 GB），所以不要为它们准备码表。响应头带 `X-Schema-Hash: sb-diagnose-v1`，
⚠️ **它是告知不是门**：读到不认识的 hash 应照常渲染已认识的帧并提示升级，中断一次只读诊断
等于在最需要它的时候把它关掉。

## 6. 状态矩阵落地

| 产品状态（P21-5 §5） | 渲染分支 |
|---|---|
| 资源充足 | 三个维度（CPU/RAM/**磁盘**）使用率均 `<80%` → ✅ 绿 + "资源充足 · 当前活跃 Task: N" |
| 资源警告 | 任一维度 `80–95%` → ⚠️ 黄 + "建议停止部分 Task"；**磁盘触发时额外给 [清理保留卷]**（审计 P1-9：磁盘才是真实瓶颈，且保留卷是最大的可回收项） |
| 资源耗尽 | 任一维度 `≥95%` → 🔴 红 + "无法创建新 Task"（与工作台 🔴 阻断类横幅同源判定） |
| 保留卷占用治理 | `retainedVolumes` 总占用超阈值 → ⚠️ 治理类横幅「已保留卷占用 X GB [去清理]」→ 跳项目菜单的已保留卷（审计 P1-9） |
| provider 正常 | 探测成功 → ✅ + 版本与通道信息 |
| provider 故障 | 探测失败 → ❌ + 错误 + [查看日志] |
| provider 未启用 | 未配置 → ⏸️ "v2.0 开放"（boxlite） |
| provider 失败率告警 | `>1%` ⚠️ / `>10%` ❌ | 阈值判定在 `lib/providerHealth.ts` |
| WS 正常 / 断连 | `readyState` → ✅ 延迟数字 / 🔴 "已断开，等待重连…" |
| 诊断运行中 | 每项 spinner，已返回项立即定格 |
| 诊断完成 | 每项 ✅/⚠️/❌ + 可复制修复建议 |
| **审计流 加载中**（v1.1） | 骨架行 × 5；**不用整块 spinner**（列表有稳定高度，避免筛选切换时页面跳动） |
| **审计流 空**（P21-5 §10.2） | 「暂无记录」+ 说明当前筛选条件；**不是空白**——空白让人以为坏了 |
| **审计流 筛选无结果** | 「当前筛选无匹配记录 [清除筛选]」——与"平台真的没有记录"**用不同文案**，否则用户以为平台没干活 |
| **审计流 该类尚未记录**（v1.1，P21-5 §10.2） | 选中**后端尚未产出**的类别且为空 → 「该类事件平台尚未记录」。⚠️ 与「筛选无匹配」是两件事：**用户的下一步动作不同**（等平台补 vs 去调筛选）。⚠️ **类别压过其它筛选**：某个未产出类别 + 仅告警而空时仍说「尚未记录」。⚠️ **2026-08-28 起 `image` / `system` 已有产出**，`AUDIT_CATEGORY_EMIT_STATUS` 两项要改成 `emitted`、msw 替身同时补上这两类事件（双向对账，单改一边过不去）——但**机制本身保留**：类别是开放增长的（automation 是 v1.1，13 §2.7；`sandbox.health` 也还空着，03 §7.8），下一个新类别落地前照样有那段窗口 |
| **审计流 失败**（§3A ⑥） | ❌「审计流加载失败 [重试]」；⛔ **绝不退化成「暂无记录」** |
| **审计流 有断层**（§3A ③） | 在断裂处插 `AuditGapNotice`：「此处有未加载的事件 [加载中间部分]」——**不静默连续渲染** |
| **审计流 到底** | 「已到最早记录」（或「已达 30 天保留期」）；不再 spinner |
| **审计行 严重度** | `info` 常规 / `warn` ⚠️ 黄 / `error` ❌ 红；**颜色不是唯一线索**（同时给图标与文字，a11y） |

**整体等级取"最差维度"而非平均**（审计 P1-9）：CPU/RAM/磁盘三个维度里只要有一个 critical，整体就是 critical——平均会把「磁盘 98% + CPU 10%」算成健康，而那恰恰是最该拦住新建 Task 的时刻。磁盘是真实瓶颈（工作区副本 + 保留卷都吃盘），因此它单独触发时还要给 [清理保留卷] 的出路，而不是只让用户"停止部分 Task"（停 Task 不释放保留卷）。

## 8. 依赖与缺口

- 依赖后端：`GET /api/system/resources`、`GET /api/system/providers`、`POST /api/system/diagnose`。
- ✅ **诊断传输方式已定案：SSE**（技术 02 §5.3，含帧格式与「单项超时不阻塞整轮」语义）。`system.service.diagnose()` 内部消费 SSE 流，对上层仍暴露"逐项回调"接口——container 与 view 不感知传输细节；**单项超时由后端判定并以一条超时结果帧下发**，前端不自行计时、也不因某项超时中断整轮；断流（非正常结束）时保留已到达项 + 显示「诊断中断 [重新诊断]」。
- ✅ `systemKeys` **已合入 15 §2.1**（含 §2.2 staleTime 分级：resources/providers 15s + 30s 轮询；`diagnose()` `staleTime: Infinity` / gcTime 30min，支撑结果跨路由保留）。
- **访问保护是 MVP**（审计 P0-3 由 v1.1 提前），本页渲染、规格见 [F21-8](./21-8-部署与初始化.md)；升级备份仍 v1.5，渲染为占位说明。
- ⏳ **审计流整块依赖两个尚未落地的后端端点**：`GET /api/system/audit`（10 §6.6.1 双向游标）与 `GET /api/system/audit/export`（tar.gz 三件套）。`audit_events` 表设计见 13 §2.8.2，沙箱侧事件清单见 03 §7.8。**前端可先以 msw 契约先行**（§7.2/§7.3 全部只依赖契约形状，不依赖真实后端），但 §7.4 的 e2e 场景 5–7 要等端点落地。
- ✅ **契约缺口已在本轮补齐**：`cursor` 单参数原本表达不了两个方向（13 §2.8.2 说的「与 `SandboxJobs` 同语义」是 read-forward 单向 tail），已拆为 `since`/`before` 互斥双向 + `hasMore`，见 [10 §6.6.1](../../shared/10-接口契约与类型共享.md)；`AuditEventDto` / `AuditListDto` 补进 10 §7.3，`AuditFilters` / `AuditRowModel` / `AuditGap` 补进 [28 §5](../28-前端类型详细设计.md)。
- ⚠️ **`durationMs` 的来源要对齐**：`sandbox.provision.stage` 才有耗时，多数事件没有。前端 model 对缺失值**不产出** `durationText`（而非填 `'—'`），占位由 view 决定——这条容易在后端补字段时被反向改坏。

### 9.4 产品侧待补验收标准（本页 0 项）

> **本页三条已全部闭合**：
> ① **保留卷占用治理阈值**——P21-5 §5 已定：占 **DATA_ROOT 总容量 ≥80%** 转 ⚠️，文案「保留卷已占 DATA_ROOT 的 80%+，建议手动清理」+ 全局治理横幅；倒计时按 FIFO、整数天向下取整（不足 1 天显示"不足 1 天"）。
> ② **资源预留 15% 的算法**——P21-8 §7 已定：**分母不变**（进度条 = 已用 ÷ 总容量），预留只影响**调度上限**（可调度 = 总容量 × 0.85）。因此三档百分比按总容量算，与预留无关。
> ③ **诊断项清单与顺序**——P21-5 §6 已定：**固定八项固定顺序** ① 容器运行时 ② /dev/kvm ③ 磁盘余量 ④ 端口占用 ⑤ 外网连通 ⑥ WS 回环 ⑦ DATA_ROOT 文件系统 ⑧ 预制镜像就绪（P21-5 §9A）；**异步并行但展示顺序固定**，已完成项即刻出 ✅/⚠️/❌、未完成项 ⏳。
>
> 三条的验收标准已分别落进 §9.1 #5（治理横幅）、§6 状态矩阵（三档口径）、§9.1 #10/#12（诊断顺序与流式）。
