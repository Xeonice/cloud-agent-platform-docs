## 1. 页面职责

运维视角看板：资源池水位、provider 可用性、连接状态、一键诊断与日志导出。**唯一允许出现资源/配额概念的页面**——任务列表与发起链路一律不暴露（P22 §4.6）。

## 2. 路由与骨架落点

| 项 | 落点 |
|---|---|
| 路由 | `/settings/system`（无深链参数，实时数据无状态） |
| 路由文件 | `app/settings/system/page.tsx` |
| 布局 | 共享 `SettingsLayout`（07 §7.2） |
| 进入方式 | 顶栏 ⚙️ → ⚙️ 系统状态；Cmd+K → Settings → System；**任何环境类错误 toast/横幅的 [诊断] 按钮**（P20 §8.4） |
| 非阻塞 | 诊断运行中不阻塞其他页面使用 → 诊断 mutation 不锁 UI、切走再回来能看到结果（结果落 Query 缓存而非组件局部 state） |

## 4. 状态与数据接入

| 类别 | 具体 | 来源 |
|---|---|---|
| Query | `systemKeys.resources()` → `GET /api/system/resources`（`ResourcePoolSnapshot` 含 CPU/RAM **及 `totalDiskMb` / `usedDiskMb`**，审计 P1-9；`refetchInterval: 30_000`） | 15 §2.1/§2.2 |
| Query | `GET /api/retained-volumes`（保留卷总占用，供治理横幅与本页占用行；按项目筛用 `?projectId=`，审计 P2-5） | 02 §5.1 |
| Query | `systemKeys.providers()` → `GET /api/system/providers`（capabilities + 健康，30s） | 15 §2.1/§2.2 |
| Query | `systemKeys.diagnose()` → 诊断结果缓存（`staleTime: Infinity`，由 SSE 流逐项写入，跨路由保留） | 15 §2.1/§2.2 |
| 本地测量 | WS 心跳延迟、终端连接数 → 读 `terminalRegistry` 与 `sandboxEvents` 的连接态（Zustand，15 §4） | 15 §3.2 |
| Mutation | `runDiagnose` → `POST /api/system/diagnose`（**SSE 逐项流式**，技术 02 §5.3） | P22 §3 |
| Mutation | `exportLogs` → 浏览器下载（**导出前脱敏**由后端保证，前端只触发下载） | P21-5 §6 |
| Zustand | 无本页专属字段 | — |

**`systemKeys` 已合入 [15 §2.1](../15-前端状态管理.md)**（`all/init/resources/providers/diagnose`），staleTime 分级见 15 §2.2：resources/providers 15s + `refetchInterval 30_000`；`diagnose()` `staleTime: Infinity` / gcTime 30min——这正是"诊断结果跨路由保留"的机制来源；`init()` `staleTime/gcTime: Infinity`（一次性放行判定，F21-8）。

## 5. 交互实现要点（产品交互表逐行映射）

| 产品交互（P21-5 §6） | container + handler | 调用 |
|---|---|---|
| 自动刷新 | Query `refetchInterval: 30_000` | 资源/provider 两个 query；页面不可见时依赖 `refetchOnWindowFocus` 回补 |
| 手动 [刷新] | `handleRefresh()` | `refetch()` 两个 query，按钮 loading |
| [查看日志] | `handleToggleLog(providerId)` | 卡片内展开 `ProviderLogPanel`（最近 20 行，滚动），**不跳页不弹层** |
| [重新诊断] | `handleDiagnose()` | `system.service.diagnose()`；结果**写入 Query 缓存**（`setQueryData(systemKeys.diagnose())`），逐项到达逐项渲染；运行中其他区域仍可交互 |
| 修复建议 [复制] | `handleCopyFix(cmd)` | clipboard API + toast「已复制」 |
| [导出日志] | `handleExportLogs()` | 触发下载（最近 24h 或 50MB 取小）；前端不解析内容 |
| 从横幅 [诊断] 进入 | 路由跳转携带 `?autorun=1`（可选） | 进入后自动触发一次 `handleDiagnose()` |

**传输方式已定案 = SSE**（技术 02 §5.3：诊断须在 WS 故障时可用，故不走 WS；单项超时 5s 不阻塞整轮）。前端把 SSE 消费封在 `system.service.diagnose()` 内，对外统一暴露"逐项回调"接口，**container 与 view 不感知传输细节**。

## 6. 状态矩阵落地

| 产品状态（P21-5 §5） | 渲染分支 |
|---|---|
| 资源充足 | 三个维度（CPU/RAM/**磁盘**）使用率均 `<80%` → ✅ 绿 + "资源充足 · 当前活跃 Task: N" |
| 资源警告 | 任一维度 `80–95%` → ⚠️ 黄 + "建议停止部分 Task"；**磁盘触发时额外给 [清理保留卷]**（审计 P1-9：磁盘才是真实瓶颈，且保留卷是最大的可回收项） |
| 资源耗尽 | 任一维度 `≥95%` → 🔴 红 + "无法创建新 Task"（与工作台 🔴 阻断类横幅同源判定） |
| 保留卷占用治理 | `retainedVolumes` 总占用超阈值 → ⚠️ 治理类横幅「已保留卷占用 X GB [去清理]」→ 跳项目菜单的已保留卷（审计 P1-9） |
| provider 正常 | 探测成功 → ✅ + 版本与通道信息 |
| provider 故障 | 探测失败 → ❌ + 错误 + [查看日志] |
| provider 未启用 | 未配置 → ⏸️ "v2.0 开放"（boxlite） |
| provider 失败率告警 | `>1%` ⚠️ / `>10%` ❌ | 阈值判定在 `lib/providerHealth.ts` |
| WS 正常 / 断连 | `readyState` → ✅ 延迟数字 / 🔴 "已断开，等待重连…" |
| 诊断运行中 | 每项 spinner，已返回项立即定格 |
| 诊断完成 | 每项 ✅/⚠️/❌ + 可复制修复建议 |

**整体等级取"最差维度"而非平均**（审计 P1-9）：CPU/RAM/磁盘三个维度里只要有一个 critical，整体就是 critical——平均会把「磁盘 98% + CPU 10%」算成健康，而那恰恰是最该拦住新建 Task 的时刻。磁盘是真实瓶颈（工作区副本 + 保留卷都吃盘），因此它单独触发时还要给 [清理保留卷] 的出路，而不是只让用户"停止部分 Task"（停 Task 不释放保留卷）。

## 7. 本页测试设计

### 7.1 unit（bun test：lib / hooks / services）

| 被测 | 用例（断言级） |
|---|---|
| `lib/resourceLevel.ts` | 单维度分档：`79.9%→ok`、`80%→warning`、`94.9%→warning`、`95%→critical`、`100%→critical`；分母为 0 → 不返回 NaN |
| `lib/overallResourceLevel.ts` | **取最差维度**（审计 P1-9）：`{cpu:10%, ram:20%, disk:98%}` → `critical`（不是平均后的 ok）；三项全 ok → ok；缺 `totalDiskMb` 字段（旧后端）→ 降级为只算 CPU/RAM 且不崩 |
| `lib/providerHealth.ts` | 失败率 `0.9%→ok`、`1.1%→warning`、`10.1%→error`；未启用 → `disabled`（不参与阈值判定） |
| `lib/formatLatency.ts` | `15→"15ms"`、`1500→"1.5s"`、`null→"—"` |
| `services/system.service.ts` | ① `diagnose()` 按 SSE 帧到达顺序触发逐项回调；② **单项超时帧**（后端下发）被当作普通结果项渲染，**不中断后续帧**；③ SSE 断流（非正常结束）→ 抛出可被 container 捕获的 `DiagnoseStreamAborted`，已到达项保留；④ 正常结束帧后关闭连接（无悬挂 EventSource）；⑤ `exportLogs` 不在前端解析 body（只触发下载） |
| `hooks/useSystemStatus.ts` | ① 两个 query 的 `refetchInterval` 为 30s；② 诊断结果写入 `systemKeys.diagnose()` 缓存而非局部 state（切走再回来仍可读）；③ 诊断 mutation `retry:0` |

## 8. 依赖与缺口

- 依赖后端：`GET /api/system/resources`、`GET /api/system/providers`、`POST /api/system/diagnose`。
- ✅ **诊断传输方式已定案：SSE**（技术 02 §5.3，含帧格式与「单项超时不阻塞整轮」语义）。`system.service.diagnose()` 内部消费 SSE 流，对上层仍暴露"逐项回调"接口——container 与 view 不感知传输细节；**单项超时由后端判定并以一条超时结果帧下发**，前端不自行计时、也不因某项超时中断整轮；断流（非正常结束）时保留已到达项 + 显示「诊断中断 [重新诊断]」。
- ✅ `systemKeys` **已合入 15 §2.1**（含 §2.2 staleTime 分级：resources/providers 15s + 30s 轮询；`diagnose()` `staleTime: Infinity` / gcTime 30min，支撑结果跨路由保留）。
- **访问保护是 MVP**（审计 P0-3 由 v1.1 提前），本页渲染、规格见 [F21-8](./21-8-部署与初始化.md)；升级备份仍 v1.5，渲染为占位说明。

### 9.2 关键功能端到端验证脚本

#### VS-1 · 一键诊断（含 SSE 流式与中断）

| 步 | 操作 | 期望 | 判定通过 |
|---|---|---|---|
| 1 | 进 `/settings/system` → [重新诊断] | 六项检测各自 spinner | 不是整块 loading |
| 2 | SSE 逐条推送前 3 项结果 | 已到达项**立即定格**为 ✅/⚠️/❌，未到达项仍 spinner | 流式而非一次性 |
| 3 | 推送一条"外网连通 ⚠️ + 建议配置 HTTP_PROXY" | 该项显示建议命令 + [复制] | 点 [复制] 后剪贴板等于命令原文 |
| 4 | 诊断进行中点 provider [查看日志] | 日志面板正常展开 | **无遮罩、无 disabled**（非阻塞） |
| 5 | 诊断完成后切到 `/settings/images` 再切回 | 结果仍在 | 来自 Query 缓存（`staleTime: Infinity`） |
| **失败路径** | 推送一条**单项超时**帧 | 该项显示超时结果，**后续项继续到达** | 单项超时不阻塞整轮 |
| **失败路径** | 中途断开 SSE | 已到达项保留 + 「诊断中断 [重新诊断]」 | 不清空已有结果 |
