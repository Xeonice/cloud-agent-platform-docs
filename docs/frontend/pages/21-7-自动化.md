## 1. 页面职责

在项目下管理**自动化规则**（runtime + prompt + 简化预设调度 + webhook 通知），每次触发产生一个标准无头 Task。规则挂靠 Project，**无独立路由**——嵌在项目菜单侧弹层内。

> **版本纪律**：本页整体属 v1.1，与"无头 Task"形态配套。MVP 阶段 `ProjectMenuPanel` 中的 [⚙️ 自动化规则] 渲染为禁用态 + "v1.1" 角标，本文的组件/状态/测试设计作为实现时的落地依据，**不进 MVP 的 story 覆盖门禁**（避免为未实现功能写空 story）。

## 2. 路由与骨架落点

| 项 | 落点 |
|---|---|

## 5. 交互实现要点（产品交互表逐行映射）

| 产品交互（P21-7 §3/§5） | container + handler | 调用 |
|---|---|---|
| 打开面板 | `ProjectMenuPanel` 的 [⚙️ 自动化规则] | `currentModal='automations'`，作用域 = `selectedProjectForMenu` |
| [+ 新建规则] | `handleNewRule()` | 面板内切到 `view='form'`（空草稿）；规则数已 20 → 入口置灰 + 上限提示 |
| 选中规则 | `handleSelectRule(id)` | `view='detail'` + 拉取 `runs` 首页 |
| [编辑] | `handleEdit(id)` | `view='form'`（以现有规则填充草稿） |
| [禁用]/[启用] | `handleToggle(id, next)` | 乐观更新 → `POST .../enable\|disable` → 失败回滚 |
| [删除] | `handleDelete(id)` | 二次确认 → `DELETE /api/automations/:id` → invalidate list |
| 保存规则 | `handleSave(draft)` | 校验（名称必填、prompt ≤8000、调度合法、webhook URL 格式）→ `POST`/`PUT` → 回 `view='detail'` + toast |
| 调度选择 | `ScheduleSelector` 三种预设 | **新建时**时区默认取 `Intl.DateTimeFormat().resolvedOptions().timeZone`（IANA 名）并随创建请求提交；**MVP 不支持裸 cron**（自定义 cron 为 v1.2，Tab 置灰） |
| **编辑规则时的 timezone 纪律** | `handleSave(draft)` 分支 | **创建请求体带 `timezone`；编辑请求体默认不带**——只有用户在表单里**显式改了时区**才把该字段放进 payload（技术 27 §8 前端纪律 0 / 23 I-AUT-9）。理由：`timezone` 是创建时快照，编辑其他字段时若顺手把当前浏览器时区又传一遍，**用户换台机器一编辑就会把凌晨任务挪走** |
| Webhook [测试连接] | `handleTestWebhook(url)` | 后端代发测试请求 → ✅/❌ 就地反馈 |
| [查看全部] 历史 | `handleLoadMoreRuns(page)` | 分页 query，每页 20 |
| 单条历史 [打开 Task] | `handleOpenTask(taskId)` | 关面板 → 工作台选中该 Task → 右侧渲染**只读输出面板**（无头 Task，F21-1 §6） |
| 连续失败 [查看原因] | `handleShowFailure(id)` | 展开最近失败运行的详情（原因 + outputSummary） |
| [重新启用]（自动禁用后） | `handleReenable(id)` | `POST .../enable`；文案明示"失败计数清零" |

## 6. 状态矩阵落地

| 产品状态（P21-7 §4） | 渲染分支 |
|---|---|
| 规则启用 | `enabled===true` → ✅ + 下次触发时间（本地时区格式化） |
| 规则禁用 | `enabled===false` → ⏸️ 灰显；因项目归档联动时附说明 |
| 降频（v1.1 状态机） | 连续失败 ≥3 → 🟡「已降频：每日重试一次」 |
| 连续失败自动禁用 | 降频后再失败 7 次 → 🔴 + [查看原因] + [重新启用]，同时触发 ⚠️ 治理类横幅 |
| 空态 | 该项目无规则 → `AutomationEmptyState` + [+ 新建] |
| 运行历史各态 | ✅ 成功 / ⏭️ 跳过（`AUTH_EXPIRED`、`PREVIOUS_RUNNING` 两种原因文案）/ ❌ 失败（含超时）/ ⚠️ 资源重试中（"已排队 n/5"）/ ⏸️ missed |

### 7.1 unit（bun test：lib / hooks）

| 被测 | 用例（断言级） |
|---|---|
| `lib/scheduleToCron.ts` | 「每天 08:00」→ 对应表达式；「每小时 :00」；「每周一三五 08:00」；时区参数参与计算；非法输入 → 返回错误而非抛出 |
| `lib/nextTriggerAt.ts` | ① 给定规则与当前时间 → 下次触发时间正确；② 跨夏令时边界按**本地墙钟**语义不重复不跳过；③ **只用规则自带的 `timezone` 快照求值、不读系统时区**——同一 `(schedule, after)` 在任何机器上结果一致（纯函数性，对齐 23 `Schedule.nextOccurrence`）；④ 篡改 `process.env.TZ` 后结果不变（结构性断言） |
| `lib/automationStatus.ts` | `enabled + 失败0 → on`；`失败3 → degraded`；`降频后失败7 → autoDisabled`；`项目归档 → archivedOff`；`[重新启用] → on 且失败计数清零` |
| `lib/validateWebhookUrl.ts` | http/https 通过；非法协议拒绝；空 URL 但启用了通知 → 拒绝保存 |
| `lib/formatRunOutcome.ts` | 五种 outcome 各自的图标 + 人话文案；`skipped/AUTH_EXPIRED` 与 `skipped/PREVIOUS_RUNNING` 文案不同 |
| `hooks/useAutomations.ts` | ① 启停乐观更新 + 失败回滚；② 保存成功后 invalidate `list`；③ 规则数达 20 → 返回 `atLimit`；④ 草稿中的 prompt **不进 persist**；⑤ **创建 payload 含 `timezone`**；⑥ **编辑 payload 的键集合不含 `timezone`**（除非用户显式改过——两条分支各断言一次，这是 I-AUT-9 的前端侧防线） |

### 10.2 ⚠️ 调度器的设计**已经齐了**，在 `03 §8`

> 本节初稿写的是「表设计答不了调度器的运行形态，有三件事要先想清楚」——**那是没读 `03 §8` 就下的结论，三条全都早有答案，而且比我问得细**。原文照录，供实现时直接对表：

| 问题 | `03 §8` 的答案 |
|---|---|
| 宕机错过怎么算 | §8.2：`next_trigger_at` 过期**超过 `missedThresholdMin`（默认 5min）** ⇒ 判宕机错过，记 `missed`、**不补跑**、直接推进到下一个未来时刻（catchup 留 v1.2）。与 §7.2 clone 中断那条「不擅自替用户跑他看不见的长操作」同一哲学 |
| 调度器形态 | §8.1：**每分钟扫表** `WHERE enabled = true AND next_trigger_at <= now()`（走 `(enabled, next_trigger_at)` 索引），整批在一个 `async-mutex` 内串行，防上一轮未结束时重入。多节点时改 DB 行级锁 + `claimed_by`（11 §4 预留） |
| 资源不够 | §8.2 第 3 行：**排队重试 24min × 最多 5 次**（≈2h 窗口），置 `retry_at`；5 次仍失败转终态。⚠️ 重试**不产生新 run 记录**，同一行更新 `retry_count`，历史上显示「已排队 n/5」 |

**还有两条容易漏掉、但已经定好的**：

- ⭐ **时区是快照语义**（§8.1）：只读规则自己的 `automations.timezone`，**绝不读服务器系统时区、也不读请求方时区**；创建时快照，此后规则存续期内不变。算法是「在该时区下按本地墙钟求下一个满足 `schedule_config` 的时刻，再转 UTC 存 `next_trigger_at`」，DST 自然处理。⛔ 编辑规则时**不隐式改写 `timezone`** —— 否则「改了个 prompt 顺手把触发时刻挪了 8 小时」是最难排查的一类 bug
- ⭐ **outcome-pending 孤儿 run 补扫**（§8.1，交叉评审 P2-7）：run 已 `finalize` 但 `recordOutcome()` 未生效时崩溃，只按 `next_trigger_at` 扫规则**发现不了它**，会漏记一次失败计数。故每轮额外扫 `status IN (failed,timeout,success) AND outcome_applied = false` 补调（幂等）

⇒ **这一期不需要新的架构裁决，是照着 `03 §8` 与 `13 §2.7` 实现。**
