## 1. 状态分类学（每个状态的归属判定）

| 状态 | 归属 | 理由 |
|---|---|---|
| **项目列表**（含各项目 Task 数聚合） | **Query** `['projects','list']` | 服务端权威资源；分组树的两个数据源之一 |
| Task（sandbox）列表 | **Query** `['sandboxes','list',{projectId}]` | 服务端权威资源：缓存/去重/后台刷新/WS 增量更新 |
| sandbox 详情 | **Query** `['sandboxes','detail',id]` | 同上，与列表共享 normalize 后的同一实体 |
| runtime 聚合（卡片元数据 + 各自凭证状态） | **Query** `['runtimes','list']` | `GET /api/runtimes`，向导 Step 1 与凭证页共用同一份 |
| runtime 鉴权状态（已登录/掩码帐号） | **Query** `['runtime-auth',provider,'status']` | 服务端资源，变化低频 |
| device-code 鉴权会话（URL/code/倒计时） | **Query** `['runtime-auth',provider,'session']`（staleTime 0 + refetchInterval） | 一次性服务端资源，Query 的轮询自带取消/去重，优于手写 setInterval |
| 镜像列表（validationStatus / isActive / supportedRuntimes） | **Query** `['images','list']` | 镜像管理页与向导镜像下拉同源，禁用/启用后下拉自动联动 |
| **WS 连接状态**（connecting/open/reconnecting + 重连计数） | **Zustand**（terminal registry slice） | 见 §4 专门论证 |
| 终端实例注册表 `Map<sandboxId,{terminal,socket,...}>` | **Zustand** | 持有非可序列化对象（Terminal/WebSocket），Query 假设数据可序列化 |
| 当前选中 Task id / 当前项目 id | **Zustand + persist** | 纯客户端态、需跨组件共享；刷新回到上次现场（P20 §2.1） |
| **任务树分组折叠** `taskListFolds: Record<projectId, boolean>` | **Zustand + persist** | UI 偏好，跨会话记忆（P21-1 §9） |
| **`selectedProjectForMenu`**（组头「⋯」菜单的目标项目） | **Zustand**（不 persist） | 纯瞬时 UI 指向，刷新后应回到无菜单态 |
| **`wizardReturn` / `wizardData`**（确认步「＋ 新建项目…」往返暂存） | **Zustand**（`wizardData.initialPrompt` **仅内存、不 persist**） | 跨 modal 边界共享（向导 ↔ 创建项目弹层），局部 state 无法承载；见 §3.5 安全红线 |
| 侧栏折叠 | **Zustand + persist** | UI 偏好，跨会话记忆 |
| **横幅"当天不再弹"抑制记录** | **Zustand + persist** | 治理类横幅显式关闭后当天不再弹（P21-1 §9） |
| 鉴权 token / API key 输入框值 | **container 局部 useState** | 生命周期极短（提交即清空）、不共享；放全局 store 反增"忘记清空"泄漏面 |
| **等待输入的任务数 N**、分组树结构 | **派生（selector）** | 由 Query 数据计算，不落任何 store——见 §5 |

**判定准则**：① 来自服务端且需要缓存语义 → Query；② 纯客户端产物且需共享/持久化 → Zustand；③ 单 container 内短生命周期 → 局部 useState（只能在 container，不能在 view——lint 已强制）；④ **可由 ①②推导得出 → 派生 selector，不新建状态**。

## 2. TanStack Query 细化

### 2.1 Query key 工厂（集中管理，防 typo）

```typescript
// services/api/queryKeys.ts
export const projectKeys = {
  all:  () => ['projects'] as const,
  list: () => [...projectKeys.all(), 'list'] as const,
};
export const sandboxKeys = {
  all:    () => ['sandboxes'] as const,
  list:   (projectId?: string) => [...sandboxKeys.all(), 'list', { projectId }] as const,
  detail: (id: string) => [...sandboxKeys.all(), 'detail', id] as const,
};
export const runtimeKeys = {
  all:  () => ['runtimes'] as const,
  list: () => [...runtimeKeys.all(), 'list'] as const,   // GET /api/runtimes 聚合
};
export const runtimeAuthKeys = {
  all:     () => ['runtime-auth'] as const,
  status:  (provider: string) => [...runtimeAuthKeys.all(), provider, 'status'] as const,
  session: (provider: string) => [...runtimeAuthKeys.all(), provider, 'session'] as const,
};
export const gitCredentialKeys = {                                 // Git 凭证专属子资源（pages/F21-3）
  all:  () => ['git-credentials'] as const,
  list: () => [...gitCredentialKeys.all(), 'list'] as const,       // GET /api/credentials?kind=git（kind 由 service 内置）
};
export const imageKeys = {
  all:  () => ['images'] as const,
  list: () => [...imageKeys.all(), 'list'] as const,
};
export const systemKeys = {
  all:       () => ['system'] as const,
  init:      () => [...systemKeys.all(), 'init'] as const,        // GET /api/system/init-status：放行判定 + 上次出网检测结果（pages/F21-8）
  settings:  () => [...systemKeys.all(), 'settings'] as const,    // GET /api/system/settings：代理等配置 + 版本信息
  resources: () => [...systemKeys.all(), 'resources'] as const,
  providers: () => [...systemKeys.all(), 'providers'] as const,
  diagnose:  () => [...systemKeys.all(), 'diagnose'] as const,    // 诊断结果写缓存，跨路由保留
};
export const automationKeys = {                                    // v1.1（pages/F21-7）
  all:  () => ['automations'] as const,
  list: (projectId: string) => [...automationKeys.all(), 'list', { projectId }] as const,
  runs: (ruleId: string, page: number) => [...automationKeys.all(), 'runs', ruleId, { page }] as const,
  run:  (runId: string) => [...automationKeys.all(), 'run', runId] as const,
};
```

`sandboxKeys.list(projectId)` 带项目维度：切换项目 = 换 key，两个项目的列表各自独立缓存，来回切换不重新 loading。分组树需要"全部项目的 Task"时，用 `projectId: undefined` 的全量 key（见 §5）。

分层原则 `[资源域, 子类型, id/参数]`，粗粒度在前，支持 `invalidateQueries({ queryKey: sandboxKeys.all() })` 整域失效。

### 2.2 staleTime / gcTime 分级

| 数据 | staleTime | gcTime | 说明 |
|---|---|---|---|
| 项目列表 | 60s | 10min | 低频变化；创建/删除项目后显式 invalidate |
| Task（sandbox）列表 | 30s | 5min | WS 推送为主，REST 只兜底，staleTime 可放宽 |
| sandbox 详情 | 10s | 5min | 用户正在看，稍敏感 |
| runtime 聚合 `['runtimes','list']` | 60s | 10min | 卡片元数据基本静态；凭证状态变化由 WS `runtime-auth.status_changed` 驱动 patch |
| 鉴权状态 | 60s | 10min | 低频变化 |
| Git 凭证列表 | 60s | 10min | 低频；保存/吊销后显式 invalidate（pages/F21-3） |
| 镜像列表 | 60s | 10min | 注册/启停后显式 invalidate，保证向导下拉即时联动 |
| device-code 会话 | **0** + `refetchInterval: 3–5s` | 1min | 轮询由 refetchInterval 驱动；到 `expiresAt`（文档 04 §3 AuthChallenge 字段）主动停（`enabled:false`），不靠 retry |
| 系统资源 / provider 健康 | 15s + `refetchInterval: 30_000` | 5min | 运维看板，30s 刷新（pages/F21-5） |
| **诊断结果** `systemKeys.diagnose()` | **`Infinity`** | 30min | 由 `POST /api/system/diagnose` 的 SSE 流写入缓存而非组件局部 state——**切走再回来结果仍在**；只有再次点 [重新诊断] 才更新 |
| 初始化判定 `systemKeys.init()` | **`Infinity`** | `Infinity` | `GET /api/system/init-status`：一次性放行判定 + 上次出网检测结果（进向导直接渲染历史结果，不重跑检测）；完成后由 mutation `setQueryData` 置 true，不重新拉（pages/F21-8） |
| 系统设置 `systemKeys.settings()` | 60s | 10min | 代理配置与版本信息，低频；`PUT` 后显式 invalidate |
| 自动化规则列表（v1.1） | 60s | 10min | 低频；增删改后显式 invalidate |
| 自动化运行历史（v1.1） | 30s | 5min | 分页 query，翻页各自缓存 |

全局默认：`staleTime 30s、gcTime 5min、queries.retry: 2（指数退避）、refetchOnWindowFocus/Reconnect: true`；**`mutations.retry: 0`**——stop/start 等非幂等操作不得静默自动重试。

sandbox 列表 query 额外配置 `refetchInterval: 45_000`（30–60s 区间取中值）——这就是文档 07 §5 "推送为主、轮询兜底"中的兜底轮询，覆盖 WS 断线期间的数据陈旧窗口。

### 2.3 WS 事件 → 缓存 patch 映射表

事件名以文档 10 §3 的 `SandboxWsEvent` union 为唯一权威，此表一一对应。

**前提纪律（审计 P2-3）：sandbox 列表的 patch 一律用 `setQueriesData` 覆盖全部匹配缓存，不用 `setQueryData` 打单个 key。**

原因：`sandboxKeys.list(projectId)` 是带参数的 key 族——树用 `list(undefined)` 的全量缓存，按项目过滤/深链场景可能同时存在 `list('A')`、`list('B')` 等缓存条目。若只 patch 其中一个，**其余缓存会静默陈旧**：用户切到 B 项目看到的还是事件到达前的旧状态，而且没有任何报错提示。

```typescript
// services/ws/patchSandboxCaches.ts —— 所有 sandbox.* 事件的统一入口
queryClient.setQueriesData(
  { queryKey: sandboxKeys.all() },                 // 匹配 list(*) 与 detail(*) 全族
  (old) => applyEvent(old, event),                 // 纯函数，按缓存形状（数组/单体）分派
);
```

`applyEvent` 必须**对缓存形状做判别**（list 是数组、detail 是单体）并对"该缓存里没有这条 Task"的情况原样返回——`setQueriesData` 会把回调作用到每一个匹配缓存上，写得不健壮会把 detail 缓存改成数组。

| WS 事件 | 目标 key | patch 方式 |
|---|---|---|
| `sandbox.created` | `sandboxKeys.all()` 全族 | `setQueriesData` 追加到每个匹配的 list 缓存；**只追加到该 Task 所属项目的 list 与全量 list**（`list('B')` 不该收到 A 的新任务） |
| `sandbox.status_changed` | `sandboxKeys.all()` 全族 | 每个含该 id 的 list 单项 patch + detail 若在缓存同步 patch；两处用同一 normalize 实体 |
| **`sandbox.waiting_input`** | `sandboxKeys.all()` 全族 | patch 该 Task 的 `waitingInput` 子字段（**不改主 `status`**——它是 running 的子态，P21 §2.1）；侧栏 🔵 指示器与「⚡ N 个任务等待你输入」汇总均由此字段派生（§5） |
| `sandbox.removed` | `sandboxKeys.all()` 全族 | 每个 list 过滤掉该 id；`removeQueries({queryKey: detail(id)})` |
| **`project.clone_progress`** | `['projects','list']` | patch 该项目的克隆进度（已下载/总量/阶段），驱动创建弹层"🔄 正在克隆仓库…（12MB/45MB）"；**终态（成功/失败）走 `invalidateQueries(projectKeys.list())`**——克隆完成会带来任务数、状态等多字段变化，patch 得不偿失 |
| `runtime-auth.status_changed` | `runtimeAuthKeys.status(provider)` + `runtimeKeys.list()` | 两处同源：卡片徽标、横幅、Task 列表标记都读同一份凭证状态；聚合端点用 invalidate，单 provider 状态用 `setQueryData` 覆盖 |
| 复杂批量事件 | 粗粒度 key | **降级 `invalidateQueries`**——patch 逻辑复杂到有出错风险时，选正确性（invalidate）不选体验（setQueryData） |

**`waiting_input` 的两个约束**：① 它是 `running` 的**子态**，patch 时绝不覆盖主状态字段，否则 6 态可视化（P21 §2.1）会错乱；② 用户在终端键入或 agent 恢复输出后事件会反向推回（`waitingInput: false`），前端不做本地超时猜测——判定权在后端 pty 静默检测。

### 2.4 乐观更新（start/stop 按钮）

```typescript
useMutation({
  mutationFn: (id) => sandboxService.stop(id),
  onMutate: async (id) => {
    await queryClient.cancelQueries({ queryKey: sandboxKeys.detail(id) });
    const previous = queryClient.getQueryData(sandboxKeys.detail(id));
    // 乐观置为中间态 stopping，终态等 WS status_changed 确认
    queryClient.setQueryData(sandboxKeys.detail(id), old => ({ ...old, status: 'stopping' }));
    return { previous };
  },
  onError: (_e, id, ctx) => queryClient.setQueryData(sandboxKeys.detail(id), ctx.previous), // 回滚
  onSettled: (id) => queryClient.invalidateQueries({ queryKey: sandboxKeys.detail(id) }),   // 最终以服务端为准
})
```

三个要点：乐观态用**中间态**而非终态；`onSettled` 兜底 invalidate 防长期不一致；mutation 不自动重试。

## 3. Zustand 细化

### 3.1 store 划分：单 store + slices（官方与社区共识）

```
stores/
  createTerminalRegistrySlice.ts   # 终端实例注册表 + WS 连接态
  createUiSlice.ts                 # 选中 Task/项目、任务树折叠、菜单指向、向导暂存、横幅抑制
  index.ts                         # slices pattern 合并为单一 useAppStore
```

中间件（devtools / persist / immer）**只在合并后的顶层 store 应用一次**，不在单个 slice 各自套（避免叠加顺序混乱）。仅当某域完全独立且有选择性订阅性能诉求时才拆多 store。

### 3.1.1 uiSlice 字段清单（产品定稿后的完整面）

```typescript
interface UiSlice {
  // —— 选中上下文（persist）——
  selectedSandboxId: string | null;
  selectedProjectId: string | null;          // 当前项目，供 CurrentProjectIndicator 只读展示
  sidebarCollapsed: boolean;

  // —— 任务树（persist）——
  taskListFolds: Record<string, boolean>;    // { [projectId]: 是否折叠 }
  toggleProjectFold(projectId: string): void;
  expandProject(projectId: string): void;    // 深链/跨项目点击/指示器定位时强制展开

  // —— 瞬时 UI 指向（不 persist）——
  selectedProjectForMenu: string | null;     // 组头 hover「⋯」打开侧弹层的目标项目
  currentModal: 'createProject' | 'registerImage' | 'wizard' | null;

  // —— 向导往返暂存（wizardData.initialPrompt 不 persist，见 §3.5）——
  wizardReturn: boolean;                     // true = 项目创建成功后回确认步而非回工作台
  wizardData: {
    runtime?: string;
    selectedProjectId?: string;
    image?: string;
    initialPrompt?: string;                  // ⚠️ 仅内存
  } | null;

  // —— Git 凭证回程暂存（不 persist）——
  // projectId 来自 POST /api/projects 的 202 响应：后端先落库再异步 clone（24 §3），
  // 因此回程时调的是 POST /api/projects/:id/retry-clone，**不是**重新创建（pages/F21-6 §5）
  pendingProjectCreate: { projectId: string; name: string; source: 'git' | 'empty'; url?: string } | null;

  // —— 横幅（persist：仅抑制记录）——
  bannerDismissedToday: Record<string, string>;  // { [bannerId]: YYYY-MM-DD }
}
```

三点纪律：

1. **`expandProject` 是 action 不是副作用**——深链 `/?taskId=` 命中其他项目、点击其他项目的 Task、点击顶部指示器定位，三条路径都调同一个 action（切 `selectedProjectId` + 展开该组），不各写一份 effect。
2. **`selectedProjectForMenu` 与 `selectedProjectId` 是两个概念**：前者是"我正在管理谁"（菜单指向，可以是非当前项目），后者是"我正在哪个项目里工作"（上下文）。合并会导致"打开 B 项目菜单顺手把工作上下文切走"。
3. **`wizardReturn` 与 Git 凭证回程的 `pendingProjectCreate` 语义分离**：前者管"创建项目后回向导确认步"，后者管"配完 Git 凭证后回创建弹层重试克隆"，两条回程互不复用状态位。

### 3.2 Terminal Registry 生命周期

```
[未创建] ─首次选中─▶ [creating] ─new Terminal()+连WS─▶ [connecting] ─open─▶ [connected] ◀─┐
                                                            │ close                       │ 重连成功
                                                            ▼                             │
                                                      [reconnecting] ─────────────────────┘
                                                            │ 达最大重试
                                                            ▼
                                                        [errored]（"连接失败，手动重试"）

任意状态：切走 → DOM display:none，entry 保留
         LRU 超限且最久未激活 → [disposing]: terminal.dispose() + socket.close() → Map 移除
```

- 数据结构：**键是 `sessionId`（会话粒度）不是 `sandboxId`**——一个 Task 可开多个终端标签（P21-1 §6），用 sandboxId 作键会让第二个标签挤掉第一个的 entry，留下既不渲染也不释放的孤儿实例（内存 + WebGL 上下文双泄漏）。完整结构与字段见 **[文档 08 §5.1](./08-前端xterm集成.md)（终端子系统的权威定义）**：

  ```
  entries:         Map<sessionId, { sessionId, sandboxId, socketSessionKey?, terminal,
                                    socket, container?, renderer, connState, lastActiveAt }>
  bySandbox:       Map<sandboxId, sessionId[]>     // 标签顺序
  activeSessionOf: Map<sandboxId, sessionId>
  ```

- **LRU 按 session 计数**（WebGL 上下文按 Terminal 实例占用，不按 Task），默认上限 **4–6**（审计 P2-11，理由见 08 §5.2）。
- **LRU 决策逻辑放 `hooks/useTerminalInstance.ts`，store 保持"哑"**——只暴露 `register/dispose/touch/patchConnState/patchRenderer/setActiveSession` 这类记账 action，不做业务判断。store 不是隐藏的第二个逻辑层，这是视图/逻辑分离的延伸原则。
- `socketSessionKey` 存在 entry 里供重连回带，**不进 persist**（会话级凭据，08 §3）。

### 3.3 selector 规范（防过度渲染）

- **禁止** `const state = useAppStore()` 整 store 订阅。
- 统一细粒度 selector：`useAppStore(s => s.selectedSandboxId)`。
- 多字段用 `useShallow` 包装防新对象引用重渲染。
- registry 场景 selector 精确到 `s => s.entries.get(sessionId)`（会话粒度，08 §5.1），避免 Map 引用变化触发所有终端组件重渲染。

### 3.4 与分层制度的结合

沿用 boundaries 规则：`views/**` 禁 import `stores/**`；**store 只被 hooks/containers 访问**，view 需要的数据由 container 传 props——保证"从 store 读数据做判断"永远发生在逻辑层。

### 3.5 persist 策略

`partialize` 采用**白名单**（列举要存的，而不是排除不存的）——新增字段默认不落盘，避免"加了个字段忘了排除"的静默泄漏：

```typescript
persist(..., {
  name: 'agent-platform-ui',
  partialize: (s) => ({
    selectedSandboxId: s.selectedSandboxId,
    selectedProjectId: s.selectedProjectId,
    sidebarCollapsed:  s.sidebarCollapsed,
    taskListFolds:     s.taskListFolds,
    bannerDismissedToday: s.bannerDismissedToday,
    terminalFontSize:  s.terminalFontSize,
    lastUsedRuntime:   s.lastUsedRuntime,   // 向导 Step 1 记忆上次选择
    lastUsedImage:     s.lastUsedImage,
  }),
})
```

- **`wizardData.initialPrompt` 绝不 persist（安全红线）**：任务指令可能含仓库路径、内部系统名、业务上下文等敏感信息，产品明确要求"任务指令仅在创建请求中传输、不落前端持久化"（P21-2 §9）。它只在向导 modal 与创建项目弹层之间的**同一次会话内存中**传递；刷新即丢失是**预期行为**（向导 modal 刷新本就直接关闭，P20 §8.5）。同理 `pendingProjectCreate` 与 `selectedProjectForMenu` 也不 persist。
- **鉴权凭证相关的任何值绝不进 store**（更不用说 persist）：粘贴的 code / API key 只在 `AuthGateContainer` 的局部 `useState`，提交即清空。
- **terminal registry 绝不 persist**（非可序列化 + 刷新后旧连接本应失效重建）。
- CI 侧建议加一条断言测试：`partialize` 的输出快照不含 `initialPrompt`/`pendingProjectCreate`/`secret` 等键——把红线变成可回归的检查（文档 12 §3.2 stores 单测）。

## 4. 连接态归属论证：Zustand（不是 Query）

1. **不是请求-响应模型**：WS 连接态是"有状态对象随时间的内部状态变化"，硬套 queryFn 语义扭曲（resolve 时机？重连算 refetch？）。
2. **与 registry 强耦合**：socket 实例已在 Zustand，状态拆到 Query 会导致同一逻辑实体双系统双写、易不一致。
3. **高频变化**不符合 Query 的低频可缓存假设。

**关键边界区分**（易混）：`sandbox.status`（running/stopped，**服务端业务状态**）→ Query；`connState`（connecting/reconnecting，**浏览器↔网关传输层状态**）→ Zustand。两者是不同维度，必须分开。

## 5. 分组任务树的数据推导（不建平行结构）

左侧栏是"全部项目 × 各自 Task"的分组树（P21-1 §3/§9）。**树本身不是状态，是派生视图**：

```
Query ['projects','list']  ─┐
                            ├─▶ selectProjectTaskTree(projects, tasks, folds)  ─▶ ProjectGroup[]
Query ['sandboxes','list']  ┘        （lib/ 纯函数，可单测）
Zustand taskListFolds       ┘
```

| 规则 | 说明 |
|---|---|
| **数据源两个 Query，不新建 store** | 树里的项目名/任务数来自 `projects`，Task 行来自 `sandboxes`；**绝不把分组结果写回任何 store**——那会造成 WS patch 后树不刷新的经典双写不一致 |
| **树的数据源是全量 Task 列表** | 树要渲染包括非当前项目在内的全部项目，因此用不带 `projectId` 的 `sandboxKeys.list()`；带 `projectId` 的 key 保留给服务端过滤场景（深链定位、项目 Task 数超限时的降级分页） |
| **分组函数放 `lib/`** | `selectProjectTaskTree()` 是纯函数（输入 projects/tasks/folds，输出 `ProjectGroup[]`），bun test 主战场；hooks 只负责取数并调用它 |
| **孤儿 Task 兜底** | `projectId` 在 projects 中找不到时归入"未分组"组并保持可见，绝不静默丢弃列表项 |
| **排序** | 组内按最后活跃倒序（P21-1 §9）；组间以 projects 返回顺序为准，当前项目组置顶 |
| **折叠只影响渲染** | 折叠的组不渲染子项，但**其 Task 仍参与全局汇总计算**（否则折叠会让"等待输入"计数凭空变小） |

**「⚡ N 个任务等待你输入」汇总 selector**：

```typescript
// hooks/useWaitingInputCount.ts —— 跨全部项目汇总，不受折叠影响
const count = useMemo(
  () => tasks.filter(t => t.status === 'running' && t.waitingInput).length,
  [tasks],
);
```

- 计数口径 = **全部项目**（用户要的是"还有几件事等我"，不是"当前项目有几件"）；点击汇总行跳到第一个等待输入的 Task 并自动展开其所属项目组（复用 §3.1.1 的 `expandProject`）。
- 该值**不落 store**：它是 `waiting_input` 事件 patch Query 缓存后的自然结果，多存一份就多一处不同步风险。

## 6. devtools

- **TanStack Query Devtools**：仅开发环境挂载（条件渲染/dynamic 懒加载）；调试"WS 事件是否正确 patch 缓存"的关键工具。
- **Zustand devtools 中间件**：接 Redux DevTools；**每个 action 显式命名**（`set(fn, false, 'terminalRegistry/dispose')`），否则时间线全是匿名 setState 无法调试。
