# 28 - 前端类型详细设计

> 定位：[07](./07-前端目录结构与视图逻辑分离.md) 给分层与目录、[15](./15-前端状态管理.md) 给状态分类、[14](../shared/14-跨仓类型安全.md) 给类型安全机制（防漂移/防绕过）。本文补齐**前端实际的类型声明**——生成类型怎么消费、store/key/props/纯函数的类型契约。

## 1. 生成类型的结构与消费

```ts
  | { event: 'sandbox.waiting_input'; sandboxId: string; waiting: boolean; sessionId?: string }
  | { event: 'project.clone_progress'; projectId: string; phase: 'cloning'|'slow'|'done'|'failed'; receivedBytes?: number; totalBytes?: number; percent?: number; errorCode?: string }
  | { event: 'runtime-auth.status_changed'; runtime: string }

// applyEvent 按缓存形状判别（15 §2.3 的两个坑：list 是数组、detail 是单体，不能混写）
```

**运行时校验边界**（16 §3）：WS 帧与不可信边缘**入口处 zod `.parse()`**——生成类型是编译期契约，WS 是无 openapi 保证的通道，必须运行时兜一层：

```ts
const SandboxEventSchema = z.discriminatedUnion('event', [ /* … */ ]);
socket.onMessage(raw => { const e = SandboxEventSchema.parse(JSON.parse(raw)); applyEvent(e); });
```

## 5. 前端自有值类型（派生逻辑的类型契约）

```ts
// lib/mapTechStatusToUserStatus.ts —— 12 技术态 → 6 用户态；入参取生成的 SandboxStatus union，全覆盖（漏一个 CI 红）
type UserStatus = 'preparing' | 'running' | 'waiting-input' | 'paused' | 'failed' | 'gone';
function mapTechStatusToUserStatus(s: SandboxStatus, waitingInput: boolean): UserStatus;

// lib/sandbox/sandboxLifecycle.ts —— 12 态 → 4 阶段格（多对一）；断言 STARTUP_PHASES 长度=4
//
// ⚠️ 本块 2026-08 订正，原文三处都与代码不符：文件名写成 `lib/mapStatusToStage.ts`（不存在）、
//    类型写成 `CreationStage`（不存在）、格数写成 5 并多一格「连接终端」（代码里没有这一步）。
//    真实导出见下；`running` **不点任何格**——`classifyStatus('running')` 返回 `'running'`，
//    进度卡退出、切去开终端。产品侧权威 P21 §2.2 写的同样是 4 格。
//    ⚠️ 「断言长度=5」这种规格照抄进测试就是一条**注定写错的断言**，而它当时看起来完全合理。
export const STARTUP_PHASES: readonly { key: StartupPhaseKey; label: string }[];  // 4 格
type StartupPhaseKey = 'init' | 'image' | 'workspace' | 'instance';
function phaseKeyForStatus(s: string): StartupPhaseKey;   // preparing-workspace→workspace, creating→image

// lib/sandbox/instanceStartupCopy.ts —— `sandbox.instance_progress` 的唯一消费点（10 §7.4）。
//
// 它与 `runtimeInstallProgress.ts` 是**同一格里前后相继的两段**（先起实例、再装 CLI），
// 两张投影表分开而不是合并：合成一个字段就得靠「谁后到谁赢」仲裁，而那正是丢帧时最容易错的地方。
// 仲裁写在 `useSandboxLifecycle` 里：install 文案一到就接管（它是更晚的那一步）。
interface InstanceStartupProgress { phase: 'starting' | 'ready'; imageStaged?: boolean }
function instanceSubCopy(p: InstanceStartupProgress | undefined): string | undefined;
// ⚠️ `imageStaged` 的**三态**是这个类型的全部意义：false（本机确实没有）/ true（有）/
//    **undefined（provider 说不出）**。第三种绝不能被当成第一种——把 `?? false` 写进 switch
//    等于把「不知道为什么慢」渲染成「因为要现拉一份 13GB 的镜像」，那是把不知道说成了知道。
// ⚠️ `true` 那一支**只陈述事实、不承诺时间**：后端那个布尔有一种排除不掉的假阳性
//    （BoxLite 的 `image_index.complete` 没透出到 SDK，半截的 pull 也会被数成「有」）。

function formatElapsed(ms: number): string;   // '3:10' / 超一小时 '1:01:01'；负数与 NaN 归 0
// ⚠️ 「已等待」这个数字**由前端自己算**，后端一个字节都不推：浏览器知道自己何时收到
//    `status_changed → starting`。锚点是 store 的 `observedAt`，而它**只由 WS 事件产生**——
//    REST 刷新恢复出来的 `starting` 没有锚点，此时 `elapsedLabel` 缺席、卡上**不渲染计时**。
//    DTO 上没有「何时进入该状态」的时间戳，从 0 数会把一个 3 分钟前开始的等待显示成「0:02」。

// ⏳ lib/audit/auditRowModel.ts —— 审计行 view model（F21-5 §3A）。同 ImageCardModel 的理由：
//    boundaries 规则里 `view` 只能 import view/type/component,**碰不到 lib**——所以时间格式化、
//    detail 的 JSON stringify、耗时人话化全部在 lib 算完,view 只收一个 model。
interface AuditFilters {                        // ⚠️ 进 query key,故必须是可稳定序列化的扁平对象
  category?: AuditCategory;                     // undefined = 全部
  severity?: 'warn-and-error';                  // 产品只给「仅告警」一个开关,不是三选一(P21-5 §10.2)
  subjectId?: string;                           // 沙箱详情时间线复用本 hook 时才有
  from?: string; to?: string;                   // ISO；与游标正交(10 §6.6.1)。⚠️ 不是翻页手段
}
interface AuditRowModel {
  seq: number;                                  // React key,且用于断层比较
  timeText: string;                             // 'HH:mm:ss.SSS' / 跨天带日期；view 不碰 Date
  //   ⚠️ 带毫秒:audit_events.at 是本仓第一处毫秒精度列,异常风暴下同一秒几十条
  severity: AuditSeverity;
  summary: string;
  actorText: string;                            // 'system' → '系统'
  durationText?: string;                        // 4231 → '4.2s'；无耗时的事件不产出
  outcome?: 'ok' | 'failed' | 'skipped';
  errorCode?: string;                           // 与 10 §6.8 同闭集,不拼进 summary
  detailText?: string;                          // 展开时渲染的已格式化 JSON；**detail 为空时不产出**
  subjectLink?: { subjectId: string; label: string };   // [查看该沙箱完整时间线]
}
type AuditGap = { afterSeq: number; beforeSeq: number };
//   ⚠️ 断层不是错误态,是**如实告知**：增量拉满 limit 说明两个 seq 之间漏了未知条数(10 §6.6.1)。
//      不产出这个类型,UI 就只能假装列表连续——那正是异常风暴时最误导人的时刻。

// ⏳ lib/image/imageCardModel.ts —— 镜像卡片 view model（F21-4 §5.1）。与 RuntimeCredentialCardModel 同形态：
//    lib 算好 → types 定形 → view 只收一个 model prop。**必须走 model**，因为 boundaries 规则里
//    `view` 只能 import view/type/component——view 连 lib 都碰不到，"解析于 3 天前"这句在 view 里算不出来。
type DigestState = 'resolved' | 'unresolved';   // 空串与 'sha256:unresolved' 都归 unresolved（哨兵已无产出方，但切片前的历史行是空 digest，F21-4 §8.4）
type RefKind     = 'tag' | 'digest';           // `repo@sha256:…` 形态无 tag ⇒ 不存在上游漂移

  refKind: RefKind;
  digestState: DigestState; digestShort?: string;      // unresolved 时不产出（**绝不产出假哈希、也不产出空串**）
  validationStatus: ImageValidationStatus; supportedRuntimes: string[];

  //     `ImageManifestResponseDto['validationStatus']`（四值：pending|valid|warning|invalid）
  isActive: boolean; isBuiltin: boolean;               // isBuiltin → 不渲染 [删除]
  resolvedAgoText?: string;                            // 「解析于 3 天前」
  canCheckUpdate: boolean;                             // refKind==='digest' 或 digestState==='unresolved' ⇒ false（置灰）
}
function imageCardModel(dto: ImageDto, now: number): ImageCardModel;
//   ⚠️ **模型上刻意没有 `staleValidation` / `validatedAgoText` 之类的"结论过期"字段**：产品裁决
//      「注册即钉住 digest」之后，结论描述的是一个不可变对象、**不会烂**（P21-4 §5 ★），会变的只是
//      "这个 tag 现在还指向它吗"——那由 [检查更新] 回答。措辞也随之从「最后验证」改为「解析于」。
//      类型上不给过期留位置，是为了别让"7 天转黄"那套设计从别处长回来（F21-4 §7.1 有否定断言）。
```

| 生成 DTO/枚举消费点 | shared/10 §7 全量 | `openapi.d.ts`（**不手写**） |
| WS union | 2 通道 | `ws-protocol.ts`（手工同步 + X-Schema-Hash） |
| Store slice 类型 | 2（Ui + TerminalRegistry） | 前端自有 |
| Query key 工厂 | 9（+ `providerKeys`） | 前端自有（`as const`） |
| 纯函数契约 | 6（mapStatus×2 / projectGroupState / validateEnvVar / selectProjectTaskTree …） | 前端自有 |
| 错误消费 | 1（`ApiError`） | = 后端 envelope |

**一句话边界**：凡"过线"的类型（DTO/枚举/错误）来自后端 zod 单源、经生成消费、永不手写；凡"前端自有"的类型（store/key/派生纯函数）在前端定义，但**输入输出仍咬合生成的 DTO/枚举类型**——`SandboxStatus` 改了，`phaseKeyForStatus` 的 switch 在 tsc 阶段就红（⚠️ 原写 `mapStatusToStage`，该函数不存在，2026-08 随本节订正）。

## 8. 四层类型流转（view/logic 分离的类型骨架）

> 07 §3 的分层铁律用类型表达：**类型从右往左收窄，副作用从左往右禁止**。一份 wire DTO 进来，每层只暴露下一层需要的形状。

```
generated DTO ──▶ service（唯一 fetch/WS）──▶ hook（唯一 useEffect/业务态）──▶ container（粘合）──▶ view（props 驱动，纯展示）
   SandboxDto        Promise<SandboxDto>         { data, isPending, mutate }      装配 props        Pick<SandboxDto,...>
```

| 层 | 类型职责 | 禁止 |
|---|---|---|
| **service** | 入参/返回全是**生成的 DTO/枚举**（`Promise<SandboxDto>`）；WS 帧是 `ws-protocol.ts` union | 不产生前端自定义形状 |
| **hook** | 返回**逻辑态契约**（Query result / mutation / 状态机 union / 派生纯函数结果）；对外暴露的是"视图要用的语义态"，不是原始 DTO | 不返回 `any`；不把 DTO 原样透传时要 Pick |
| **container** | 只做类型装配：`hook 返回` → `view props`；本身几乎无自有类型 | 不写业务类型 |
| **view** | props 是 `Pick/Omit<DTO>` 或 hook 结果的窄切片 + 回调签名 | 不 import service/hook 的类型以外的东西 |
