# CLI 版本升级与用户触发更新测试计划

本计划验证 Codex `0.150.1→0.163.0`、Claude Code `2.1.251→2.1.302` 的实际交付，以及管理员手动升级时原沙箱的连续性。对应 [升级与实验发包计划](../../ops/2026-10-17-Codex与ClaudeCode升级发包计划.md)。下列场景均待实现后执行；本计划本身不构成测试通过回执。

## 统一部署前置验收

本机与 `100.73.71.22` 均使用 macOS 宿主、Colima Linux arm64／VZ 嵌套虚拟化、Docker 分离角色。远端已完成基础迁移与来源封存退役，结果见 [迁移验收报告](../results/2026-10-17-统一部署与在线升级验收.md)。本计划从远端已确认的 `.3`、专属实例／渠道与固定信任根出发；基础迁移和真实新 Guest 通过不等于跨升级连续性或 CLI 发包通过。

每次执行仍冻结实际来源版本、实例／渠道、信任目录、API／Web 入口和角色物理身份，作为下表中的“来源基线”。不沿用主线上 C 或历史预演的身份。

## 版本和镜像交付

| 场景 | 操作与必须断言 |
| --- | --- |
| V01 固定版本 | 两份 Dockerfile、adapter 安装回退及发布收据版本一致；安装命令不含漂移的 latest；已有 CLI 探测不得执行升级。 |
| V02 真实运行 | AIO／BoxLite 各 linux/arm64、linux/amd64；通过实际执行用户及 provider 入口检查 command -v、CLI 精确 --version、Node 22、tmux、UTF-8。不能只看构建 ARG／LABEL。 |
| V03 原生依赖 | npm optional platform binary 实际存在且可执行，AIO PATH 不被旧 shim 遮挡；Claude 的后台更新策略生效；无凭据／用户缓存进入镜像或包。 |
| V04 镜像登记 | 已存在同仓旧版时补入新固定 tag；重试不重复；普通 REST 不能伪造 builtin；已禁用版本不自动启用，同 tag 漂移不偷偷激活。旧 manifest／digest／配置／别名保持。 |
| V05 默认和回退 | 新角色实际选择新固定引用，现网官方 latest 配置不会把它覆盖；自定义覆盖保持；新旧 tag 均可按既有规则选择。恢复旧版本后默认恢复原引用，已有任务快照不变。 |
| V06 发布资产 | 匿名下载、字节数／摘要／签名、架构、冻结提交、镜像索引／平台 digest、升级路径和实例／渠道均一致；错误摘要、错平台、未知签名、过期目录被拒绝。 |
| V07 登录 helper | 记录实际 container／host helper 的 CLI 版本及有效 PATH；验证既有凭据对新沙箱及保留旧沙箱均可用，未完成的登录挑战仍路由原 helper，不因更新被擅自结束。无对应测试凭据则标为未验证。 |
| V08 持续签名 | 后续候选使用实例安装时固定的 trust root 与持久发布密钥，经 `signQualificationManifest` 签名；API／Installer 均实际验签，原 envelope 继续可验证。不通过 `buildQualificationDistribution` 重新生成信任根；私钥不传远端或发布资产。签验测试不计作升级或 CLI 发包通过。 |

CLI 兼容回归包括交互启动、无头输出事件解析、工具执行、session resume、凭证文件注入及隔离。重点验证 Codex exec/resume 参数与 JSON 事件，Claude root/IS_SANDBOX、permission-mode 与无头 JSON 行为。升级不主动修改用户显式模型／权限配置；未显式设置时，核对并记录新 CLI 的默认模型和权限行为，不能保证默认行为相同。没有专用模型凭据时，先运行真实 CLI 的本地协议测试与真实 Guest 计数验收；模型质量及外部服务连续性保留未验证，不能用假 CLI 进程替代。

## 后端和真实升级

| 场景 | 操作与必须断言 |
| --- | --- |
| B01 发布不升级 | 发布目录后当前版本、generation、角色 PID 与沙箱保持；只读检查不产生升级 attempt。CD 不调用管理员升级接口。 |
| B02 真实候选 | 在隔离 Linux arm64／KVM／生产 adapter 中，从验收收据冻结的来源基线经正常用户入口执行候选包真实升级。记录构建判定的复用／替换范围；API／Coordinator／Owner 变化不能伪称复用。 |
| B03 Owner 并存 | 原 VM 仍由原 Owner／SDK home／assignment 持有，新 Owner home 不同；新 Coordinator 恢复所有路由。原 Owner 不被停止，新建 VM 分配新 Owner。 |
| B04 原资源连续 | 原 Guest kernel boot ID、计数进程 PID/birth、tmux 身份、终端书签／runtimeIdentity 不变；完整文件计数前缀连续，无重播 prompt、重建 VM 或替代计数进程。 |
| B05 真正就绪 | 核对持久 ready、confirmed、generation、真实角色状态及 availableWeb；完成后持续观察至少 120 秒，不仅检查 HTTP 200 或 confirmed 投影。原失败事件保留。 |
| B06 失败恢复 | 在 Owner prepare/adopt、API／Coordinator 切换及镜像导入处注入失败；原 VM 保持运行，恢复已确认路由／默认引用。新 Owner 已有任务时不得销毁它。恢复失败须显示真实 unknown／failed，不改数据库造成功。 |
| B07 数据与配置 | 使用隔离业务副本，核对旧任务镜像快照、工作区、凭据可用性及既有数据；不整卷恢复覆盖新写入。受管镜像配置随版本切换，自定义配置不丢失。 |
| B08 registry 慢／离线 | 对新固定 tag 的元数据请求注入延迟／失败；prepare 时原 writer 继续服务，本地材料不足则拒绝或延后。adopt 不触网，控制暂停不超过 2 秒，不得放宽预算或确认后才发现新默认镜像未登记。 |

成功流程与失败注入先在隔离环境完成。在线实验只进行管理员自选的正常升级，不在线上制造故障，也不操作用户原有资源的生命周期。首次真实 API／Coordinator／Owner 更新的结果不能由历史 Installer-only 记录代替。

## 前端和用户现场验收

| 场景 | 操作与必须断言 |
| --- | --- |
| F01 发现新版 | 本轮选定并验收的实例显示新版本入口与常驻浮层；关闭后当天不再自动弹出。仍显示来源基线版本，未主动刷新／升级／断开终端。 |
| F02 用户点击 | 已通过现有访问保护的操作人直接点击后单次受理升级，无升级专用口令／密钥／授权对话框，百分比来自同一真实 attempt；重复点击不重复执行；失败、未知和停滞显示真实状态。 |
| F03 刷新重连 | 完成后由用户主动刷新；原路由和终端选择保留，原书签在 5 秒内 confirmed attach；不新建会话，不重发任务输入，不把网络超时写成任务停止。 |
| F04 新旧沙箱 | 原沙箱继续原 CLI／任务。升级后新建沙箱，前端镜像默认与后端实际 ref／digest 一致，实际 --version 为本轮两个目标版本；显式选旧镜像仍可运行。 |

现场最小操作：升级前在一个专用沙箱保留每秒计数与原终端书签；包发布后由用户点击升级并主动刷新；核对原计数、身份和书签，再新建一个沙箱检查新版 CLI。CLI 已经是新版但原沙箱被停止，或沙箱连续但新建仍旧版，均判失败。

## 测量、证据和清理

从用户点击前开始连续采样同一 IP／公网入口的 API health、Web、Guest 计数与 WebSocket，记录时间、响应状态、延迟、超时和断连；保留失败样本，区分真实切换、连接延迟和未能确定的异常。原始 TTY 有 ANSI 重绘，不能把画面重复历史行判为业务计数回退；递增前缀由实际 Guest 文件验证，WS 另验证真实新增输出。

保存包与镜像收据、前后版本／digest、角色 container/PID/birth、Owner assignment／home、Guest live snapshots、ready/撤销事件、浏览器进度与请求计数、原 bookmark 两次 attach 耗时。签名私钥、口令、cookie、socketSessionKey 和凭据内容不进入报告／仓库。

只有全部实际成立才发布本次验证结论：发现新包不自动升级；用户触发真实角色更新；原沙箱／任务保持；原终端续接；新沙箱真正使用新 CLI。正式资格状态按实际平台矩阵分别记录。完成后只通过普通 API 清理本轮专用资源，核对其删除及服务 ready；用户原任务不参与清理。
