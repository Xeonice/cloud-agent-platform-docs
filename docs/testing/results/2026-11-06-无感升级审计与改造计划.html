03

共同根因：设计、验证与执行同时失守

CAUSE 01

首迁顺序与连续性目标冲突

旧入口和写者退出后，仍需进行导出、冷启动、完整树验证和控制交接。用户可见服务承担了整个关键路径的耗时与风险。

CAUSE 02

局部测试没有覆盖实际整条链路

模块与隔离启动分别通过，没有一起验证同一签名包、真实数据量、实际镜像依赖、公共收据、最终配置及切换后的业务行为。

CAUSE 03

多处手工派生扩大了错误面

路径、角色数量、身份、模块选择散落在多层适配件。单处修复未覆盖下游消费者。历史证据应保留，活动执行定义需要统一。

CAUSE 04

失败后缺少及时止损

修复眼前报错后继续生产尝试，回退自身也发生阻碍。线上实例承担了最终集成测试，恢复成功被当作继续尝试的起点。

执行责任：应在前几次暴露基础集成错误与真实入口中断时暂停生产尝试，先重新验证方案。增加超时、扩容和单项补丁只能局部缓解，不能补足错误的切换顺序。

04

目标：把服务按生命周期拆清楚

保留现有角色中可复用的能力，集中重构首迁、升级、恢复与对应状态展示。下图是拟议职责划分，尚未完成实现和完整验证。

业务包不替换底座；底座使用独立版本和维护流程。查询、执行与恢复的控制权不依赖待替换业务 API 存活。

旧新版本可在兼容窗口共存；候选先准备、再验证、再交接。只替换实际发生变化的组件。

运行层

原 RuntimeOwner原沙箱 / Guest / PTY新 Owner → 新分配

原任务与原会话保持归属；新镜像及 CLI 用于新沙箱。旧 Owner 的资源、环境和连接仍被引用时继续保留。

部分计划修改必须证明
公共入口常规升级不停止入口；binding 更新只切新请求，保留旧连接并按后端统计在途。候选失败仍由旧服务接请求；入口自身替换单独验证。
升级控制与恢复独立控制账本与持久计划；恢复不要求原失败执行器重新存活。固定动作支持原结果查询。执行器崩溃、ACK 丢失、租约过期后仍能核对实际结果，且不重复发命令。
API / Web候选提前启动并验证业务；保留旧 Web 资源、访问会话和兼容窗口。新旧 Web/API 四组组合均可用；失败回切不丢新版已接纳的数据。
Coordinator无副作用初始化前移；排空事务后进行单 writer 的 generation / fence 交接。无双写者、无重复调度；实测写暂停上界满足请求时限。
Owner / 沙箱维持 sandbox → 原 Owner 映射；新 Owner 只接新分配。原进程、任务轮次、终端身份与持续输出保持，升级不触发任务停止。
数据库保留同一业务文件；兼容扩展、分批回填、读切换，最后独立收缩。旧版能处理新写数据；恢复不使用旧快照覆盖当前业务数据。
前端沿用低打扰提示；展示真实阶段、失败及当前组合，确认完成才显示 100%。刷新只续接原任务；失败不误报完成，不强制刷新或重新创建任务。
CD / 发布链统一正式构建、演练、签名与发布；业务包、控制包和执行引擎一起绑定资格。演练与线上执行字节一致；CD 只发包，实例由用户决定升级时机。

准备、验证及切换观察期间保留健康服务组合。长期 WebSocket 可保持旧 API，或按明确协议重新附着原终端；不声称把 TCP 连接直接迁移给另一个进程。

首要可行性关口：旧入口不重启时，能否合法接入新控制面？

现网入口是 Mac :3000 → Linux :3181。旧入口没有新控制协议要求的全部路由、签名和 epoch 接口；旧 Supervisor 也不能仅靠“不再调用”证明退权。优先验证保留旧入口的兼容接入，但目前尚不能判定直接可用。

  • 用真实、合法的旧 binding / fence 协议验证新 HTTP 与旧 WebSocket 的分流。
  • 验证真实授权能够委托新控制面，保持访问会话和签名校验，不伪造升级记录。
  • 验证旧执行器全部变更入口及历史请求均不能重新取得执行权。

同端口监听权和既有连接的接管能力通过隔离验证，是确定首迁实施方案的前提。这里仍是待解决的设计难点。

数据库写权交接与失败恢复的具体边界
  1. 新版 Coordinator 先以 prepared 状态完成无副作用初始化，不启动写者和后台调度。
  2. 旧写者停止接新变更并排空在途事务；读请求尽量持续，必要写请求在原操作标识下有界等待。
  3. 在同一业务数据库的事务守卫中交接 generation / fence，确认旧异步回调无法继续写，再让新写者接管。
  4. 新写者 ready、路由和业务确认后才排空旧进程；写暂停时限必须实测，不能用增加超时替代连续性验收。
  5. 切流前失败保留旧服务；切流后先验证旧版兼容当前数据，再最小回切。新写者已经提交数据时，回退通过兼容写权交接完成，不能恢复过期数据库覆盖新写。

07

以用户连续性决定能否上线

以下为既有 UPG 要求及本轮必须补齐的交付门槛，属于目标，尚未由新方案证明通过。

1
业务请求连续

受控同构环境持续每秒 10 次合法读/幂等写请求；升级不引入请求失败，单次响应不超过 2 秒。

2
原任务持续运行

真实沙箱进程、Owner、Provider 实例、任务轮次及输出序号保持；停止、重启和重复执行均为零。

3
终端回到原会话

需要重连时 5 秒内自动附着原终端/运行身份；不新建任务、不重新执行初始指令，不重放断线输入。

4
写权唯一、数据不倒退

交接期旧异步写被 fence 阻挡，后台任务不重复；回切保留最新业务写入、游标、取消意图和幂等记录。

5
失败恢复真正执行过

覆盖启动失败、健康错误、资源不足、交接中断、ACK 丢失和执行器崩溃；每个结果未知分支均核对原动作。

6
演练与生产是同一套字节

业务包、控制包、执行引擎、真实配置和受测升级路径绑定；现场不另换私有 adapter 或未验收脚本。
