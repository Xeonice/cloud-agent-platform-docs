首要可行性关口：旧入口不重启时，能否合法接入新控制面？

现网入口是 Mac :3000 → Linux :3181。旧入口没有新控制协议要求的全部路由、签名和 epoch 接口；旧 Supervisor 也不能仅靠“不再调用”证明退权。优先验证保留旧入口的兼容接入，但目前尚不能判定直接可用。

  • 用真实、合法的旧 binding / fence 协议验证新 HTTP 与旧 WebSocket 的分流。
  • 验证真实授权能够委托新控制面，保持访问会话和签名校验，不伪造升级记录。
  • 验证旧执行器全部变更入口及历史请求均不能重新取得执行权。

数据库写权交接与失败恢复的具体边界
  1. 新版 Coordinator 先以 prepared 状态完成无副作用初始化，不启动写者和后台调度。
  2. 旧写者停止接新变更并排空在途事务；读请求尽量持续，必要写请求在原操作标识下有界等待。
  3. 在同一业务数据库的事务守卫中交接 generation / fence，确认旧异步回调无法继续写，再让新写者接管。
  4. 新写者 ready、路由和业务确认后才排空旧进程；写暂停时限必须实测，不能用增加超时替代连续性验收。
  5. 切流前失败保留旧服务；切流后先验证旧版兼容当前数据，再最小回切。新写者已经提交数据时，回退通过兼容写权交接完成，不能恢复过期数据库覆盖新写。
