第一次 admission barrier 预检因 credentials 散列变化拒绝切换，旧 API 未停止，barrier 撤销。只读逐字段比较确认其余 16 张业务表不变；新旧 scanner 可每 15 分钟刷新凭据，idle／drain 不统计 scanner。新副本一个刷新 tuple 比源库新 388 秒，因此停止旧 API 后没有盲目覆盖新凭据。真实主密钥解密验证后事务合并两条凭据：一条保留 clone 较新值、一条相等，并保留较晚 last_used_at；16 张其他 clone 表不变。

旧 v0.3.8 API 在持有 admission barrier 并确认 idle 后正常停止，原容器、原数据卷与迁移前数据库备份保留。新实例沿用原 3101 隧道入口，经 foundation TCP bridge 到 StableEntry 3181。主页面 `https://agent.douglasdong.com` 现在 307 跳转到 `https://agent-api.douglasdong.com`，路径和查询参数保留。

## B 实验发现的问题与 C 修复

B 由真实页面单次点击接受，attempt `475fddcf-dc71-4abd-816f-abe93445e1c5`。`21:31:11.832Z` 确认 generation=2 后，`21:31:13.120Z` 发生 `CONTROL_OR_OWNERSHIP_UNKNOWN`，数据库 `ready` 撤销为 0。虽然 HTTP、沙箱与终端正常，且升级状态仍显示 confirmed，**B 未通过持续就绪验收**。原始失败事件和早期报告保留，另附纠正说明。

原因是 Installer 的后续监测硬编码 observe(weight=100)，实际 API 复用时绑定为 weight=0／candidateApi=null，严格的路由校验正确拒绝了不匹配输入。C 改为读取真实绑定并验证目标 API 摘要；只有 API 复用才允许 weight=0，API 真替换仍要求 100。没有修改 ready 字段、伪造 candidate、删除失败事件或降低门禁。真实新旧分支与故障回归通过。

C 签名使用新的本轮临时 key，实验信任根同时保留 B 公钥、增加 C 公钥，purpose／channel／实例范围与两条 HTTPS 分发来源不变。私有 installation proof 只更新实际 trustRootDigest；信任文件、proof 和目录均原 inode 写入并 fsync，现有角色只读挂载即时看到更新。正常生产签名信任根未修改，RPC／鉴权 key 未轮换，业务角色未重启。
