### 2.2 v0.3.4：发现作业只跟固定分支

上线顺序：合并前停用 release（发现作业 #877–#879 因 409 变红，属预期）→ 合并 PR #62 → 用合并后的 `main` 构建并替换三个 agent（第一次构建失败，换新输出目录重试成功）→ 同步模板并 refresh → 发布。发布前两次失败：release #43 因 API #52 拉取基础镜像报 `tls: bad record MAC`；release #44 在 API #53 已替换生产 API 之后，于 Vercel 阶段报 `git failed (128)`。第三次 release #45 成功；两次失败都是宿主代理造成的网络抖动，期间出现过数分钟“新 API + 旧前端”的窗口。

**回退到原发现规则**（只在新规则出现严重问题时使用，至今未执行）

- **适用场景**：需要撤销 v0.3.4 的发现规则。
- **影响**：旧规则会自动构建全部 open PR（含 fork），并按旧校验器检查所有分支名。
- **前置条件**：Mac、干净 `main` 克隆的仓库根目录、Node 22；先停用 `agent-platform-ci-discovery` 与 `agent-platform-release`，并关闭 fork PR（改由同仓分支重开）。
- **步骤**：
  1. 优先只撤销“PR 只认同仓”的过滤，保留“只跟 `main`”的过滤。
  2. 若要整体回退到旧版，先删除或改名三仓中不满足旧校验器 `validRef` 的分支；用下面的命令检查，输出为空才能换回。
  3. 换回后首轮会构建状态中没有记录或已变化的 API 分支与 PR；等这些构建结束后再启用 release。

```sh
# Mac，干净 main 克隆的仓库根目录，Node 22（$NODE22 见参考表 §0）
for repo in cloud-agent-platform-docs agent-platform-api agent-platform-web; do
  git ls-remote --heads "https://github.com/Xeonice/$repo.git" |
    "$NODE22" --input-type=module -e 'import { readFileSync } from "node:fs"; import { validRef } from "./deploy/jenkins/jenkins-ci.mjs"; for (const line of readFileSync(0, "utf8").split("\n")) { const ref = line.split("\t")[1]; if (ref && !validRef(ref)) console.log(process.argv[1], ref); }' "$repo"
done
```

- **验证**：发现作业恢复 `SUCCESS`，三仓的必需状态继续回写。
- **回退**：重新部署 v0.3.4 及以后的发现工具（升级 agent）。不要删除 `discovery-state.json` 的 `initializedAt` 来跳过补跑，否则期间新推的镜像标签只会被记录、不会发布。
