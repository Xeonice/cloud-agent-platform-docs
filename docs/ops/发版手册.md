# 发版手册

- **读者**：发版人（维护者）；合并 PR 的开发者和 AI agent 至少读 §1、§2、§7。
- **用途与边界**：从合并到上线的全部受控操作。不含 VM、磁盘与凭据维护（见 [运维手册](./运维手册.md)），不含备份恢复与重建（见 [灾备与重建](./灾备与重建.md)），不解释架构（见 [生产架构](./生产架构.md)）。
- **权威范围**：合并即发布、改动生效对照表、跨仓发版、agent 升级、发布卡住处置、含迁移的发版规则、回滚、沙箱镜像发版、版本号与 CHANGELOG 规则。
- **适用基线**：v0.3.6（主仓 `7eb7176`）起；`manage.mjs` 的 `quiet-down`、`cancel-quiet-down`、`queue`、`wait-idle`、`deploy/ops/upgrade-agents.mjs` 与宿主布局模块 `deploy/containers/host-layout.mjs` 随本文同批入库。

## 0. 操作前提

- 本文的写操作只由维护者执行（权限约定见 [CONTRIBUTING](../../CONTRIBUTING.md)）。在 Mac 上以运维账号执行（拥有私有目录与 Colima socket 的普通账号，由宿主布局推导，见参考表 §12），不用 sudo；接入方式见[运维手册](./运维手册.md) §0。
- 命令里的 `$NODE22`、`dk <jenkins|build|runtime>` 与 `jstatus` 按 [参考表](./参考表.md) §0 定义。`manage.mjs` 各子命令的作用与恢复方式也列在参考表 §0，它读取[私有目录](./README.md#术语表)里的 `admin-api.json`。
- `sync-pipelines`、`refresh` 与升级脚本只在[干净 main 克隆](./README.md#术语表) `$SRC` 里执行，它们会把克隆里的模板和工具写进生产。`main` 每前进一次（包括刚合并的 PR），都要重新执行下面的命令，得到新的 `$SHA` 与 `$SRC`。
- `$SRC` 只用来执行，不在里面改文件或提交；开发和更新子模块指针在[工作克隆](./README.md#术语表)里做。后文的 `$SRC`、`$SHA`、`$P` 都指这里。

```sh
# Mac，任意目录：为当前主仓 main 准备干净克隆
P="$HOME/.local/share/agent-platform-jenkins-tools"; install -d -m 700 "$P"
SHA=$(git ls-remote https://github.com/Xeonice/cloud-agent-platform-docs.git refs/heads/main | cut -f1)
SRC="$P/upgrade-src-${SHA:0:7}"
test -d "$SRC" || git clone https://github.com/Xeonice/cloud-agent-platform-docs.git "$SRC"
cd "$SRC" && git status --short && git rev-parse HEAD    # 不应有改动；HEAD 应等于 $SHA
```

## 1. 发布怎么触发

[发现作业](./README.md#术语表)每 2 分钟读一次三仓 `main`。三仓组合与上次成功发布的不同，就排一次[统一发布](./README.md#术语表) `agent-platform-release`，不需要任何人工操作。发布单位是三仓 `main` 的 head，主仓的子模块指针（[gitlink](./README.md#术语表)）不参与，也不被校验。

| 阶段 | 节点 | 产出 | 失败或等待时（作业描述或报错） |
|---|---|---|---|
| 计划与钉住 | linux-deploy | 三仓 SHA、预留版本号 | `Discovery request was superseded…`：组合已变，下一轮按新组合重排 |
| 前端 CI 与跨仓验收 | linux-web-amd64、linux-ci | Web prebuilt 包；contract 结果 | `Frontend CI …; nothing is uploaded` 或 `Complete project acceptance …` |
| API CI、构建与替换 | linux-ci、linux-deploy | API 镜像与包、数据备份、新 API 容器 | UNSTABLE：`waiting for safe API publication`；FAILURE：`API publication FAILURE…` |
| Vercel 上传与提升 | linux-deploy | production 部署 | FAILURE，此时 API 已经替换（§6） |
| 打包与 GitHub Release | linux-deploy | 7 个资产（5 个 tgz、`release-manifest.json`、`SHA256SUMS`）；Release 设为 Latest | FAILURE |

- 任何 FAILURE 或 UNSTABLE，发现作业下一轮都会重排，没有退避；同一组合已通过的前端与验收结果会复用。
- 整次发布通常 6–13 分钟；替换 API 时生产中断约 1.5 分钟。各作业耗时与保留期见参考表 §1。
- 只合 Web 不替换 API（API 判定为 `current`）。合 API 或主仓（包括纯文档）一定替换 API：新的 `ROOT_SHA` 会构建出新镜像，替换前要等[生产空闲](./README.md#术语表)（§7.1）。

| `deploy/jenkins/*.groovy`、`bootstrap.groovy` | §5 同步模板 |
| `deploy/jenkins/*.mjs`（测试与只在 Mac 上运行的 `manage.mjs`、`setup-github-app.mjs`、`import-ghcr-token.mjs` 除外）；`deploy/containers/` 下的 `api-container.mjs`、`api-context.mjs`、`deploy-agent-entrypoint.mjs`、`prepare-context.mjs`、`prepare-deploy-context.mjs`、`deploy.Dockerfile`、`ci.Dockerfile`、`ci-tools/` | §4 升级 agent（脚本一次升级三个） |

| controller 相关：`controller.Dockerfile`、`plugins.mjs`、`controller-entrypoint.sh`、`init.groovy.d/`、`plugins.lock.json` | 维护者按下方「重建 controller」处理 |

| 只在 Mac 上运行的工具：上面除外的三个、`host-layout.mjs`、`*-smoke.mjs`、`verify-controller.mjs`、`controller.mjs`、`deploy/ops/` | 无额外动作，下次在 Mac 上运行时生效 |

```sh
# Mac，$SRC：线上 agent 是否落后于 main 的部署工具
deployed=$(dk runtime inspect --format '{{index .Config.Labels "com.agent-platform.root-sha"}}' agent-platform-linux-deploy)
git fetch -q origin main && git diff --name-only "$deployed" origin/main -- deploy/jenkins deploy/containers
```

判读：有上表要求升级 agent 的文件，就做 §4；只有 `.groovy` 时做 §5。只有 `*.md`、`*.test.mjs`、`deploy/containers/env/` 模板、CONTAINER_INPUTS 所列文件或上表“只在 Mac 上运行”的工具时，不用动。

**宿主布局（host-layout）改动的上线**：分两个阶段，一次性计划与进度见[运维记录](./运维记录.md) §2.5。

- 阶段 1，只在 Mac 上运行的工具：`host-layout.mjs`、升级脚本、`manage.mjs`、`bootstrap-host.mjs`、`controller.mjs`、`verify-controller.mjs`、`ci-smoke.mjs`、`setup-github-app.mjs`、`import-ghcr-token.mjs`。不用升级 agent，也不用重装 LaunchDaemon（按上表用 `doctor --stage launchd` 确认渲染结果不变），下次运行即生效；下次 apply-system 之前重新 `prepare`，审阅包升到 schema 2。
- 阶段 2，镜像内的模块：`deployment-platform.mjs`、`ci-platform.mjs`、`jenkins-web.mjs`、`project-release.mjs`、`jenkins-ci.mjs`、`project-ci.mjs`、`github-status-app.mjs`、`ci-agent-entrypoint.mjs`（删除原生 Mac 分支与 UID 501）。按 §4 用新脚本升级三个 agent。build 之前先用下面的命令只读核对三份 agent 连接密钥，期望三行都是 `1000:1000 600`：入口脚本不再接受属主 501，属主不对的 agent 升级后会反复重启。
- 建议先合阶段 1，用新脚本做一次低风险的 §4 升级（这时 deploy 镜像里只有三个 Mac 专用 CLI 的字节变化），确认无误再合阶段 2。两个阶段同批合并时，合并后的那次 §4 升级就是新脚本第一次在生产上 apply：合并前先按运维记录 §2.5 做同 SHA 对照；新脚本本身出问题时按 §4 的“回退工件”处理。

```sh
# Mac，任意目录：三份 agent 连接密钥的属主与权限，期望三行 1000:1000 600
dk build exec agent-platform-linux-ci-agent-1 stat -c '%u:%g %a' /run/secrets/jenkins_agent_secret
dk build exec agent-platform-linux-ci-web-1 stat -c '%u:%g %a' /run/secrets/jenkins_agent_secret
dk runtime exec agent-platform-linux-deploy stat -c '%u:%g %a' /run/secrets/jenkins_agent_secret
```

重建 controller（维护者，尚未演练，见[运维记录](./运维记录.md) §3 的 T29）：先删掉旧的 lab 容器与 `agent-platform-jenkins-lab-home` 卷（lab 模式要求空 Home），用 `prepare-context.mjs controller` 生成构建上下文，以 lab 项目（`compose.lab.json`）在 `127.0.0.1:18080` 构建并启动，再运行 `"$NODE22" deploy/containers/verify-controller.mjs` 验证。通过后停用 release 与 discovery 并等空闲，把新镜像 ID 写进 `container-stack.env` 的 `CONTROLLER_IMAGE`，对 `controller` 单独 up，核对三个节点重新在线。回退：改回旧镜像 ID 再 up。

## 3. 常规发版与跨仓发版

单仓、单个 PR：合并即可，发现作业会自动发布。合并前确认生产能在接下来十几分钟内进入空闲（§7.1）。

跨仓改动，或把几个主仓 PR 合成一次 API 替换：

- **适用场景**：一个改动涉及 api、web、主仓中的两个以上，或要攒批合并多个主仓 PR。
- **影响**：停用期间不发布；最后一次发布替换 API，约中断 1.5 分钟。停用期间发现作业每轮因 `Discovery HTTP 409` 变红，PR 的 CI 照常运行，均属预期。
- **前置条件**：各 PR 的 `jenkins/*` 检查为绿；在 Mac 的 `$SRC` 执行 `manage.mjs`；要升级 agent 时预留 §4 的时间。

```sh
# Mac，$SRC（合并前按 §0 准备的即可），Node 22
"$NODE22" deploy/jenkins/manage.mjs disable agent-platform-release   # 1 只停发布
# 2 按 CONTRIBUTING 的跨仓合并顺序合并 api、web，再在工作克隆里更新两个指针并合并主仓 PR
# 3 合并后重新执行 §0，得到新的 $SHA 与 $SRC；§2 要求升级 agent 时用它做 §4（它的 refresh 会顺带重新启用 release）
"$NODE22" deploy/jenkins/manage.mjs enable agent-platform-release    # 4 放行，下一轮自动发布
```

- web PR 的检查是对当时的 API `main` 跑的；发布会对最终组合重跑前端 CI 与跨仓验收，不会跳过。想提前看结果，给 PR 推一个空提交。
- **验证**：§6 的清单。
- **回退**：发现问题时保持 release 停用，按 §9 处理。

## 4. 升级 Jenkins agent

- **适用场景**：§2 要求升级 agent，或 §2 的核对命令显示 agent 落后于 main。脚本一次升级两个 [CI agent](./README.md#术语表) 与[可信 deploy agent](./README.md#术语表)。
- **影响**：窗口内不跑任何构建；生产 API、[Tunnel](./README.md#术语表)、DNS、controller 不受影响（脚本会核对它们没有变化）。
- **前置条件**：改动已合入 main，release 在合并前已停用；`$SRC`、`$SHA` 按 §0 为合并后的 main 新准备，`origin` 为主仓地址（https 或 ssh）；在 `$SRC` 运行宿主自检 `doctor --stage full`，结果为 `doctor-passed`（判读见参考表 §12.5）。
- **同一宿主、同一份脚本**：脚本的宿主值由 `host-layout.mjs` 按运行账号推导，不写死账号与路径。build 与 apply 必须用同一个运维账号、同一个 `$NODE22`、同一份 `host-layout.json`，并且都在 `$SRC` 里运行仓库的 `deploy/ops/upgrade-agents.mjs`。`plan.json`（schemaVersion 2）记录了宿主布局、两份 env 的路径、docker CLI 与插件的真实路径和哈希，以及脚本与 `host-layout.mjs` 的哈希；任一项变化，apply 都在改动线上之前拒绝。例如 OrbStack 在 build 与 apply 之间自动更新过，就用新的 `OUT` 重新 build。
- **回退工件**：`$HOME/agent-platform/ops/upgrade/` 下的旧版脚本 `agent-platform-upgrade-three-agents.mjs`（sha256 `b0b23f0a…`，旁边有 `SHA256SUMS`）在新脚本于生产上验证通过之前保留，不得删除（何时可删见运维记录 §2.5）。两版的 plan 互不通用：schemaVersion 2 的 plan 只能用新脚本 apply；旧脚本 build 出的 plan（schemaVersion 1）只能用同一份旧脚本 apply。旧脚本写死了原来这台 Mac 的账号与路径，只能在这台 Mac 上用。
- **步骤**：每步核对注释里的期望输出；不符或退出码非 0 就停在这一步，按“回退”处理。apply 没有成功时禁止执行第 4、5 步：`refresh` 会重新启用全部作业，release 会在旧 agent 上恢复；是否退出维护按“回退”决定。

```sh
# Mac，$SRC，Node 22。0 期望输出 SRC is main；没有输出就回 §0 重新准备。宿主自检期望 "state":"doctor-passed"
test "$(git -C "$SRC" rev-parse HEAD)" = "$(git ls-remote https://github.com/Xeonice/cloud-agent-platform-docs.git refs/heads/main | cut -f1)" && echo "SRC is main"
"$NODE22" deploy/containers/host-layout.mjs doctor --stage full | jq -c '{state, counts}'
OUT="$P/upgrade-out-${SHA:0:7}"   # 必须是尚不存在的新目录；build 与 apply 必须用同一份脚本（apply 会核对其 sha256）
"$NODE22" deploy/ops/upgrade-agents.mjs build "$SRC" "$SHA" "$OUT"   # 1 期望 "state":"built-not-applied" 与 "pinned":true
# 2 按运维手册 §0 进入维护，期望最后输出 "quietingDown":true
"$NODE22" deploy/ops/upgrade-agents.mjs apply "$OUT/plan.json"   # 3 期望 "state":"three-agents-upgraded-jenkins-still-quiesced"
"$NODE22" deploy/jenkins/manage.mjs sync-pipelines   # 4 期望 Reviewed managed pipeline templates synchronized
"$NODE22" deploy/jenkins/manage.mjs refresh          # 5 期望 Agent Platform Jenkins configuration loaded…；会重新启用全部作业
# 6 按运维手册 §0 退出维护
```

- **验证**：`jstatus` 三个节点在线、`quietingDown` 为 false；下面两条命令输出的三个 `root-sha` 都等于 `$SHA`。之后发现作业照常排发布。

```sh
# Mac，任意目录
dk build inspect --format '{{.Name}} {{index .Config.Labels "com.agent-platform.root-sha"}}' agent-platform-linux-ci-agent-1 agent-platform-linux-ci-web-1
dk runtime inspect --format '{{.Name}} {{index .Config.Labels "com.agent-platform.root-sha"}}' agent-platform-linux-deploy
```

- `"pinned":false` 表示 build 用的脚本不是 `$SRC` 里的那份（或与 `git show $SHA:…` 不一致），这份 plan 不能 apply；回到 `$SRC` 重新 build。
- `prepare-context.mjs` 与 `prepare-deploy-context.mjs` 只生成构建上下文，不构建镜像、不改 env、不重建容器；升级一律用升级脚本。
- **回退与失败边界**：脚本失败时输出 `stopped-for-operator-review`、`stage`、原因码 `code` 与脱敏后的 `reason`（文件类拒绝另带 `path`，宿主检查另带 `check`），`$OUT/apply-checkpoint.json` 记录同样的内容；按[参考表](./参考表.md) §10 的阶段表处置，`HL_*` 原因码见参考表 §12.6。
  - 第 1 步 build 失败：线上未受影响，也还没进入维护。排除原因后用新的 `OUT`（如末尾加 `-r2`）重跑；`main` 已前进就回 §0。
  - `quiet-down` 拒绝执行：按提示补齐后再试；放弃本次升级就按运维手册 §0 退出维护。
  - apply 停在 `not-started`、`host-layout`、`apply-preflight` 或 `transfer-deploy`：线上 agent 未改动。排除原因后可用同一 `plan.json` 重跑；`main` 前进、env 变化，或 build 之后换了账号、Node、`host-layout.json`、docker CLI 时，从第 1 步重来。放弃就退出维护。
  - apply 停在之后的阶段：env 可能已部分改写、agent 可能已部分重建。不要重跑，保持维护状态，交维护者对照 `$OUT/env-backup/` 与现有容器处理；要回到旧 agent 时执行下面第二段命令（旧镜像仍在本机）。
  - 新脚本本身出问题（而不是线上状态或输入问题）时：用回退工件重做本节，build 与 apply 用同一份旧脚本（下面第三段命令）。
  - `$OUT`（尤其 `env-backup/`）含私有内容，禁止上传、归档到构建产物或公开。

```sh
# Mac，$SRC：stage 为 source-check 时的自查，四项都应满足
git -C "$SRC" status --porcelain --untracked-files=all       # 无输出
git -C "$SRC" rev-parse HEAD; git -C "$SRC" ls-remote origin refs/heads/main   # 两个 SHA 都等于 $SHA
git -C "$SRC" remote get-url origin                          # 主仓的 https 或 ssh 地址
ls -l "$P/container-stack.env" "$P/container-runtime.env"    # 本人所有、-rw-------、链接数 1
```

```sh
# Mac，$SRC：维护者回退到 env-backup 记录的旧镜像
cp -p "$OUT/env-backup/container-stack.env" "$OUT/env-backup/container-runtime.env" "$P/"
dk build compose --project-name agent-platform-linux-ci --env-file "$P/container-stack.env" --file deploy/containers/compose.ci.json up --detach --no-deps --force-recreate --pull never agent web
dk runtime compose --project-name agent-platform-runtime --env-file "$P/container-runtime.env" --file deploy/containers/compose.runtime.json up --detach --no-deps --force-recreate --pull never deploy
```

```sh
# Mac，$SRC，Node 22：新脚本本身有问题时，用回退工件重做升级。先核对副本未被改动（期望两行 OK），OUT 用新的目录
OLD="$HOME/agent-platform/ops/upgrade"
(cd "$OLD" && shasum -a 256 -c SHA256SUMS)
"$NODE22" "$OLD/agent-platform-upgrade-three-agents.mjs" build "$SRC" "$SHA" "$OUT-old"     # 期望 "state":"built-not-applied"
# 按运维手册 §0 进入维护后执行；成功后同样做上面的第 4–6 步
"$NODE22" "$OLD/agent-platform-upgrade-three-agents.mjs" apply "$OUT-old/plan.json"
```

## 5. 只改 Jenkins 模板

- **适用场景**：只改了 `deploy/jenkins/*.groovy` 或 `bootstrap.groovy`。改了 `.mjs` 走 §4，§4 已包含本节。
- **影响**：正在运行的构建不受影响；`refresh` 会重新启用全部作业，之前停用的要重新停用。
- **前置条件**：PR 合并前已在工作克隆里用 `pipeline-lint` 校验改动的模板；合并后在新的 `$SRC` 执行。

```sh

"$NODE22" deploy/jenkins/manage.mjs pipeline-lint deploy/jenkins/web.groovy   # 换成改动的文件
"$NODE22" deploy/jenkins/manage.mjs sync-pipelines
"$NODE22" deploy/jenkins/manage.mjs refresh
```

- **验证**：`pipeline-lint` 输出 `Jenkinsfile successfully validated.`；`jstatus` 里作业都不是 `disabled`；该作业下一次实际运行成功。改 `web.groovy` 后至少确认一次：contract 子作业失败时 Web 作业整体不成功，成功时归档 `web-cross-repository/contract.json`。
- **回退**：revert 模板并合并，在新的 `$SRC` 重做本节。

## 7. 发布卡住

先判断要不要止损：同一组合失败后每轮都会重试，没有退避。下列情况先执行 `"$NODE22" deploy/jenkins/manage.mjs disable agent-platform-release` 再排查：API 被自动回滚（`rolled-back`，每轮重试都会再停机一次，见 §9）、同一错误连续 3 轮、`waiting-migration-review`、部署锁。`manage.mjs` 被拒（如 `HL_JENKINS_LISTENER`）或运行不了时，在 Jenkins 页面停用该作业。错误原文速查见参考表 §10。

### 7.1 `waiting-idle`

- **现象**：`agent-platform-api` 描述为 `<sha> · waiting-idle`，release 为 UNSTABLE、描述 `vX · waiting for safe API publication`。生产没被替换；约每 4 分钟重试一轮，每轮重跑一次 native-ci。
- **看阻塞项**：API 作业该次构建的 `Service status and logs` 页面里的 `deployment` 段，或运维手册 §9 的只读诊断。字段口径见 [10 §6.6.2](../shared/10-接口契约与类型共享.md)。

| 不为 0 的项 | 处置 |
|---|---|
| `sandboxes`、`agentTasks`、`automationRuns` | 等任务结束，或在 Web 上停止任务（停止会保留磁盘与名额） |
| `enabledAutomations` | 在 Web 的自动化页面暂停已启用的规则，发布后恢复；启用但未触发的也会阻塞 |
| `cloningProjects`、`projectCleanupJobs`、`credentialAuth`、`inFlightHTTP` | 等它们自然结束 |
| 只剩 `resourceAllocations` | 做[停止名额](./README.md#术语表)核验：运维手册 §9 的探针 |
| 阻塞项全为 0，但 `ready` 为 false | 看 `readiness` 哪一项为 false，按运维手册 §9 查 API 日志或镜像管理页 |

- `activeWS`（浏览器连接）不阻塞发布。处理完不需要别的操作，下一轮自动继续；停止任务或暂停自动化之前先通知用户。
- Web 上的操作要用生产访问口令：向维护者索取，维护者的取用方法见运维手册 §9（不回显）。
- 建议：同一阻塞项 1 小时没有变化，就按上表处置；处置不了就止损（§7 开头），等低峰再放行。
- 探针报 `Stopped reservation proof unavailable` 时，最常见的原因是 [auth helper](./README.md#术语表) 已失效：按运维手册 §9 确认后，在 Web 上发起一次帐号登录并立即取消，触发重建，再等下一轮。
- API 作业只保留最近 10 次构建的产物；需要留证的构建，先在构建页面设为永久保留（Keep this build forever）。

### 7.2 部署锁与 `operator-recovery-required`

- **现象**：API 作业失败，报 `Deployment lock exists; review the checkpoint before operator recovery`，或 `…retained for operator recovery`。锁不解除，之后每次构建与部署都失败。
- **含义**：上次部署被中断（作业被取消、VM 重启），或工具遇到无法自动确认的状态，把锁、[checkpoint](./README.md#术语表) 和[维护屏障](./README.md#术语表)留给人工。
- **前置条件**：release 已停用；`agent-platform-api` 没有运行中的构建（`status`）。以下是约定流程，尚无专用工具（运维记录 T27），流程本身待维护者确认；判断不了就停下交维护者。

| checkpoint 的 `state` | 生产现状 | 处置 |
|---|---|---|
| 没有 `checkpoint.json` | 锁来自被中断的构建或部署，API 未动 | owner 进程已不在、API 健康且没有屏障时，归档锁 |
| `draining` | 旧 API 仍在运行，但屏障挡住了新任务 | owner 进程已不在时，用 checkpoint 里的 `barrier` 释放屏障，再归档锁 |
| `stopping`、`backed-up`、`initial-adopting`、`operator-recovery-required` | 旧容器可能已停或已删，新容器状态未知 | 不要自行处理；交维护者对照 `reason`、备份与容器身份恢复 |

```sh
# Mac，$SRC，Node 22。1 只读查看锁、checkpoint、owner 进程、生产容器与屏障（ls 报 No such file 即没有屏障）
dk runtime exec agent-platform-linux-deploy sh -c 'cd /srv/agent-platform/deploy/deployment.lock && ls -l && cat checkpoint.json'
dk runtime exec agent-platform-linux-deploy node -e 'const { pid } = require("/srv/agent-platform/deploy/deployment.lock/owner.json"); console.log("owner", pid, require("fs").existsSync("/proc/" + pid) ? "alive" : "gone")'
dk runtime ps -a --filter label=com.agent-platform.role=production-api
dk runtime exec agent-platform-api ls -l /data/deployment-drain
# 2 只在 draining 时：释放屏障
script=$("$NODE22" --input-type=module -e 'import { BARRIER_SCRIPT as s } from "./deploy/containers/api-container.mjs"; process.stdout.write(s)')
dk runtime exec agent-platform-api node -e "$script" release '<checkpoint.json 里 barrier 字段的 JSON 原文>'
# 3 归档：沿用 operator-recovery-history/<原因>-api-<构建号>-<日期>/ 的既有格式，把锁目录整个移进去，再写复核记录
reason=""; build=""; cp_state="none"   # 前两项必填：原因（如 cancelled-build-lock）与留下锁的 API 构建号；cp_state 填 checkpoint 的 state
dir="operator-recovery-history/$reason-api-$build-$(date -u +%Y%m%d)"
[ -n "$reason" ] && [ -n "$build" ] && dk runtime exec agent-platform-linux-deploy sh -c "set -eu; cd /srv/agent-platform/deploy; mkdir -p -m 700 operator-recovery-history; mkdir -m 700 '$dir'; mv deployment.lock '$dir/'"
printf '{"state":"reviewed-lock-archived","apiBuild":%s,"checkpointState":"%s","ownerProcessAbsent":true,"productionUntouched":true,"capturedAt":"%s"}\n' "$build" "$cp_state" "$(date -u +%FT%TZ)" | dk runtime exec -i agent-platform-linux-deploy sh -c "umask 077; cat > '/srv/agent-platform/deploy/$dir/recovery-review.json'"
```

- **验证**：`deployment.lock` 已不存在，`$dir` 下有锁目录与 `recovery-review.json`；部署状态的 `draining` 为 false（运维手册 §9）。在运维记录登记这次恢复，再启用 release。
- **回退**：屏障身份与 checkpoint 不符时，释放脚本报 `Maintenance ownership changed` 并且不做任何改动，此时交维护者。

### 7.3 其他常见卡点

| 现象（原文） | 含义 | 处置 |
|---|---|---|
| API 描述为 `waiting-migration-review` | 新旧版本的数据库迁移指纹不同，永远不会自行通过 | 止损，按 §8 处理 |
| API 描述为 `waiting-initial-adoption` | runtime VM 上没有生产 API 容器（新机器，或容器被删） | 发布不会自动创建 API，按灾备与重建 §3 接管 |
| `Pinned root image input missing`，或 Docker 构建在 `COPY` 处找不到文件 | deploy agent 里的 CONTAINER_INPUTS 清单与钉住的主仓不一致 | 止损，按 §4 升级 agent 再放行。要移除清单里的文件时 fix-forward：先改清单并升级 agent，不要直接 revert 引入它的提交 |
| `Discovery request was superseded…`、`Pinned project commit is no longer the production branch head`，或 API 描述为 `superseded` | 发布期间 `main` 又前进了 | 无需处理，下一轮按新组合重排；频繁出现就按 §3 攒批 |
| `tls: bad record MAC`、`EOF`、`git failed (128)`、`Source discovery failed`、拉镜像失败 | 宿主网络经代理，访问 Docker Hub 与 GitHub 偶发失败 | 等下一轮重试；同一错误连续 3 轮以上就止损，用 `git ls-remote` 逐个访问三仓查网络 |

## 8. 含数据库迁移的发版

- **放行方式**：不同 schema 指纹默认仍返回 `waiting-migration-review`。维护者审阅迁移后，用 `review-migration` 为指定的 API 构建生成私有许可；不删除生产容器，不改镜像标签或指纹，不使用灾备 `adopt` 入口。
- **合并前**：安排维护窗口并停用 release（§3），审阅线上与目标 API 的 `drizzle/` 差异。改了发布工具时，合并主仓后按 §4 升级 agent；其 `refresh` 会重新启用所有作业。含迁移时，在 `quietDown` 仍生效期间再次停用 release，然后才解除 `quietDown`、恢复发现作业，避免自动发布抢先运行。PR 检查仍照常运行。
- **许可范围**：精确绑定 CI 构建号、旧容器 ID、新旧 imageId、API/root commit 与 schema 指纹。目标镜像使用 SQLite backup API 将运行时数据库（含已提交 WAL）一致性复制到容器临时盘；已有 `__drizzle_migrations` 的 SQL 哈希和时间戳必须与候选 journal 的有序前缀一致，只能追加迁移。仅在副本执行实际应用迁移，校验 quick_check、外键和既有表行数。生产数据卷只读；历史 SQL/迁移时间戳改写、改名、删表或改变既有表行数的迁移会被拒绝，需要另外设计迁移方案。
- **部署保障**：放行后保留原有空闲检查、维护屏障、精确容器身份、停库完整备份、健康检查和回滚。仅在原容器确已停止、完整备份验证通过后，最终预演复制封存主库到临时盘：复制前后必须没有 WAL/SHM（含不安全链接），主库身份和大小、mtime、ctime 必须保持一致。迁移只写临时副本；预演前后再核对原容器仍停止且维护屏障仍归工具所有，才允许替换。运行中的审阅仍用 SQLite backup API，不允许主库复制兜底。
- **重试**：`waiting-idle` 或 `superseded` 不消耗许可；首次实际 stop 尝试前标为 `consumed`。失败、回滚、变更 main、换构建号或换容器后必须重新审阅，不能复用。许可不会让统一发布跳过跨仓验收。

```sh
# Mac，api 仓的克隆：线上 API 与 main 之间是否有迁移改动，有输出即含迁移
live=$(dk runtime inspect --format '{{index .Config.Labels "com.agent-platform.api-sha"}}' agent-platform-api)
git fetch -q origin main && git diff --stat "$live" origin/main -- drizzle/
```

```sh
# Mac，干净 $SRC，Node 22；release 保持停用。先单独构建当前 main 的 API，等构建结束并取得准确构建号 N
API_SHA=$(git ls-remote https://github.com/Xeonice/agent-platform-api.git refs/heads/main | cut -f1)
printf '{"SHA":"%s","ROOT_SHA":"%s"}' "$API_SHA" "$SHA" > "$TMPDIR/api.json"
"$NODE22" deploy/jenkins/manage.mjs build agent-platform-api "$TMPDIR/api.json"
"$NODE22" deploy/jenkins/manage.mjs wait-idle --timeout 3600
N=$("$NODE22" deploy/jenkins/manage.mjs status | jq '.controller.jobs[] | select(.name == "agent-platform-api") | .lastBuild.number')
"$NODE22" deploy/jenkins/manage.mjs build-status agent-platform-api "$N" | jq '{result, description}'   # UNSTABLE，waiting-migration-review
OLD_SCHEMA=$(dk runtime inspect --format '{{index .Config.Labels "com.agent-platform.schema-fingerprint"}}' agent-platform-api)
NEW_SCHEMA=$(dk runtime exec agent-platform-linux-deploy cat "/srv/agent-platform/deploy/releases/$SHA-$API_SHA/release.json" | jq -r .schemaFingerprint)
# 对照已审阅的迁移差异和两个指纹，再生成许可；输出 state=reviewed
dk runtime exec agent-platform-linux-deploy node /opt/agent-platform/tools/api-container.mjs review-migration "$API_SHA" "$N" "$OLD_SCHEMA" "$NEW_SCHEMA"
# 必须部署同一个 CI receipt；waiting-idle 时保留许可，等空闲后重试同一命令
dk runtime exec agent-platform-linux-deploy node /opt/agent-platform/tools/api-container.mjs deploy "$API_SHA" "$N"
# state=deployed 后按 §6 验证，再放行统一发布；它会重跑 Web/跨仓验收，API 判为 current
"$NODE22" deploy/jenkins/manage.mjs enable agent-platform-release
```

- **失败处置**：副本预检失败不生成许可、不停生产。`rolled-back` 后保持 release 停用，查原因并重新审阅；`operator-recovery-required` 保留屏障和检查点，按 §7.2 处理。迁移尚未实际部署时，revert 迁移可使指纹回到线上一致；已上线后只能 fix-forward。

## 9. 回滚

- **适用场景**：新版本上线后有问题；或部署结果为 `rolled-back`。`reason` 为 `Post-stop preparation failed; unchanged original release restarted` 表示新容器尚未启动，停库预备失败后重启了原容器，原数据未被替换；`Replacement publication failed; verified backup and original release restored` 表示替换失败，工具恢复了完整备份与旧镜像。含 schema 改动时不能仅切换旧代码。
- **怎么认出 `rolled-back`**：API 作业记为 FAILURE，描述停在 `<sha> · Linux image packaged`；结果写在该次构建的产物 `deployment.json`，以及 `dk runtime exec agent-platform-linux-deploy cat /srv/agent-platform/deploy/runtime-state.json | jq .state`。
- **影响**：回滚就是发一个新的 patch 版本，替换 API 同样要等生产空闲、约中断 1.5 分钟。工具只部署三仓当前的 `main` head，不能指定旧版本重新部署。急需时按 §7.1 通知用户后停任务、暂停自动化；前端可先按下文用 Vercel 回滚止血。
- **前置条件**：维护者；已确认问题所在的仓。
- **禁止**：用旧镜像手工 `docker run` 替换 API 容器。这样的容器没有发布工具的标签，之后每次发布都报 `Production container has not been safely adopted`。

```sh
# Mac，$SRC，Node 22
"$NODE22" deploy/jenkins/manage.mjs disable agent-platform-release   # 1 止损：失败版本每轮重试都会再停机
# 2 在出问题的仓 revert 或 fix-forward，CI 绿后合并；只动了 api 或 web 时，再更新主仓指针并合并
"$NODE22" deploy/jenkins/manage.mjs enable agent-platform-release    # 3 自动发出下一个 patch 版本
```

- 含 schema 改动的版本不能靠代码回滚撤销：迁移已上线后再 revert，指纹又会变化并卡在 `waiting-migration-review`。只能 fix-forward，交维护者。
- 前端紧急止血可在 Vercel 控制台用 Instant Rollback 把 production 指回上一个部署。此后线上前端与 Release 记录不一致，直到下一次发布；不要手动重跑同一组合的 release。
- **验证**：§6 的清单。

## 10. 沙箱镜像发版

- **适用场景**：API 仓 `images/platform-sandbox` 或 `images/platform-boxlite` 的改动要发布到 GHCR。
- **影响**：构建在生产 runtime VM 上执行（buildx builder `agent-platform-runtime`），与生产 API 共用 CPU、内存和磁盘，单次最长 190 分钟；选低峰时段。
- **前置条件**：维护者；改动已合入 API `main`（合并时发现作业已用 `MODE=check` 核对过坐标与 builder）。

```sh
# 本地 api 仓克隆：在 main 的目标提交上打一个从未用过的版本标签
VERSION=""                          # 必填：从未用过的版本号，如 3 或 3.1.0
COMMIT=$(git rev-parse origin/main) # 或 main 上的其他目标提交
test -n "$VERSION" && git tag "sandbox-image-v$VERSION" "$COMMIT" && git push origin "sandbox-image-v$VERSION"
```

- 发现作业下一轮触发 `agent-platform-sandbox-images`（`MODE=publish`），推送 `ghcr.io/xeonice/agent-platform-sandbox` 与 `ghcr.io/xeonice/agent-platform-boxlite` 的 `v<版本>` 和 `latest`，并以匿名方式核对 digest。
- 已发布的标签不能改指向，工具会拒绝（`Immutable image tag belongs to a different source revision`）；每次都用新版本号。GHCR token 失效会在这一步失败，轮换见运维手册 §7。
- 生产不会自动换用新的 `:latest`：[播种](./README.md#术语表)按镜像名判重。要用新版本，在 Web 的镜像管理页登记该版本（页面规格见 [P21-4 镜像管理](../product/pages/21-4-镜像管理.md)）。
- **验证**：镜像作业 SUCCESS，描述为 `<sha> · publish · published`。
- **回退**：GHCR 上的版本不可变；有问题就修 Dockerfile 再发新版本，`latest` 会随之更新。

## 11. 版本号、GitHub Release 与 CHANGELOG

- **自动版本号**：取 GitHub 上全部 `v0.3.x` Release（含草稿）的最大 patch 加 1。同一组合第一次排发布时预留，重试沿用同一个号；每次 `main` 变化都只升 patch，不区分 feat 与 fix。根 `package.json` 的 `version` 与发布号无关。
- **不可变**：同名 tag 或 Release 已存在时拒绝（`Release/tag already exists; it is immutable`）。发布失败可能留下同名草稿，下一轮会续用，不要手动发布或改名草稿；历史遗留草稿见参考表 §11。
- **手动指定版本**（例如升 minor）：只在该组合第一次排发布时有效，否则报 `This pinned combination already reserved another immutable tag`。自动规则只认 `v0.3` 前缀：发过 v0.4.0 之后，下一次自动版本会回到 v0.3.x 并被标为 Latest，所以先改 `project-release.mjs` 的规则（运维记录 T16）。

```sh
# Mac，$SRC：合并前先停用 release 与 discovery，合并后执行
printf '{"TAG":"v0.4.0","REQUEST_KEY":""}' > "$TMPDIR/release-tag.json"
"$NODE22" deploy/jenkins/manage.mjs enable agent-platform-release
"$NODE22" deploy/jenkins/manage.mjs build agent-platform-release "$TMPDIR/release-tag.json"
"$NODE22" deploy/jenkins/manage.mjs enable agent-platform-ci-discovery
```

- **CHANGELOG**：合并主仓 PR 的人在同一个 PR 里补条目，版本号按“最新 Release 的 patch + 1”预填，日期在合并前改为当天；只合 api 或 web 产生的版本，在下一个主仓 PR 里补记。不要为补 CHANGELOG 单独合一个主仓 PR，那会多发一版、多替换一次 API。Release 正文只列三个 SHA，改动说明以 [CHANGELOG](../../CHANGELOG.md) 为准。

## 12. 高风险改动的隔离回归

- **何时必须跑**：改了 CONTAINER_INPUTS 所列文件、`api-container.mjs` 里的容器参数、API 的 BoxLite SDK 版本或 provider 实现、auth helper 代码。Jenkins CI 没有 KVM，覆盖不到这些。
- **怎么跑**：在临时 nested VM 里构建候选镜像并运行 api-smoke，步骤见 [BoxLite 验证工具](../../deploy/containers/boxlite-proof/README.md)。不得复用生产 [profile](./README.md#术语表)、卷与凭据，期间盯着生产；结果记入运维记录。
