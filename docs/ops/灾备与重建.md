# 灾备与重建

- **读者**：执行备份导出、灾备恢复或新机器重建的维护者。
- **用途与边界**：备份、恢复、从零重建和冷启动演练。不含日常维护（见 [运维手册](./运维手册.md)）与发版（见 [发版手册](./发版手册.md)）；卷、凭据、版本等数值见 [参考表](./参考表.md)。
- **权威范围**：备份清单与离机导出方法、生产数据与 Jenkins Home 的恢复步骤、从零重建的顺序、外部服务核对项、开机核对清单。
- **适用基线**：v0.3.6（主仓 `7eb7176`）起。本文的恢复与重建步骤都没有完整演练过，执行时逐步核对，结果记入[运维记录](./运维记录.md)。

## 1. 现状与风险

- 生产数据只在每次替换 API 时备份一次，放在 runtime VM 的备份卷里，与生产数据在同一块虚拟盘上；没有离机副本，也没有保留策略。
- Jenkins Home、[可信 deploy agent](./README.md#术语表) 的[私有卷](./README.md#术语表)、API 与 [Tunnel](./README.md#术语表) 的秘密卷都没有任何备份。两份 `runtime.env` 与 Vercel 登录态只存在于这些卷里。
- RPO 是最近一次替换 API 的时刻，可能已过去数天；RTO 未演练，未知。
- Home 丢失后没有验证过的重建办法（§5.8），全新空数据的生产也没有受支持的接管路径（§5.12）。所以先按 §2 做离机导出；对应待办见[运维记录](./运维记录.md) §3 的 T6、T25、T26。

## 2. 备份清单与离机导出

| 对象 | 位置 | 现有备份 | 导出要求 |
|---|---|---|---|
| 生产数据 `/data`（含 `.master.key`） | runtime：`agent-platform-production-data` | 每次替换 API 时在 `agent-platform-runtime-backups` 生成一个 `api-backup-<ROOT>-<API>-<runId>-<uuid>.tgz` | 导出最新一份；加密 |
| Jenkins Home（配置、用户、主密钥、构建历史） | jenkins：`agent-platform-jenkins-home` | 无 | 停 controller 后整卷导出 |
| deploy agent 私有卷与秘密卷 | runtime：`linux-deploy-private`、`linux-deploy-state`、`api-secrets`、`tunnel-secrets`（均带 `agent-platform-` 前缀） | 无 | 整卷导出；发布缓存可排除 |
| Mac 私有目录的在用文件、三份 `colima.yaml` | `$P` 与 `$HOME/.colima/<profile>/` | 无 | 只导出在用文件（清单见参考表 §6）；其中两份 compose env 与 `colima.yaml` 重建时只作参考，不直接解回（§5.7） |

[Lima override](./README.md#术语表) 与 LaunchDaemon 可由仓库重建，不必导出。私有目录里可选的 `host-layout.json` 是本机配置（参考表 §12.2），不导出，新机器按自己的软件位置重写。所有导出物都含秘密：加密后放到这台 Mac 以外（位置见[私有笔记](./README.md#术语表)），加密口令另行保管。

```sh
# Mac，$SRC，Node 22。先按运维手册 §0 进入维护（要停 controller），再导出到私有目录 D；每个文件都会提示输入加密口令
umask 077; P="$HOME/.local/share/agent-platform-jenkins-tools"; D="$HOME/agent-platform-backups/$(date +%Y%m%d)"; mkdir -p "$D"
enc() { openssl enc -aes-256-cbc -pbkdf2 -iter 200000 -salt -out "$1"; }
IMG=$(dk runtime inspect --format '{{.Image}}' agent-platform-linux-deploy)
f=$(dk runtime run --rm --network none --user 0:0 --entrypoint sh --mount type=volume,source=agent-platform-runtime-backups,target=/b,readonly "$IMG" -c 'ls -t /b | head -n 1')
dk runtime run --rm --network none --user 0:0 --entrypoint cat --mount type=volume,source=agent-platform-runtime-backups,target=/b,readonly "$IMG" "/b/$f" | enc "$D/$f.enc"
for v in linux-deploy-private linux-deploy-state api-secrets tunnel-secrets; do
  dk runtime run --rm --network none --user 0:0 --entrypoint tar --mount type=volume,source=agent-platform-$v,target=/v,readonly "$IMG" \
    --exclude=./releases --exclude=./project-releases --exclude=./web-releases -czf - -C /v . | enc "$D/agent-platform-$v.tgz.enc"
done
tar -czf - -C "$HOME" .local/share/agent-platform-jenkins-tools/{admin-login.json,admin-api.json,github-token,ghcr-token,github-status-app.json,github-status-app.pem,container-stack.env,container-runtime.env} \
  .colima/agent-platform-{jenkins,build,runtime}/colima.yaml | enc "$D/mac-private.tgz.enc"
# Jenkins Home：停 controller 几分钟再整卷导出
C=agent-platform-jenkins-controller-controller-1; CIMG=$(dk jenkins inspect --format '{{.Image}}' $C)
dk jenkins stop --time 90 $C
dk jenkins run --rm --network none --entrypoint tar --mount type=volume,source=agent-platform-jenkins-home,target=/h,readonly "$CIMG" -czf - -C /h . | enc "$D/jenkins-home.tgz.enc"
dk jenkins start $C    # jstatus 显示三个节点在线后，按运维手册 §0 退出维护
```

- **验证**：`openssl enc -d -aes-256-cbc -pbkdf2 -iter 200000 -in "$D/<文件>.enc" | tar -tzf - | head` 能列出内容。
- 拷到离机位置后删除本机的 `$D`；本机的备份卷按运维手册 §5 只保留最近几份。

## 3. 从备份恢复生产数据

- **适用场景**：生产数据损坏或误删，要回到某份备份；新机器重建时导入数据（§5.12）。
- **影响**：生产停机直到恢复完成；备份之后产生的数据全部丢失。
- **前置条件**：在 `$SRC` 执行；release 与 discovery 已停用、Jenkins 空闲；deploy agent 与两个 [CI agent](./README.md#术语表) 在线（第 5 步要跑 API 作业）；两份 `runtime.env` 已就位且一致。要保留现场时，先按 §2 的写法导出当前数据卷。
- **限制**：这里借用的是“原生迁移后首次接管”的 `adopt` 入口。它的数据探针要求没有运行中的任务、启用的自动化与未释放的资源名额，且没有 `platform.db-wal`；任务停止后仍保留名额，所以真实备份常被拒。第 2 步先在临时卷里跑同一个探针，通过了才动生产。

```sh
# Mac，$SRC，Node 22。IMG 与 D 同 §2
f=""   # 必填：要用的备份文件名，形如 api-backup-<ROOT>-<API>-<runId>-<uuid>.tgz
# 1 离机文件先解密放回备份卷（卷里已有该文件时跳过）
openssl enc -d -aes-256-cbc -pbkdf2 -iter 200000 -in "$D/$f.enc" | dk runtime run --rm -i --network none --user 0:0 --entrypoint sh --mount type=volume,source=agent-platform-runtime-backups,target=/b "$IMG" -c "umask 077; cat > /b/$f"
# 2 预检（不动生产）：在临时卷里解开备份，跑 adopt 用的同一个数据探针，期望输出 migration-data-probe-passed
probe=$("$NODE22" --input-type=module -e 'import { MIGRATION_DATA_PROBE as p } from "./deploy/containers/api-container.mjs"; process.stdout.write(p)')
dk runtime volume create agent-platform-restore-check
dk runtime run --rm --network none --user 0:0 --entrypoint sh --mount type=volume,source=agent-platform-restore-check,target=/data --mount type=volume,source=agent-platform-runtime-backups,target=/b,readonly "$IMG" -c "set -eu; tar -xzf /b/$f -C /data"
dk runtime run --rm --network none --user 0:0 --entrypoint /usr/local/bin/node --mount type=volume,source=agent-platform-restore-check,target=/data,readonly "$IMG" -e "$probe"
dk runtime volume rm agent-platform-restore-check
# 3 停掉并删除现有 API 容器（数据在卷里，不受影响；新机器上没有就跳过）
dk runtime stop --time 90 agent-platform-api && dk runtime rm agent-platform-api
# 4 先校验归档，再清空数据卷并解包
dk runtime run --rm --network none --user 0:0 --entrypoint sh --mount type=volume,source=agent-platform-production-data,target=/data \
  --mount type=volume,source=agent-platform-runtime-backups,target=/b,readonly "$IMG" -c "set -eu; tar -tzf /b/$f >/dev/null; find /data -mindepth 1 -maxdepth 1 -exec rm -rf -- {} +; tar -xzf /b/$f -C /data"
# 5 为当前 main 构建 API 以取得收据，等它结束；期望 UNSTABLE、描述 <sha> · waiting-initial-adoption
printf '{"SHA":"","ROOT_SHA":""}' > "$TMPDIR/api.json" && "$NODE22" deploy/jenkins/manage.mjs build agent-platform-api "$TMPDIR/api.json"
"$NODE22" deploy/jenkins/manage.mjs wait-idle --timeout 3600
N=$("$NODE22" deploy/jenkins/manage.mjs status | jq '.controller.jobs[] | select(.name == "agent-platform-api") | .lastBuild.number')
"$NODE22" deploy/jenkins/manage.mjs build-status agent-platform-api "$N" | jq '{result, description}'
# 6 写接管许可：字段固定，dataManifestSha256 填该备份的 sha256（只作留档）
API_SHA=$(git ls-remote https://github.com/Xeonice/agent-platform-api.git refs/heads/main | cut -f1)
sum=$(dk runtime run --rm --network none --user 0:0 --entrypoint sha256sum --mount type=volume,source=agent-platform-runtime-backups,target=/b,readonly "$IMG" "/b/$f" | cut -d' ' -f1)
printf '{"state":"native-stopped-data-imported","sha":"%s","rootSha":"%s","volume":"agent-platform-production-data","dataManifestSha256":"%s","previousNativeApiStopped":true,"previousDedicatedTunnelStopped":true}\n' "$API_SHA" "$SHA" "$sum" \
  | dk runtime exec -i agent-platform-linux-deploy sh -c 'umask 077; cd /srv/agent-platform/deploy && cat > native-migration-ready.json.tmp && mv native-migration-ready.json.tmp native-migration-ready.json'
# 7 在 deploy agent 里接管，输出 state 为 initial-adopted
dk runtime exec agent-platform-linux-deploy node /opt/agent-platform/tools/api-container.mjs adopt "$API_SHA" "$N"
```

- 第 2 步不通过就停在这里，生产还没动。报 `Migrated database has live work` 多为已停止任务保留的名额，adopt 一定会拒绝。同机数据损坏且 API 容器还在时，候选做法是走发布工具自动回滚的同一路径原地恢复：停 API 但不删除容器，用 `api-container.mjs` 的 `CLEAR_DATA_SCRIPT` 清空数据卷，解包后启动同一个容器。它不经过 adopt、不受探针限制，但未演练，须维护者确认后执行（运维记录 T26）。
- `$SHA` 与 `$API_SHA` 必须仍是三仓 `main` 的 head；第 5 步之后 `main` 有变化，就从第 5 步重做。
- **验证**：API 容器为 healthy，标签 `api-sha`、`root-sha` 等于上面两个 SHA；公网 health 为 200；在 Web 上抽查数据。然后启用 discovery 与 release，下一次发布 API 判定为 `current`。
- **回退**：第 7 步在持有[维护屏障](./README.md#术语表)之后失败，会留下 `operator-recovery-required` 的锁（发版手册 §7.2），交维护者。第 7 步报 `Unsafe or unsealed migrated database`、`Migrated database has live work` 等探针错误时，数据卷可以再次从备份覆盖，但要先交维护者确认原因。

## 4. 恢复 Jenkins Home

- **适用场景**：Home 卷损坏，或新机器重建（§5.8）。
- **影响**：恢复期间 Jenkins 不可用；备份之后的构建记录与配置改动丢失。
- **前置条件**：有 §2 导出的 `jenkins-home.tgz.enc`；controller 镜像 ID 已写进 `container-stack.env`。不要把同一个 Home 同时挂给两个 controller。

```sh
# Mac，$SRC。1 解密到私有目录并检查归档
umask 077; openssl enc -d -aes-256-cbc -pbkdf2 -iter 200000 -in "$D/jenkins-home.tgz.enc" -out "$D/jenkins-home.tgz" && tar -tzf "$D/jenkins-home.tgz" >/dev/null
# 2 停 controller（新机器上还没有就跳过），清空 Home 卷后解包，属主 1000
C=agent-platform-jenkins-controller-controller-1; CIMG=$(sed -n 's/^CONTROLLER_IMAGE=//p' "$P/container-stack.env")
dk jenkins stop --time 90 $C
dk jenkins run --rm -i --network none --user 0:0 --entrypoint sh --mount type=volume,source=agent-platform-jenkins-home,target=/h "$CIMG" \
  -c 'set -eu; find /h -mindepth 1 -maxdepth 1 -exec rm -rf -- {} +; tar -xzpf - -C /h; chown 1000:1000 /h' < "$D/jenkins-home.tgz"
rm "$D/jenkins-home.tgz"
# 3 启动（新机器用 §5.8 的 compose 命令），最多等 10 分钟，期望最后输出 healthy
dk jenkins start $C
for i in $(seq 60); do [ "$(dk jenkins inspect -f '{{.State.Health.Status}}' $C)" = healthy ] && break; sleep 10; done; dk jenkins inspect -f '{{.State.Health.Status}}' $C
# 4 构建号会回退到导出时刻：用临时容器只读读出 deploy-state 里记录过的最大构建号（新机器上也可执行）
IMG=$(sed -n 's/^DEPLOY_IMAGE=//p' "$P/container-runtime.env")
dk runtime run --rm --network none --user 1000:1000 --entrypoint /usr/local/bin/node --mount type=volume,source=agent-platform-linux-deploy-state,target=/s,readonly "$IMG" -e 'const fs = require("fs"), r = "/s", ls = (d) => (fs.existsSync(d) ? fs.readdirSync(d) : []), max = {};
for (const f of ls(r + "/jenkins-receipts")) { const n = Number((f.match(/-(\d+)\.json$/) || [])[1]); if (n) max.api = Math.max(max.api || 0, n); }
for (const d of ls(r + "/project-releases")) { let b; try { b = JSON.parse(fs.readFileSync(`${r}/project-releases/${d}/builds.json`, "utf8")); } catch { continue; } for (const [k, v] of Object.entries(b)) max[k] = Math.max(max[k] || 0, v.number); }
console.log(JSON.stringify(max));'
```

第 4 步输出形如 `{"api":56,"web":23,"contract":34}`。启用任何作业之前，在 Jenkins 页面的“系统管理 → 脚本命令行”（Script Console）执行下面一行，把三个数换成输出值加 1；输出为空对象时跳过。

```groovy
['agent-platform-api': 57, 'agent-platform-web': 24, 'agent-platform-contract': 35].each { n, v -> def job = Jenkins.get().getItem(n); if (job.nextBuildNumber < v) job.updateNextBuildNumber(v) }
```

- 不调构建号时，新构建会与旧收据同号，API 作业报 `Immutable deployment metadata conflict`，发布也会按 `builds.json` 查到同号的别的构建而失败。
- **验证**：`dk jenkins inspect --format '{{.State.Health.Status}}' $C` 为 healthy（启动脚本会核对插件锁与账号，不符时日志里有原因）；能用原账号登录，作业与历史都在；三个 agent 用原有密钥重新连上。节点显示 `Container migration requires explicit agent activation` 时，确认 `CONTROLLER_MODE=active` 后运行 `manage.mjs activate`。
- Mac 上的 `admin-api.json` 丢了时，可从 Home 的 `bootstrap-secrets/admin-api.json` 取回（`dk jenkins exec $C cat …`），但只在 token 没有轮换过时有效。
- **回退**：用另一份导出重做第 2 步。

## 5. 新机器从零重建

按顺序执行；每步的核对通过后再做下一步。先把 §2 的离机导出拷回这台 Mac 的私有位置，执行 `D=<该目录>`，全文的 `$D` 都指它；再按发版手册 §0 准备 `$SRC`、`$SHA`、`$P`。

各步末尾的宿主自检用 `doctor --stage <阶段>`：每个阶段只检查此时应当存在的东西，之后阶段的项输出 `not-yet`、不算失败（阶段划分与本机期望见参考表 §12.5）。

**5.1 宿主前提**

- 硬件：M3 及以上的 Apple Silicon，macOS 15 及以上（runtime VM 的 VZ 嵌套虚拟化与 `/dev/kvm` 需要）；内存要容下三台 VM 的 28 GiB 与宿主自身；磁盘为三台 VM 合计 260 GiB 的上限留出余量。
- 账号：任一普通管理员账号都可以，它就是[运维账号](./README.md#术语表)，LaunchDaemon 也以它运行。要求 UID ≥ 501、名称以小写字母开头且只含小写字母、数字与 `._-`（以 `_` 开头的服务账号不行）、HOME 为普通绝对路径；工具从系统账户库推导它的 HOME 与 UID，不读环境变量（参考表 §12）。admin 组里除 root、该账号与 `_mbsetupuser` 外不能有别的成员：`/opt/homebrew/bin` 与 `/Applications` 对 admin 组可写，多出的管理员会让可信位置检查失败（`HL_GROUP_MEMBERS`）。不要设置指向别处的 `COLIMA_HOME`。
- 软件（版本见参考表 §8）：`brew install colima lima docker openssl git gh fnm`；jq 用 macOS 15 起自带的 `/usr/bin/jq`；OrbStack.app（提供 compose 与 buildx 插件；工具默认的 docker CLI 是它的 `$HOME/.orbstack/bin/docker`，装好后启动一次让它生成）。没有 OrbStack 时，在 `$P/host-layout.json` 里设 `dockerCli`，并把下面 `config.json` 的 `cliPluginsExtraDirs` 改成提供 compose 与 buildx 插件的目录（如 Homebrew 的 `<prefix>/lib/docker/cli-plugins`），写法见参考表 §12.2。Homebrew 装到的版本与参考表 §8 不同时，先用临时 profile 验证 VM 能启动、override 能通过校验，再继续。
- Node：`FNM_DIR="$HOME/.local/share/fnm" fnm install 22.23.3`，再按参考表 §0 设 `NODE22` 并执行 `test -x "$NODE22"`。工具用运行它的 Node，任意 Node 22 都可以，装在别处时改 `NODE22` 即可。
- 无人值守恢复的要求：断电恢复后自动开机、开机不需要人工解锁、不睡眠。当前的设置见私有笔记。

```sh
# Mac：私有目录与私有 Docker 配置（compose、buildx 插件从 OrbStack 加载）；install -d 对已存在的目录也会改成 0700，
# config.json 按私有文件检查，必须是 0600
P="$HOME/.local/share/agent-platform-jenkins-tools"; install -d -m 700 "$P" && mkdir -m 700 "$P/container-docker-context"
(umask 077; printf '{"cliPluginsExtraDirs":["/Applications/OrbStack.app/Contents/MacOS/xbin"]}\n' > "$P/container-docker-context/config.json")
export DOCKER_CONFIG="$P/container-docker-context"
# 宿主自检（Node 22），期望 "state":"doctor-passed"（之后阶段的项为 not-yet）
"$NODE22" "$SRC/deploy/containers/host-layout.mjs" doctor --stage host | jq -c '{state, counts}'
```

**5.2 Lima override**：在创建任何 VM 之前放好，第一次开机就生效。

```sh
# Mac，$SRC
mkdir -p "$HOME/.colima/_lima/_config" && cp deploy/host/lima-override.yaml "$HOME/.colima/_lima/_config/override.yaml"
```

**5.3 创建三个 [profile](./README.md#术语表)**：只在首次创建时手动 start，之后交给 LaunchDaemon。

```sh
# Mac，已导出私有 DOCKER_CONFIG
common=(--vm-type vz --mount none --activate=false --ssh-agent=false --ssh-config=false)
colima start --profile agent-platform-jenkins "${common[@]}" --cpus 2 --memory 4 --disk 40
colima start --profile agent-platform-build "${common[@]}" --vz-rosetta --cpus 4 --memory 8 --disk 100
colima start --profile agent-platform-runtime "${common[@]}" --nested-virtualization --cpus 6 --memory 16 --disk 120
```

核对：三台的 `$HOME/.colima/_lima/colima-agent-platform-<p>/lima.yaml` 里都没有 `mounts` 段；`colima ssh --profile agent-platform-runtime -- ls -l /dev/kvm` 存在；`colima ssh --profile agent-platform-runtime -- getent group docker` 的 GID 为 991。GID 不是 991 时停下：deploy agent 的 `group_add` 写死了它，要先改 `compose.runtime.json`。最后在 `$SRC` 运行 `"$NODE22" deploy/containers/host-layout.mjs doctor --stage engines | jq -c '{state, counts}'`，期望 `doctor-passed`（三个 socket 与 daemon 名在这一步核对）。

**5.4 安装 LaunchDaemon**

```sh
# Mac，$SRC，Node 22：先停掉手动启动的三台，再以运维账号生成审阅目录，并以 sudo 安装（root 的 PATH 里没有 Node 22，要写绝对路径）
for p in jenkins build runtime; do colima --profile agent-platform-$p stop; done
"$NODE22" deploy/containers/bootstrap-host.mjs prepare
sudo "$NODE22" "$P/container-boot/bootstrap-host.mjs" apply-system
# 三台被 launchd 拉起后（约 1 分钟），期望 "state":"doctor-passed"
"$NODE22" deploy/containers/host-layout.mjs doctor --stage launchd | jq -c '{state, counts}'
```

- `prepare` 以运维账号运行，在审阅目录（`0700`）里生成三份 plist、`review.json`（schema 2，记录运维账号与主组、宿主布局、colima 的真实路径与哈希、三份 `colima.yaml` 的哈希），以及安装脚本与 `host-layout.mjs` 的副本；先审阅再 apply。改过 `colima.yaml`、升级过 colima（`brew upgrade colima`）或改过 `host-layout.json` 之后，下次 apply 之前都要重新 `prepare`。
- `apply-system` 只执行审阅目录里那份脚本。它先把 sudo 的发起人（`SUDO_UID`、`SUDO_USER`）锚定到系统账户库，要求与 `review.json` 记录的运维账号、主组逐项一致，再用同一模块重新推导布局并比对；没有 sudo 发起人（如直接以 root 登录执行）时拒绝。另有 plist 启动同一个 profile 时也拒绝（参考表 §10）。
- 核对：`colima list` 三台 Running；上面的 doctor 显示三个 `launchd:*` 为 `bytes and fields match; running`（Label 规则见参考表 §8）。

**5.6 构建镜像**

```sh
# Mac，$SRC，Node 22。0 宿主自检，期望 "state":"doctor-passed"（两份 env 在这一步核对；admin-api.json 与 Jenkins 还是 not-yet）
"$NODE22" deploy/containers/host-layout.mjs doctor --stage images | jq -c '{state, counts}'
# 1 两个 CI 镜像与 deploy 镜像：在 build daemon 上构建并自检，再把 deploy 镜像搬到 runtime。
#   build 只检查 build VM 的 socket 与 env 文件，不需要 admin-api.json 与 Jenkins
```

把镜像 ID 填进 env 文件：`CI_IMAGE`、`WEB_CI_IMAGE`、`DEPLOY_IMAGE` 直接用上面 jq 输出的 `arm64`、`amd64`、`deploy` 三个 ID（deploy 镜像搬到 runtime 后没有标签）；`CONTROLLER_IMAGE` 与 `DNS_IMAGE` 用 `dk jenkins image inspect --format '{{.Id}}' agent-platform-jenkins-controller:2.580.1` 与 `dk runtime image inspect --format '{{.Id}}' "agent-platform-dns:main-${SHA:0:12}"` 读取。`API_IMAGE` 不能留空（compose 会对整份文件插值），新机器上先填 `DEPLOY_IMAGE` 的值，它不会被用来创建 API。

**5.7 卷与私有文件**

```sh
# Mac：创建 external 卷（CI 工作区卷由 compose 自动创建），再把 deploy agent 用的卷根目录交给 1000
dk jenkins volume create agent-platform-jenkins-home
for v in ci web; do dk build volume create agent-platform-linux-$v-credentials; done
for v in production-data api-secrets tunnel-secrets runtime-backups linux-deploy-home linux-deploy-workspace linux-deploy-jenkins-state linux-deploy-state linux-deploy-private linux-deploy-credentials; do dk runtime volume create agent-platform-$v; done
DEPLOY_IMAGE=$(sed -n 's/^DEPLOY_IMAGE=//p' "$P/container-runtime.env")
dk runtime run --rm --network none --user 0:0 --entrypoint sh --mount type=volume,source=agent-platform-linux-deploy-state,target=/a \
  --mount type=volume,source=agent-platform-linux-deploy-private,target=/b --mount type=volume,source=agent-platform-linux-deploy-home,target=/c \
  --mount type=volume,source=agent-platform-linux-deploy-workspace,target=/d --mount type=volume,source=agent-platform-linux-deploy-jenkins-state,target=/e \
  "$DEPLOY_IMAGE" -c 'chown 1000:1000 /a /b /c /d /e && chmod 700 /a /b'
# 有 §2 的导出时，还原四个私有卷与秘密卷（保留属主与权限）
for v in linux-deploy-private linux-deploy-state api-secrets tunnel-secrets; do
  openssl enc -d -aes-256-cbc -pbkdf2 -iter 200000 -in "$D/agent-platform-$v.tgz.enc" | dk runtime run --rm -i --network none --user 0:0 --entrypoint tar --mount type=volume,source=agent-platform-$v,target=/v "$DEPLOY_IMAGE" -xzpf - -C /v
done
# Mac 私有文件先解到 $D 下的临时目录，只把凭据装回 $P
mkdir -m 700 "$D/mac-private" && openssl enc -d -aes-256-cbc -pbkdf2 -iter 200000 -in "$D/mac-private.tgz.enc" | tar -xzpf - -C "$D/mac-private"
for f in admin-login.json admin-api.json github-token ghcr-token github-status-app.json github-status-app.pem; do install -m 600 "$D/mac-private/.local/share/agent-platform-jenkins-tools/$f" "$P/$f"; done
```

- 导出里的两份 compose env 记的是旧机器的镜像 ID，`colima.yaml` 会让 §5.4 `prepare` 记下的哈希失效（下次 apply 报 `Engine configuration changed; prepare again`）。它们只用来对照参考表 §7、§8，不要覆盖新文件；用完 `rm -rf "$D/mac-private"`。
- 没有导出时跳过本步的还原，凭据在 §5.11 写入；§5.10 起 Tunnel 在拿到 token 前会反复重启，属预期。此时 deploy-state 是空的，首轮发布会把当前组合当成新版本再发一个 patch 号。

**重新注册 GitHub App**（只在原 App 被删除时）

1. 打开 `serve` 输出的本机地址，在 GitHub 审阅并创建 App；权限只能是 contents 读、pull requests 读、statuses 写。

4. 管理员把三仓分支保护的必需状态改绑新 App ID（参考表 §9 同步更新）。

- **验证**：下一轮 `discovery.json` 的 `githubStatusSource.kind` 为 `github-app`；新提交的 `jenkins/*` 状态来自新 App。
