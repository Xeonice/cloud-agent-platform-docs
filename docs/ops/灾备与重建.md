# 灾备与重建

本文描述统一 Colima Linux arm64／Foundation 与五角色实例的备份对象、恢复顺序和安全边界。日常运维见 [运维手册](./运维手册.md)，管理员升级与回退见 [发版手册](./发版手册.md)，实际实例身份及运行根见 [统一虚拟化与实例部署](./统一虚拟化与实例部署.md)。

**完整离机恢复、宿主冷启动与 Guest 连续性尚未取得本轮验收证明。** 本文给出恢复前必须满足的条件，不提供未经验证的一键恢复命令，也不把已封存迁移副本当作已建立周期备份。

## 1. 恢复目标与当前风险

先区分入口／连接故障、单个业务角色故障、运行卷损坏、整台 VM 丢失及宿主丢失。入口故障优先恢复 transport 与已确认绑定，保留现有 Owner；数据丢失才进入离线数据恢复。

RPO 取决于最近一份**已验证一致且可解密**的异机备份；RTO 只有实际恢复演练才能给出。当前不能从最近升级时间、同盘快照或一个压缩包推断两者。

同一宿主、同一 VM、同一 Docker 数据盘中的副本不构成异机灾备。包、签名、公钥、业务数据和加密材料各自完整仍不等于整套可恢复，必须验证它们的相互绑定。

## 2. 备份清单与一致性

| 对象 | 必须覆盖的内容 | 一致性与保护要求 |
| --- | --- | --- |
| 业务数据 | SQLite、业务文件、工作区、日志及相关主密钥 | 由唯一 writer 生成一致备份；数据库与文件处于可解释的同一边界 |
| Foundation 持久状态 | 实例身份、路由绑定、generation、已确认角色与恢复配置 | 保留完整引用关系，不能只导出页面版本号 |
| Installer／升级状态 | 受理意图、attempt、事件、计划、安装与切换记录 | 保留失败与未知；不能只备份成功结果 |
| Owner 持久状态 | 每个 Owner 的独立 SDK home、资源归属、持久 Guest 磁盘和工作区引用 | 按实际 Owner 分别记录；磁盘副本不能代表运行内存、进程或终端连续 |
| 发行与信任材料 | 已确认版本及允许恢复目标的包、摘要、签名、固定信任根和镜像 digest | 公钥与已签材料可随备份保存；发布私钥另行保护，不分发到实例 |
| 宿主与 VM 配置 | profile 规格、实际网络／转发、入口 bridge、私有配置与权限 | 保留作重建依据；新机器重新生成自身路径与身份 |
| Jenkins／发布基础设施 | Jenkins Home、必要插件／工具、发布状态和凭据引用 | 与业务实例分别备份恢复；不能顺带启用实例 deploy／promote |
| 外部资源 | OCI 镜像、registry 数据、DNS／Tunnel／Access 配置引用 | 确认可取回、有效期及作用域；外部登录态不等于可长期恢复 |

备份目录 0700、文件 0600；含秘密的数据使用组织认可的加密方式放到独立故障域，解密材料另行保存。记录实例、时间、来源包／schema、文件长度与摘要、权限、加密方法与一致性边界，定期从备份还原验证。

活动 SQLite 必须通过支持的一致备份或受控冻结导出，不能复制正在变化的主库再忽略 WAL。封存导入工具只适用于已经证明一致、停止写入并核验字节的副本，不是活动数据库的在线备份替代品。

不在公开文档记录私钥路径、令牌、口令或备份解密材料。实际备份位置与保留策略由维护者在私有记录中维护；没有可验证证据时标记未建立。

## 3. 业务实例恢复

1. 保护现有卷、进程、路由与失败证据，确认是否仍有可用 writer 或 Owner。网络隔离时不能假定原节点已死。
2. 核对备份来源、加密可用性、完整性、包／schema／信任关系和允许恢复范围，说明可能的数据损失；不写回运行卷。
3. 在隔离环境使用新目标卷恢复副本，保留来源只读。核对数据库完整性、外键、业务行、文件树、权限、主密钥与凭据解密。
4. 对 Foundation、Coordinator、Owner、Installer 的记录做交叉对账，证明唯一 writer、资源归属和物理身份；不能让两套实例同时写同一数据或控制同一 Guest。
5. 校验目标平台与原生 ABI、固定包／镜像、网络、KVM、鉴权、同源 HTTP／WebSocket，以及允许验证的自有 Guest／终端链路。
6. 具备可审核的切换与退回方案后才改变用户入口；记录实际维护窗口、数据损失与验收结果，保留原副本。

备份中的 Guest 磁盘不包含原进程内存。换 VM 或宿主后不能宣称同一 Guest／shell 已连续运行，不能把重建 Guest 或重播输入当作续接。

已有新写入时，整体恢复旧副本会覆盖它们；必须先明确数据恢复点并另行解决新增写入，不能作为普通升级回退。无法证明 writer 或控制权时停止推进，显示真实未知状态。

## 4. Jenkins 与发布基础设施恢复

Jenkins Home 含用户、主密钥、凭据和构建历史，需使用与其版本、插件及加密关系匹配的恢复材料。先在隔离 controller 验证，再恢复所需 CI 节点；controller 不执行 PR 构建。

恢复后核对管理员登录、CSRF、节点密钥、GitHub App 状态权限、仓库保护与工具身份。先维持作业不排新构建，逐个恢复已确认的 CI；发布权限与运行 socket 的挂载单独审阅。

**影响实例的 deploy／promote 持续停用。** 还原 Home、同步模板、`refresh` 或 agent 恢复都不能自动放开它们。CI、产物发布与实例升级是独立恢复项，最后仍由管理员决定实例升级时机。

## 5. 新机器准备与实例重建

新机器使用同一部署架构，不从其他宿主直接搬运运行路径或整份启动配置。执行前形成该机器的可审阅计划：

- 核对 Apple VZ 嵌套虚拟化实际支持、Linux arm64、资源预算、Colima／Lima／Docker／Node 与原生依赖；KVM 在 Owner 实际权限下验证。
- 建立独立 profile、显式 Docker socket 和私有 Docker 配置，不改变已有 OrbStack context 或无关 registry。
- 按该机器实际网络设置 DNS、最小端口转发和同源稳定入口；内部管理端口不向外开放。
- 准备该实例固定身份、渠道、信任材料、不可变包与持久卷，密钥按用途分别保护；不把克隆仓库当运行目录。
- 通过已审阅的首次部署工具准备 Foundation 与五角色，并逐项核对安装收据。已有持久实例使用恢复路径，不能重新初始化覆盖它。
- 恢复数据按上一节隔离验证，确认角色绑定、唯一 writer、资源路由、用户入口、鉴权与真实业务后再切换。

部署工具见 [bootstrap-upgrade-instance.mjs](../../deploy/ops/bootstrap-upgrade-instance.mjs)，它的输入和适用阶段必须按固定提交审阅。存在工具不等于任意旧状态都能安全重建；不能临时编写 `docker run` 或执行初始化绕过拒绝。

只有明确存在用户资源连续性方案、当前操作无损且已得到相应授权时，才可将工作从原实例迁出。统一首次部署有实际维护窗口，与后续在线升级分开记录。

## 6. 外部服务核对

| 服务 | 恢复前核对 |
| --- | --- |
| Cloudflare Tunnel／Access／DNS | 正确宿主与源站、Access 应用策略、JWT 校验、TLS、最小监听与路由 |
| GitHub | 仓库、保护规则、App 权限、签名资产、不可变 Release 与摘要 |
| OCI registry／GHCR | 匿名或授权拉取、固定 digest、各平台镜像和恢复所需历史版本 |
| Jenkins | controller 与 agent 身份、私有卷、工具、作业启停及构建隔离 |
| 用户入口 | 该实例确认的 Web 与 API 同源，WebSocket 可达；独立预览不能替代实际入口 |
| 认证与模型服务 | 凭据有效性、加密关系与最小作用域；不将另一实例的凭据复制过来绕过失败 |

外部服务可用不授予业务恢复通过。发布私钥不因恢复另一台机器而传过去；签名材料失效时按既定信任更新规则处理，不能替换固定信任根跳过校验。

## 7. 冷启动与恢复验收

完整冷启动演练是独立维护工作，须有受控测试环境、明确影响范围和原始证据。至少覆盖宿主／VM、Docker、DNS、入口、Foundation transport、角色绑定、writer／fencing、Owner home、资源路由、鉴权及真实业务；对无法保留的进程与终端连续性明确报告。

本轮受控 VM／DNS 重启与 registry 检查，只验证了对应基础设施范围；真实 Guest／终端重连也只证明已执行场景。它们不能合并成整台机器断电恢复、模型 Agent 或跨升级资格。

恢复验收必须记录实际包、实例／渠道、物理角色、卷和文件摘要、恢复点、时间窗口、失败与未知，以及自有测试资源清理结果。当前已执行事实见[统一部署验收](../testing/results/2026-10-17-统一部署与在线升级验收.md)，其余演练与周期异机备份保持待验证。
