# 升级失败恢复与回滚方案

**状态：实现与隔离验收进行中，尚未取得真实迁移和线上升级资格。** 本文定义单实例、单个管理员主动升级后的安全恢复路径。实际工具已实现，但必须先完成同构资格和本实例容量、身份及状态预检，再运行首次维护迁移。新增控制系统见[独立升级控制系统](../backend/changes/2026-10-20-独立升级控制系统.md)，用户行为见[产品方案](../product/changes/2026-10-20-独立升级控制与失败恢复.md)，验收以[独立测试计划](../testing/changes/2026-10-20-独立升级控制与恢复测试计划.md)为准。

用户一次明确发起升级，包含该固定计划内及其约定保留期内经过资格验证的安全自动恢复；不需要再次输入升级密钥或逐次审批。恢复结束后重新升级、换目标、扩大恢复范围或执行灾难恢复，仍须用户另行明确发起。CD只发布产物，不触发升级、恢复或重试。

## 1. 当前缺口与目标边界

`.19`第四次失败后，入口停在25%，原attempt已failed且控制租约过期；入口变更又依赖它的checkOnly校验，而partial-source只接受0%或100%。业务仍可服务，普通恢复却无法取得授权。随后经用户批准的一次性维护退流成功，不能代替产品恢复协议。[`.19`原始验收](../testing/results/2026-10-19-BoxLite句柄额度发版与远端更新验收.md)与[`.20`维护及安装结果](../testing/results/2026-10-19-升级证据开销修复与恢复准备.md)保持原结论，不因本方案改写。

| 当前已证缺口 | 本方案目标 |
| --- | --- |
| 恢复权限受原attempt终态、过期租约及业务Coordinator读取影响 | 由稳定Control Agent受理独立恢复意图，取得新的恢复控制epoch；旧attempt只是关联证据 |
| 控制判断可能等待完整snapshot／观测，角色准备与业务请求争用资源 | 轻量控制授权、进度查询与昂贵资格检查分离；准备候选前预留完整重叠资源 |
| 失败后已有部分组件推进，整包版本不足以描述现场 | 按实际组件、路由、writer与数据epoch冻结恢复计划；优先最小退流，必要时才回退组件 |
| 失败候选和历史角色需要逐个手工证明可退役 | 产品维护受引用保护的候选生命周期、排空及退役回执；不触碰仍承载资源的Owner |
| 缺少请求类别、Native阶段和prepared-ready证据 | 恢复journal记录有界的阶段、操作身份、分段耗时、实际结果和未知原因 |

目标不是保证任何故障都能自动退到任意旧版。数据、writer或替代路径无法证明安全时，必须停止变更并如实记录影响；不得通过停止沙箱、覆盖数据或放宽门槛制造“恢复成功”。

## 2. 四类动作分别定义

| 动作 | 改变什么 | 保持什么／不能声称什么 |
| --- | --- | --- |
| 退流 | 将新HTTP／WS连接改到已验证能服务当前数据的API或兼容桥；必要时退Web入口 | 保留在途操作与原连接归属；不等于Coordinator、Owner、数据库或整个版本已回退 |
| 组件版本回退 | 对确有故障且具备资格的API、Web、Coordinator或受限安装工作器，恢复兼容产物；Coordinator必须另做唯一writer交接 | 使用当前数据库；健康的新组件可以保留，不要求凑成某个旧版本号；不回滚稳定控制器 |
| 数据前向修复／兼容桥 | 暂停后续迁移或不兼容新功能，保留已提交新数据，退到兼容桥或提交可审计的修复事务 | 不倒退业务事实、取消意图、幂等账本或日志游标，不重放外部副作用 |
| 备份恢复／灾难恢复 | 在另行批准的恢复点和隔离目标卷中重建损坏或丢失的数据 | 不是普通升级回退；须说明RPO、可能损失、对账和切换，不能自动覆盖活动卷 |

数据库事务回滚仅指撤销尚未提交的那笔事务。已经提交的业务结果不能因服务退版被撤销。备份存在、schema编号相同或旧包仍可下载，均不构成代码回退资格。

## 3. 恢复权威、授权与持久记录

### 3.1 稳定控制系统拥有恢复执行权

Control Agent作为Foundation中的独立受监督进程，使用独立`control.db`保存控制意图、恢复计划、控制epoch和步骤journal。普通业务版本更新不替换Control Agent。它不加载业务AppModule、持有业务数据库RW连接、创建Guest或执行用户指令。

StableEntry按稳定控制权威验证退流命令，不再调用失败业务Coordinator的`upgrade_attempts`租约或完整snapshot取得许可。现有访问会话、Origin／CSRF和实例绑定继续有效；内部角色认证由系统维护，不成为用户的新口令或密钥。

控制权限与业务写入权限分开：

- `controlEpoch`只授权本实例的升级／恢复控制动作。Control Agent在`control.db`中CAS授予一个活动执行者；恢复可以获得新epoch，原升级执行者的迟到命令必须被拒绝。
- 业务writer的holder／generation／fence仍在业务库的同一事务内检查与更新。Control Agent不能先查`control.db`再直接写业务库，冒充跨库原子性；它只能调用经过验证的角色交接协议。
- RuntimeOwner保持独立home和原资源归属。升级／恢复控制身份没有用户Guest的stop、destroy、kill、cancel或初始指令执行权限。
- 受限安装工作器、业务Coordinator或用户页面故障，不应导致稳定恢复journal、入口控制监听和控制授权一起消失。Foundation或宿主整体故障另按灾备范围处理，不能承诺仍无感。

目标体系将原Installer的编排职责迁入独立Control Agent；安装工作器只承担限额的下载、校验与安装工作，没有推进升级或恢复的权威。本文出现的legacy Installer仅指历史混合来源或迁移期组件。业务包不能更新或回滚旧Installer控制器，也不能借安装工作器重新引入旧编排器。

### 3.2 新恢复意图不重开旧attempt

故障发生后，先持久化`recoveryIntent`，关联原用户升级意图和实际故障范围。原attempt可以保持failed；若此前已activation-confirmed，保留当时成功与100%，另追加当前可用性撤销和恢复事件。

新的`recoveryId`、冻结`recoveryPlan`和恢复控制epoch不依赖旧attempt重新claim。无需修改旧attempt的controller、fence、lease、sequence或失败原因；旧租约过期不能堵住入口退流。业务库中原升级记录是历史／投影来源，不再兼任稳定恢复授权账本。

同一实例只允许一个活动变更流程。恢复意图受理后持久冻结原升级推进、扩流、迁移后续批次及退役动作；重复点击、页面重开或响应丢失查询同一`recoveryId`。这处理单个管理员的重复操作和旧进程迟到，不引入多人审批流程。

### 3.3 恢复journal与真实操作回执

`control.db`至少保存以下信息；具体字段与协议由技术方案冻结，不在运维文档提供临时SQL：

| 记录 | 必需事实 |
| --- | --- |
| 恢复意图 | instance、recoveryId、原用户意图／upgradeId、触发原因、授权范围及保留期 |
| 冻结计划 | 计划摘要、允许恢复的组件组合、兼容／数据边界、预计动作、预算、回退底线与容量预留 |
| 控制所有权 | 当前执行者、controlEpoch、执行租约、单调sequence；与业务writer代际分别记录 |
| 步骤意图 | operationId父关联、stepId、精确commandId、不可变副作用spec摘要、预期binding／角色／数据epoch、原截止时间与预算；先持久化再执行 |
| 步骤结果 | applied／definitely-not-applied／pending／unknown、实际身份、前后状态摘要及原始回执引用 |
| 故障上下文 | requestKind、Native phase、目标角色与incarnation、请求／响应分段时间、错误码和最后已确认事实 |
| 恢复确认 | 实际服务组合、路由／Web／writer／数据身份、独立连续性结果、用户影响及未确认项 |

同一完整证明只保存一次，心跳引用经过核验的摘要，不重复写大evidence。控制journal与状态查询保持有界，不同步执行整库检查、整树重验或模型访问；不记录密钥、headers、用户命令或终端正文。

一个operation可包含多个步骤。执行幂等键固定为`(instanceId, operationId, commandId)`，绑定stepId及不可变副作用spec摘要；operationId本身只是父关联，不能作为所有步骤共用的去重键。spec固定动作、目标、预期前态、原计划、原deadline和预算。接管时可以提高授权envelope中的controlEpoch、变更执行者，不能因此更换commandId、改动作或暗延deadline／预算。超时精确查询原commandId；已过期命令只查结果，不重新执行。恢复确需的新动作可有新commandId，但不能用新ID复制未知旧动作。

## 4. 单实例恢复状态机

主路径为：

```text
created → reconciling → restoring → verifying → recovered
任一未完成状态 → blocked
执行者崩溃／租约到期 → 同一recoveryId由新controlEpoch接管 → reconciling
```

| 状态 | 允许动作 | 离开条件 |
| --- | --- | --- |
| created | 固定故障、授权、计划和控制权；冻结原升级 | 稳定journal已提交，本步涉及的Entry／Supervisor已确认新的epoch屏障；仅退流不向业务Coordinator申请控制许可 |
| reconciling | 查询实际Entry、角色交接、业务writer、数据epoch及原操作结果；不发猜测性补偿 | 下一步骤的前态、资格、预算和容量都已确认 |
| restoring | 按冻结计划执行最少退流／组件交接；每个命令带父operationId、stepId、原commandId和精确CAS | 实际结果与回执匹配，或进入unknown／blocked |
| verifying | 对当前实际组合取得新的恢复观察和原资源连续性证明 | 满足全部恢复门槛才进入recovered；否则blocked |
| recovered | 记录“升级失败，服务已恢复”或“确认后故障已恢复”；停止自动变更 | 不自动继续原升级、不自动换目标；用户下一次明确发起才建立新升级 |
| blocked | 保留可证明安全的服务路径、原资源及现场；只做有界只读核验 | 用户明确继续恢复／修复前进后固定续接计划；不能因健康回升自动循环切流 |

恢复执行租约过期只表示执行者需要接管，不撤销已持久接纳的恢复意图。接管者取得更高控制epoch，读取原journal和执行端结果后续同一恢复；计划预算已经耗尽、状态改变或原资格失效时进入blocked。**接管恢复与再次尝试升级是两个动作。**

## 5. 各升级阶段失败后的处理矩阵

实际升级可先交接Coordinator再进行API灰度；以下按故障时的真实状态判定，不凭UI阶段名推断已发生交接。

| 故障阶段／实际状态 | 自动恢复的第一步 | 有资格时的最小恢复 | 禁止动作／确认重点 |
| --- | --- | --- | --- |
| 下载、验证、候选准备，尚未接流 | 停止继续创建候选及迁移后续批次；核对是否已有Owner默认分配或迁移期legacy Installer变更 | 生产路由不动；隔离未接流候选。已健康推进的非故障组件可保留 | 不把“准备中”视为全旧状态；不能为释放内存停止原Owner／Guest |
| API部分或全部灰度，writer未变 | 冻结扩流，按当前数据与现存Web核验替代API | StableEntry CAS退新连接到合格API／桥；在途操作和旧WS按实际归属保留 | 不先摘掉唯一可用后端，不跨API重发未知写请求，不等旧attempt续租后才退流 |
| Coordinator候选准备，尚未quiesce／release | 保持原writer与调度权，核对prepared候选是否实际ready及有无在途交接 | 取消后续接管推进；候选确无引用／业务责任后进入退役 | Docker started不是prepared-ready；不将准备失败写成已切换writer |
| Coordinator交接处于quiesced／releasing／adopting或结果未知 | 按原handoff父操作和精确commandId查询，核对实际业务lease及必要Owner动作回执；阻断另一条交接 | 仅完成该已知交接，或按已演练的恢复计划恢复来源。重新接管使用有效新writer代际，不倒退generation | 旧进程失联不等于已死；不能同时resume旧writer和adopt新writer；不kill Owner或SDK进程解阻塞 |
| 新Coordinator已adopt且健康，API／Web后续失败 | 核验当前writer与数据格式 | 优先只退API／Web，保留健康的新Coordinator和Owner；受限安装工作器按引用保留，控制权威不变 | 不为了回到旧版本标签额外交接writer；若Coor确有故障，才启用当前数据兼容的独立组件回退 |
| Web入口切换或整体激活提交附近 | 查原激活命令是否已提交，撤销不成立的目标ready／刷新资格 | Web-only故障优先退Web指针；API需退时验证已打开Web A和B均可用 | Web指针退回不会卸载用户浏览器的B；激活结果未知不重复提交或假写100% |
| 已activation-confirmed，仍在授权保留期 | 追加新故障和当前ready撤销事件 | 新recoveryId按冻结范围恢复合格组合；保留原成功记录 | 不改写历史100，不将恢复旧组合当作原目标现在仍ready；恢复再失败不A↔B循环 |
| 保留期结束、旧角色退役或contract之后 | 按当前数据回退底线重新判断 | 仅使用仍兼容的保留桥或修复前进；需要新授权时明确受理 | 不能只因旧包存在就重新拉旧二进制；不自动恢复历史数据库 |

Owner版本恢复只影响后续新资源的默认分配。若新Owner已经承载新Guest，该Owner和其资源仍须保留；不能通过切回默认Owner搬走原assignment或复制SDK home。Owner故障涉及既有Guest时进入独立运行环境故障处置，不能伪装成普通控制组件回滚。

受限安装工作器可选择经过验证的兼容版本，但它没有编排权威，也不能复活原升级。迁移期legacy Installer须按迁移计划解除旧控制权，不能作为目标体系的业务回退组件。Control Agent自身使用独立控制包维护，不是业务组件回退目标。

## 6. 恢复资格、数据边界与确认

### 6.1 执行前必须成立的资格

冻结升级计划时先声明允许的恢复组合与最低数据兼容底线；恢复时仍核对最新事实。不是要求每次退流先重扫全库，而是由兼容写规则、当前数据epoch和已验证产物证明当前写入没有越过该底线；最新资格缺失或已出现损坏信号时不得猜测放行。

1. 新恢复控制epoch有效，原控制者已被执行端fence拒绝；instance、计划和操作身份完全匹配。
2. 替代路径真实可用且有容量，API／Web／Coordinator／全部既有Owner协议兼容；认证会话和当前已打开Web A／B仍被支持。
3. 替代组件能处理当前数据库、已提交的新数据及当前读写／迁移epoch；保留operationId、occurrence、取消意图、资源账本和日志游标语义。
4. 原交接／迁移操作已知提交结果；未确认的控制副作用必须先按原父操作及精确commandId对账，不能拿重试得到的新结果覆盖未知。业务任务原有幂等键继续保持。
5. 原Guest／Owner及终端身份可寻址；切API不重放prompt，切writer不重复调度、pump、Outbox或业务清理。
6. 当前实际路由及角色身份与冻结前态相符；超时、错代际、数据epoch变化或回退底线提高均重新判定，不改旧时间戳继续使用。

候选树与全量兼容证明在短控制授权路径之外完成；短控制校验只读取必要的当前事实和证明引用。整库／整树验证、Worker退出和网络等待仍纳入各自真实预算，不用延长租约RPC掩盖昂贵工作。

### 6.2 数据变化如何约束恢复

| 当前数据状态 | 可采取的策略 |
| --- | --- |
| 仅兼容扩展／部分回填，旧表示仍完整 | 暂停后续批次，保留新结构与已提交数据，可退API／Web／读策略 |
| 已切新读，旧表示仍可无损表达当前新写入 | 按当前水位／epoch核验后退旧读或兼容桥；不倒退rowRevision／tombstone |
| 新数据或语义不能由旧版无损表达 | forward-only到兼容桥或修复版本，限制相关新功能；不退会误读或覆盖数据的旧组件 |
| contract已删除旧表示 | 旧二进制永久失去本数据阶段的回退资格，仅当前回退底线以上的桥／修复包可用 |
| 共享库损坏、丢盘或所有候选均不能安全写 | 隔离受影响的危险写入，保留可证明安全的读取和原Owner；进入数据修复／另行批准的灾难恢复 |

**自动恢复不得导入、替换或覆盖活动业务数据库、Owner卷、SDK home和Guest磁盘快照。** 灾备先在隔离目标卷恢复副本，说明恢复点、后续新写入如何处理和切换影响；原件保留。快照不含原进程内存，不能把重建Guest称为续接。

### 6.3 两层收据，不把止损写成验收通过

快速退流与恢复确认分别留痕：

- `containment-applied`只证明执行端已应用指定epoch及父operation下精确commandId的实际路由或角色动作。保存前后binding摘要、API／Web身份、writer代际及实际时间，不表示恢复观察通过。
- `recovery-confirmed`必须取得新的恢复范围证据，绑定recoveryId、实际路由代际、API incarnation、writer generation／fence和数据epoch，不能复用旧升级窗口补样本。

恢复观察沿用冻结策略的业务2秒、attach5秒、证据时效、真实10Hz／60秒窗口与硬不变量；不足样本、陈旧、共享状态未知或硬约束失败均不确认。退流不必等待完整60秒观察才止损，但止损后仍要取得完整恢复确认；已经发生的错误保留在本次用户影响中。

最终收据记录实际服务组合，而不是只写一个旧版本号：API／Web artifact及incarnation、Coordinator holder／generation／fence、受限安装工作器身份、新资源默认Owner与保留Owner registry摘要、schema／数据epoch、原资源身份与日志／执行连续性、独立入口观测和未覆盖项。历史混合来源中的legacy Installer另列实际身份与已解除的控制权限，不混同目标工作器。安全混合组合可以记录为“服务已恢复，升级未完成”，不能伪造目标整体激活。

## 7. 超时、再次失败与执行者崩溃

| 事件 | 必须如何收敛 |
| --- | --- |
| 命令超时／响应丢失 | 保存unknown，按父operationId和stepId查询原commandId及执行端实际状态；不得换新ID重发同一副作用 |
| 状态显示前态，但旧请求可能仍在队列 | 不能仅据前态认定未应用；先用更高控制epoch拒绝迟到旧动作，再查询权威操作状态 |
| 执行端确认definitely-not-applied | 在同一恢复计划、原deadline、预算和资格仍有效时，续原commandId；不是重新发起升级或另造恢复目标 |
| 执行端确认applied，但回执未进入journal | 核对原命令摘要和当前实际状态，补记同一回执；不重复执行 |
| 升级执行器崩溃 | Control Agent从独立journal接续恢复；业务Coordinator和原Owner不随其退出 |
| Control Agent进程崩溃 | 受监督的新进程独占打开control.db，取得新控制epoch，fence旧执行者后恢复同一recoveryId；状态查询保留最后事实与时间 |
| 恢复目标本身失败／资格失效／步骤预算耗尽 | 进入blocked，保留当前可证明安全的路径及全部原资源，不在A／B间自动循环切换 |
| control.db不可写、Entry结果不明、业务writer或数据安全未知 | 不启动新副作用，保留最后已应用配置和故障证据；明确降级／不可用范围，不能假报recovered |

恢复journal和执行端之间不宣称存在跨进程事务。执行端必须提供持久的精确commandId查询、精确前态CAS与控制epoch屏障；接管前后的命令身份和副作用spec保持不变，执行授权epoch可以提高。父operation下不同步骤分别留痕，不能互相去重或以不同内容复用一个commandId。迟到旧响应只能作为历史证据，不能覆盖较新的实际状态。

对Coordinator的控制权丢失不得靠外部SQL或重置旧generation补救。原writer无法证明已释放时，按业务lease／handoff协议核验；候选只能通过业务库内原子claim与writer guard取得唯一写权。锁仍被占用或外部副作用未知时保持blocked，不把控制journal中的新epoch当作已经拥有业务写权。

## 8. 候选清理与容量准入

### 8.1 准备之前预留重叠容量

准入预算覆盖当前服务、所有存量Owner／Guest、必要回退角色、新API／prepared Coordinator／受限安装工作器、产物校验峰值、观察器和恢复保留空间；迁移期尚未退役的legacy角色也计入。按真实写入位置检查业务DB／WAL、control.db journal及下载／解包磁盘；内存、CPU、I/O、事件循环及队列均有演练后的有界预算。

不把“普通运行尚有余量”当作能够同时启动新角色；也不把Coordinator灾难恢复的`freemem > writer RSS`谓词直接移作所有普通升级的唯一容量门槛。容量不足应在创建候选之前延期并继续原服务，不停止用户资源、清cache或降低SLO来腾空间。准备过程中超出冻结上限则停止继续分配并进入安全恢复，不靠持续创建更多候选碰运气。

### 8.2 退役是受保护的产品操作

仅以下条件全部证实时，Control Agent才可通过受控Supervisor退役候选控制角色：

- 完整container／process incarnation、实例、role、来源attempt／recovery、签名包与artifact均匹配；RestartPolicy及实际启动身份已知。
- 无当前入口、在途HTTP／WS、控制命令、writer、handoff／recovery、回退保留或活跃用户操作引用。
- 不是业务writer，无活动workers／动作；历史`workersStarted`闭包值不能单独代替实时排空证明。
- 所属变更已终止推进，原执行者无权重新启用该角色；退役前再次CAS核对引用与身份。
- 先停止新分配、排空，再请求正常退出并确认结果；超时／未知只核验，不自动force kill、删卷或删除失败证据。

API／Coordinator／受限安装工作器／Web的候选清理不能泛化为Owner清理。迁移期legacy Installer另按已解除旧编排权的迁移回执处理。所有承载运行或用户保留环境的Owner及home均受保护；空且从未承载资源的新Owner也须走独立Owner退役协议，不能只凭running数0或未被默认指针引用而停止。

正常退出与删除产物是不同动作。连接、恢复计划、历史回执或允许回退的角色仍引用产物时不删；SDK home、用户磁盘和业务数据不进入控制候选GC。退役和实际释放的资源量分别记录，不把进程RSS直接当作净回收内存。

## 9. 控制系统维护与一次性迁移

Control Agent、control.db协议和StableEntry恢复授权属于独立控制包。业务API／Coordinator／Owner／受限安装工作器升级或回退不替换它们，也不允许回滚旧Installer控制器。控制包更新必须单独验证journal前后向兼容、入口协议、执行者交接和失败恢复，不能把“回退业务版本”用于回退控制权威或恢复旧控制数据库。

当前实例仍依赖旧attempt租约，不能直接套用本文新接口。首次接入需另列固定版本、范围和验收的迁移计划：

1. 只读封存实际路由、当前writer、组件／数据epoch、原Owner／Guest身份和所有未明操作；不把当前混合状态改写为某个整体成功版本。
2. 准备独立控制包和新Entry授权协议，导入可核验的来源引用，保留原业务库与升级历史；新控制epoch与业务writer fence分域，不复用数值冒充相同权限。
3. 验证旧执行者不能迟到修改入口或继续部署，再切换入口的控制授权模式；旧角色协议需要兼容适配时，必须先有明确受信适配与同构演练，不能假定旧包已支持新协议。
4. 保留原Owner及Guest，核验新的只读状态、故障恢复与已有会话；迁移失败按预先固定的控制包恢复计划处置。

**一次性替换Entry监听可能断开HTTP／WS连接，应独立列为维护影响并测量，不归入常规无感升级成功。** 浏览器重连只附着原资源；Guest、任务与Owner保持运行。若当前部署方式不能保证这一点，迁移延期。本文不授权重启Foundation、runtime VM或宿主，也不提供跳过旧守卫的SQL／文件修改方法。

现有[签名路由维护恢复](./失败升级的签名路由维护恢复.md)是旧协议下的受限维护材料，含特定schema／签名要求，不能当作新正常恢复入口或照抄用于当前实例。历史一次性维护证据继续保留，不把已消费授权用于本方案。

## 10. 验收不变量与交付门禁

| 不变量 | 必须取得的证据 |
| --- | --- |
| 单个有效控制执行者 | 原升级与恢复互斥，controlEpoch单调；旧控制者恢复、排队命令迟到、回执乱序均无越权效果 |
| 单个业务writer | 任意交接／恢复断点，业务库同事务holder／generation／fence守卫成立；不出现跨库先查后写替代保护 |
| 原资源不被部署结束 | 原Guest／provider handle／Owner home／boot／PTY／job及执行轮次保持；无stop／destroy／cancel／重放初始指令 |
| 已提交业务事实不倒退 | 新写入、取消、tombstone、幂等结果、occurrence、日志seq／cursor和迁移checkpoint保持；没有活动卷快照覆盖 |
| 路由恢复不依赖旧attempt存活 | old attempt failed且lease过期、业务读取慢或执行器退出时，新RecoveryIntent仍可在稳定系统取得权限并完成合格退流 |
| unknown可核验而非重放 | 每个执行断点均按父operation与精确commandId查询；接管不更换副作用spec或暗延预算，applied不重复执行，未能证明结果时blocked并保留现场 |
| 恢复确认不伪造升级成功 | 原失败／原100历史不变；containment、recovery、目标激活与页面身份分别记录 |
| 清理有边界 | 已引用候选、原Owner、保留Guest和回退锚点不被退役；准备与清理资源有上界且有真实回执 |

独立测试至少覆盖准备、每档灰度、Coordinator release前后／adopt前后、Web切换、激活提交及保留期的故障。每个动作还要覆盖：effect前崩溃、effect后receipt前崩溃、控制进程重启、迟到请求、响应丢失、control.db写入失败、业务锁占用、数据epoch变化、回退目标不兼容或丢失、无容量、旧Web B仍打开、活跃WS和真实输出继续。

资格必须在与来源版本、既有混合组合、历史数据量、多代角色和活跃任务同构的隔离环境取得。控制器崩溃后续同一recovery的验收，与用户再次发起新升级的验收分开；失败恢复不重新下载／执行原用户命令。前端状态、后端协议、真实Native窗口和外部观测分别取证，任何已有超时不归零覆盖。

本文完成只表示方案已记录。现有`.18`成功、`.19`四次失败、`.20`一次失败及原Guest保持的证据继续按原范围成立；它们不自动授予本方案新的实现或上线资格。
