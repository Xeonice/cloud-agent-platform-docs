# 失败升级的签名路由维护恢复

当实例升级已经失败、Entry 停在部分流量比例，且自动回退没有取得完整资格时，实例可能保持业务可用但显示“升级未确认”。现有普通升级协议不会把这类状态推测成健康版本，也不会重用过期的 Controller 租约。

`deploy/ops/recover-failed-source-route.mjs` 提供单独的管理员维护入口。它需要实例已经信任的发布者签署一份独立维护授权，不能只凭内部 API 密钥执行。此操作把新 HTTP 请求切回已经确认版本的原 API 端点，保留现有 Coordinator、RuntimeOwner、Web、Installer、数据库和已经建立的连接。它不会完成整个版本回退，也不会把失败的升级改成成功。

## 授权和执行范围

授权固定 `purpose=operator-maintenance`、`action=recover-failed-source-route`，并包含实例、channel、实例根目录、Foundation 容器完整 ID、失败 attempt、原序号和 fence、实例 generation、attempt generation、schema28、Entry binding/admission 摘要、已确认原 API 的完整身份、当前唯一 Coordinator writer 和原 Guest 身份证明。目标只能是相同原 API 端点的 `weight=0`。

授权最多有效五分钟，每次维护使用新的 operationId 和 controllerId。新 fence 必须大于数据库全部升级 fence、contract fence 和当前 Entry admission fence；维护租约最多 120 秒。授权中的签名不能用于任意 SQL、任意路由、停止任务、重建 Guest 或修改数据库 schema。

执行前保存不可覆盖的签名授权、实际 before proof 和预计控制字段变更，目录权限 0700，文件权限 0600。随后在 `BEGIN IMMEDIATE` 获锁后再次验证授权时间、刚取得的源进程身份、实例/attempt/路由/Owner/writer 状态。维护只修改失败 attempt 的三个控制字段：`controller_id`、`fence`、`lease_expires_at`。这些字段承载新的管理员维护授权；它们不表示原 Controller 获得续租。

工具使用现有 Coordinator 的 `checkOnly` 验证新 fence，再调用经过认证的 Entry `/fence` 和 `/binding`。路由 generation 增加一，原 API 端点保持不变，weight 从部分流量降为零。原失败 state、序号、generation、ready、confirmed release、schema 和业务表均保持原值。维护结束只释放本次拥有的租约，新的高 fence 保留。

昂贵的原包完整树验签在申请维护权限之前完成。源 API 和 Coordinator 的实际进程身份在这之后、取得维护权限之前、以及两次 Entry 写入之前分别重新检查，整个身份请求窗口不得超过两秒。源包还必须通过 API/Web/Installer 内容摘要及 Coordinator/Owner 与 API 内容关系验证。新建登录会话仅记录 `sourceAuthenticationWorking`，表示原 API 当前可以认证；旧浏览器 Cookie 是否续接由后续浏览器检查单独验证，工具不会声称已经证明旧 Cookie 连续性。原 Guest 通过原 Owner 的只读文件接口验证 boot ID、内核和 init 进程出生时间，不使用 SDK 停止或重建资源。

## 审阅和运行

由操作员在实例外使用已信任发布者私钥调用模块导出的 `signOperatorRecovery(plan, keyId, privatePem)`。私钥不进入实例，不在日志或聊天中展示。运行前必须由外部 Docker wrapper 核对实际执行容器的完整 ID 等于授权指定的 Foundation ID，同时固定本次已审阅工具及依赖字节。只比较配置文件中的容器 ID 不足以证明实际执行容器身份。

在该 Foundation 内运行：

```sh
node /reviewed-tool/deploy/ops/recover-failed-source-route.mjs preflight /exact/instance /private/authorization.json
node /reviewed-tool/deploy/ops/recover-failed-source-route.mjs apply /exact/instance /private/authorization.json
node /reviewed-tool/deploy/ops/recover-failed-source-route.mjs inspect /exact/instance OPERATION_UUID
```

`preflight` 只读。`apply` 需要完整签名授权，操作目录位于实例根目录下的 `operator-maintenance/OPERATION_UUID/`。遇到进程身份变化、签名过期、该实例任何其他 active attempt 或尚未到期的 Controller 租约、schema 变化或临界 handoff/recovery 时拒绝执行。维护重入只接受本次 operation 的精确 controller/fence/lease 元组。服务的 `/data/platform.db` 与实例目录的 `business/platform.db` 必须具有相同 dev/inode，复制出来的相同内容文件也会被拒绝。已经写入新 admission 后进程中断，同一份仍有效授权可以依据不可变收据和原维护租约核对后继续；不会延长租约。租约已过期或结果无法确认时，只能 inspect 并重新审阅新的维护授权。

维护结果明确记录 `manualMaintenance` 和 `automaticFallbackQualified=false`。它不生成正式发版 rehearsal 或 readiness 证明。后续仍需普通用户升级 API，以新的 requestId 和实测 `repairableCurrent` 发起签名修复包升级，保留原失败 attempt 的全部历史。

实例 generation 与 attempt generation 分开核对。例如实例仍为 generation3，但失败 attempt 已经占用 generation4，下一次普通升级可能接受 generation5；工具不能假定成功后只是原 generation 加一，更不能修改 generation 迁就验收脚本。

## 验证边界

测试使用独立临时 SQLite、真实 Stable Entry HTTP 服务和原始 WebSocket，验证签名/过期/竞争拒绝、三个控制字段的限定范围、原 WebSocket 在切换后保持、崩溃重入及租约不延长。HTTP double 检查实际源进程 incarnation、writer 标志和两秒请求预算。这些测试不声称完成真实 Guest、模型调用或正式发版资格；线上执行仍需对应实例的前后资源证明和实际健康观察。
