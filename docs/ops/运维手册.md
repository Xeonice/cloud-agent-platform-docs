# 运维手册

- **读者**：负责 Mac mini 的运维人员（维护者）。
- **用途与边界**：计划内维护与服务故障排查。不含发版与发布卡住（见 [发版手册](./发版手册.md)），不含备份、恢复与重建（见 [灾备与重建](./灾备与重建.md)）；端口、卷、凭据位置等数值只在 [参考表](./参考表.md)。
- **权威范围**：进入与退出维护（quietDown）的步骤、VM 的重启与停机方式、Lima override 修改流程、日常巡检、容量与清理、内存预算、凭据同步与轮换步骤、排查树、只读诊断方法。
- **适用基线**：v0.3.6（主仓 `7eb7176`）起。

## 0. 操作前提

- 以[运维账号](./README.md#术语表)操作：拥有私有目录与三个 Colima socket 的普通账号（不是 root，UID ≥ 501，名称不以 `_` 开头）。仓库工具从系统账户库推导它的 HOME 与 UID，不读 `$HOME`、`$USER` 等环境变量（参考表 §12）。只有标了 `sudo` 的命令需要管理员权限。新运维的接入方式（账号与远程登录）向维护者申请，见[运维记录](./运维记录.md) §3 的 T23。宿主软件与版本见参考表 §8。
- 第一次在某台机器或某个账号上操作前，先跑下面的宿主自检，期望 `"state":"doctor-passed"`；有 `fail` 时按失败项的 `code` 查参考表 §12.6。
- 生产命令一律用参考表 §0 的 `dk <jenkins|build|runtime>`、`$NODE22` 与 `jstatus`。Mac 默认的 docker context 是开发用的 OrbStack，裸 `docker` 看不到生产容器。
- `colima` 命令要带私有 `DOCKER_CONFIG`（见下），否则会在默认的 `~/.docker` 里新建 context；也不要设置指向别处的 `COLIMA_HOME`，操作 VM 的仓库工具遇到它会拒绝运行。`$SRC`、`$P` 的约定见发版手册 §0。
- 文中的“私有笔记”见[术语表](./README.md#术语表)；尚未整理成文前，向维护者索取。

```sh
# Mac：本手册里的 colima 命令都假定当前终端已执行这一行
export DOCKER_CONFIG="$HOME/.local/share/agent-platform-jenkins-tools/container-docker-context"
```

```sh
# Mac，仓库根目录，Node 22：宿主自检（只读）；各阶段的含义与本机期望输出见参考表 §12.5
"$NODE22" deploy/containers/host-layout.mjs doctor | jq -c '{state, counts}'
```

### 进入与退出维护

重启 VM、升级 agent、修文件系统、冷启动演练等会中断 Jenkins 的操作，都先进入维护、结束后退出。顺序不能反：release、api、web 作业会等待子作业，[quietDown](./README.md#术语表) 期间子作业不会启动，父作业会挂到超时（release 为 4 小时）。

```sh
# Mac，$SRC，Node 22。进入维护：逐行核对期望输出，不符就停
for j in agent-platform-release agent-platform-ci-discovery agent-platform-service-monitor; do "$NODE22" deploy/jenkins/manage.mjs disable "$j"; done   # 期望三行 disable: <作业>
"$NODE22" deploy/jenkins/manage.mjs wait-idle     # 期望 "state":"idle"；有发布在跑时加 --timeout 14400
"$NODE22" deploy/jenkins/manage.mjs quiet-down    # 期望 "quietingDown":true
```

```sh
# Mac，$SRC，Node 22。退出维护
"$NODE22" deploy/jenkins/manage.mjs cancel-quiet-down   # 期望 "quietingDown":false
for j in agent-platform-service-monitor agent-platform-ci-discovery agent-platform-release; do "$NODE22" deploy/jenkins/manage.mjs enable "$j"; done
jstatus   # 正常输出见参考表 §0
```

- 停用 service-monitor 是为了不让它的定时构建在 quietDown 期间排进队列；升级脚本要求队列为空。
- `quiet-down` 报 `quietDown was not sent: …` 时，按提示补齐停用或再 `wait-idle`。放弃维护时直接执行退出维护。
- `manage.mjs` 是止损入口，只依赖运行账号、私有目录与 `admin-api.json`。它在发凭据前确认 `127.0.0.1:8080` 的监听进程属于运维账号，否则拒绝（`HL_JENKINS_LISTENER`）。它被拒或运行不了时，在 Jenkins 页面停用作业，用“准备关闭”（Prepare for shutdown）代替 `quiet-down`。

## 2. 日常巡检

建议每天一次，发版前再做一次。

```sh
# Mac，$SRC，Node 22，已按 §0 导出 DOCKER_CONFIG
jstatus                                                    # quietingDown、作业颜色、节点在线
curl -fsS https://agent-api.douglasdong.com/api/health; echo
df -h /System/Volumes/Data; du -sh "$HOME"/.colima/_lima/_disks/*
for p in jenkins build runtime; do colima ssh --profile agent-platform-$p -- df -h /var/lib/docker; done
memory_pressure | tail -n 1; sysctl kern.memorystatus_vm_pressure_level vm.swapusage
diff -q deploy/host/lima-override.yaml "$HOME/.colima/_lima/_config/override.yaml"   # 无输出即与仓库一致
"$NODE22" deploy/containers/host-layout.mjs doctor | jq -c '{state, counts}'   # 宿主自检，期望 doctor-passed
```

| 看什么 | 正常 | 不正常时 |
|---|---|---|
| 宿主自检 | `doctor-passed`；warn 的含义见参考表 §12.5 | 按失败项的 `code` 查参考表 §12.6 |
| `agent-platform-service-monitor` | 蓝色（`blue`） | 黄色：runtime 容器或 API 不健康，按 §8 排查；红色：快照采集失败 |
| `agent-platform-release` | 蓝色 | 黄色：在等空闲或待审阅；红色：失败。见发版手册 §7 |
| `agent-platform-ci-discovery` | 蓝色 | 红色：release 停用期间的 `Discovery HTTP 409` 属预期，其他多为网络问题 |
| 节点 `linux-ci`、`linux-web-amd64`、`linux-deploy` | 在线 | 查对应 VM 与容器（§8） |
| 磁盘、内存 | 低于 §5、§6 的阈值 | 按 §5、§6 处理 |

- `mac-ci`、`mac-deploy` 与 Built-In Node 离线属预期（参考表 §11）。
- 作业描述（如 monitor 的 `Runtime snapshot N · healthy`）不在 `status` 里，要用 `"$NODE22" deploy/jenkins/manage.mjs build-status <作业> <构建号>` 或 Jenkins 页面查看；构建号取 `status` 里的 `lastBuild.number`。
- 监控盲区：没有任何告警通知；monitor、discovery、release 都跑在 runtime VM 的[可信 deploy agent](./README.md#术语表)上，runtime 挂了监控也一起停，所以公网 health 要从外部看。

## 3. 重启或停机一台 VM

- **适用场景**：让 override 生效、改 VM 规格、VM 异常。
- **影响**：runtime 停机等于生产 API、Tunnel、DNS 与 deploy agent 全停；jenkins 停机会中断全部作业，期间 build VM 无法解析域名（已知缺陷，见[运维记录](./运维记录.md) §3 的 T2）；build 停机只中断 CI。
- **前置条件**：按 §0 进入维护。重启 runtime 还要[生产空闲](./README.md#术语表)：把 §9 第一条命令的输出接到 `| jq '.ready and ([.blockers[]] | add) == 0 and .inFlightHTTP == 0 and .credentialAuth == 0'`，为 `true` 才停机。手工重启不经过维护屏障，判定之后新建的任务会被直接中断，所以提前通知用户、判定后立即停机。

```sh
# Mac，已按 §0 导出 DOCKER_CONFIG
p=""   # 必填：jenkins、build 或 runtime
test -n "$p" && colima --profile "agent-platform-$p" stop
pgrep -fl "agent-platform-$p start --foreground" && pkill -f "agent-platform-$p start --foreground"
# launchd 约 1 分钟内按原参数拉起。有管理员权限时，也可以不做上面两步，改用（仓库根目录；Label 取自宿主布局）：
#   L=$("$NODE22" deploy/containers/host-layout.mjs print | jq -r --arg p "$p" '.profiles[$p].label'); sudo launchctl kickstart -k "system/$L"
```

- 只 `colima stop` 而不结束前台进程，launchd 会认为任务仍在运行，不会拉起 VM。不要手动 `colima start` 或 `limactl start`。
- 要让 VM 保持停机（改磁盘或规格），stop 之后执行 `sudo launchctl bootout system/<Label>`；恢复用 `sudo launchctl bootstrap system /Library/LaunchDaemons/<Label>.plist`。`bootout` 只管到下次开机，要跨重启保持停机再加 `sudo launchctl disable system/<Label>`（恢复时先 `enable`）。Label 的规则见参考表 §8，本机的值用上面的 `print` 读取。
- **验证**：`colima list` 为 Running；`"$NODE22" deploy/containers/host-layout.mjs doctor --stage launchd` 为 `doctor-passed`（含三个 socket、daemon 名与 LaunchDaemon 状态）；`dk <p> ps` 里容器为 Up，带健康检查的为 healthy；`jstatus` 三节点在线；`grep -c Mixing "$HOME/.colima/_lima/colima-agent-platform-<p>/ha.stderr.log"` 至少为 1；`lsof -nP -iTCP -sTCP:LISTEN | grep -E ':(3101|20241|53) '` 无输出。之后按 §0 退出维护。
- **回退**：3 分钟内没有拉起，看 `$P/container-boot/logs/agent-platform-<p>.log` 与 `ha.stderr.log`，按 §8 的第 5 层排查。

## 4. 修改 Lima override

- **适用场景**：改 [Lima override](./README.md#术语表) 的转发规则（规则原因见[生产架构](./生产架构.md) §6）。
- **影响**：文件写坏会让所有 VM 都起不来；改动要等各 VM 下次启动才生效。
- **前置条件**：改动在主仓 PR 里审阅。合并前在 PR 分支的工作区先做第 1、2 步；合并（会触发一次发版，宜与其他主仓改动同批）后，在按发版手册 §0 新准备的 `$SRC` 里从第 1 步再做一遍。

```sh
# Mac，PR 分支工作区或 $SRC 的仓库根目录。1 线上与新模板的差异应只有本次 PR 的改动
diff -u "$HOME/.colima/_lima/_config/override.yaml" deploy/host/lima-override.yaml
# 2 在临时 LIMA_HOME 里对三台校验，三台都输出 OK 才继续
T=$(mktemp -d); mkdir "$T/_config"; cp deploy/host/lima-override.yaml "$T/_config/override.yaml"
for p in jenkins build runtime; do LIMA_HOME="$T" limactl validate "$HOME/.colima/_lima/colima-agent-platform-$p/lima.yaml"; done; rm -rf "$T"
# 3（只在 $SRC）备份后在同一目录内原子替换；子 shell 执行，不改变当前目录
(cd "$HOME/.colima/_lima/_config" && cp -p override.yaml "override.yaml.bak-$(date +%Y%m%d%H%M)" && cp "$SRC/deploy/host/lima-override.yaml" override.yaml.new && mv override.yaml.new override.yaml)
```

- 4：按 §3 逐台重启，每台都核对后再动下一台。
- **验证**：每台的 `ha.stderr.log` 有 `Mixing`；VM 内有与新规则匹配的监听时，还有对应的 `Not forwarding …` 记录。Mac 上没有 3101、20241、`*:53` 与 VM 随机端口的监听；`http://127.0.0.1:8080/` 仍可访问。
- **回退**：用 `.bak-*` 文件同样原子换回，再逐台重启。

## 5. 容量与清理

宿主可用空间低于 60 GiB，或任一 VM 的 `/var/lib/docker` 使用率超过 80%，就清理（巡检命令见 §2）。三台 VM 的虚拟盘上限合计超过宿主剩余空间，宿主写满会让 VM 的 ext4 出错。备份与发布缓存都没有自动保留策略，只能按下表人工清理（运维记录 T6、T28）。

先看每台的 `dk <p> system df`，以 RECLAIMABLE 列判断能腾出多少。旧 API 与 deploy 镜像大多共享层，删掉几乎不释放空间；占空间的主要是 build VM 的构建缓存、deploy-state 卷里的发布缓存和备份卷。

**禁止**：在任何 VM 上执行 prune 类命令（下表的 `builder prune` 除外）。

- `docker volume prune -a`：删除所有没有容器挂载的具名卷，备份卷平时就没有挂载。
- `docker image prune`、`docker system prune`：删除没有标签的镜像。runtime 上的旧 deploy 镜像经 save/load 传入、没有标签，发版手册 §4 的回退要用它们。
- 加 `-a` 时还会删除 `releases/` 仍在引用的 API 镜像，之后同一组合的 API 构建每轮失败。

| 顺序 | 可以清理 | 怎么做 | 注意 |
|---|---|---|---|
| 1 | build VM 构建缓存（通常最多） | `dk build builder prune -af` | 没有构建运行时执行；之后的首次构建变慢 |
| 2 | 旧发布缓存 | 见下方命令 | 先停用 release 并 `wait-idle` |
| 3 | 旧数据备份 | 先按灾备与重建 §2 离机导出，再删旧文件 | 至少保留最近 2 份 |
| 4 | runtime VM 构建缓存 | `dk runtime builder prune -af` | 同 1 |
| 5 | VM 内已释放的块 | `colima ssh --profile agent-platform-<p> -- sudo fstrim -av` | 删除后执行，把空间还给宿主 |
| — | 旧 API 镜像 | `dk runtime image rm agent-platform-api:<ROOT>-<API>` | 几乎不释放空间；只删已没有对应 `releases/` 目录的 |

```sh
# Mac：发布缓存在 deploy-state 卷。保留：线上 API 对应的 releases/<ROOT>-<API>、当前发布记录 key 对应的
# project-releases/<key> 与 web-releases/<key>、各目录里最新的一项（可能是待发布的组合）；其余可删
live=$(dk runtime inspect --format '{{index .Config.Labels "com.agent-platform.root-sha"}}-{{index .Config.Labels "com.agent-platform.api-sha"}}' agent-platform-api)
key=$(dk runtime exec agent-platform-linux-deploy cat /srv/agent-platform/deploy/project-release-current.json | jq -r .key)
dk runtime exec agent-platform-linux-deploy sh -c 'cd /srv/agent-platform/deploy && ls -t releases project-releases web-releases'
d=""   # 必填：要删的一项，如 releases/<ROOT>-<API>；逐个删除。格式不符或是线上在用的项时不执行
[ -n "$live" ] && [ -n "$key" ] && case "$d" in "releases/$live"|*"-releases/$key") echo "in use, refused" ;; *) printf '%s\n' "$d" | grep -Eqx 'releases/[0-9a-f]{40}-[0-9a-f]{40}|(project|web)-releases/[0-9a-f]{64}' && dk runtime exec agent-platform-linux-deploy rm -rf "/srv/agent-platform/deploy/$d" ;; esac
# 旧数据备份：文件属 root，用临时容器列出和删除
IMG=$(dk runtime inspect --format '{{.Image}}' agent-platform-linux-deploy)
dk runtime run --rm --network none --user 0:0 --entrypoint ls --mount type=volume,source=agent-platform-runtime-backups,target=/b "$IMG" -lt /b
name=""   # 必填：要删的备份文件名
test -n "$name" && dk runtime run --rm --network none --user 0:0 --entrypoint rm --mount type=volume,source=agent-platform-runtime-backups,target=/b "$IMG" "/b/$name"
```

VM 数据盘出错（VM 内 `dmesg` 有 `EXT4-fs error` 或 `Aborting journal`，或 `/var/lib/docker` 变成只读）时，先在宿主腾出空间，再修复文件系统。停 Docker、卸载数据盘、`e2fsck` 的做法曾用于 jenkins VM。

```sh
# Mac：p 为出错的 VM（jenkins、build 或 runtime）；jenkins 或 build 出错时先按 §0 进入维护
colima ssh --profile "agent-platform-$p" -- sudo sh -c 'systemctl stop docker.socket docker containerd; findmnt -rn -S /dev/vdb1 -o TARGET | xargs -r -n1 umount; e2fsck -fy /dev/vdb1'
```

然后按 §3 重启该 VM。

## 6. 内存

- 预算：三台 VM 固定占 28 GiB（VZ 不把客体用过的内存还给宿主），宿主上的其他常驻负载要一起算进总量。VM 规格见参考表 §8，各容器的内存上限见[生产架构](./生产架构.md) §2。
- 巡检：宿主 `sysctl kern.memorystatus_vm_pressure_level`（1 正常、2 告警、4 严重）、`memory_pressure | tail -n 1`、`sysctl vm.swapusage`；VM 内 `colima ssh --profile agent-platform-<p> -- free -m`。压力等级持续为 2 及以上，就按下面的顺序降压。
- 降压顺序：先停宿主上非必需的大内存进程（哪些可停见私有笔记）；再让 build VM 保持停机（只影响 CI，按 §3）；最后缩小 build VM 的内存。runtime 不要低于 16 GiB，API 容器上限就有 14 GiB。
- 改规格：编辑 `$HOME/.colima/agent-platform-<p>/colima.yaml` 的 `cpu` 或 `memory`，按 §3 重启。LaunchDaemon 以 `--save-config=false` 启动，规格只以该文件为准；下次重装 LaunchDaemon 前要重新运行 `bootstrap-host.mjs prepare`（它记录了文件哈希，过期时 doctor 的 `bootReview` 会给出警告）。
- 不要把 `mounts` 改回默认值，默认会把 `$HOME` 可写挂进 VM；改完核对 `$HOME/.colima/_lima/colima-agent-platform-<p>/lima.yaml` 里没有 `mounts` 段。

## 7. 凭据同步与轮换

各凭据的用途、读取方、位置与权限见参考表 §6；本节只写操作。[私有目录](./README.md#术语表)（`$P`）里的一份是生成工具写入的源副本，生产作业读的是 runtime VM 卷里的副本：改了 Mac 上的文件，必须同步进卷才生效。

### 7.1 通用写法

```sh
# Mac：把私有目录里的文件同步进 deploy-private 卷（容器内属主 1000、权限 0600），再比对两边的哈希
f=github-token   # 换成要同步的文件名，如 ghcr-token、admin-api.json、github-status-app.pem
dk runtime exec -i agent-platform-linux-deploy sh -c "umask 077; cd /run/agent-platform/jenkins-tools && cat > $f.tmp && mv $f.tmp $f" < "$P/$f"
shasum -a 256 "$P/$f"; dk runtime exec agent-platform-linux-deploy sha256sum "/run/agent-platform/jenkins-tools/$f"
# 写入只读挂载的卷（api-secrets、tunnel-secrets，文件属 root、0600）：用临时容器从标准输入写
vol=agent-platform-tunnel-secrets; name=tunnel.token; src=/path/to/source   # 换成实际的卷、文件名与源文件
IMG=$(dk runtime inspect --format '{{.Image}}' agent-platform-linux-deploy)
dk runtime run --rm -i --network none --user 0:0 --entrypoint sh --mount "type=volume,source=$vol,target=/s" "$IMG" -c "umask 077; cat > /s/$name.tmp && mv /s/$name.tmp /s/$name" < "$src"
```

### 7.2 两份 runtime.env（含访问口令、cookie 密钥与 cgroup 开关）

- **适用场景**：改 `runtime.env` 的任一键：轮换 `ACCESS_PASSCODE`、`PASSCODE_COOKIE_SECRET`，或加一行 `API_CGROUP_DELEGATION=off` 关闭 cgroup 委派（不要回退代码，原因见生产架构 §6）。
- **影响**：重启 API 才生效，生产中断约 1–2 分钟，正在运行的任务会中断。改 cookie 密钥会让所有浏览器重新输入口令；生产固定了口令，Web 里“重新生成口令”会被拒绝，只能走本流程。
- **前置条件**：在 `$SRC` 执行；`"$NODE22" deploy/jenkins/manage.mjs disable agent-platform-release` 已停用发布；生产空闲（判定方法同 §3）。必需键与固定取值见 [runtime.env 模板](../../deploy/containers/env/runtime.env.example)。`HOST`、`PORT`、`API_ALLOWED_ORIGINS` 等键只从这份文件读入，写错会在重启后立即生效，所以写入前先用发布工具的同一规则校验。

```sh
# Mac，$SRC，Node 22。1 在私有临时目录里改，内容不要打印到终端
umask 077; T=$(mktemp -d); IMG=$(dk runtime inspect --format '{{.Image}}' agent-platform-linux-deploy)
dk runtime exec agent-platform-linux-deploy cat /srv/agent-platform/deploy/runtime.env > "$T/runtime.env"
cp "$T/runtime.env" "$T/runtime.env.orig"
"${EDITOR:-vi}" "$T/runtime.env"    # 新口令可用 openssl rand -hex 16，cookie 密钥可用 openssl rand -hex 32
# 2 校验，期望 runtime.env policy ok；报错就回到第 1 步修改
"$NODE22" --input-type=module -e 'import { runtimePolicy } from "./deploy/containers/api-container.mjs"; import { readFileSync } from "node:fs"; runtimePolicy(readFileSync(process.argv[1], "utf8")); console.log("runtime.env policy ok")' "$T/runtime.env"
# 3 写入两份
dk runtime exec -i agent-platform-linux-deploy sh -c 'umask 077; cd /srv/agent-platform/deploy && cat > runtime.env.tmp && mv runtime.env.tmp runtime.env' < "$T/runtime.env"
dk runtime run --rm -i --network none --user 0:0 --entrypoint sh --mount type=volume,source=agent-platform-api-secrets,target=/s "$IMG" -c 'umask 077; cat > /s/runtime.env.tmp && mv /s/runtime.env.tmp /s/runtime.env' < "$T/runtime.env"
# 4 三个哈希都相同才重启，期望先输出 three copies match
a=$(shasum -a 256 < "$T/runtime.env" | cut -d' ' -f1)
b=$(dk runtime exec agent-platform-linux-deploy sha256sum /srv/agent-platform/deploy/runtime.env | cut -d' ' -f1)
c=$(dk runtime run --rm --network none --user 0:0 --entrypoint sha256sum --mount type=volume,source=agent-platform-api-secrets,target=/s,readonly "$IMG" /s/runtime.env | cut -d' ' -f1)
[ "$a" = "$b" ] && [ "$a" = "$c" ] && echo "three copies match" && dk runtime restart agent-platform-api
```

- **验证**：`dk runtime inspect --format '{{.State.Health.Status}}' agent-platform-api` 回到 healthy；公网 health 为 200；用新口令能登录 Web。关闭委派时，`dk runtime logs agent-platform-api 2>&1 | grep cgroup-delegation` 显示 `status=skipped reason=disabled`。最后 `rm -rf "$T"`，新口令经私密渠道告知用户，再执行 `"$NODE22" deploy/jenkins/manage.mjs enable agent-platform-release`。
- **回退**：`cp "$T/runtime.env.orig" "$T/runtime.env"`，再按第 3、4 步写回两份并重启 API，然后同样启用 release。两份不一致时，之后的每次发布都会报 `API secret volume differs from the verified deployment runtime`。

注：
1. `github-token` 所需最小权限：三仓 Contents 与 Pull requests 只读，主仓 Contents 读写（创建 Release）。GitHub App 不可用时，发现作业改用它回写状态，需要三仓 Commit statuses 写；这样写入的状态不满足分支保护（必需状态绑定 App 5204009），不授予时 App 失效期间发现作业每轮报错。
2. Jenkins Home 的 `bootstrap-secrets/admin-login.json` 也存着一份口令，只在初始化空 Home 时读取；改口令后它仍是旧值，需要时一并更新或删除。
3. 在 Cloudflare One 控制台的 Networks → Tunnels 里选中该隧道，用控制台的刷新 token 操作生成新 token（入口以当前界面为准），复制到剪贴板后执行下方命令。

不要重新注册 GitHub App：新 App 的 ID 与分支保护绑定的 5204009 不符（参考表 §9）。

# Mac：Vercel 重新登录（交互），收紧权限后用 whoami 验证

## 8. 服务不可用排查树

公网打不开时从外往里查，每层正常再看下一层。

1. **公网**：`curl -sS -o /dev/null -w '%{http_code}\n' https://agent-api.douglasdong.com/api/health`。200 正常；530（Cloudflare 1033）多为 Tunnel 没连上，看第 2 层；502 为源站不通，看第 3 层。
2. **Tunnel 与 DNS**：`dk runtime ps -a --filter name=agent-platform-tunnel --filter name=agent-platform-dns`，再看 `dk runtime logs --tail 50 agent-platform-tunnel`。正常应有 `Registered tunnel connection`；启动时一条 `No ingress rules…` 加 503 属正常，随后会收到远程配置。DNS 不是 healthy 时 Tunnel 解析不了 Cloudflare。
3. **API 容器**：`dk runtime ps -a --filter name=agent-platform-api` 应为 Up（healthy）；再看 `dk runtime logs --tail 100 agent-platform-api`。容器不存在时多半是部署中断，按发版手册 §7.2 处理；反复重启时看日志与 §5 的磁盘。
4. **runtime VM**：`colima list` 为 Running，`dk runtime info --format '{{.Name}}'` 返回 `colima-agent-platform-runtime`。socket 连不上时看第 5 层。
5. **launchd 与 Colima**：仓库根目录运行 `"$NODE22" deploy/containers/host-layout.mjs doctor --stage launchd`，`launchd:runtime` 应为 `ok`（`bytes and fields match; running`）；也可以 `launchctl print "system/<runtime 的 Label>" | grep -E 'state|pid'`（Label 取自 `host-layout.mjs print`）。再看 `$P/container-boot/logs/agent-platform-runtime.log` 与 `ha.stderr.log`。`docker not found` 表示 Homebrew 的 docker CLI 缺失（doctor 的 `homebrewDocker` 项同样会失败）；磁盘满按 §5。

Jenkins 打不开：Mac 上 `curl -sS -o /dev/null -w '%{http_code}\n' http://127.0.0.1:8080/login` 为 200 时，问题在 Access 或 Tunnel（按上面第 2 层）。不是 200 就看 `dk jenkins ps -a` 与 `dk jenkins logs --tail 100 agent-platform-jenkins-controller-controller-1`：controller 不健康多为插件锁或模式问题，`CONTROLLER_MODE` 必须为 `active`（参考表 §7）。

## 9. 只读诊断

受保护接口要带口令。`docker exec` 起的进程拿不到入口脚本加载的口令，所以先在进程内 `loadEnvFile`，再用 Bearer 调用，只打印结果。

```sh
# Mac：生产的部署状态（字段口径见 10 §6.6.2）
dk runtime exec agent-platform-api node -e 'process.loadEnvFile("/run/secrets/runtime.env");
fetch("http://127.0.0.1:3101/api/deployment/status", { headers: { authorization: "Bearer " + process.env.ACCESS_PASSCODE } })
  .then((r) => r.json()).then((v) => console.log(JSON.stringify(v, null, 2)));'
```

接口的 `idle` 把浏览器连接（`activeWS`）也算作忙，发布工具不看它：`ready` 为 true、`blockers` 全为 0、`inFlightHTTP` 与 `credentialAuth` 为 0 时，即使 `idle` 为 false 也能替换。`ready` 为 false 时看 `readiness` 里哪一项为 false：`database`、`provider` 看 API 日志，`image` 看 Web 的镜像管理页。

在 Web 上停任务、暂停自动化要用生产访问口令。维护者可用下面的命令把它放进剪贴板，不在终端显示；用完清空。

```sh
# Mac：生产访问口令进剪贴板（不回显），用完执行 pbcopy < /dev/null
dk runtime exec agent-platform-linux-deploy sed -n 's/^ACCESS_PASSCODE=//p' /srv/agent-platform/deploy/runtime.env | tr -d '\n' | pbcopy
```

[停止名额](./README.md#术语表)探针：只在 `resourceAllocations` 大于 0 时有意义（为 0 时也会报不可用）。它与发布工具用的是同一段代码，在 API 容器里只读运行。

```sh
# Mac，$SRC，Node 22
probe=$("$NODE22" --input-type=module -e 'import { STOPPED_RESERVATIONS_PROBE as p } from "./deploy/containers/api-container.mjs"; process.stdout.write(p)')
dk runtime exec agent-platform-api node -e "$probe"
```

输出 `{"stoppedReservations":N}` 且 N 等于 `resourceAllocations` 为通过；报 `Stopped reservation proof unavailable` 为判忙，接着查 [auth helper](./README.md#术语表)。helper 的 box 名为 `platform-boxlite-6f5caf0e18c363f1-auth-helper`：中间 16 位是字符串 `/data/platform.db` 的 sha256 前缀，哈希的是路径，不是文件内容。

```sh
# Mac：只读查 helper 的 BoxLite 记录，再看 shim 进程是否存活（<id> 取上一条输出的 id）
dk runtime exec agent-platform-api node -e 'const { DatabaseSync } = require("node:sqlite");
const db = new DatabaseSync("/data/boxlite/db/boxlite.db", { readOnly: true }); db.exec("PRAGMA query_only=ON");
const sql = "SELECT c.id, c.name, s.status, s.pid FROM box_config c LEFT JOIN box_state s ON s.id = c.id WHERE c.name LIKE ?";
console.log(JSON.stringify(db.prepare(sql).all("%-auth-helper"))); db.close();'
dk runtime exec agent-platform-api sh -c 'p=$(head -n1 /data/boxlite/boxes/<id>/shim.pid); test -d /proc/$p && echo alive || echo dead'
```

- 正常：恰好一条、`status` 为 `running`、shim 进程存活。记录为 running 而进程已死，或为 `failed` 却还留着 `shim.pid`，就是失效。
- 平台没有后台自愈：在 Web 上发起一次帐号登录并立即取消，触发重建（发版手册 §7.1）。helper 的设计与生命周期见 [11 §1.1](../shared/11-部署与扩展预留.md)。
- 每次 api、release、service-monitor 构建都有 `Service status and logs` 页面，保存当次的容器状态、部署状态与脱敏日志，可作为事后诊断的依据。
