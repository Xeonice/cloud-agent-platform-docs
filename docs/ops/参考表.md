## 0. 命令模板

本目录所有命令都假定已定义下面三项。命令块第一行注释写执行位置。

```sh
# Mac，任意目录：加入当前 shell 或 ~/.zshrc。NODE22 可指向任意 Node 22（推荐与 CI 一致的 22.23.3，用 fnm 安装）；
# 仓库工具用运行它的那个 Node，不依赖这个位置
export NODE22="$HOME/.local/share/fnm/node-versions/v22.23.3/installation/bin/node"
dk() {
  local profile="$1"; shift
  DOCKER_CONFIG="$HOME/.local/share/agent-platform-jenkins-tools/container-docker-context" \
    docker --host "unix://$HOME/.colima/agent-platform-$profile/docker.sock" "$@"
}
# 精简的 Jenkins 状态：quietingDown、作业颜色、节点在线；在仓库根目录执行
jstatus() {
  "$NODE22" deploy/jenkins/manage.mjs status | jq -c '{quietingDown: .controller.quietingDown,
    jobs: [.controller.jobs[] | "\(.name)=\(.color)"],
    nodes: [.computers.computer[] | "\(.displayName)=\(if .offline then "offline" else "online" end)"]}'
}
```

| 写法                 | 连接的 Docker                     | 例子                                            |
| -------------------- | --------------------------------- | ----------------------------------------------- |
| `dk jenkins …`       | jenkins VM（controller）          | `dk jenkins ps`                                 |
| `dk build …`         | build VM（两个 CI agent）         | `dk build system df`                            |
| `dk runtime …`       | runtime VM（生产 API 与发布）     | `dk runtime logs --tail 100 agent-platform-api` |

注：
- Mac 的默认 docker context 是 `orbstack`（开发用）。裸 `docker` 看不到生产容器，OrbStack 未运行时直接报连接失败。
- 文中的 `$HOME/…` 写法与宿主布局的推导结果等价：工具从系统账户库取运维账号的 HOME，不读 `$HOME`（§12）。
- `dk` 用 `PATH` 里的 docker CLI（Homebrew）；仓库工具（升级脚本、`verify-controller.mjs`、`ci-smoke.mjs`、doctor）用宿主布局的 `dockerCli`，默认是 OrbStack 的 `$HOME/.orbstack/bin/docker`。两者版本不同（§8），但都带同一个私有 `DOCKER_CONFIG` 与 socket。
- 私有 `DOCKER_CONFIG` 只配置了 `cliPluginsExtraDirs`，指向 `/Applications/OrbStack.app/Contents/MacOS/xbin`；compose 与 buildx 插件来自 OrbStack，卸载后 `dk … compose` 不可用。doctor 会核对这两个插件存在且位置可信（§12.4）。
- `colima` 命令也要带同一个 `DOCKER_CONFIG`，否则会在默认的 `~/.docker` 里新建 context（§11 的遗留 context 就是这样产生的）。
- 仓库里的 `.mjs` 工具一律用 `"$NODE22"` 在仓库根目录执行，在别的目录执行会报 `ERR_MODULE_NOT_FOUND`。
- `jstatus` 正常时：`quietingDown` 为 false；除 mutation（`notbuilt`）外作业都不是 `disabled`；`linux-ci`、`linux-web-amd64`、`linux-deploy` 为 online（`mac-ci`、`mac-deploy`、Built-In Node 离线属预期，见 §11）。

**`manage.mjs` 子命令**（Mac，仓库根目录，`"$NODE22" deploy/jenkins/manage.mjs <子命令>`；读取私有目录里的 `admin-api.json`。每次带凭据的请求前，先确认 `127.0.0.1:8080` 的监听进程属于运维账号，否则不发送并报 `HL_JENKINS_LISTENER`。它是止损入口，只检查运行账号、私有目录与 `admin-api.json`，不读 `host-layout.json`，也不查 `COLIMA_HOME` 与 socket；它用不了时，在 Jenkins 页面停用作业或用“准备关闭”兜底）

| 子命令                                | 作用                                                                                   | 输出或恢复                                   |
| ------------------------------------- | -------------------------------------------------------------------------------------- | -------------------------------------------- |
| `status`                              | 只读：作业颜色与最近一次构建号、节点在线、`quietingDown`；不含作业描述                 | 精简输出用 `jstatus`                         |

## 2. 发现规则

本节是发现规则的唯一权威描述，来自 `deploy/jenkins/jenkins-discover.mjs`。

| 来源                                                        | 处理                                                                       |
| ----------------------------------------------------------- | -------------------------------------------------------------------------- |
| 三仓 `refs/heads/main`（精确匹配）                          | SHA 变化时排对应 CI 并回写状态；三仓组合与已发布组合不同时排统一发布       |
| 同仓、base 为 `main` 的 open PR（含 draft）                 | PR head SHA 变化时排对应 CI 并回写状态                                     |
| API `main` 改了 `images/platform-sandbox/Dockerfile` 或 `images/platform-boxlite/Dockerfile` | 另外排 `agent-platform-sandbox-images`，`MODE=check` |
| API 仓 `sandbox-image-v*` 标签                              | 首轮只记录已有标签；之后新增的标签排镜像作业，`MODE=publish`               |
| fork PR（包括 head 仓已删除）                               | 不构建、不记录                                                             |
| 栈式 PR（base 不是 `main`）                                 | 不构建、不记录；把 base 改成 `main` 后按新条目构建                         |
| 其他分支与标签（任意名称）                                  | 校验前丢弃：不触发、不记录，也不会让整轮失败                               |

每类检查用哪组提交（Web 与主仓的 CI 取另外两仓的 `main` head，不读 PR 里的 gitlink）见 [CONTRIBUTING](../../CONTRIBUTING.md) §3.1。

注：
- 同一 SHA 只排一次；已成功的历史构建会被复用。CI 失败后要推新提交才会重跑。
- release 与镜像作业不是 `SUCCESS` 时，下一轮按同一组合重新排队，没有退避。
- 回写的状态为 `pending`、`success`、`failure`，链接指向公网 Jenkins，需要通过 Access 才能查看。
- 没有 PR 的分支不跑 CI；需要 CI 时开指向 `main` 的 PR（可为 draft）。未经 PR 构建的提交直接推 `main`，会因缺少必需状态被拒。
- 禁止创建名称以 `/refs/heads/main` 或 `/refs/tags/sandbox-image-v*` 结尾的分支（如 `x/refs/heads/main`）：发布、Web、镜像与 mutation 工具用 `git ls-remote` 按尾部匹配，会多匹配到它们而拒绝执行。

## 4. 容器栈与 compose 命令

生产 API（`agent-platform-api`）**不归 compose 管**，由 `deploy/containers/api-container.mjs` 用 `docker run` 创建与替换。其余服务由下表三个 compose 项目管理。

| 项目                                | VM      | compose 文件                                | env 文件                | 允许单独 up 的服务                         |
| ----------------------------------- | ------- | ------------------------------------------- | ----------------------- | ------------------------------------------ |
| `agent-platform-jenkins-controller` | jenkins | `deploy/containers/compose.controller.json` | `container-stack.env`   | `controller`                               |
| `agent-platform-linux-ci`           | build   | `deploy/containers/compose.ci.json`         | `container-stack.env`   | `agent`、`web`                             |
| `agent-platform-runtime`            | runtime | `deploy/containers/compose.runtime.json`    | `container-runtime.env` | `dns`、`tunnel`、`deploy`；**禁止 `api`**  |
| `agent-platform-jenkins-lab`        | jenkins | `deploy/containers/compose.lab.json`        | 无                      | `controller`（只用于 controller 升级验证） |

```sh
# Mac，干净 main 克隆的仓库根目录（$SRC，准备方法见发版手册 §0）
dk <profile> compose --project-name <项目> \
  --env-file "$HOME/.local/share/agent-platform-jenkins-tools/<env 文件>" \
  --file deploy/containers/<compose 文件> \
  up --detach --no-deps --pull never <服务…>
```

注：
- 一律写明服务名；需要用同一镜像替换容器时再加 `--force-recreate`。影响与前置条件见 [运维手册](./运维手册.md) §3 与 [发版手册](./发版手册.md) §4。
- env 文件在 Mac 私有目录（§6），键与仓库模板见 §7。
- 每个容器的 compose 来源记在标签 `com.docker.compose.project.config_files` 里；controller、dns、tunnel 的现状见 [运维记录](./运维记录.md) §3 的 T8。
- 容器名：controller 为 `agent-platform-jenkins-controller-controller-1`，CI agent 为 `agent-platform-linux-ci-agent-1` 与 `agent-platform-linux-ci-web-1`，runtime 服务为 `agent-platform-dns`、`agent-platform-tunnel`、`agent-platform-linux-deploy`。

- `releases/<ROOT_SHA>-<API_SHA>` 是 API 镜像包缓存；当前线上版本对应的目录必须保留，部署与回滚都要读取它。

| ----------------------------------------- | -------------------------------------------------------------------------------------------------------- | ---------- | ---------------------------------------------------------- |

## 12. 宿主布局与覆盖

Mac 上的仓库工具（升级脚本、`manage.mjs`、`bootstrap-host.mjs`、`controller.mjs`、`verify-controller.mjs`、`ci-smoke.mjs`、`setup-github-app.mjs`、`import-ghcr-token.mjs`）不写死账号、HOME、UID 或宿主路径，一律由 `deploy/containers/host-layout.mjs` 推导。这个模块只在 Mac 上使用，不进任何镜像；镜像内的路径仍是容器里的固定布局（`/home/jenkins`、uid 1000 等），与换哪台 Mac 无关。

### 12.1 推导规则

运维账号就是系统账户库（`os.userInfo()`，即 passwd）报告的运行账号。不读 `HOME`、`USER`、`LOGNAME`、`XDG_*`、`AGENT_PLATFORM_*` 等环境变量，也不用 `os.homedir()`（它跟随 `$HOME`）。下表 `<home>` 指运维账号的 HOME；文档里的 `$HOME/…` 与 `$P` 写法与推导结果等价。

| 字段                                    | 推导规则                                                                                          | 能否覆盖              | 使用方                                         |
| --------------------------------------- | ------------------------------------------------------------------------------------------------- | --------------------- | ---------------------------------------------- |
| `operator`                              | passwd 的用户名、UID、GID 与 HOME，须满足 §12.4 的身份策略                                        | 否                    | 全部                                           |
| `node`                                  | 运行工具的 Node（`process.execPath`）；升级脚本子进程的 `PATH` 以它所在目录开头                   | 否                    | 升级脚本、bootstrap 审阅包                     |
| `privateDir`                            | `<home>/.local/share/agent-platform-jenkins-tools`（`$P`）                                        | 否                    | 全部                                           |
| `dockerConfig`、`stackEnv`、`runtimeEnv`、`adminApi` | `$P/container-docker-context`、`$P/container-stack.env`、`$P/container-runtime.env`、`$P/admin-api.json` | 否 | 升级脚本、`manage.mjs`、verify-controller、ci-smoke |
| `bootReview`、`overrideFile`            | `$P/container-boot`（日志在其下 `logs/`）、`$P/host-layout.json`                                  | 否                    | bootstrap-host；全部                           |
| `colimaHome`、`limaOverride`            | `<home>/.colima`、`<home>/.colima/_lima/_config/override.yaml`；`COLIMA_HOME` 已设置且不等于前者时拒绝 | 否               | 所有操作 VM 的工具                             |
| `profiles`                              | 固定 `agent-platform-{jenkins,build,runtime}`；socket `unix://<home>/.colima/<profile>/docker.sock`、`colima.yaml`、daemon 名 `colima-<profile>` | 否 | 同上                          |
| `launchAgents`、`userDomain`            | `<home>/Library/LaunchAgents`、`gui/<uid>`                                                        | 否                    | bootstrap-host                                 |
| `dockerCli`                             | 默认 `<home>/.orbstack/bin/docker`                                                                | `dockerCli`           | 升级脚本、verify-controller、ci-smoke、doctor  |
| `homebrewPrefix`                        | 默认 `/opt/homebrew`；派生 `colima`、`limactl` 与 Homebrew `docker` 的路径 `<prefix>/bin/…`，以及 LaunchDaemon 的 `PATH=<prefix>/bin:/usr/bin:/bin:/usr/sbin:/sbin` | `homebrewPrefix` | bootstrap-host、doctor |
| `launchdLabelPrefix`                    | 默认 `com.douglasdong.agent-platform.container-engine.`；Label 为前缀加 profile 名                | `launchdLabelPrefix`  | bootstrap-host、doctor                         |

优先级：系统账户库的身份 > 固定的相对布局 > `host-layout.json` > 内置默认值。不接受环境变量或命令行参数覆盖：环境变量会在交互 shell、sudo 与 launchd 之间漂移。

### 12.2 `host-layout.json`

可选文件，缺省不存在，三项都用内置默认值。例如没有 OrbStack、改用 Homebrew 的 docker CLI 时：

```json
{ "schemaVersion": 1, "dockerCli": "/opt/homebrew/bin/docker" }
```

| 校验对象 | 规则（不满足时以 `HL_OVERRIDE_*` 拒绝）                                                                                                   |
| -------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| 文件     | 从 HOME 到私有目录的每一级都属于运维账号；文件属主为运维账号、`0600`、链接数 1、64 KiB 以内，以不跟随符号链接的方式打开；没有 deny 以外的 ACL |
| 内容     | JSON 对象；`schemaVersion` 为 1；其余键只能是 `dockerCli`、`homebrewPrefix`、`launchdLabelPrefix`                                            |
| 路径值   | `dockerCli` 与 `homebrewPrefix` 只做词法规范化：绝对路径，没有 `.` 或 `..` 段，没有重复或末尾的斜杠，字符限 `A-Z a-z 0-9 . _ - /`。允许指向符号链接、不解析，记录的是原字符串（`/opt/homebrew/bin/colima` 不会变成 Cellar 下带版本号的路径）；可执行文件是否可信另行检查（§12.4） |
| Label 前缀 | 匹配 `^[a-z0-9]+(\.[a-z0-9-]+)+\.$`（小写、点分、以点结尾）；拼出的 Label 不得含 `/` 或 `..`                                              |

- 它是本机配置：不放进离机导出（[灾备与重建](./灾备与重建.md) §2），新机器按自己的软件位置重写。
- 升级脚本的 `plan.json` 与 bootstrap 审阅包都记录了覆盖值；改了这个文件，要重新 build 或重新 prepare。
- 没有 OrbStack 时，除了 `dockerCli`，还要把私有 `DOCKER_CONFIG` 的 `cliPluginsExtraDirs` 改到提供 `docker-compose` 与 `docker-buildx` 的目录（如 Homebrew 的 `<prefix>/lib/docker/cli-plugins`）。

### 12.3 名字

- profile 名固定，不开放覆盖：`dk`、`colima.yaml` 的位置、Lima 实例目录、Label 后缀与 ci-smoke 的 daemon 名校验都依赖它。改名等于重建 VM。
- Label 前缀默认是部署域名的反写，属于部署名字而不是路径。改前缀等于换一套服务：先 `bootout` 并移除旧 plist（对应 VM 停机），再重新 `prepare`、`sudo` 执行 `apply-system`。`homebrewPrefix` 变化同样会改变 plist（程序路径与 `PATH`），也按这个顺序重装。本机两项都不改。

### 12.4 身份策略与检查集合

**身份策略**（各工具入口）：

- macOS、Apple Silicon、Node 22（`manage.mjs` 不查这一条，见下表）；
- 真实 UID 等于有效 UID；不是 root，也不经 sudo；
- UID ≥ 501（更小的是系统服务账号）；用户名匹配 `^[a-z][a-z0-9._-]*$`（以 `_` 开头的服务账号不满足）；HOME 是普通的绝对路径。

`sudo` 执行的 `bootstrap-host.mjs apply-system` 不用 root 自己的身份：先严格解析 `SUDO_UID`，用 `/usr/bin/id -P -- <SUDO_USER>` 取 passwd 记录并要求 UID 一致，再对这个账号执行同一套身份策略；审阅包里记录的运维账号与主组必须与它逐项相等。

**检查项**：

| 检查                                                         | 内容                                                                                                                         |
| ------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------- |
| `platform`、`operator`（合称 `identity`）                    | 上面的身份策略                                                                                                               |
| `colimaEnv`                                                  | `COLIMA_HOME` 未设置，或等于 `<home>/.colima`；声明了任何 VM 相关检查时自动加入                                              |
| `home`                                                       | HOME 属于运维账号、组与他人不可写；HOME 以上各级属于 root，组与他人不可写或带 sticky 位。其余检查对 HOME 以下直到目标的每一级目录做同样的属主链检查（运维账号所有、组与他人不可写）；ACL 用 `/bin/ls -lde` 读取，deny 以外的项一律拒绝 |
| `overrideFile`                                               | §12.2                                                                                                                        |
| `privateDir`                                                 | 属主链，加 `0700`                                                                                                            |
| `dockerConfig`                                               | 私有 `DOCKER_CONFIG` 为 `0700`；`config.json` 为私有文件，不得设置 `credsStore`、`credHelpers`；`cliPluginsExtraDirs` 下有位置可信的 `docker-compose` 与 `docker-buildx` |
| `stackEnv`、`runtimeEnv`、`adminApi`                         | 私有文件：属主链；运维账号所有、`0600`、链接数 1；以不跟随符号链接的方式打开后用 `fstat` 复核；只看属性，不读内容              |
| `dockerCli`、`colima`、`limactl`、`homebrewDocker`、`node`、`launchdPath` | 可执行文件与搜索路径在可信位置（见下）；`node` 还要求等于正在运行的 Node，子进程 `PATH` 的各目录也须可信              |
| `colimaYaml`、`limaOverride`                                 | 三份 `colima.yaml`、Lima override 属于运维账号、组与他人不可写                                                               |
| `socket:jenkins`、`socket:build`、`socket:runtime`           | `lstat` 为 socket、属于运维账号、`0600`，上级目录走属主链                                                                    |

**可信位置**：逐跳解析符号链接，路径上每一级目录、每个链接与最终文件的属主只能是 root 或运维账号，他人不可写；组可写只在属组为 admin 或 wheel、且组内只有 root、运维账号与 `_mbsetupuser` 时放行（`/opt/homebrew/bin` 与 `/Applications` 默认对 admin 组可写，不产生警告）；不得有 allow 类 ACL。组里出现其他成员时直接失败（`HL_GROUP_MEMBERS`）。

**各工具声明的检查集合**（只检查本动作用得到的东西，所以 VM 还没建好时 `manage.mjs` 与升级脚本的 build 照样可用）：

| 工具与动作                              | 检查集合                                                                                               |
| --------------------------------------- | ------------------------------------------------------------------------------------------------------ |
| `manage.mjs`（全部子命令）              | `operator`、`privateDir`、`adminApi`；不查平台、不读 `host-layout.json`、不查 `COLIMA_HOME` 与 socket   |
| 升级脚本 build                          | `identity`、`colimaEnv`、`overrideFile`、`privateDir`、`dockerConfig`、`stackEnv`、`runtimeEnv`、`dockerCli`、`node`、`socket:build` |
| 升级脚本 apply                          | build 的全部，加 `adminApi`、`socket:runtime`、`socket:jenkins`                                        |
| `bootstrap-host.mjs prepare`            | `identity`、`colimaEnv`、`overrideFile`、`colimaYaml`、`colima`、`launchdPath`，以及 `privateDir`（审阅包写在私有目录里） |
| `bootstrap-host.mjs apply-system`       | 锚定 sudo 发起人之后：`privateDir`、`colimaEnv`、`colimaYaml`、`colima`、`launchdPath`                  |
| `verify-controller.mjs`                 | `identity`、`colimaEnv`、`overrideFile`、`privateDir`、`dockerConfig`、`dockerCli`、`socket:jenkins`、`socket:build` |
| `ci-smoke.mjs`                          | `identity`、`colimaEnv`、`overrideFile`、`privateDir`、`dockerConfig`、`dockerCli`、`socket:build`     |
| `setup-github-app.mjs`、`import-ghcr-token.mjs` | `identity`、`privateDir`                                                                       |
| `host-layout.mjs print`                 | `identity`、`colimaEnv`、`overrideFile`                                                                |

另外两条规则：

- 发送 Jenkins 凭据之前（`manage.mjs`、升级脚本、`verify-controller.mjs`），用 `/usr/sbin/lsof -nP -a -iTCP@127.0.0.1:<端口> -sTCP:LISTEN -Fpu` 确认监听进程属于运维账号（生产 8080，lab 18080），否则不发送（`HL_JENKINS_LISTENER`）。回环端口对所有账号先到先得；普通账号的 lsof 看不到别人的进程，所以“看不到监听者”也拒绝。
- 升级脚本的 `plan.json`（schemaVersion 2）记录推导结果、两份 env 的路径、docker CLI 与插件的真实路径和哈希、脚本与 `host-layout.mjs` 的哈希；bootstrap 审阅包（`review.json` schema 2）记录运维账号与主组、推导结果、colima 的真实路径和哈希。apply 时重新推导并逐项比对。这些记录只用于发现漂移，不是对运维账号本人的安全边界：相关文件都归它所有。

### 12.5 print 与 doctor

```sh
# Mac，仓库根目录，Node 22；都只读
"$NODE22" deploy/containers/host-layout.mjs print                 # 推导结果与三个覆盖项的来源（default 或 host-layout.json）
"$NODE22" deploy/containers/host-layout.mjs print --shell         # 同一组值，输出 HL_HOME='…' 形式的赋值（单引号转义）
"$NODE22" deploy/containers/host-layout.mjs doctor --stage full | jq -c '{state, counts}'
"$NODE22" deploy/containers/host-layout.mjs doctor --stage full | jq -c '.checks[] | select(.status != "ok" and .status != "not-yet")'
```

doctor 对凭据与 env 文件只看属性（`fstat`），不读内容；读取的只有 `config.json`、`host-layout.json`、`review.json`、`colima.yaml` 与 plist 这类配置。它不使用 Jenkins 凭据，也不运行 colima 与 limactl。每个阶段在前一阶段的基础上增加检查；之后阶段的项输出 `not-yet`，不算失败；前置项失败时依赖它的项为 `blocked`。有 `fail` 或 `blocked` 时 `state` 为 `doctor-failed`、退出码为 1。不写 `--stage` 时为 `full`。

| 阶段      | 增加的检查                                                                                                                         | 灾备重建中的时点（[灾备与重建](./灾备与重建.md) §5） |
| --------- | ---------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------- |
| `host`    | 身份、`COLIMA_HOME`、HOME 属主链、`host-layout.json`、私有目录、私有 `DOCKER_CONFIG` 与插件、`docker --version`、`compose version`、`buildx version`；Node、colima、limactl、Homebrew docker 与 LaunchDaemon `PATH` 是否在可信位置 | 5.1 末尾 |
| `engines` | Lima override 与仓库副本一致、三份 `colima.yaml`、三个 socket、`docker info` 返回的 Name 为 `colima-<profile>`                      | 5.3 末尾（5.4 之前）                                 |
| `launchd` | 三份 plist 为 root 的 0644 文件，字节等于 `bootstrap-host.mjs` 按本机布局的渲染结果、字段一致，`launchctl print` 为 running；没有别的 plist 启动同一个 profile；审阅包的 schema 与 `colima.yaml` 哈希 | 5.4 之后 |
| `images`  | 两份 compose env 文件                                                                                                              | 5.5 之后、5.6 之前                                   |
| `full`    | `admin-api.json`；`127.0.0.1:8080` 的监听进程属于运维账号；`/login` 不带凭据返回 200                                               | 5.8 之后；日常巡检与升级 agent 之前                  |

本机期望（v0.3.6 基线实测，五个阶段的 `layoutSha256` 相同）：

| 阶段      | ok | warn | not-yet | `state`         |
| --------- | -- | ---- | ------- | --------------- |
| `host`    | 14 | 0    | 18      | `doctor-passed` |
| `engines` | 22 | 0    | 10      | `doctor-passed` |
| `launchd` | 26 | 1    | 5       | `doctor-passed` |
| `images`  | 28 | 1    | 3       | `doctor-passed` |
| `full`    | 31 | 1    | 0       | `doctor-passed` |

本机的 1 个 warn 是 `bootReview`：审阅包仍是 schema 1，jenkins 的 `colima.yaml` 在上次 prepare 之后改过。下次 apply-system 之前重新 `prepare` 即可消除，plist 字节不变，不需要重装（[运维记录](./运维记录.md) §2.5）。

| 会出现 warn 的检查  | 含义                                                                         | 处置                                                       |
| ------------------- | ---------------------------------------------------------------------------- | ---------------------------------------------------------- |
| `bootReview`        | 没有审阅包、`review.json` 的 schema 低于 2，或 `colima.yaml` 在 prepare 之后改过 | 正常；只影响下次 apply-system，之前重新 `prepare`          |
| `dockerConfig`      | `config.json` 除 `cliPluginsExtraDirs` 外还有别的键                          | 核对后决定保留或删除；`credsStore`、`credHelpers` 直接失败 |
| `launchdDuplicates` | 用户 LaunchAgents 里还有提到三个 profile 的定义                              | 保持禁用（§11）；系统域里有重复则直接失败                  |
| `limaOverride`      | 模块旁找不到仓库副本 `deploy/host/lima-override.yaml`，内容未比对             | 在仓库根目录运行 doctor                                    |

### 12.6 原因码

工具报错的形式是 `Host layout refused [<原因码>]: <原因> (<路径>)`；doctor 把同样的原因码写在失败项的 `code` 里，升级脚本写在输出的 `code` 里。

| 原因码                                                                     | 含义                                                         | 处置                                                                 |
| -------------------------------------------------------------------------- | ------------------------------------------------------------ | -------------------------------------------------------------------- |
| `HL_USAGE`、`HL_REQUIRE`                                                   | 命令行写错，或工具声明的检查集合有误                         | 按提示修正命令；工具代码问题交维护者                                 |
| `HL_PLATFORM`、`HL_NODE`                                                   | 不是 Apple Silicon 上的 macOS，或不是 Node 22                | 在 Mac 上用 `$NODE22` 运行                                           |
| `HL_IDENTITY_ROOT`、`HL_IDENTITY_EUID`                                     | 以 root、经 sudo 或 setuid 运行                              | 以运维账号运行；只有 apply-system 用 sudo                            |
| `HL_IDENTITY_SERVICE`、`HL_IDENTITY_NAME`、`HL_IDENTITY_HOME`、`HL_IDENTITY_PASSWD` | 账号不满足身份策略，或 passwd 查不到                 | 换成运维账号；新机器见灾备与重建 §5.1                                |
| `HL_IDENTITY_MISMATCH`                                                     | 布局是为另一个账号推导的                                     | 用原账号运行                                                         |
| `HL_SUDO`                                                                  | apply-system 无法把 sudo 发起人锚定到 passwd（如直接以 root 登录执行） | 由运维账号执行 `sudo …`                                    |
| `HL_COLIMA_HOME`                                                           | `COLIMA_HOME` 指向 `<home>/.colima` 以外                     | `unset COLIMA_HOME`                                                  |
| `HL_OVERRIDE_FILE`、`HL_OVERRIDE_SCHEMA`、`HL_OVERRIDE_VALUE`              | `host-layout.json` 的属性、格式或取值不合规                  | 按 §12.2 修正或删除这个文件                                          |
| `HL_LAYOUT_CHANGED`                                                        | 推导结果与 plan 或审阅包记录的不同                           | 恢复原账号、原 Node、原覆盖文件；或重新 build、重新 prepare          |
| `HL_MISSING`、`HL_UNREADABLE`                                              | 必需的路径不存在（如 VM 没在运行时的 socket），或无法检查    | 按报错里的路径补齐；VM 未运行见[运维手册](./运维手册.md) §3          |
| `HL_OWNER_CHAIN`、`HL_ACL`                                                 | 路径上某级目录的属主或权限不对，或有 deny 以外的 ACL         | 按路径修正（`ls -lde <路径>` 查看）；不要放宽到组或他人              |
| `HL_PRIVATE_DIR`、`HL_PRIVATE_FILE`、`HL_FILE`、`HL_SOCKET`、`HL_DOCKER_CONFIG` | 私有目录、私有文件、运维文件、socket 或私有 `DOCKER_CONFIG` 的属性不对 | 按 §6 与 §12.4 修正属主与权限                          |
| `HL_UNTRUSTED_PATH`、`HL_GROUP_MEMBERS`                                    | 可执行文件或搜索路径不在可信位置；能写它的组还有其他成员     | 不要放宽检查；交维护者移除多余的管理员或改装到可信位置               |
| `HL_JENKINS_LISTENER`                                                      | 回环 Jenkins 端口没有运维账号的监听，或被别的账号占用        | 见 §10 的 `… the Jenkins credential is not sent`                     |
| `HL_LAUNCHD`                                                               | plist 与本机布局的渲染结果不同、没在运行，或有别的定义启动同一个 profile | [运维手册](./运维手册.md) §8 第 5 层；重装见灾备与重建 §5.4 |
| `HL_REVIEW`                                                                | 审阅包过期（只作警告）                                       | 下次 apply-system 之前重新 `prepare`                                 |
| `HL_PROBE`、`HL_INTERNAL`                                                  | doctor 的只读探测失败；print 或 doctor 自身的意外错误        | 按 `detail` 排查；`HL_INTERNAL` 交维护者                             |
