# Legacy → independent control Native qualification

Status: **not-run**. The executable scenario is `migration-control-native.spec.mjs`; syntax and local preflight tests do not qualify Docker, KVM, migration or task continuity. Do not run it on an existing instance or a VM shared with production. Storage and the dedicated QA VM must be ready first.

The scenario provisions the source itself. No caller supplies a “legacy ready” record, PID, writer or Guest proof. It uses the actual immutable v20 package, starts its old production roles and old Entry/Supervisor code inside a separate Foundation container, then creates a real BoxLite Guest and Claude CLI job. The generated Foundation wrapper has a hashed listener-only rollback branch; restarting it does not launch a second Owner. The privileged migration worker uses the immutable new control package's `control-migration-main.mjs` for `plan`, `prepare`, `apply` and the same-ID `resume`. Finally it submits one ordinary B upgrade through the browser and verifies original process and session continuity.

## Execution and evidence

From `e2e-contract` on the prepared dedicated Linux arm64 Node 22 worker:

```sh
MIGRATION_UPGRADE_ACCEPTANCE_CONFIG=/absolute/private/migration-native.json \
  pnpm exec playwright test --config migration-upgrade.playwright.config.ts
```

No VM provisioning or package building is implicit in that command. Browser traces, screenshots and video remain off to avoid recording private sessions. Evidence includes source archive/signature pins, hashed bootstrap code and real source process records, immutable CLI receipts, the original migration ID/specs/deadlines, readonly history comparison, unchanged access-cookie digest, real Owner/SDK/VMM/KVM identities, continuous Guest Bash PID/birth/counter, and the single ordinary B request. Only after these succeed does `nativeQualified` become true.

Failed or unknown scenarios keep their original resources and journals; they never relaunch under a new migration ID. Successful scenarios cancel/delete their own sandbox through the product API, then normally SIGTERM only exact owned role/container births. No forced termination, container removal, volume pruning, SDK migration or business snapshot restoration is performed.
